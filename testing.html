叢集元件 測試與 smoke-test

這頁說明怎麼用 playbooks/k8s/smoke-test.yml 確認整個叢集真的在運作。它把建置過程中反覆手動驗證的步驟，收斂成一個可重複執行、自動判斷成敗的 playbook。

怎麼執行

repo 根目錄
$ scripts/ansible.sh ansible-playbook playbooks/k8s/smoke-test.yml

預期結果：playbook 全部 task 成功。任何一段驗證失敗，ansible 都會直接報錯並停止。

這個 playbook 可以隨時重跑。連續執行兩次都完全成功，第二次沒有受到殘留狀態干擾，所以懷疑系統壞掉時不需要先手動清理。

現在的驗證內容

驗證分成四段，由淺到深。前三段確認狀態，第四段才實際發送流量。

段落驗證什麼通過條件
1節點與系統 pod全部 Ready
2tor 上的 apiserver haproxy3 台 master 全部 UP
3tor 上的 BGP PodCIDR 路由*>i 條目數等於 groups['k8s_nodes'] | length，目前是 8
4跨節點 pod-to-pod 流量A 用 wget 拿到 B 的預期回應

1. 節點與系統 pod

playbook 執行的檢查
kubectl wait --for=condition=Ready node --all --timeout=60s
kubectl wait --for=condition=Ready pod --all -n kube-system --timeout=120s

這裡用 kubectl 內建的 wait --for=condition=Ready，不自己解析 kubectl get nodes 的輸出。條件不滿足就會逾時失敗，ansible task 直接報錯，不需要額外寫判斷邏輯。

2. apiserver haproxy backend

這段讀取 tor 上 haproxy 的 CSV 統計頁，確認 3 台 master 全部 UP。

haproxy CSV 的 status 是第 18 欄，中間還隔著 qcur、qmax、scur 等欄位。所以要先用 cut -d, -f1,2,18 取出 pxname,svname,status，再比對內容。

3. BGP PodCIDR 傳播數量

這段在 tor 上數 show ip bgp 裡標記 *>i（valid、best、internal）的條目。每個 k8s 節點恰好一條 PodCIDR，所以數量要等於 groups['k8s_nodes'] | length。

這段只證明路由存在，無法證明路由能用，所以還需要第四段。

4. 跨節點 pod-to-pod 連線

這是最重要的一段，也是唯一會建立真實資源、實際發送流量的測試。

playbook 在 groups['masters'][0]（ms-0001）和 groups['workers'][-1]（ap-0003）各建一個 busybox pod。B 跑一個小型 httpd，A 用 wget 連 B 的 pod IP，並斷言回應內容。

清掉舊測試 pod
ignore_errors 式保險
→
建 pod A 與 pod B
各自釘在不同節點
→
A wget B 的 pod IP
斷言回應內容
→
always：清掉測試 pod
不管成功失敗都執行

整段包在 block／always 裡。不管哪一步失敗，always 都會清掉測試 pod，不會在叢集留下垃圾。

這段對應封包路徑實例裡的跨節點 Pod 流量。測試通過，代表 Cilium native routing 和 FRR fabric 的整條路徑都在運作。

已知限制

  • smoke test 只涵蓋節點、apiserver、BGP 和 pod 連線，沒有驗證 Istio、Cloudflare Tunnel 或內部工具。
  • 第三段的條目數綁定目前的 BGP 表內容。有其他前綴也標記 *>i 時，要同步調整預期數量。

實測踩到的 ansible 陷阱

📊

haproxy CSV 欄位位置

第一版直接對整行字串找 server,UP，永遠比對不到。status 欄位在很後面，要先用 cut 取出正確欄位。

🔤

command 模組的 JSON 引號

ansible.builtin.command 給純字串時不走 shell，而是靠 shlex 解析。--overrides={"spec":...} 裡的雙引號會被當成 quoting 字元吃掉，變成不合法的 JSON。改用 argv: list 形式就能避開。
