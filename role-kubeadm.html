Ansible 自動化Role: kubeadm_init / kubeadm_join

這兩個 role 加上 playbooks/k8s/kubeadm.yml、 playbooks/kubeadm-reset.yml,負責把 7 台空機器變成一個 3-master HA 的 Kubernetes 控制平面 + 4 台成員節點。

kubeadm_init:只在第一台 master 上跑一次

roles/kubeadm_init/tasks/main.yml
kubeadm init \
  --control-plane-endpoint k8s-api.internal:6443 \
  --apiserver-advertise-address 10.10.0.20 \
  --service-cidr 172.18.0.0/16 \
  --skip-phases=addon/kube-proxy \
  --upload-certs
參數為什麼
--control-plane-endpoint 指到 k8s-api.internal,這個名稱由 apiserver_dns role 解析到 tor 的 fabric_ip,tor 的 haproxy 再轉發給三台 master。 寫進 kubeconfig 跟叢集內部設定的入口永遠是這個固定 名稱,不會綁死在某一台 master 的 IP 上——任何一台 master 掛掉都不影響其他人怎麼連進來。
--apiserver-advertise-address 用這台的 fabric_ip(k8s-net),不是 mgmt-net——apiserver 對外(其他 master 之間、etcd、worker) 服務走的是資料平面,跟 ansible 自己連線管理用的 mgmt-net 是兩個網路,詳見 網路架構 總覽。
--service-cidr 設定 kube-apiserver 的 --service-cluster-ip-range (group_vars/all/main.yml 的 service_cidr) ——這個值一旦 init 之後就固定死,改不了,見下方 CIDR 變更的完整故事。
(沒有) --pod-network-cidr 刻意沒帶——podSubnet 留給裝 CNI 的時候(見 Role: cilium)才決定,不在 這裡一次到位。裝 CNI 前 kubectl get nodes 全部都會是 NotReady,是預期行為,不是這個 role 沒做完。
--skip-phases=addon/kube-proxy 使用者明確要求移除 kube-proxy、改用 Cilium 的 eBPF kube-proxy replacement(見 Role: cilium)。這個 flag 讓 kubeadm 從一開始就不部署 kube-proxy 的 DaemonSet,不是 裝完再手動刪除——避免刪除時序踩到 kube-proxy 已經寫過 iptables 規則、需要額外清理的問題。

kubeadm_join:其他 6 個節點怎麼加入

其他 6 個節點(2 個 master、2 個 lb、2 個 worker)分成兩種 join 方式,但用同一套邏輯處理:

確認自己有沒有
join 過
stat /etc/kubernetes/kubelet.conf
→
delegate_to 第一台 master
要一次性的 join 指令
kubeadm token create --print-join-command
→
是 master 的話
再加 --control-plane
+ --certificate-key
→
kubeadm join

整個流程可重複執行,不只是「第一次跑會成功」: kubeadm token create 跟 kubeadm init phase upload-certs --upload-certs 兩個指令都可以重複呼叫,不是一次性的——所以這裡選擇「每次都即時跟 第一台 master 要一次新的」,而不是在 kubeadm_init 那一步就把輸出手動複製貼上到別的地方存起來。這代表以後要加新節點, 重跑一次同一個 playbook 就夠了,不需要另外準備一套「加節點專用」 的流程。

實測到的 race condition:certificate-key 不能各要各的

第一版實作讓每個要加入 control-plane 的 master,自己各自呼叫 kubeadm init phase upload-certs --upload-certs 拿 certificate-key。結果 ms-0002 跟 ms-0003 同時 join 時,ms-0002 直接失敗:

ms-0002 · kubeadm join 失敗
error execution phase control-plane-prepare/download-certs: error downloading certs: error decoding secret data with provided key: cipher: message authentication failed

根因:--upload-certs 每次被呼叫, 都會用一把新的 key 重新加密同一份 kubeadm-certs Secret。ms-0002 跟 ms-0003 幾乎同時各自呼叫了一次——ms-0002 先拿到 key A,但在它真正用 key A 去解密憑證之前, ms-0003 的呼叫已經把整份 Secret 用新的 key B 重新加密了。ms-0002 手上的 key A 這時候已經對不上 Secret 裡實際的加密內容,解密直接失敗。

修法是把 upload-certs 這個呼叫只在 kubeadm_init 執行一次(見上方 kubeadm_init 的最後一步),結果存進 certificate_key_out 這個 registered 變數,其他 master join 時用 hostvars[groups['masters'][0]]['certificate_key_out'] 直接讀,不再自己呼叫。Ansible 的 hostvars 在整個 playbook 執行期間 (跨 play)都能互相讀取,不需要額外的變數傳遞機制。

另一個 upload-certs 的坑:單獨呼叫時自己猜錯 advertise address

把這一步從「完整 kubeadm init 的一部分」拆成 單獨呼叫 kubeadm init phase upload-certs --upload-certs(因為這裡只想拿 certificate-key,不想重跑 整個 init)之後,實測撞到另一個完全不同的問題:

x509 SAN 不匹配
certificate is valid for 172.18.0.1, 10.10.0.20, not 192.168.200.20

根因:kubeadm init phase upload-certs 單獨執行時,沒有沿用同一次 kubeadm init 的上下文——它會從零重建一份自己的預設 InitConfiguration,而這份預設設定裡的 localAPIEndpoint.advertiseAddress 是靠「找預設路由 所在的介面」這種自動偵測邏輯決定的(-v=5 開 verbose 看得到 Default route transits interface "ens4")。 這台機器的 k8s-net(no_gateway=true,沒有預設路由) 不會被選中,自動偵測落到有預設路由的 mgmt-net ——選出跟原本 init 時完全不同的位址。

第一次嘗試用 --apiserver-advertise-address 這個 flag 修正,結果發現kubeadm init phase upload-certs 根本沒有這個 flag(用 --help 確認過,不是猜 的)——這個 flag 只存在於完整的 kubeadm init,phase 層級的子指令沒有對應的參數。最終修法是給這個獨立呼叫帶一份最小的 --config:

/tmp/upload-certs-config.yaml(渲染後)
apiVersion: kubeadm.k8s.io/v1beta4
kind: InitConfiguration
localAPIEndpoint:
  advertiseAddress: 10.10.0.20
  bindPort: 6443

對應的呼叫變成 kubeadm init phase upload-certs --config /tmp/upload-certs-config.yaml --upload-certs——用一份明確 的 InitConfiguration 蓋掉自動偵測邏輯,強制它用正確的 fabric_ip。這個修法在寫進 role 之前,先用 ansible ad-hoc 手動跑過 一次確認有效,才更新進正式的 roles/kubeadm_init。

join 指令的 argv 陷阱

組出實際要執行的 join 指令時,如果是 master 節點,要在 kubeadm token create --print-join-command 的輸出後面 再接上 --control-plane --certificate-key ... --apiserver-advertise-address ... 三個額外參數。這裡用 set_fact 先組好 extra_join_args 字串,再用 "{{ join_cmd.stdout }} {{ extra_join_args | default('') }}" 接起來——worker/lb 節點沒有觸發那個 set_fact(它的 when 限定只有 master 才跑),extra_join_args 對它們來說是 undefined,靠 | default('') 補一個空字串, 不會讓整條指令因為變數不存在而報錯。

CIDR 變更:為什麼不能只改變數重新 apply

Pod CIDR 跟 Service CIDR 都屬於「叢集初始化時就固定死」的參數: Service CIDR 直接寫進 kube-apiserver 的 --service-cluster-ip-range,而每個 Node 物件的 .spec.podCIDR 一旦被 kube-controller-manager 配發過, 就不可變。這代表要換成不同的 CIDR(這個專案曾經從 10.244.0.0/16/10.96.0.0/12 改成 172.16.0.0/16/172.18.0.0/16),沒有「改個 ansible 變數重新 apply」這條路,只能整個叢集重建。

playbooks/kubeadm-reset.yml
1. helm uninstall cilium(bastion)
2. kubeadm reset -f(所有 k8s_nodes)
3. 清掉 /etc/cni/net.d 的內容(只清內容,見下方)
4. 刪掉 cilium_host / cilium_net / cilium_vxlan 介面殘留
5. 清掉這個節點在 FRR 裡宣告的舊 PodCIDR(network 陳述式 + Null0 後盾路由)

跑完 kubeadm-reset.yml,重新走一次 k8s/kubeadm.yml → k8s/cilium.yml,整個叢集就會用 新的 CIDR 重建。這個 playbook 也在過程中揪出一個 CRI-O 相關的 bug ——完整經過見 Bug 事後檢討: 不能把 /etc/cni/net.d 整個目錄刪掉重建, 只能清內容、保留目錄本身,不然 CRI-O 對這個目錄的 inode 監看會失效, Cilium 重新裝好之後寫的新設定檔永遠不會被發現。
