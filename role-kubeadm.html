cloudnative.tw · AS 65000

叢集元件 Role: kubeadm

這組 role 負責把空機器變成 3 台 master 的 HA 控制平面，加上 4 台 worker 節點。kubeadm_init 只在第一台 master 執行一次，kubeadm_join 讓其餘 6 個節點加入。它們在 playbooks/k8s/kubeadm.yml 裡接在 Role: kubelet 之後，依賴 CRI-O 與 apiserver-lb 先完成。

最後一個 play 匯入 playbooks/bastion/kubeconfig.yml，把 admin kubeconfig 放到 bastion。裝 CNI 之前，kubectl get nodes 會全部顯示 NotReady，屬於預期，CNI 由 Role: cilium 在下一步安裝。

kubeadm_init

role 先檢查 /etc/kubernetes/admin.conf 是否存在，已存在就跳過 init，所以可以重複執行。實際指令如下：

第一台 master（ms-0001）上，roles/kubeadm_init
kubeadm init \
  --control-plane-endpoint k8s-api.internal:6443 \
  --apiserver-advertise-address 10.10.0.20 \
  --service-cidr 172.18.0.0/16 \
  --skip-phases=addon/kube-proxy \
  --upload-certs
參數值為什麼
--control-plane-endpointapiserver_hostname:apiserver_port，即 k8s-api.internal:6443名稱由 apiserver_dns 解析到 tor 的 fabric_ip，tor 上的 haproxy 再轉給三台 master。kubeconfig 與叢集內部設定記錄的入口永遠是這個名稱，不綁死某台 master 的 IP，任一台 master 掛掉都不影響其他人連線
--apiserver-advertise-address本機的 fabric_ipapiserver 對 master、etcd、worker 的服務走資料平面 k8s-net，不走維運用的 mgmt-net，見雙網卡模型
--service-cidrservice_cidr，即 172.18.0.0/16設定 kube-apiserver 的 --service-cluster-ip-range，init 之後無法更改，見重建叢集
--pod-network-cidr不帶Pod CIDR 完全交給 Cilium 的 ipam.mode=cluster-pool 配發，不需要 kubeadm 設定 Node.spec.podCIDR，見 Role: cilium
--skip-phases=addon/kube-proxy跳過 kube-proxyService 負載平衡全部交給 Cilium 的 eBPF 資料平面（見 kube-proxy 取代）。從 init 就不部署 kube-proxy 的 DaemonSet，避免事後刪除時還要清理已寫入的 iptables 規則
--upload-certs啟用把控制平面憑證加密上傳為 kubeadm-certs Secret，供其他 master join

init 之後，role 把 admin.conf 複製到 /home/ubuntu/.kube/config（0600），讓 ubuntu 使用者可直接用 kubectl。接著產生給其他 master 使用的 certificate key，做法見下一節。

certificate key 只產生一次

role 在第一台 master 上執行一次 kubeadm init phase upload-certs --config /tmp/upload-certs-config.yaml --upload-certs，輸出存進 certificate_key_out。其他 master 用 hostvars[groups['masters'][0]]['certificate_key_out'] 讀取，不再各自呼叫。

這個設計來自兩個實測 bug，見實測踩到的 bug。--config 檔只含最小的 InitConfiguration：

/tmp/upload-certs-config.yaml（渲染後）
apiVersion: kubeadm.k8s.io/v1beta4
kind: InitConfiguration
localAPIEndpoint:
  advertiseAddress: 10.10.0.20
  bindPort: 6443

kubeadm_join

其餘 6 個節點分兩種：2 台 master 加 --control-plane，2 台 l4 和 2 台 ap 做一般 join。兩者共用同一套流程：

確認是否 join 過
stat /etc/kubernetes/kubelet.conf
→
跟第一台 master 要 join 指令
delegate_to，kubeadm token create --print-join-command
→
master 再加三個參數
--control-plane、--certificate-key、--apiserver-advertise-address
→
kubeadm join

token 和 certificate key 都即時向第一台 master 要，不在 init 時手動複製存放。kubeadm token create 可以重複呼叫，所以整個流程可以重跑，之後加新節點只要再跑一次同一個 playbook。已有 kubelet.conf 的節點會跳過。

master 的額外參數由 set_fact 組成 extra_join_args，最後以 "{{ join_cmd.stdout }} {{ extra_join_args | default('') }}" 接起來。worker 和 l4 不會觸發那個 set_fact，變數是 undefined，靠 | default('') 補空字串，指令才不會因為變數不存在而報錯。

重建叢集

有些參數在叢集初始化時就固定，不能只改變數再 apply。Service CIDR 直接寫進 kube-apiserver 的 --service-cluster-ip-range，Kubernetes minor 版本也屬於這一類。Pod CIDR 由 Cilium 配發並對應到 FRR 的 BGP 宣告，同樣要整個叢集重建才能換。專案曾把 CIDR 從 10.244.0.0/16、10.96.0.0/12 改成 172.16.0.0/16、172.18.0.0/16，走的就是這條路。

playbooks/kubeadm-reset.yml 會清空整個叢集狀態。它刻意不在 k8s.yml 的匯入鏈裡，避免一次「部署全部」的操作誤清掉運作中的叢集。只在確實需要改初始化參數時才執行。

repo 根目錄，重建順序
$ scripts/ansible.sh ansible-playbook playbooks/kubeadm-reset.yml
$ scripts/ansible.sh ansible-playbook playbooks/k8s/kubeadm.yml
$ scripts/ansible.sh ansible-playbook playbooks/k8s/cilium.yml
$ scripts/ansible.sh ansible-playbook playbooks/k8s/smoke-test.yml

預期結果：新參數生效，smoke-test 全部通過。crio 和 apiserver-lb 不需要重做。

kubeadm-reset.yml 做了什麼

  1. 在 bastion 執行 helm uninstall cilium。
  2. 在所有 k8s_nodes 執行 kubeadm reset -f。
  3. 清掉 /etc/cni/net.d/ 的內容。只清內容，不刪目錄本身。
  4. 重啟 crio，讓它重新掃描 CNI 目錄。
  5. 刪除 cilium_host、cilium_net、cilium_vxlan 這幾個介面的殘留。
  6. 清掉該節點在 FRR 裡宣告的舊 PodCIDR，包含 network 陳述式和 Null0 後盾路由（見 FRR / iBGP Fabric）。

第 6 步先讀 FRR 目前實際的 network 陳述式再移除，不拿 group_vars 的新值反推，因為這個 playbook 本來就是在準備換成新 CIDR 時執行，新舊值不同。目錄不能刪掉重建的原因見 Bug #20。playbooks/decommission.yml 會匯入這個 playbook，用於「清掉叢集狀態但保留 VM」的終態。

已知限制

實測踩到的 bug

#16 · 第二台 master join 失敗，cipher: message authentication failed

  • 症狀：ms-0002 與 ms-0003 同時 join 時，ms-0002 失敗：
    ms-0002 · kubeadm join
    error execution phase control-plane-prepare/download-certs: error downloading certs: error decoding secret data with provided key: cipher: message authentication failed
  • 根因：第一版讓每台要加入的 master 各自呼叫 kubeadm init phase upload-certs --upload-certs。這個指令每次都用新 key 重新加密同一份 kubeadm-certs Secret。ms-0002 拿到 key A，但還沒用它解密時，ms-0003 的呼叫已把整份 Secret 改用 key B 加密。key A 對不上，解密失敗。
  • 修法：upload-certs 只在 kubeadm_init 呼叫一次，結果存進 certificate_key_out，其他 master 用 hostvars 直接讀取。hostvars 在整個 playbook 執行期間可跨 play 互相讀取，不需要額外傳遞機制。
  • 怎麼確認修好：兩台 master 同時 join 都成功。
  • 相關：Bug 事後檢討 #16、Bug #23。

#23 · 單獨呼叫 upload-certs 時 x509 SAN 不匹配

  • 症狀：把 upload-certs 拆成單獨呼叫後，出現憑證錯誤：
    x509 SAN 不匹配
    certificate is valid for 172.18.0.1, 10.10.0.20, not 192.168.200.20
  • 根因：單獨執行的 phase 指令沒有沿用完整 kubeadm init 的上下文，會從零建立一份預設的 InitConfiguration。其中 localAPIEndpoint.advertiseAddress 靠「找預設路由所在介面」自動偵測。k8s-net 沒有預設路由，偵測落到 mgmt-net，選出和 init 時不同的位址。用 -v=5 可看到 Default route transits interface "ens4"。
  • 修法：第一次嘗試加 --apiserver-advertise-address，但用 --help 確認這個 phase 子指令沒有該 flag，這個 flag 只存在於完整的 kubeadm init。最終改為帶最小的 --config，明確指定 advertiseAddress，見上方設定檔。寫進 role 之前，先用 ansible ad-hoc 手動執行確認有效。
  • 怎麼確認修好：upload-certs 不再出現 SAN 錯誤，其他 master 可以成功 join。
  • 相關：Bug 事後檢討 #23、Bug #16。

#20 · 改 CIDR 重建後 pod 卡在 ContainerCreating，no CNI configuration file

  • 症狀：改 CIDR 重建叢集後，pod 卡在 ContainerCreating，錯誤是 no CNI configuration file，但檔案明明存在。
  • 根因：reset 時把 /etc/cni/net.d 整個目錄刪掉，由 Cilium 重新建立。CRI-O 對這個目錄的監看綁在 inode 上，新目錄是新 inode，CRI-O 看不到，新寫入的 CNI 設定檔永遠不會被讀到。
  • 修法：只清目錄內容，保留目錄本身。同時在清理後加一步重啟 crio，重新掃描目錄。兩個保險都保留，因為實測唯一能讓已失效的監看恢復的方法就是重啟 crio。
  • 怎麼確認修好：重建後 pod 能正常建立 sandbox，不再出現 no CNI configuration file。
  • 相關：Bug 事後檢討 #20。

驗證方式

在 bastion 上
$ kubectl get nodes

預期結果：8 個節點全部出現，3 台 control-plane。裝 CNI 之前狀態都是 NotReady，Cilium 安裝後轉為 Ready。tor 上的 haproxy backend 在 apiserver 啟動後自動變成 UP。完整的叢集驗證見測試與 smoke-test。
