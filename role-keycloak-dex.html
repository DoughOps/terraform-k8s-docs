Ansible 自動化Role: keycloak / dex

一個 Dex → Keycloak → Cloudflare Access 的 OIDC 聯邦 PoC—— 不是為了取代這個 lab 既有的 Cloudflare Access 驗證,而是模擬真實公司 環境常見的拓樸:Keycloak 是跨團隊共用的獨立 SSO 來源,Dex 是 每個叢集各自的 OIDC broker,叢集內的工具只認自己這個 Dex, 不用直接知道公司到底用哪套上游 IdP。三個 role 一起完成這個故事: roles/keycloak_server(bastion 上的獨立 Keycloak, Docker + Postgres)、roles/dex(叢集內的 Dex,broker 到 Keycloak)、roles/dex_test_app(oauth2-proxy + whoami,拿來驗證整條鏈真的能靜默通過)。這頁記錄 為什麼這樣設計、過程中撞到的五個實測 bug,不是重講 OIDC 概念。

為什麼中間要多一層 Dex,不是讓每個工具直接串 Keycloak

如果叢集內的每個工具(Grafana、ArgoCD、自訂 app……)都各自去跟 Keycloak 註冊 OIDC client,Keycloak 那邊的 client 清單會隨著叢集數 量線性增長,而且每個叢集都要單獨管理一份「這個叢集可以用哪些 client」的權限。Dex 把這件事收斂成叢集只需要跟 Keycloak 談一次(Dex 自己是 Keycloak 眼中唯一的 client),叢集內部 再由 Dex 用 staticClients 分發給各個工具——對 Keycloak(跨團隊共用資源)來說,新增/淘汰一個叢集只是增減一個 client,不需要知道叢集內部裝了哪些工具。這個 PoC 只接了 whoami 一個測試 app,驗證的是這條鏈本身通不通,不是 Dex 的完整功能。

Keycloak 為什麼也跑在 bastion,不是叢集內

跟 Role: vault 同一個理由:這個 PoC 裡 Keycloak 扮演「公司既有的 SSO 系統」,現實中它不會因為 某個叢集重建就跟著消失,所以資料要能在 bastion 重建之後 自動復原。直接沿用 bastion 那顆已經有 prevent_destroy + delete_on_termination = false 保護的 user-data 持久化 volume,Postgres 資料放 /userap/keycloak/pgdata——bastion 被 terraform destroy/apply 重建之後,容器 重新啟動會直接接回既有資料,不需要重新建 realm/client。

Bug #1:Keycloak 26 的健康檢查在另一個 port,不是應用本身的 port

第一版直覺假設 /health/ready 掛在 Keycloak 對外服務的 同一個 port(8090),容器一直起不來、docker inspect 顯示 healthcheck 持續失敗。查 docker logs 才發現 Keycloak 26 把 health/metrics 端點搬到獨立的 management port(預設 9000),而且要顯式打開:

roles/keycloak_server/defaults/main.yml
keycloak_port: 8090
keycloak_management_port: 9000

容器環境變數要加 KC_HEALTH_ENABLED=true,healthcheck 改打 keycloak_management_port 而不是 keycloak_port,才拿得到正確的 UP 狀態。

Bug #2:Postgres 資料目錄的 owner 每次重跑都被 Ansible 蓋回 root

第一版把 secrets 目錄跟 Postgres 資料目錄用同一個 ansible.builtin.file task 建,owner: root。 容器內的 Postgres 是用 uid 999 跑的,第一次啟動能正常 init(容器自己 chown),但只要這個 role 重跑一次, Ansible 的 file task 會把目錄 owner 宣告式地蓋回 root,下次容器重啟 Postgres 就炸開:

實測:keycloak-postgres 容器 log
FATAL: data directory "/var/lib/postgresql/data" has invalid permissions
could not open file "global/pg_filenode.map": Permission denied

修法是把 Postgres 資料目錄拆成獨立的一個 task,owner: "999" ——secrets 目錄仍然是 root(給 Ansible/root 讀寫,不給容器內非 root 使用者碰),兩個目錄的所有權模型本來就不該一樣,合併成同一個 task 是最初的設計錯誤。

Bug #3:Dex 打 Keycloak 被既有的萬用字元 Cloudflare Access 擋住

Dex 的 oidc connector 要對 issuer 做真正的 .well-known discovery、走真實網路連線——不像瀏覽器 那樣有 team session 可以用,Dex 對 Keycloak 發的是 machine-to-machine 的 HTTP 請求。Keycloak 掛在 keycloak.dough-ops.com,而這個網域落在既有的萬用字元 Cloudflare Access Application(*.dough-ops.com)底下, 沒有互動式登入的機器連線一律被擋在 Access 的驗證頁前面, discovery 直接失敗。第一版嘗試用 hostAliases 讓 Dex 直連 Keycloak 的內部位址繞過 DNS,結果卡在 Keycloak 沒有在那個 位址上監聽 TLS——這條路本質上就是錯的,不該讓 Dex 繞過 Cloudflare 去猜內部拓樸。

真正的修法來自使用者對架構的直接提問(「keycloak 不能經過 cloudflare 吧?」「dex 也要過 cloudflare?這樣不會卡住嗎?」)—— 答案是兩邊都繼續經過 Cloudflare(TLS 照樣終止在 Cloudflare),只是額外開一條精準比對的 bypass Access policy,只放行 Dex 需要打的那幾條路徑,不是整個 拿掉 Access 保護:

cloudflare/access.tf(keycloak_direct Application)
domain   = "${var.keycloak_hostname}/realms/${var.keycloak_realm}/*"
decision = "bypass"

精準比對範圍是後來收斂的——最早的版本直接放行 整個 var.keycloak_hostname,等於把 Keycloak 的 admin console 跟 master realm 的 token 端點都對整個網路開放,在最終審查 階段被抓出來,改成只放行 /realms/{realm}/* 這個 Dex 實際需要打的子路徑。

精準比對的 Application(type = "self_hosted",domain 直接寫完整路徑)優先權高於萬用字元 Application,不需要調整既有的 *.dough-ops.com policy。

Bug #4:Dex 沒有自己的瀏覽器 session,每次登入都跳 Keycloak 的同意畫面

驗證階段發現每次重新整理 whoami.dough-ops.com,都要 重新在 Dex 面前按一次「Grant Access」,不是預期中「登入一次、之後 靜默通過」。追查後確認這是 Dex 本身的已知行為(見 dexidp/dex#4560) ——Dex 對瀏覽器完全是無狀態的,沒有持久化的 SSO cookie, 每次收到新的 authorization request 都會重新觸發 connector 流程。 加上 oauth2.skipApprovalScreen: true 有一定幫助,但這個 設定對帶著 approval_prompt=force 的請求無效 ——而 oauth2-proxy 的 --approval-prompt 預設 值正是 force,且經實測確認無法透過設定清空(對應 oauth2-proxy/oauth2-proxy#3426 這個仍開著的上游 issue)。這是外部限制,目前無法單靠改設定 解決,直接在程式碼註解裡寫清楚,不假裝這是已修好的問題。

Bug #5:oauth2-proxy 500——id_token 的 email 沒有 verified 旗標

kubectl logs 追出 oauth2-proxy 直接 500,訊息是「email in id_token isn't verified」。根因是 Cloudflare Access → Keycloak → Dex 這條鏈組出來的 id_token, email_verified 沒有被設成 true(來源是 Cloudflare Access 這一層的身份,不是 Keycloak 自己核發的帳號), oauth2-proxy 預設拒絕未驗證的 email claim。加一個 flag 解決:

roles/dex_test_app/tasks/main.yml(extraArgs)
insecure-oidc-allow-unverified-email: "true"

跨 playbook 的變數作用域:role 的 defaults 不會自動跨 play 共用

這個 PoC 橫跨 bastion.yml(裝 Keycloak)跟 k8s.yml 底下兩個完全獨立的 ansible-playbook 呼叫(dex.yml、dex_test_app.yml)。Ansible 的 role defaults/ 只在該 role 實際被載入的那個 play 裡有效——這個限制在 Task 4/5 分別踩到兩次(dex_hostname 在 dex_test_app.yml 裡讀不到、keycloak_secrets_dir /keycloak_realm 同理),修法是統一把跨 play 共用的 變數搬進 group_vars/all/main.yml,不是留在個別 role 的 defaults/ 裡。

永久管理員:Keycloak 沒有「安裝時直接建永久帳號」的官方作法

Keycloak 的 KC_BOOTSTRAP_ADMIN_USERNAME/ _PASSWORD 建出來的一定是「temporary admin」——這是 Keycloak 官方文件明確記載的行為,沒有繞過的啟動參數,唯一的正式 流程是「先建臨時帳號,登入後再手動升級成永久帳號」。這個 role 把這段流程自動化:密碼不是自動產生,而是讀 secrets.yml 的 keycloak_permanent_admin_password (使用者自己指定、可重跑更換),用 admin REST API 建立/更新永久 帳號、指派 admin realm role、驗證能用新帳密登入之後, 才刪除原本的 bootstrap temporary admin。取得 admin token 那段做了 「先試永久帳密、失敗再退回 bootstrap 帳密」的雙軌嘗試,搭配 ansible.builtin.assert 兜底,確保這段邏輯在 temporary admin 已經被刪除之後重跑也不會卡死。

驗證方式

  • Keycloak 健康狀態:curl http://<fabric_ip>:9000/health/ready 確認回傳 UP。
  • Keycloak OIDC discovery:curl https://keycloak.dough-ops.com/realms/<realm>/.well-known/openid-configuration (從外部,走 Cloudflare)確認回傳合法的 endpoint 清單。
  • Dex → Keycloak 的 machine-to-machine 連線:kubectl logs -n dex deploy/dex 確認 connector 啟動時沒有 discovery 錯誤。
  • 端對端瀏覽器驗證:開 whoami.dough-ops.com,依序過 Cloudflare Access → Dex(Keycloak connector)→ Keycloak 登入, 最後看到 whoami 印出的請求 header 含正確的 email/groups claim。
  • 永久管理員:用 secrets.yml 設定的帳密登入 Keycloak admin console,確認沒有「temporary admin」警告,且 temporary 帳號已經不存在。
