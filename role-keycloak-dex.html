對外入口與身份驗證 Role: keycloak / dex

這組 role 建出一條 Cloudflare Access → Keycloak → Dex → 應用程式 的 OIDC 聯邦鏈。它模擬真實公司常見的拓樸：Keycloak 是跨團隊共用的獨立 SSO 來源，Dex 是每個叢集自己的 OIDC broker，叢集內的工具只認自己的 Dex，不必知道公司用哪套上游 IdP。Keycloak 的相關 role 屬於 bastion.yml（接在 vault.yml 之後），Dex 和三個測試 app 屬於 k8s.yml，Keycloak 一定要先於 Dex 就位。登入流程全貌見身份聯邦登入流程，這頁說明部署設計與實測踩到的五個 bug。

現在的設定

Role位置做什麼
keycloak_serverbastion（Docker + Postgres）獨立的 Keycloak，建 doughops realm 與 client，並建立永久管理員
dex叢集內 dex namespaceOIDC broker，connector 指向 Keycloak
dex_test_app叢集內oauth2-proxy + whoami，經 Dex 驗證整條鏈能通過
keycloak_test_app叢集內第二個 oauth2-proxy + whoami，不經 Dex、直接串 Keycloak
keycloak_native_app叢集內第三種：app 自己講 OIDC，不用任何 proxy

為什麼中間要多一層 Dex

如果叢集內每個工具都各自向 Keycloak 註冊 OIDC client，Keycloak 的 client 清單會隨叢集數量線性增長，每個叢集還要單獨管理自己能用哪些 client。Dex 把這件事收斂成叢集只跟 Keycloak 談一次：Dex 自己是 Keycloak 眼中唯一的 client，叢集內部再由 Dex 用 staticClients 分發給各個工具。對 Keycloak 這個跨團隊共用資源來說，新增或淘汰一個叢集，只是增減一個 client。

這個 PoC 只接 whoami 一個 client，驗證的是整條鏈通不通，不是 Dex 的完整功能。

Dex 的設定

設定值為什麼

Keycloak 跑在 bastion

理由和 Vault 相同。這個 PoC 中 Keycloak 扮演公司既有的 SSO 系統，現實中它不會因為某個叢集重建就消失，所以資料要在 bastion 重建後自動復原。Postgres 資料放 /userap/keycloak/pgdata，也就是 user-data 持久化 volume 上。bastion 重建後容器重啟，會直接接回既有資料，不必重建 realm 和 client。volume 的保護機制見 Terraform / OpenStack § 資料碟。

設定值
keycloak_imagequay.io/keycloak/keycloak:26.5.2
keycloak_postgres_imagepostgres:16

keycloak_pgdata_dir/userap/keycloak/pgdata
Docker networkkeycloak-net。bastion 的 Docker 預設位址池設為 10.99.0.0/16，避開叢集 Service CIDR 172.18.0.0/16

永久管理員

Keycloak 的 KC_BOOTSTRAP_ADMIN_USERNAME 與 _PASSWORD 建出來的一定是 temporary admin。官方文件明確記載這個行為，沒有繞過的啟動參數，正式流程是先建臨時帳號，登入後再手動升級成永久帳號。role 把這段流程自動化：

  1. 密碼不自動產生，而是讀 secrets.yml 的 keycloak_permanent_admin_password，帳號名稱是 keycloak_permanent_admin_username（預設 keycloak-admin）。
  2. 用 admin REST API 建立或更新永久帳號，並指派 admin realm role。
  3. 驗證能用新帳密登入之後，才刪除原本的 bootstrap temporary admin。

取得 admin token 時，先試永久帳密，失敗再退回 bootstrap 帳密，並搭配 ansible.builtin.assert 兜底，確保 temporary admin 已被刪除後重跑也不會卡死。送出表單用 body_format: form-urlencoded，讓 uri 模組自己做 URL encoding。密碼若含 +，手動拼 body 會把它誤解成空白，Keycloak 會回 invalid_grant，見 Bug #65。

三個測試 app

三個 app 各自獨立，使用不同 namespace、client 和 secret，驗證三種接法。

Role接法備註
dex_test_appoauth2-proxy → Dex → Keycloak用 --skip-oidc-discovery：Dex 的 hostname 沒有 Access 例外，discovery 在叢集內會被擋
keycloak_test_appoauth2-proxy → KeycloakKeycloak realm 路徑已有 Access 例外，瀏覽器和叢集內呼叫都能直達，用標準 OIDC discovery
keycloak_native_appapp 自己對 Keycloak 做 authorization code 流程單檔、只用標準函式庫的 Python（files/app.py），跑在 python:3.13-slim，不需 build 與 push image，顯示解碼後的 id_token claims

keycloak_server 在 bastion 的 /userap 下為 Dex 以及後兩個 app 各產生一份 client secret，再由各 role 讀取。所以 dex_test_app 另外依賴 dex.yml，後兩個只依賴 bastion.yml 和 istio.yml。

跨 playbook 的變數作用域

這個 PoC 橫跨 bastion.yml（裝 Keycloak）和 k8s.yml 下多個獨立的 ansible-playbook 呼叫。Ansible role 的 defaults/ 只在該 role 被載入的那個 play 裡有效。dex_hostname、keycloak_secrets_dir、keycloak_realm 在其他 play 都曾讀不到。跨 play 共用的變數一律放在 group_vars/all/main.yml，不放在個別 role 的 defaults/。

已知限制與 workaround

  • 每次登入都會看到 Dex 的同意畫面。Dex 對瀏覽器無狀態，oauth2-proxy 又固定送 approval_prompt=force。這是外部限制，要等上游修好，見 #51。
  • Keycloak 的 realm 路徑沒有 Cloudflare Access 保護。Dex 對 Keycloak 是機器對機器連線，沒有互動登入的 session，所以 Keycloak 的 realm 路徑與登入頁需要的靜態資源路徑獨立設成 bypass。這代表這些路徑只剩 Keycloak 自己的帳密與 OIDC 機制擋著，沒有多一層 Cloudflare 的檢查。範圍已縮到 realm 路徑，管理後台和 master realm 不在其中。bypass 的整體原則見 Cloudflare 設定清單 § Access 規則。
  • oauth2-proxy 接受未驗證的 email。dex_test_app 設了 insecure-oidc-allow-unverified-email，因為上游身份鏈本來就不提供 email_verified。這是 PoC 的設定。
  • Keycloak client secret 放在檔案裡。Dex 與各 app 的 client secret 存在 bastion 的 /userap（root-only 目錄），保護靠 bastion 的存取控制。Keycloak 的 client 查詢回應本身含明碼 secret，相關 task 必須帶 no_log，否則每次重跑都會把 secret 印進 ansible log，見 Bug #66。
  • Keycloak HTTP client 逾時偶發。Keycloak 向 Cloudflare Access token 端點的呼叫要跨公網來回，偶發 SocketTimeoutException。container 啟動時把 HTTP client timeout 調成 10 秒，見 Bug #64。這只緩解「會成功但較慢」的呼叫，不會讓真正掛掉的呼叫變快。docker run 參數只在首次建立 container 時生效，所以 role 會偵測舊 container 缺少這個設定並重建。

實測踩到的 bug

#48 · Keycloak 26 容器一直 unhealthy

  • 症狀：容器起不來，docker inspect 顯示 healthcheck 持續失敗，打 /health/ready 一路 404。
  • 根因：第一版假設 /health/ready 掛在對外服務的同一個 port 8090。Keycloak 26 把 health 與 metrics 端點移到獨立的 management port，預設 9000，並且要顯式開啟。
  • 修法：容器環境變數加 KC_HEALTH_ENABLED=true，healthcheck 改打 keycloak_management_port。
  • 怎麼確認修好：curl http://<fabric_ip>:9000/health/ready 回傳 UP。
  • 相關：Bug #48。
roles/keycloak_server/defaults/main.yml
keycloak_port: 8090
keycloak_management_port: 9000

#49 · role 重跑後 Postgres 起不來

  • 症狀：Keycloak 的 Postgres 容器重啟後報 FATAL: data directory "/var/lib/postgresql/data" has invalid permissions 和 could not open file "global/pg_filenode.map": Permission denied。
  • 根因：第一版用同一個 ansible.builtin.file task 建 secrets 目錄與 Postgres 資料目錄，owner: root。容器內 Postgres 以 uid 999 執行，首次啟動時容器自己會 chown，一切正常。但 role 每次重跑，宣告式的 file task 會把 owner 蓋回 root，下次容器重啟就炸開。
  • 修法：Postgres 資料目錄拆成獨立 task，owner: "999"，用數字 uid，因為 bastion 上 uid 999 已被 Vault 的系統帳號 vault 佔用，用名稱會混淆。secrets 目錄仍是 root，不給容器內非 root 使用者碰。兩個目錄的所有權模型本來就不同，合併成一個 task 是最初的設計錯誤。
  • 怎麼確認修好：重跑 role 後重啟 Postgres 容器，不再報權限錯誤。
  • 相關：Bug #49。

#50 · Dex 連 Keycloak 被 Cloudflare Access 擋住

  • 症狀：Dex 的 connector 啟動時 discovery 失敗，收到的是 Access 的 HTML 登入頁，不是 JSON。
  • 根因：Dex 的 oidc connector 要對 issuer 做真正的 .well-known discovery，是機器對機器的 HTTP 請求，沒有瀏覽器的 team session。而 keycloak.dough-ops.com 落在萬用字元 Access Application（*.dough-ops.com）底下，沒有互動登入的連線一律被擋。第一版嘗試用 hostAliases 讓 Dex 直連 Keycloak 的內部位址，結果 Keycloak 沒有在那個位址監聽 TLS，這條路本質上就錯，不該讓 Dex 繞過 Cloudflare 去猜內部拓樸。
  • 修法：兩邊都繼續經過 Cloudflare，TLS 照樣在 Cloudflare 終止。另外開一條範圍精準的 bypass Access policy，只放行 Dex 需要打的 Keycloak realm 路徑，定義在 cloudflare/access.tf 的 keycloak_direct。它是 self_hosted 類型，優先權高於萬用字元 Application，不必調整既有的 *.dough-ops.com policy。
  • 怎麼確認修好：kubectl logs -n dex deploy/dex 啟動時沒有 discovery 錯誤。
  • 相關：Bug #50。

最早的版本直接放行整個 Keycloak hostname，等於把管理後台與 master realm 的 token 端點對整個網路開放。最終審查抓到後，範圍收斂到 realm 路徑。收窄後又發現，登入頁載入的靜態主題資源位於 realm 路徑之外。它們被 Access 攔下後，瀏覽器端表現為 CORS 錯誤和整頁沒有 CSS，因此另外為這類純靜態資源加了一條 bypass，見 Bug #63。靜態資源沒有認證邏輯或使用者資料，風險等級不同。精確的路徑比對規則見 cloudflare/access.tf。

#51 · 每次登入都要在 Dex 按 Grant Access

  • 症狀：每次重新整理 whoami.dough-ops.com，都要在 Dex 的同意畫面按一次「Grant Access」，不是預期的登入一次後靜默通過。
  • 根因：Dex 對瀏覽器完全無狀態，沒有持久化的 SSO cookie，見 dexidp/dex#4560。每次新的 authorization request 都重新觸發 connector 流程。oauth2.skipApprovalScreen: true 有幫助，但對帶 approval_prompt=force 的請求無效。oauth2-proxy 的 --approval-prompt 預設正是 force，實測無法透過設定清空。對應的上游 issue 是 oauth2-proxy/oauth2-proxy#3426，目前仍開著。
  • 修法：目前沒有。這是外部限制，單靠改設定解決不了。程式碼註解保留了 approval-prompt: "" 的設定，作為已試過但無效的紀錄。
  • 怎麼確認修好：等上游修好後，登入一次再重新整理，不再出現同意畫面。
  • 相關：Bug #51。

#52 · oauth2-proxy 回 500：email in id_token isn't verified

  • 症狀：oauth2-proxy 登入後回 500，kubectl logs 看到「email in id_token isn't verified」。Dex 的登入紀錄也印出 email="...(unverified)"。
  • 根因：Cloudflare Access → Keycloak → Dex 這條鏈組出的 id_token，email_verified 不是 true。身份來自 Cloudflare Access 這一層，不是 Keycloak 自己核發的帳號。oauth2-proxy 預設拒絕未驗證的 email。
  • 修法：extraArgs 加 insecure-oidc-allow-unverified-email: "true"。這是 oauth2-proxy 自己的標準開關。
  • 怎麼確認修好：登入後 whoami 顯示正確的請求 header。
  • 相關：Bug #52。ArgoCD 內建 Dex 遇到同類問題，見 Role: argocd。
roles/dex_test_app/tasks/main.yml（extraArgs）
insecure-oidc-allow-unverified-email: "true"

#63 · Keycloak 登入頁無 CSS，瀏覽器顯示 CORS 錯誤

  • 症狀：登入頁整頁沒有 CSS，瀏覽器 console 顯示 CORS 錯誤。
  • 根因：登入頁載入的靜態主題資源（/resources/*）位於 realm 路徑之外。#50 把 bypass 收斂到 realm 路徑後，這些資源落回萬用字元 Access Application，被 Access 攔下。
  • 修法：在 cloudflare/access.tf 為這類純靜態資源另加一條範圍收窄的 bypass。靜態資源沒有認證邏輯或使用者資料，風險與 token 端點不同。
  • 怎麼確認修好：重新載入登入頁，樣式正常，console 不再出現 CORS 錯誤。
  • 相關：Bug #63、#50。

#64 · Keycloak 呼叫 Cloudflare Access token 端點偶發 SocketTimeoutException

  • 症狀：Keycloak 向 Cloudflare Access 的 token 端點發出的呼叫偶發 SocketTimeoutException。
  • 根因：呼叫要跨公網來回，預設的 HTTP client timeout 容不下偏慢的回應。
  • 修法：container 啟動時把 HTTP client timeout 調成 10 秒。這只緩解「會成功但較慢」的呼叫。docker run 參數只在首次建立 container 時生效，所以 role 會偵測舊 container 缺少這個設定並重建。
  • 怎麼確認修好：docker inspect 看到 container 帶有 10 秒的 timeout 設定。偶發逾時是否完全消失需要長期觀察。
  • 相關：Bug #64。

#65 · 手動送 form 時密碼含 +，Keycloak 回 invalid_grant

  • 症狀：取得 admin token 時回 invalid_grant，帳密明明正確。
  • 根因：手動拼接 form body 時，密碼裡的 + 被當成空白，Keycloak 收到另一組密碼。
  • 修法：改用 ansible.builtin.uri 的 body_format: form-urlencoded，讓模組做 URL encoding。
  • 怎麼確認修好：含 + 的密碼可取得 admin token，role 重跑不再卡住。
  • 相關：Bug #65。

#66 · Keycloak client 查詢的回應含明碼 secret，被印進 ansible log

  • 症狀：查詢 client 的 task 輸出把明碼 client secret 印進 ansible log。
  • 根因：回應本身含 secret，task 漏了 no_log，ansible 預設印出完整回應。
  • 修法：所有處理 admin 密碼、Postgres 密碼與 client secret 的 task 補上 no_log: true。
  • 怎麼確認修好：重跑 role，這些 task 只顯示 censored 提示。
  • 相關：Bug #66。

驗證方式

  • Keycloak 健康狀態：curl http://<fabric_ip>:9000/health/ready，確認回傳 UP。
  • Keycloak OIDC discovery：從外部走 Cloudflare，curl https://keycloak.dough-ops.com/realms/<realm>/.well-known/openid-configuration，確認回傳合法的 endpoint 清單。
  • Dex 連 Keycloak：kubectl logs -n dex deploy/dex，確認 connector 啟動時沒有 discovery 錯誤。
  • 端對端：用瀏覽器開 whoami.dough-ops.com，依序通過 Cloudflare Access、Dex 和 Keycloak 登入。最後 whoami 印出的請求 header 應含正確的 email 與 groups claim。
  • 永久管理員：用 secrets.yml 設定的帳密登入 Keycloak admin console，確認沒有「temporary admin」警告，temporary 帳號也已不存在。

演進歷史

這組 PoC 的第一版 Dex 對 Keycloak 使用 hostAliases 直連內部位址，後來改成經 Cloudflare 並加上精確的 bypass Application，細節見 #50。Keycloak 的 bypass 範圍先是整個 hostname，後來收窄到 realm 路徑，再補上靜態資源。三個測試 app 依序加入：先是經 Dex 的 dex_test_app，接著是直接串 Keycloak 的 keycloak_test_app，最後是不用 proxy 的 keycloak_native_app。變更紀錄見 Changelog。
