身份驗證身份聯邦登入流程:元件介紹 + 完整走一遍

開瀏覽器打 whoami.dough-ops.com 這個測試網址,到最後看到頁面印出自己的身份資訊,中間其實 經過五個獨立的元件、跳了兩次 Cloudflare。Role: keycloak / dex 那頁記錄的是 「為什麼這樣設計」跟「實測撞到的五個 bug」,這頁專門補那頁刻意跳過的部分:每個元件是什麼、 在這條鏈裡各自扮演什麼角色,以及一次登入實際會經過哪些跳轉。

牽涉到的五個元件

先建立一個共同的詞彙表,後面的流程圖會直接用這些名字,不再重新解釋。

元件它是什麼在這條鏈裡的角色對應的實際設定
Cloudflare Access Cloudflare Zero Trust 底下的反向代理驗證層——請求先到 Cloudflare 的邊緣節點,通過身份檢查才放行到真正的 origin。這個 lab 裡每個 *.dough-ops.com 網址預設都先過這一關(GitHub org 成員限定)。 這裡出現兩次、是兩個不同的 Access Application:一次是 whoami/dex/keycloak 三個 hostname 共用的萬用字元 Application(擋一般瀏覽器流量);另一次是 Keycloak 拿 Cloudflare Access 當 upstream OIDC provider 用的 keycloak-sso(type = "saas",讓 Cloudflare 自己扮演一個標準 OIDC IdP,不是擋流量用的)。 cloudflare/access.tf 的 wildcard / keycloak_sso / keycloak_direct 三個 resource
oauth2-proxy 開源的認證反向代理——本身不管理任何使用者資料,只認一個上游 OIDC provider,驗證通過後 把身份轉成 HTTP header 塞給後面真正的 app,自己再維護一份 session cookie 避免每個請求都重新驗證一次。 擋在 whoami(測試 app 本體)前面,上游指向 Dex,不是直接指向 Keycloak 或 Cloudflare——app 只需要認識 oauth2-proxy 幫它轉出來的 header,不需要自己懂 OIDC。 roles/dex_test_app,oidc-issuer-url: https://dex.dough-ops.com
Dex dexidp/dex,一個 OIDC broker——本身不管密碼,只是把 一個標準 OIDC 介面轉接到後面各種不同的「connector」(可以是 LDAP、SAML、另一個 OIDC provider……)。 叢集內唯一對外的 OIDC issuer(https://dex.dough-ops.com)。叢集裡的工具(這次只接了 whoami 一個)都只需要認識 Dex,不需要各自知道公司實際用的是 Keycloak——這是 Role: keycloak / dex 頁裡「為什麼中間要多一層 Dex」那段的答案。 roles/dex,connector type: oidc,指向 Keycloak 的 doughops realm
Keycloak 開源的身份與存取管理系統(IAM)——可以自己管帳號密碼,也可以反過來當 broker,把驗證動作轉發給上游另一個 IdP。 這裡模擬「公司既有、獨立於任何一個叢集的 SSO 來源」。它自己不直接管密碼——realm 裡設定了一個 type = OIDC 的 Identity Provider,指向上面的 keycloak-sso,把真正的登入動作再轉一手給 Cloudflare Access 的 GitHub org policy。 roles/keycloak_server,realm doughops,IdP alias cloudflare-access
whoami traefik/whoami,一個只會把收到的 HTTP request 原封不動印出來的極簡測試網站。 純粹拿來驗證整條鏈最後有沒有把正確的身份資訊帶到——不是真正要用的應用,看到的 header 就是驗收結果。 roles/dex_test_app

OAuth2/OIDC 本身的規格(authorization code flow、id_token 是什麼)這裡不重講——上面這張表已經是這個 PoC 需要知道的全部背景,把每個元件當成一個「收到請求 → 可能轉發給下一個 → 帶著結果往回傳」的黑盒子就夠讀懂下面的流程圖。

這是整條鏈裡唯一會讓人覺得「怎麼又跳出 Cloudflare」的地方——因為 keycloak-sso 是 跟第 1 步的萬用字元完全不同的一個 Access Application,即使底層 GitHub session 還在,Cloudflare 通常還是會擋一個 選擇/確認身份提供者的畫面,只是不需要重新輸入帳密,點一下就過。Keycloak 用 IdP 設定裡的 authorizationUrl/tokenUrl/userInfoUrl(都是 {cloudflare_access_team_domain}/cdn-cgi/access/sso/oidc/{client_id}/…這個固定形狀)完成 OIDC code exchange,拿到 Cloudflare 那邊核發的身份(email claim),用 syncMode: IMPORT 匯入成 Keycloak 自己 realm 裡的一個使用者,並且在 keycloak.dough-ops.com 這個 hostname 上建立它自己的 realm SSO session——這個 session 是 下面「為什麼第二次是靜默的」能成立的關鍵之一。

Keycloak 把授權碼交還給 Dex 的 redirectURI(https://dex.dough-ops.com/callback), Dex 拿它跟 Keycloak 換 token、用自己的身份重新簽發一份自己的 id_token(iss 是 https://dex.dough-ops.com,不是 Keycloak),導回 oauth2-proxy 的 redirect-url(https://whoami.dough-ops.com/oauth2/callback)。oauth2-proxy 驗證 這份 id_token(--insecure-oidc-allow-unverified-email 這個 flag 就是在這一步生效,見 Bug #5)、設定自己的 _oauth2_proxy session cookie,最後才把 請求真的轉發給 whoami,順便注入 Authorization(帶 Dex 簽的 id_token)、 X-Forwarded-Email、X-Forwarded-User 這些 header——whoami 把收到的原始 request 印出來,就是你在瀏覽器上看到的那頁。

為什麼第二次(靜默)登入不會跳任何畫面

整條鏈上有四層各自獨立的 session,生命週期互不相同:

層級session 存在哪有效期沒了會發生什麼
Cloudflare Access(萬用字元)CF_Authorization cookie24h重新跳 GitHub org 選擇畫面(通常瞬間過,因為 GitHub 自己的瀏覽器 session 還在)
Cloudflare Access(keycloak-sso)CF_Authorization + CF_AppSession cookie730h(~30 天)Keycloak 點「Login with Cloudflare」時要重新過一次確認畫面
Keycloak(doughops realm)Keycloak 自己在 keycloak.dough-ops.com 設的 session cookieKeycloak realm 預設 SSO session 設定Dex 導過去時,Keycloak 的登入頁/broker 按鈕會重新出現,不是自動通過
oauth2-proxy_oauth2_proxy cookiehelm values 設定的 cookie expire整個瀏覽器流程從第 1 步重新跑一次

單純重新整理 whoami.dough-ops.com(跟你剛剛實測的一樣)通常連 Dex 都不會再打——oauth2-proxy 自己的 _oauth2_proxy cookie 還有效的話,它會直接放行,完全不會發出上面任何一次跳轉。真正驗證「整條聯邦鏈的 session 都還在」的情境,是 _oauth2_proxy 這個 cookie 過期或被清掉之後再訪問一次——這時候流程會重新從 第 1 步跑,但因為 Keycloak/Cloudflare 那三層的 session 都還沒過期,每一站都是瞬間直接被放行,不需要任何 手動點擊,只有 Dex 這一站因為天生沒有自己的 session,一定會物理上 重新跳轉一次去問 Keycloak,只是這一次 Keycloak 秒答,肉眼看不出來。這正是 設計文件 驗收標準裡「第二次完全靜默」要驗證的東西。

自己重新驗證一次

跟 Role: keycloak / dex 頁「驗證方式」那段是同一套檢查,這裡補一個對照:

  • 清 cookie(或無痕視窗)開 whoami.dough-ops.com,應該依序看到:Cloudflare GitHub org 畫面 → Keycloak 登入頁(帳密欄位 + Login with Cloudflare)→ 點下去之後可能再跳一次 Cloudflare 確認畫面 → 落地在 whoami,印出的 Authorization header 是一段 JWT,iss 解出來應該是 https://dex.dough-ops.com。
  • 同一個分頁重新整理:應該完全不跳任何畫面,直接看到 whoami 頁——這一步如果又跳出任何畫面,回頭查上面那張表,是 哪一層的 session 先過期了。
