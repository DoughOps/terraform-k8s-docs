對外入口與身份驗證 身份聯邦登入流程

從瀏覽器開啟 whoami.dough-ops.com，到頁面印出你的身份資訊，中間會經過六個節點。這頁說明整個系統的組成，以及一次登入實際怎麼走。設計理由和實測踩到的 bug 見 Role: keycloak / dex。

瀏覽器沿著這條路徑一路往右，走到最後一站再沿原路被送回來，最後停在 whoami 頁面。下一節逐站說明每個節點在做什麼，完整的來回順序見登入流程。

Cloudflare Access 在圖上出現兩次，是兩組獨立的設定。第一組是最外層的邊緣閘門：任何人開任何一個 *.dough-ops.com 網址，都會先經過它，確認是 doughops GitHub org 的成員。第二組是 Keycloak 的上游身份來源，只有 Keycloak 會呼叫它，一般瀏覽器流量不會直接碰到。兩組用同一個產品，但設定與 session 各自獨立。

六個節點的職責

Cloudflare Access（邊緣閘門）

Cloudflare 的反向代理驗證層。請求先到 Cloudflare 邊緣，確認身份之後才放行到真正的伺服器。Lab 裡每個 *.dough-ops.com 網址預設都在這一關底下，只放行 doughops GitHub org 的成員。

oauth2-proxy

擋在 whoami 前面的認證反向代理。它自己不管理任何使用者資料，只認一個上游 OIDC provider，這裡是 Dex。驗證通過後，它把身份轉成 HTTP header 塞給後面的 whoami，自己另外 維護一份 session cookie，不用每個請求都重新驗證一次。

Dex

dexidp/dex，叢集內唯一對外的 OIDC issuer （https://dex.dough-ops.com）。它本身不管密碼，只是把一個標準的 OIDC 介面，轉接到後面某一個 「connector」——這裡接的是 Keycloak。叢集裡的工具只需要認識 Dex 這一個 issuer，不需要各自知道公司實際用的是 Keycloak，原因見 Role: keycloak / dex 的 Dex 設計說明。

Keycloak

開源的身份與存取管理系統，模擬「公司既有、獨立於任何一個叢集的 SSO 來源」。它自己不直接管密碼。realm 裡設定了 一個 Identity Provider，把真正的登入動作再轉一手給下一個節點：Cloudflare Access。

Cloudflare Access（Keycloak 的上游 IdP）

跟第一站是同一個產品，設定完全獨立，名字叫 keycloak-sso。它讓 Cloudflare 反過來扮演一個標準 OIDC provider，給 Keycloak 當上游用。所以 Keycloak 也不用管密碼，驗證責任一路往外推，最終落在 Cloudflare 的 GitHub org 檢查上。

whoami

traefik/whoami，一個只會把收到的 HTTP request 原封不動印出來的測試網站。它不是真正要用的應用，純粹用來驗證整條鏈最後有沒有把正確的身份資訊帶到。你在瀏覽器看到的那些 header，就是驗收結果。

Keycloak 把結果交還給 Dex。Dex 拿它去跟 Keycloak 換 token，再用自己的身份簽出一份新的 id_token，iss 是 https://dex.dough-ops.com，不是 Keycloak。

這份 id_token 交給 oauth2-proxy 驗證，--insecure-oidc-allow-unverified-email 就是在這一步生效，見 Bug #52。驗證通過後，oauth2-proxy 設好自己的 session cookie，再把請求轉發給 whoami，同時附上 Authorization 和 X-Forwarded-Email 等 header。whoami 把收到的 request 印出來，就是你看到的那頁。

為什麼重新整理會直接過

上面走完一輪之後，鏈上四個節點各自留下一份 session，彼此獨立、有效期也不同：

節點session 存在哪有效期
Cloudflare Access（邊緣閘門）CF_Authorization cookie24h
Cloudflare Access（keycloak-sso）CF_Authorization + CF_AppSession cookie730h（約 30 天）
Keycloak（doughops realm）Keycloak 在 keycloak.dough-ops.com 上設的 session cookierealm 的預設 SSO session 設定
oauth2-proxy_oauth2_proxy cookiehelm values 設定的 cookie expire

單純重新整理 whoami.dough-ops.com，通常連 Dex 都不會再打：oauth2-proxy 自己的 _oauth2_proxy cookie 還有效，它就直接放行，上面四步都不會發生。

比較嚴格的驗證方式，是等 _oauth2_proxy 這個 cookie 過期或被清掉之後再訪問一次。這時候流程會重新從 第 1 步跑，但因為 Keycloak 跟兩個 Cloudflare Access 的 session 都還在，每一站都是瞬間放行，不需要任何手動點擊。 唯一的例外是 Dex，它天生沒有自己的 session，一定會重新跳轉一次去問 Keycloak，只是 Keycloak 這邊秒答，肉眼看不出來。這就是「第二次完全靜默」這條驗收標準要驗證的事。

自己重新驗證一次

跟 Role: keycloak / dex 頁「驗證方式」那段是同一套檢查：

  • 清除 cookie（或用無痕視窗）後開 whoami.dough-ops.com，依序應該看到：Cloudflare GitHub org 畫面 → Keycloak 登入頁 → 點「Login with Cloudflare」後可能再跳一次 Cloudflare 確認畫面 → 落地在 whoami。印出的 Authorization header 解開來，iss 應該是 https://dex.dough-ops.com。
  • 同一個分頁重新整理：應該完全不跳任何畫面，直接看到 whoami 頁。如果又跳出畫面，回頭查上面那張表，看是哪一層的 session 先過期了。

已知現象：第一次或很久沒登入之後，點下 Cloudflare 頁面上的 GitHub 按鈕，可能會卡 10-20 秒。 用瀏覽器 DevTools 的 Network 分頁實測過：卡住的是 doughops.cloudflareaccess.com 這個網域自己的 兩個請求（GitHub 授權碼的 callback、Access for SaaS 自己的 token 端點)，各自要 2.8 秒左右，是 Cloudflare Access 驗證 GitHub 身份、核發這個 SaaS Application token 的內部處理時間，不是 Keycloak、不是這裡的測試 app、 也不是網路品質問題，這幾層都在幾百毫秒內處理完。同一個瀏覽器再測一次在 session 還在時通常會秒過。
