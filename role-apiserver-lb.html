叢集元件 Role: apiserver-lb

這組 role 為 3 台 master 提供 apiserver 的 HA 入口：所有節點用 k8s-api.internal:6443 連線，名稱解析到 tor，tor 上的 haproxy 以 L4 轉發給其中一台 master。apiserver_lb 在 tor 上安裝 haproxy，apiserver_dns 在每台機器寫 /etc/hosts。

兩個 role 由 playbooks/k8s/apiserver-lb.yml 執行，在建置順序中排在 Role: crio 之後、Role: kubeadm 之前。kubeadm 的 --control-plane-endpoint 指向這個名稱，所以入口必須先存在。

任意節點
連 k8s-api.internal:6443

/etc/hosts
apiserver_dns 寫死指向 tor
→
tor:6443
apiserver_lb，haproxy mode tcp

round robin + health check

現在的設定

項目值為什麼
名稱解析每台機器 /etc/hosts 一行：10.10.0.10 k8s-api.internal規模小，不值得為一個名稱架 DNS server。叢集還沒 bootstrap 時 CoreDNS 也不存在
解析目標tor 的 fabric_ip（k8s-net），不是 ansible_host節點對 apiserver 的存取走資料平面。ansible_host 是 mgmt-net，inventory 把兩個值分開存放，就是為了避免混淆
haproxy 監聽10.10.0.10:6443綁定 tor 自己的 fabric_ip，不綁 0.0.0.0，tor 同時是 fabric 成員，指定位址比較明確，也不會和 mgmt-net 的其他服務混淆
模式mode tcp不終止 TLS，見下方 ADR
backend以 groups['masters'] | sort 迴圈產生，balance roundrobin增減 master 只要改 terraform.tfvars 並重跑，haproxy 設定自動跟上，不用手改範本
健康檢查option tcp-check、check inter 5s fall 3 rise 2連續 3 次失敗才標 DOWN，連續 2 次成功才標回 UP，避免單次網路抖動誤判整台 master 掛了
逾時connect 5s、client 1m、server 1m，retries 2haproxy 全域預設值
stats 頁面10.10.0.10:8404，mode http，stats uri /，stats refresh 10s只在 fabric 網段監聽，供驗證三台 master 是否 UP。smoke-test 就是讀它的 CSV 輸出
套用設定validate: "haproxy -c -f %s"覆蓋正式設定檔之前先做語法檢查，失敗就中止，避免語法錯誤讓 haproxy 重啟失敗而斷掉整個 apiserver 入口
tor 上的 /etc/haproxy/haproxy.cfg（渲染後，精簡）
defaults
    mode    tcp          # 全域預設
    timeout connect 5s
    timeout client  1m
    timeout server  1m
frontend apiserver_front
    bind 10.10.0.10:6443
    default_backend apiserver_back
backend apiserver_back
    balance roundrobin
    option tcp-check
    server ms-0001 10.10.0.20:6443 check inter 5s fall 3 rise 2
    server ms-0002 10.10.0.21:6443 check inter 5s fall 3 rise 2
    server ms-0003 10.10.0.22:6443 check inter 5s fall 3 rise 2
listen stats
    mode http            # 蓋掉全域的 tcp
    bind 10.10.0.10:8404
    stats enable
    stats uri /
roles/apiserver_dns/tasks/main.yml（精簡）
- lineinfile:
    path: /etc/hosts
    regexp: '^\S*\s+k8s-api.internal$'
    line: "10.10.0.10 k8s-api.internal"   # tor 的 fabric_ip

lineinfile 用 regexp 比對「任意位址加 apiserver_hostname」的行。tor 的 fabric_ip 改變時，這行會被取代，不會疊出重複紀錄。

haproxy 使用 mode tcp

決策：haproxy 對 apiserver 一律使用 mode tcp，只做 L4 轉發，不終止 TLS。

理由：kube-apiserver 支援 client certificate 認證。kubelet 和其他元件拿自己的憑證直接和 apiserver 做 TLS 交握，apiserver 從憑證讀出呼叫者身分。haproxy 若終止 TLS，會另外對 apiserver 開一條自己的連線，apiserver 看到的 handshake 來自 haproxy，client cert 認證因此失效。mode tcp 讓整個 TLS session 從原始 client 一路延伸到後端 apiserver，haproxy 不碰加密內容。

考慮過的替代方案：mode http 反向代理並終止 TLS — 會打斷 client cert 認證，不可行。

代價：haproxy 看不到 HTTP 內容，只能做 TCP 層健康檢查，無法依 API 路徑分流或做 L7 檢查。

為什麼 haproxy 放在 tor 上

決策：haproxy 直接跑在 tor 上，節點用 DNS 名稱存取 apiserver，tor 自動轉發給 master。

理由：tor 本來就是一台必須存在且穩定運作的機器（route reflector），和 3 台 master 在 k8s-net 上的鄰居關係早就建好。不必再解決「LB 節點如何加入 fabric」的問題，也不必多開 VM。

考慮過的替代方案：

  • Cilium BGP-based L4LB — apiserver 的 HA 在叢集啟動階段就需要。Cilium 的 eBPF 資料平面要靠 apiserver 才能初始化，形成先有雞還是先有蛋的問題。此外原本規劃當 L4LB 的 l4-0001、l4-0002 同時要當一般 worker，並非專職 LB 節點。
  • 另開專用 LB 節點跑 keepalived + haproxy（VRRP 做 VIP 漂移）— 這是標準的 kubeadm HA 做法，技術上可行，但要多開 VM。OpenStack quota 從專案一開始就吃緊。

代價：tor 成為 apiserver 入口的單點。tor 本身也是 route reflector 和 NAT 邊界，它故障時 fabric 與 apiserver 入口一起中斷，不像 keepalived 方案可獨立漂移 VIP。

已知限制

  • 安裝這個 role 時，kube-apiserver 還不存在，haproxy 的 backend 一開始全部是 DOWN，屬於預期。Role: kubeadm 裝好 apiserver 後會自動變 UP，不需要回頭改任何設定。
  • haproxy 只有 tor 一台，沒有備援，見上方 ADR 的代價。
  • stats 頁面只在 fabric 網段監聽，且沒有認證。fabric port 的 port security 是關閉的（見 Terraform / OpenStack），同一網段的節點都能讀取。

實測踩到的 bug

#13 · haproxy 設定驗證失敗，unknown keyword 'Ansible'

  • 症狀：haproxy -c 驗證失敗：unknown keyword 'Ansible' out of section。
  • 根因：範本檔頭用了 {{ ansible_managed }}，但沒有加 # 註解字元，渲染出來的第一行不是合法的 haproxy 語法。
  • 修法：範本檔頭改成純文字的 # 註解。
  • 怎麼確認修好：validate: "haproxy -c -f %s" 通過，haproxy 正常重啟。
  • 相關：Bug 事後檢討 #13。

#14 · haproxy stats 頁面打不開

  • 症狀：連 10.10.0.10:8404 的 stats 頁面沒有回應。
  • 根因：listen stats 沿用全域 defaults 的 mode tcp，而 stats 頁面本質是 HTTP 服務。
  • 修法：在 listen stats 區塊內明確寫 mode http。
  • 怎麼確認修好：對 stats 端點發 HTTP 請求能取得頁面和 CSV。
  • 相關：Bug 事後檢討 #14、Bug #21 是 smoke-test 讀 stats CSV 時的欄位定位問題。

驗證方式

最直接的驗證是讀 tor 上 haproxy 的 CSV 統計。smoke-test 的第二段就是這麼做：用 cut -d, -f1,2,18 取出 pxname,svname,status，確認三台 master 全是 UP。

在 tor 上
$ curl -s 'http://10.10.0.10:8404/;csv' | cut -d, -f1,2,18

預期結果：apiserver_back 底下 ms-0001 到 ms-0003 的 status 都是 UP。在 kubeadm 安裝完成之前，全部為 DOWN 是正常現象。
