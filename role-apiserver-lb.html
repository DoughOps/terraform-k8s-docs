Ansible 自動化Role: apiserver_lb / apiserver_dns

3 台 master 要做 apiserver HA,一定要有某種東西把 k8s-api.internal:6443 分派到 3 台 master 的其中一台。 這頁記錄怎麼選定「tor 上跑 haproxy」這個方案,以及為什麼放棄了 另外兩個看起來更「雲原生」的選項。

被放棄的方案一:Cilium BGP-based L4LB(arthurchiao.art 那篇架構)

Cilium 的 BGP Control Plane 可以把 Service 的 VIP 用 BGP 廣播出去, 搭配 eBPF 做負載平衡,做出「不需要額外 LB 節點」的架構。這個方案在 討論階段被提出過,但有一個直接的矛盾:這個 lab 裡原本規劃 「當 L4LB」的兩個節點(l4-0001/l4-0002), 後來決定同時也要當一般的 k8s worker——它們不是專職的 LB 節點。而且更根本的問題是:apiserver 的 HA 是叢集啟動階段 就需要的東西,Cilium 的 eBPF 資料平面本身要靠 apiserver 才能初始化 (要讀 Kubernetes API 物件),這是一個先有雞還是先有蛋的問題—— 不能用「靠 CNI 才能運作的機制」去解決「CNI 還沒起來之前要怎麼連上 apiserver」這件事。

被放棄的方案二:另開專用 LB 節點跑 keepalived + haproxy

比較「標準」的 kubeadm HA 教學做法,是另外準備 1~2 台專職的 LB 機器,跑 keepalived(VRRP 做 VIP 漂移)+ haproxy。這個方案技術上 沒問題,但使用者明確表達不想再多開一台 VM(OpenStack quota 吃緊是這整個專案從第一天就有的限制,見 總覽的建置脈絡)。

最終方案:haproxy 直接跑在 tor 上

使用者的原話是「還是用 tor 節點當 haproxy 吧,並且 worker 會用 DNS 紀錄存取 apiserver,這個 DNS 紀錄會指向 tor 節點,tor 自動轉發給 master 節點,這樣比較單純」——這個決定的關鍵字是 「單純」:tor 本來就是一台一定會存在、一定要穩定運作的機器 (route reflector),它跟 3 台 master 的網路關係(k8s-net 上的 鄰居)本來就已經建立好了,不需要再多解決一次「LB 節點要怎麼加入 這個 fabric」的問題。

apiserver_dns:不架真的 DNS server

roles/apiserver_dns/tasks/main.yml
- lineinfile:
    path: /etc/hosts
    regexp: '^\S*\s+k8s-api.internal$'
    line: "10.10.0.10 k8s-api.internal"   # tor 的 fabric_ip

每台機器的 /etc/hosts 各自寫一條靜態紀錄——這個 lab 規模小到不值得為了一個名稱解析架一個真的 DNS server(CoreDNS 這時候 甚至還不存在,叢集都還沒 bootstrap)。lineinfile 用 regexp 比對「這一行的格式是任意內容 + apiserver_hostname」, 確保重跑時如果 IP 變了(例如 tor 的 fabric_ip 因為某種原因改變), 這行紀錄會被取代而不是疊加出重複的行。

刻意讀 tor 的 fabric_ip,不是 ansible_host ——worker/master/lb 對 apiserver 的存取是走資料平面(k8s-net), 跟 ansible 自己用來連線管理的 mgmt-net 是兩個完全不同的網路, 這兩個值在 inventory 裡分開存放正是為了避免這種地方搞混 (見 框架設計)。

apiserver_lb:haproxy 設定的每一行

roles/apiserver_lb/templates/haproxy.cfg.j2
defaults
    mode    tcp          # 全域預設,見下方說明
    timeout connect 5s
    timeout client  1m
    timeout server  1m

frontend apiserver_front
    bind 10.10.0.10:6443
    default_backend apiserver_back

backend apiserver_back
    balance roundrobin
    option tcp-check
    server ms-0001 10.10.0.20:6443 check inter 5s fall 3 rise 2
    server ms-0002 10.10.0.21:6443 check inter 5s fall 3 rise 2
    server ms-0003 10.10.0.22:6443 check inter 5s fall 3 rise 2

listen stats
    mode http            # 蓋掉全域的 tcp,這個 block 專屬 http
    bind 10.10.0.10:8404
    stats enable
    stats uri /

為什麼一定要是 mode tcp,絕對不能在這裡終止 TLS: kube-apiserver 支援 client certificate 認證——kubelet、其他元件 拿它們自己的憑證直接跟 apiserver 做 TLS 交握,apiserver 從憑證裡 讀出呼叫者身分。如果 haproxy 在這一層做 TLS termination(變成 mode http 反向代理),這個「client 憑證直接被 apiserver 驗證」的路徑會被打斷——haproxy 會終止原始的 TLS 連線,重新對 apiserver 開一條它自己的連線,apiserver 收到的 TLS handshake 資訊來自 haproxy,不是原始 client,client cert 認證直接失效。mode tcp 讓 haproxy 純粹做 L4 轉發, 整個 TLS session(包含 client cert 交握)完整地從原始 client 一路延伸到後端的 kube-apiserver,haproxy 完全不碰 加密內容。

frontend 監聽在 tor 自己的 fabric_ip (不是 0.0.0.0)——因為這台機器同時也是 fabric 的一員,監聽在特定位址比較明確,而且跟 mgmt-net 上可能存在的 其他服務不會混淆。backend 用 Jinja for host in groups['masters'] | sort 迴圈動態產生, 新增/移除 master 只要改 terraform.tfvars 重新 apply,haproxy 設定會自動反映,不用手動改這個模板。 option tcp-check + fall 3 rise 2 做健康檢查——3 次探測失敗才標記 DOWN,2 次成功才標記回 UP, 避免單一次網路抖動就誤判整台 master 掛了。

listen stats 這個區塊要單獨蓋回 mode http,不然會沿用上面 defaults 的 tcp——haproxy 的統計頁面本質上是一個簡單的 HTTP 服務,用 tcp 模式監聽它完全無法運作。這個統計頁面 只監聽在 fabric 網段(fabric port_security 目前是關閉的, 見 Terraform / OpenStack), 拿來驗證「3 台 master 是不是都 UP」很方便, k8s/smoke-test.yml 就是直接讀這個頁面的 CSV 輸出做自動化驗證。

套用設定時用 validate: "haproxy -c -f %s" ——ansible 的 template 模組在真正覆蓋掉正式設定檔之前, 會先把渲染結果丟給 haproxy -c 做語法檢查,檢查失敗就 直接中止、不套用,不會讓一個語法錯誤的設定檔讓 haproxy 重啟失敗、 整個 apiserver 入口斷線。

裝這個 role 的時候,kube-apiserver 根本還沒存在 ——這個 playbook 是在 kubeadm bootstrap之前先跑的, 所以 haproxy 的 backend health check 一開始全部會是 DOWN, 這是預期行為,不代表哪裡壞了。等 Role: kubeadm 把 apiserver 實際裝起來, backend 會自動變成 UP,不需要回頭改這裡任何設定。
