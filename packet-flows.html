網路架構五個具體情境的完整封包路徑

上一頁(網路架構總覽)講的是 「系統怎麼拼起來」,這頁把它換成五個具體情境,逐跳畫出封包實際會走的路徑。 每個情境都是這個 lab 實測驗證過的行為,不是理論推導。

情境一:Pod ↔ Pod,同一個節點

最簡單的情況——兩個 pod 剛好排程到同一台節點上,完全不需要離開這台機器。

Pod A
172.16.4.10
→
veth pair
→
Cilium eBPF
datapath,同節點直接轉發
→
veth pair
→
Pod B
172.16.4.20

這一段完全不會出現在 tcpdump -i ens3 上——封包從頭到尾沒有離開 這台主機的 kernel network namespace 邊界,FRR/BGP 完全不參與。

情境二:Pod ↔ Pod,跨節點(native routing 的核心場景)

這是整個 Cilium native routing 設計要解決的 主要情境,例如 ms-0001 上的 pod 要連到 ap-0002 上的 pod:

Pod A
172.16.4.10
on ms-0001
→
cilium_host
本節點 PodCIDR
connected route
→
ms-0001 查路由表
172.16.6.0/24
via 10.10.0.41 dev ens3
(BGP 學到的)
→
k8s-net(flat L3)
直接送到 ap-0002
的 ens3,一個 IP hop
→
cilium_host
ap-0002 本地 PodCIDR
→
Pod B
172.16.6.20
on ap-0002

實測用 tcpdump 在 ms-0001 的 ens3 上抓包,看到的是完全不加密封裝的原始 IP/TCP,來源/目的地 直接是兩個 pod 的真實 IP(10.244.2.6 → 10.244.5.201,CIDR 改版前的測試截圖;改版後同樣邏輯,只是位址換成 172.16.x.x) ——沒有任何 VXLAN/Geneve header,這就是「native」routing 這個名字的來源。

為什麼「一個 IP hop」就夠了:因為 k8s-net 是單一 flat subnet(10.10.0.0/24),任何一個節點的 ens3 都可以直接 ARP 解析到同網段任何其他節點的 ens3——BGP 在這裡的角色不是「決定下一個 IP 路由器」(像傳統多網段的 BGP 網路那樣), 而是「決定這個 PodCIDR 應該送去哪一個節點的位址」,決定完之後,實際送達 是靠 L2/L3 flat network 本身的直連能力,不需要再多繞路。

情境三:Pod → ClusterIP(Service)

Pod 要連一個 Service(例如叢集內部呼叫 kubernetes.default 這個內建 Service,ClusterIP 是 172.18.0.1)：

Pod
連 172.18.0.1:443
→
本機 iptables
KUBE-SERVICES chain
(kube-proxy 產生)
→
DNAT
目的地改成某個
真實 master fabric_ip:6443
→
查路由表(這時候
查的已經是改寫後的目的地)
→
k8s-net
直接送到目標 master

要注意的是這條路徑跟情境二(Pod↔Pod)完全不共用機制——ClusterIP 從來 不是一個「路由得到」的位址,它純粹是 iptables DNAT 表的一個 key。 如果流量的發起端是節點本身(hostNetwork,不是 pod 裡面), DNAT 生效前的來源位址選擇會因為 172.18.0.0/16 沒有專屬路由 而選錯网段——這正是 service-cidr 靜態路由要解決的問題,詳見 Role: kubelet。 Pod 內部發起的流量不會有這個問題,因為 pod 的網路 namespace 裡本來就只有 cilium_host 這條路可以走,不會意外選到 mgmt-net。

情境四:任意節點 → kube-apiserver(HA 入口)

Worker 的 kubelet、其他 master 的 apiserver 互連、或是 bastion 上的 kubectl,全部走同一條固定路徑,細節見 Role: apiserver-lb:

任意節點
連 k8s-api.internal:6443
→
/etc/hosts
解析成 tor 的
fabric_ip(10.10.0.10)
→
tor:6443
haproxy,mode tcp
→
3 台 master 之一
round robin,health check

這條路徑刻意不用 DNS server,而是每個節點的 /etc/hosts 各自寫一條靜態紀錄——這個 lab 規模小到不值得為了 一個名稱解析架一個真的 DNS server,而且 /etc/hosts 在 apiserver 都還沒起來、kube-dns/CoreDNS 都不存在的 kubeadm bootstrap 階段也一樣可靠(不依賴叢集本身已經在運作)。

情境五:外部 SSH 進入(唯一的公開入口)

你的筆電
→
floating ip
只掛在 bastion 上
→
bastion
唯一的操作入口
→
bastion 容器內
ansible-runner,同一個
mgmt-net,直連任何節點

整條路徑只有一次 SSH(筆電到 bastion),bastion 到其他 所有節點是容器直連 mgmt-net,不需要 ProxyJump——詳見 Ansible 框架設計裡「為什麼連線用 mgmt-net 不是走 jump host」那段。這個 lab 裡唯一一個 floating ip 就掛在 bastion 上,任何其他節點都沒有公開可達的位址, 整個叢集對外的攻擊面被壓縮到只有 bastion 這一台。

情境附錄:DNS 解析(CoreDNS)怎麼融入這個架構

Pod 要解析一個 Service 名稱(例如 kubernetes.default.svc.cluster.local) 走的是叢集內建的 CoreDNS,運作方式是「情境一或情境二」(取決於發起 pod 跟 CoreDNS pod 是不是同一節點)+「情境三」的組合——kubelet 幫每個 pod 注入的 /etc/resolv.conf 指向 CoreDNS 的 ClusterIP,查詢本身 先走情境三(Pod → ClusterIP → DNAT 到真正的 CoreDNS pod IP), 拿到解析結果之後,真正的資料連線才走情境二(Pod → Pod,原生路由)。 這也是為什麼 Cilium 裝完之前, coredns 這兩個 pod 會卡在 Pending——沒有 CNI, 連 CoreDNS 自己都排不上 pod 網路,更別提幫其他 pod 解析。
