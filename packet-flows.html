網路架構 封包路徑實例

這頁把網路架構總覽的設計換成六個具體情境，逐跳畫出封包實際走的路徑。每個情境都是這個 lab 實測驗證過的行為。

情境一：同節點的 Pod 互連

兩個 Pod 排程到同一台節點，封包完全不需要離開這台機器。

Pod A
172.16.4.10
→
veth pair
→
Cilium eBPF
datapath，同節點直接轉發
→
veth pair
→
Pod B
172.16.4.20

這一段不會出現在 tcpdump -i ens3 上。封包從頭到尾沒有離開這台主機的 network namespace 邊界，FRR 與 BGP 完全不參與。

情境二：跨節點的 Pod 互連

這是 Cilium native routing 要解決的主要情境。例如 ms-0001 上的 Pod 連到 ap-0002 上的 Pod：

Pod A
172.16.4.10
on ms-0001
→
cilium_host
本節點 PodCIDR
的路由
→
ms-0001 查路由表
172.16.6.0/24
via 10.10.0.10 dev ens3
（BGP 學到，next-hop 是 tor）
→
tor 查自己的 RIB
172.16.6.0/24
via 10.10.0.41
唯一的 L3 hop
→
ap-0002 的 ens3
同一個 k8s-net
flat L2
→
Pod B
172.16.6.20
on ap-0002

在 ms-0001 的 ens3 上用 tcpdump 抓包，看到的是沒有封裝的原始 IP/TCP，來源與目的地直接是兩個 Pod 的真實 IP。這張抓包取自 Pod CIDR 還是 10.244.0.0/16 的時期（10.244.2.6 → 10.244.5.201），改成 172.16.0.0/16 後邏輯相同，位址換成 172.16.x.x。沒有任何 VXLAN 或 Geneve header，這就是「native」routing 名稱的由來。

為什麼只有 tor 一個 L3 hop：k8s-net 是單一 flat subnet，節點之間其實可以直接 ARP。但 tor 對每個 client 設定 next-hop-self all，所有節點學到的 Pod 路由 next-hop 都是 tor，封包因此一律先到 tor，再由 tor 轉回同一個網段的目標節點。BGP 在這裡決定的是「這個 PodCIDR 要先交給誰」，而不是「下一個傳統路由器在哪裡」。這條路徑能成立，還需要節點與 tor 都關閉 ICMP redirect，細節見 FRR / iBGP Fabric。

情境三：Pod 連 ClusterIP

Pod 連一個 Service，例如叢集內部呼叫 kubernetes.default，ClusterIP 是 172.18.0.1：

Pod
連 172.18.0.1:443
→
Cilium eBPF
Service 表
（取代 kube-proxy）
→
位址轉換
目的地改成某個
真實 master fabric_ip:6443
→
查路由表
此時查的是
轉換後的目的地
→
k8s-net
送到目標 master

這條路徑與情境二不共用機制。ClusterIP 不是路由得到的位址，它只是 Cilium Service 表的一個 key。

如果發起端是節點本身（hostNetwork，而不是 Pod 內部），轉換生效前的來源位址選擇會因為 172.18.0.0/16 沒有專屬路由而選錯網段。這正是 service-cidr 靜態路由要解決的問題，Ansible 實作見 Role: kubelet。Pod 內部發起的流量沒有這個問題，因為 Pod 的 network namespace 裡只有 cilium_host 這條路可走，不會選到 mgmt-net。

上面的 kubernetes Service 有個特例：它的 backend 是 master 的真實 IP。Pod 來源的封包還會被 masquerade 成節點 IP，原因見 Role: cilium。

情境四：任意節點連 kube-apiserver

Worker 的 kubelet、其他 master 的 apiserver，以及 bastion 上的 kubectl，全部走同一條固定路徑，細節見 Role: apiserver-lb：

任意節點
連 k8s-api.internal:6443
→
/etc/hosts
解析成 tor 的
fabric_ip（10.10.0.10）
→
tor:6443
haproxy，mode tcp
→
3 台 master 之一
round robin，health check

這條路徑刻意不用 DNS server，每個節點的 /etc/hosts 各寫一條靜態紀錄。這個規模不值得為一個名稱架 DNS server。另外，在 kubeadm bootstrap 階段 apiserver 與 CoreDNS 都還不存在，/etc/hosts 不依賴叢集已經運作，所以一樣可靠。

情境五：外部 HTTPS 請求

瀏覽器連 *.dough-ops.com 底下的服務，例如 Grafana。流量從叢集內主動連出去的 tunnel 進來：

→

→
istio-ingressgateway

ClusterIP
→
VirtualService
導向後端 Pod
情境二或情境三

cloudflared 到 gateway 的連線是叢集內部的 Service 流量，走情境三的機制。整條路徑沒有經過 Floating IP、tor 或任何 NodePort。入口的設計與兩條 tunnel 的分工見網路架構總覽。

情境六：外部 SSH 進入

你的筆電
→
Floating IP
只掛在 bastion
→
bastion
唯一的操作入口
→
bastion 上的容器
ansible-runner，同在 mgmt-net
直連任何節點

整條路徑只有一次 SSH（筆電到 bastion）。bastion 到其他節點由容器直連 mgmt-net，不需要 ProxyJump，見 Ansible 框架設計。整個叢集唯一的 Floating IP 就在 bastion 上，其他節點沒有公開可達的位址，對外攻擊面因此縮到 bastion 一台。

補充：DNS 解析怎麼融入

Pod 解析 Service 名稱，例如 kubernetes.default.svc.cluster.local，走叢集內建的 CoreDNS。流程是情境三加上情境一或二的組合：

  1. kubelet 幫每個 Pod 注入的 /etc/resolv.conf 指向 CoreDNS 的 ClusterIP。
  2. 查詢本身走情境三：Pod 連 ClusterIP，被轉換成某個 CoreDNS Pod 的 IP。
  3. 拿到解析結果後，真正的資料連線走情境二：Pod 到 Pod，native routing。

所以 Cilium 裝完之前，兩個 coredns Pod 會卡在 Pending。沒有 CNI，連 CoreDNS 自己都排不上 Pod 網路。
