對外入口與身份驗證 Role: cloudflare_tunnel

這個 role 在叢集的 cloudflare namespace 部署 cloudflared，對 Cloudflare 邊緣建立 outbound-only 的連線，不開任何 inbound port。它是整個 lab 唯一的對外入口，在建置順序中接在 cert-manager 之後，依賴已經存在的叢集與 bastion 上的 kubeconfig。同一頁也說明 bastion 上的第二條獨立 Tunnel（roles/bastion_ssh_tunnel）。

現在的路徑

Client
瀏覽器
→

整條路徑沒有任何一段需要對外開放 port。cloudflared 主動對 Cloudflare 邊緣發起連線，屬於 reverse tunnel 類技術。瀏覽器到邊緣這段由 Cloudflare 的 Universal SSL 處理。邊緣到 Istio 這段由 Origin CA 憑證加密並驗證，見 Role: cert_manager。整體路徑的逐跳說明見對外入口的現況路徑。

所有 *.dough-ops.com 的請求都要先通過 Cloudflare Access 才會進到這條 Tunnel，規則見 Cloudflare Access 規則。

現在的設定

項目值為什麼
部署位置cloudflare namespace，Deployment cloudflared-deployment與叢集內其他系統元件分開
replica 數2同一條 Tunnel 可以有多個 cloudflared 同時連線，邊緣自行負載平衡與 failover
映像cloudflare/cloudflared:latest，加 --no-autoupdate版本由映像 tag 決定，不讓程式自行更新

roles/cloudflare_tunnel/templates/cloudflare-tunnel.yaml.j2（精簡）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cloudflared-deployment
  namespace: cloudflare
spec:
  replicas: 2
  template:
    spec:
      containers:
        - name: cloudflared
          image: cloudflare/cloudflared:latest
          command:
            - cloudflared
            - tunnel
            - --no-autoupdate
            - --loglevel
            - info
            - --metrics
            - 0.0.0.0:2000
            - run
          env:
            - name: TUNNEL_TOKEN
              valueFrom:
                secretKeyRef:
                  name: cloudflare-tunnel-token
                  key: token
          livenessProbe:
            httpGet:
              path: /ready
              port: 2000

這是 remotely-managed 模式的 Tunnel。cloudflared 啟動時只帶 TUNNEL_TOKEN，routing 與 ingress 規則（*.dough-ops.com 轉給哪個叢集內服務）都在 Cloudflare 側，由 cloudflare/ 的 Terraform 管理，不是本地 config.yaml。所以這個 role 的責任只到「把 cloudflared 跑起來、連上正確的 Tunnel」，DNS 與 ingress 規則見 Cloudflare 設定清單。

Cloudflare 側設定

項目設定
Tunnelopenstack-k8s
DNS*.dough-ops.com CNAME → <tunnel-id>.cfargotunnel.com（proxied）
Tunnel ingress 規則*.dough-ops.com → https://istio-ingressgateway.istio.svc.cluster.local:443
originServerName: gateway.dough-ops.com
caPool: /etc/cloudflared/certs/origin-ca-ecc-root.pem

重建叢集不會動到這三項。同一條 Tunnel 與同一個 token，cloudflared 重新啟動後會用同一個 identity 連回邊緣，DNS 與 ingress 規則不用重設。

為什麼是第一層萬用字元

決策：對外服務使用 apex 底下第一層的萬用字元 *.dough-ops.com，不使用 *.k8s.dough-ops.com 這類多層萬用字元。

理由：Cloudflare 免費方案的 Universal SSL 只涵蓋 apex 與第一層萬用字元。用 /zones/{id}/ssl/certificate_packs 查證，*.dough-ops.com 的狀態是 active，多層萬用字元不在涵蓋範圍，TLS handshake 在請求到達 Tunnel 之前就失敗。

考慮過的替代方案：每個服務各自一筆 exact-match DNS 紀錄 — 每新增服務都要改 Cloudflare 設定，不選。

代價：服務名稱只能是單層子網域。

單一一筆 *.dough-ops.com DNS 紀錄加一條 Tunnel ingress 規則，就能涵蓋任何子網域。新增服務只要在 Istio 加 VirtualService。

token 與 Secret 處理

token 的值放在 ansible/inventory/group_vars/all/secrets.yml，這份檔案以 ansible-vault 加密，欄位範本是 secrets.yml.example。加解密與密碼管理見 Ansible 框架設計 § 密鑰管理。Terraform 產生 token 後由 scripts/sync-cloudflare-secrets.sh 寫入，這支腳本與加密檔的相容問題見 Cloudflare 設定清單 § 用 Terraform 建立或重建。

roles/cloudflare_tunnel/tasks/main.yml（assert 部分）
- name: 確認 cloudflare_tunnel_token 有設定
  ansible.builtin.assert:
    that: cloudflare_tunnel_token is defined and cloudflare_tunnel_token | length > 0 and cloudflare_tunnel_token != "REPLACE_ME"

role 先 assert 再 template 與 apply。secrets.yml 沒建好時，會用清楚的錯誤訊息中止，不會把空字串或字面值 REPLACE_ME 部署成 Secret，產生一個看似正常、實際連不上任何 Tunnel 的 pod。

在 bastion 上執行

role 只在 bastion 上跑，因為 bastion 是唯一有 kubectl 與 kubeconfig 的地方。流程是產生 manifest、kubectl apply，再用 kubectl -n cloudflare rollout status deployment/cloudflared-deployment 確認兩個 replica 都 Ready，不只看 apply 沒報錯。

叢集尚未建立時，bastion 上沒有 /home/ubuntu/.kube/config，role 會印出提示並跳過 apply，不讓 bastion.yml 後面無關的步驟被拖累。bastion/cloudflare-tunnel.yml 因此只在 k8s.yml 的 cert-manager 之後匯入一次，那是叢集第一次真的可用的時間點。細節見 Bug #37。Tunnel token 輪替後重跑單一 playbook：

repo 根目錄
$ scripts/ansible.sh ansible-playbook playbooks/bastion/cloudflare-tunnel.yml

預期結果：playbook 成功，最後一個 task 等到 cloudflared-deployment 完全 ready。

token 輪替

Terraform 重建 Tunnel 之後 token 會換新，單純更新 secrets.yml 再重跑 playbook 不夠，兩個 role 都需要額外處理。

叢集內的 cloudflared

TUNNEL_TOKEN 是 env.valueFrom.secretKeyRef，環境變數只在 Pod 啟動時讀一次。Secret 內容更新後，已經在跑的 Pod 拿不到新值。

role 在 kubectl apply 之後檢查輸出。只有看到 secret/cloudflare-tunnel-token configured（不是 unchanged）時，才執行 kubectl -n cloudflare rollout restart deployment/cloudflared-deployment。

bastion 上的 cloudflared

cloudflared service install <token> 不是冪等指令。systemd unit 已存在時，它會報 cloudflared service is already installed at ... 並拒絕重跑。role 因此用 ansible.builtin.stat 檢查 /etc/systemd/system/cloudflared.service，安裝 task 用 when: not cloudflared_service_file.stat.exists 守衛，只在第一次執行。token 出現在指令列，task 加了 no_log: true，避免被印進執行紀錄。

只靠這個守衛，token 換新後重跑會直接跳過，新 token 永遠不會套用。所以 role 另有一個獨立 task，用 ansible.builtin.copy 把 token 寫進 /etc/cloudflared/token。這個 task 每次都跑，靠內容 diff 判斷有沒有變，變了才透過 handler 重啟 cloudflared service。

這兩個輪替問題登錄為 Bug #56（叢集內）與 Bug #57（bastion）。

bastion 上的第二條 Tunnel

roles/bastion_ssh_tunnel 在 bastion 主機上以 systemd service 跑另一個 cloudflared，連接獨立的 bastion-ssh Tunnel。它與叢集內的 openstack-k8s 不共用 Tunnel 和 token。

決策：瀏覽器 SSH 使用獨立的 Tunnel，cloudflared 直接裝在 bastion 主機，不放進叢集。

理由：SSH 的目標是 bastion 這台機器，cloudflared 要連 localhost:22。放在叢集內還要多處理 network namespace。Tunnel 分開之後，叢集的對外服務與 bastion 維運入口互不影響，其中一條的 token 換掉也不會波及另一條。

考慮過的替代方案：共用 openstack-k8s Tunnel — 叢集故障時連 SSH 入口一起失效，不選。

代價：多維護一個 token 和一個 systemd service。

這條 Tunnel 現在還服務 bastion 本機上的 Vault、Keycloak 和 GitLab，ingress 規則見 Cloudflare 設定清單 § Tunnel。

roles/bastion_ssh_tunnel/tasks/main.yml（順序）
1. assert cloudflare_bastion_ssh_tunnel_token 已設定
2. 加 cloudflared 的官方 apt repo（使用目前有效的簽章金鑰）
3. apt 裝 cloudflared
4. 用 stat 檢查 systemd unit 存不存在
5. cloudflared service install <token>（只在第一次跑，no_log）
6. 把目前的 token 寫進 /etc/cloudflared/token（每次跑，變了才 notify 重啟）
7. 確保 systemd service started + enabled

apt 簽章金鑰從 https://pkg.cloudflare.com/cloudflare-main.gpg 下載。Cloudflare 在 2026 年輪替過簽章金鑰，網路上流傳的舊版安裝指令已經失效。

已知限制與 workaround

  • 映像使用 latest：重新建立 Pod 時可能拿到新版本，行為不一定與上次相同。Tunnel 數量少，目前可接受。
  • token 輪替要人工觸發：Terraform 換掉 token 後，要照 換掉 token 之後重跑的 playbook 重跑，期間 cloudflared 連不上邊緣。
  • 叢集不存在時 role 會跳過：這是刻意設計，跑完 bastion.yml 不代表 cloudflared 已經部署，要等叢集建好後由 k8s.yml 補上。

實測踩到的 bug

#25 · secrets 檔放在 group_vars 下沒有被載入

  • 症狀：cloudflare_tunnel_token is undefined，即使 secrets.yml 確實存在。
  • 根因：第一版把檔案放在 group_vars/secrets.yml，與 all.yml 同一層。這個檔名不對應任何真實存在的 inventory group，沒有叫 secrets 的 group，Ansible 的 group_vars/ 自動載入機制不會處理它。
  • 修法：改用每個 group 一個目錄的寫法。group_vars/all.yml 搬到 group_vars/all/main.yml，機密變數放 group_vars/all/secrets.yml。Ansible 會自動合併載入 all/ 底下所有 .yml，公開變數與機密變數分檔，也不用額外的 vars_files。
  • 怎麼確認修好：重跑 playbook，cloudflare_tunnel_token 有值，assert 通過。
  • 相關：Bug #25、Ansible 框架設計 § 密鑰管理。

瀏覽器 SSH 的 Access 設定有另外兩個 bug，見 Cloudflare 設定清單 § 實測踩到的 bug（#29、#30）。cloudflared 到 Gateway 的 SNI 問題見 Bug #28。

驗證方式

在 bastion 上
$ kubectl -n cloudflare rollout status deployment/cloudflared-deployment
$ curl -s -o /dev/null -w "%{http_code}\n" https://test.dough-ops.com/

預期結果：rollout 顯示 2 個 replica 都已 Ready，curl 回 302。302 代表請求經過 Tunnel 到達 Cloudflare 邊緣，並被 Access 導向登入頁。要測後端本身，必須從叢集內部繞過 Access 直接打 Gateway 的 443，做法見 Role: cert_manager § 驗證方式。

演進歷史

曾經的 floating IP 方案

裝 Istio 之初，對外入口的第一版做法是延續「用既有機器解決問題」的風格，不使用 Tunnel：

  • 在 bastion 的 floating IP 上開 allow_http 的 security group rule。
  • Istio ingress gateway 改成 NodePort，固定 30080 與 30443。
  • 新增 roles/ingress_proxy，在 bastion 上跑 nginx，把 floating IP 的 80 port 轉給某個節點的 NodePort。

決策：對外入口使用 outbound-only 的 Cloudflare Tunnel，撤掉 floating IP 加 NodePort 加 nginx 的方案。

理由：Tunnel 由叢集內主動向外連線，不需要開任何 inbound port，攻擊面只有 Cloudflare 邊緣一個入口。floating IP 方案要在公網開放 80 port，並且多維護 nginx 這一跳和一組固定 NodePort。TLS 與 Access 檢查也能集中在邊緣完成。

考慮過的替代方案：bastion 上的 nginx 反向代理 — 要開 inbound port，bastion 同時承擔入口和維運兩種角色，不選。直接用 NodePort — 節點 IP 要暴露，且沒有統一的身份檢查，不選。

代價：對外可用性依賴 Cloudflare 服務，Tunnel token 洩漏時別人可以冒充 connector。

撤掉方案時，三個地方都完整清除，沒有保留為備用。Terraform 新增的 allow_http rule 用 terraform apply 撤銷。roles/ingress_proxy 整個目錄刪除。Istio gateway 的 Service 改回 ClusterIP，見 Role: istio。Floating IP 現在只用於 bastion 的 SSH 與維運。

網域的演進

入口最初規劃使用 kunchiee.com，命名想法是 *.k8s.kunchiee.com。實測 Cloudflare 免費方案的 Universal SSL 只涵蓋 kunchiee.com 與 *.kunchiee.com，不含子網域上的萬用字元，TLS handshake 在到達 Tunnel 之前失敗。這是用 /zones/{id}/ssl/certificate_packs API 查證的。

當時的權宜解法是每個服務一筆獨立的 xxx-k8s.kunchiee.com exact-match DNS 紀錄，吃既有 *.kunchiee.com 憑證的涵蓋範圍。之後改用新網域 dough-ops.com，同一條 Tunnel 繼續使用，不再需要 exact-match 的 workaround。

改由 Terraform 管理

Cloudflare 設定原本是手動用 API 逐項建立。改成獨立目錄、獨立 state 的 cloudflare/，用官方 cloudflare/cloudflare provider v5.22.0 管理。

管理的內容是 2 條 Tunnel、3 個 Access Application 與 Policy、2 筆 DNS CNAME 和 Zero Trust org 設定，共 7 種資源、15 個物件。

Tunnel token 不是 Terraform 資源的可查詢屬性。做法是用 random_id 產生 tunnel secret，在本地算出 base64encode(jsonencode({a,t,s}))。三個欄位依序是 account tag、tunnel id、secret。

Terraform 因此不依賴 cloudflared 或叢集存在，就能建出可用的 token。

既有的 7 個活資源是刪除後重建，沒有用 import。連鎖影響如下，細節見 Cloudflare 設定清單 § 已知限制：

  • 萬用字元 Application 的 AUD 換新，kube-apiserver 的 OIDC 失效。
  • Grafana 的 SaaS client ID 與 secret 換新，Grafana SSO 失效。
  • DNS 與 Tunnel 短暫中斷。

重建後依序重跑 cloudflare-tunnel.yml、bastion-ssh-tunnel.yml、oidc-auth.yml 與 kube-prometheus-stack.yml。驗證結果：5 個受保護 hostname 都回 302，JWT 的 kid 對得到新的 AUD，Grafana pod 內確認新的 client ID，smoke-test.yml 全綠。
