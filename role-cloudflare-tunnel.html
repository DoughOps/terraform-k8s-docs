Ansible 自動化Role: cloudflare_tunnel

在 cluster 內的 cloudflare namespace 裝 cloudflared,對 Cloudflare 邊緣建立一條 outbound-only 的連線——不開任何 inbound port、 不用 floating ip、不用 NodePort。這是目前整個 lab 唯一的對外入口, 也是這個專案在對外流量這件事上,走過一次錯誤方向又被使用者明確 拉回來的地方,值得記錄完整的決策轉折。

被否決的第一版方案:bastion floating ip + NodePort + nginx

裝 Istio 之初,第一個直覺方案是延續這個專案一貫「用既有機器 解決問題,不多開資源」的風格:在 bastion 的 floating ip 上開一個 allow_http 的 security group rule,Istio ingress gateway 改成 NodePort(固定 30080/30443),再裝一個 roles/ingress_proxy 在 bastion 上跑 nginx 反向代理,把 floating ip 的 80 port 轉給某個 k8s 節點的 NodePort。

這整個方案被使用者明確否決,原文:「我跟你說了 不要管dns 我沒有要透過這個floating ip expose出去 我已經設定好 cloudflare tunnel了」——使用者已經獨立設定好一條 Cloudflare Tunnel,根本不需要透過 floating ip 對外開放 任何東西。收到這個指正後,三個地方被完整清除,不是留著當「備用 方案」:Terraform 裡新增的 allow_http security group rule 用 terraform apply 撤銷、roles/ingress_proxy 整個 role 目錄刪除、Istio gateway 的 Service 改回 ClusterIP(見 Role: istio)。

現在的路徑:cloudflared 從 cluster 內部直連 Istio

整條路徑沒有任何一段需要對外開放 port—— cloudflared 是主動對 Cloudflare 邊緣發起的 outbound 連線(跟一般的「打洞」/reverse tunnel 同類技術),TLS 在 Cloudflare 邊緣就終止了,cluster 內部只需要處理 plain HTTP,這也是 Role: istio 的 Gateway 只監聽 port 80、不處理任何憑證的原因。

Deployment manifest

roles/cloudflare_tunnel/templates/cloudflare-tunnel.yaml.j2(精簡)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cloudflared-deployment
  namespace: cloudflare
spec:
  replicas: 2
  template:
    spec:
      containers:
        - name: cloudflared
          image: cloudflare/cloudflared:latest
          args:
            - tunnel
            - --no-autoupdate
            - --loglevel
            - info
            - --metrics
            - 0.0.0.0:2000
            - run
          env:
            - name: TUNNEL_TOKEN
              valueFrom:
                secretKeyRef:
                  name: cloudflare-tunnel-token
                  key: token
          livenessProbe:
            httpGet:
              path: /ready
              port: 2000

2 個 replica 是 Cloudflare 官方建議的最低高可用設定——同一條 tunnel 可以有多個 cloudflared instance 同時對邊緣建立 連線,邊緣自己做負載平衡/failover,不需要 cluster 內部另外處理 cloudflared 本身的高可用。

這是「remotely-managed」模式的 tunnel—— cloudflared 啟動時只帶一個 TUNNEL_TOKEN, routing/ingress 規則(「*.dough-ops.com 要轉給哪個 cluster 內部服務」)完全在 Cloudflare 那邊的 Tunnel 設定/API 裡 管理,不是本地 config.yaml ConfigMap 的舊模式。這代表這個 ansible role 的責任範圍只到「把 cloudflared 跑起來、連上正確的 tunnel」,ingress 規則、 DNS CNAME 這兩件事都在 Cloudflare 側,不是 ansible 管的,見下方。

Cloudflare 側設定(不是 ansible 管的,列出來只是為了完整)

項目目前設定
Tunnelopenstack-k8s
DNS*.dough-ops.com CNAME → <tunnel-id>.cfargotunnel.com(proxied)
Tunnel ingress 規則*.dough-ops.com → http://istio-ingressgateway.istio.svc.cluster.local:80

重建叢集不會動到這三項——同一條既有的 tunnel、同一個 token, cloudflared 重新啟動後會自動用同一個 tunnel identity 重新連上邊緣,DNS/ingress 規則完全不用重設。

網域選擇:為什麼是 *.dough-ops.com 這種「第一層」萬用字元

這個入口一開始規劃用使用者既有的 kunchiee.com,命名 想法是 *.k8s.kunchiee.com——但實測 Cloudflare 免費方案 的 Universal SSL 只涵蓋 kunchiee.com 跟 *.kunchiee.com(單層萬用字元),不含 *.k8s.kunchiee.com 這種「子網域上的萬用字元」,TLS handshake 在請求到得了 tunnel 之前就先失敗(用 /zones/{id}/ssl/certificate_packs API 查證實的,不是 猜的)。當時的權宜解法是改用「每個服務各自一個 xxx-k8s.kunchiee.com 獨立 exact-match DNS 紀錄」的 命名慣例,吃得到既有 *.kunchiee.com 憑證的涵蓋範圍。

後來使用者買了全新的 dough-ops.com,同一條既有 tunnel 繼續用,不用另外建。*.dough-ops.com 本身就是 apex 底下的第一層萬用字元,免費方案的 Universal SSL 直接涵蓋(同樣用 API 查證實,狀態是 active),不 再需要 exact-match workaround——單一一筆 *.dough-ops.com DNS 紀錄跟一條 tunnel ingress 規則,就能涵蓋任何子網域,新增服務 只要在 Istio 那層加 VirtualService 就好,不用每次都回來改 Cloudflare 設定。

Secret 處理:token 絕對不能進 git

使用者的明確要求。真正的 token 值放在 ansible/inventory/group_vars/all/secrets.yml(已被 .gitignore 排除),git 裡只留一份範本 secrets.yml.example,只寫變數名稱跟一個明顯的佔位值 REPLACE_ME,不含真正的 token。跟這個專案處理 SSH 私鑰的做法不完全一樣(SSH 私鑰是 ansible-vault 加密後直接進版控, 見 Ansible 框架設計的 「私鑰處理」一節)——這裡的 token 沒有走同一套加密機制,單純是 「不進版控 + 範本檔案」這個更基本的模式。

roles/cloudflare_tunnel/tasks/main.yml(assert 部分)
- assert:
    that:
      - cloudflare_tunnel_token is defined
      - cloudflare_tunnel_token | length > 0
      - cloudflare_tunnel_token != "REPLACE_ME"
    fail_msg: "cloudflare_tunnel_token 沒設好,見
      group_vars/all/secrets.yml.example 的說明"

先 assert 再 template/apply——如果有人 clone 這個 repo、忘記照 secrets.yml.example 建一份真正的 secrets.yml, 這裡會用清楚的錯誤訊息直接中止,不會讓一個帶著 REPLACE_ME 字面值的 token 被部署出去、產生一個看起來 正常但實際連不上任何 tunnel 的 cloudflared pod。

Bug:group_vars/secrets.yml 這種扁平檔案 永遠不會被自動載入——第一版直接把 secrets 檔案放在 group_vars/secrets.yml(跟 all.yml 同一層),結果實測 cloudflare_tunnel_token is undefined ——因為這個檔名不對應任何一個實際存在的 inventory group(沒有 叫做「secrets」的 group),ansible 的 group_vars/ 自動載入機制完全不會理它。

修法是改用 「每個 group 一個目錄」的寫法:把 group_vars/all.yml 整份改名搬進 group_vars/all/main.yml,secrets 另外放 group_vars/all/secrets.yml——兩個檔案都在 all/ 這個目錄底下,對應到真正存在的 all group,ansible 會自動合併載入目錄底下的所有 .yml 檔案。這樣既能把公開變數跟機密變數的檔案分開 (機密檔案單獨 gitignore),又能讓兩者同時生效,不用額外的 vars_files include。

bastion 的角色:唯一有 kubectl/kubeconfig 的地方

這個 role 只在 bastion 上跑(跟 Role: istio 一樣)——manifest 用 kubectl apply -f 直接套用,不透過 helm,因為這只是 一個固定的 Deployment + Secret + Namespace,沒有 chart 化的必要。 套用完之後用 kubectl -n cloudflare rollout status deployment/cloudflared-deployment 確認兩個 replica 真的 Ready,不是只看 kubectl apply 沒噴錯就假設成功。

第二條獨立的 Tunnel:roles/bastion_ssh_tunnel,給瀏覽器 SSH 用

使用者明確要求:要透過 Cloudflare Access 用瀏覽器內建終端機 SSH 進 bastion,但不能用上面這條給 cluster 對外服務用 的 openstack-k8s tunnel——兩者刻意完全獨立,不共用 tunnel、不共用 token。這裡另外建了一條叫 bastion-ssh 的 tunnel,而且 cloudflared 這次不是 裝在 k8s pod 裡,是直接裝在 bastion 主機本身(systemd service)——道理很簡單:SSH 的目標是 bastion 這台機器,cloudflared 要能連到 localhost:22,裝在 cluster 裡反而要多繞一手 network namespace。

roles/bastion_ssh_tunnel/tasks/main.yml(順序)
1. 加 cloudflared 的官方 apt repo(2026 年輪替後目前有效的簽章金鑰)
2. apt 裝 cloudflared
3. 用 stat 檢查 systemd unit 存不存在(見下方冪等性說明)
4. cloudflared service install <token>(只在第一次跑)
5. 確保 systemd service started + enabled

cloudflared service install 不是冪等指令 ——如果 systemd unit 已經存在,直接報錯拒絕重跑 (cloudflared service is already installed at ...), 不像這個專案其他 kubectl apply/helm 操作可以無腦重跑。 這裡用 ansible.builtin.stat 先檢查 /etc/systemd/system/cloudflared.service 存不存在, 整個安裝 task 包在 when: not cloudflared_service_file.stat.exists 底下,只在真正第一次 跑。token 會出現在指令列引數裡,task 額外加了 no_log: true,避免它被印進 ansible 的執行紀錄。

Cloudflare 那一側對應的手動設定(建 tunnel、設 ingress 規則、 DNS、Access Application)完整記錄在 Cloudflare 手動設定 清單,包含一個真的撞到的 bug:一般的 self_hosted Access Application 沒辦法讓瀏覽器渲染出 SSH 終端機,要用專門的 type: "ssh" Application 才行。
