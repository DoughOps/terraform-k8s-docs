叢集元件 Role: kubelet

這個 role 在所有 k8s_nodes 上安裝 kubeadm、kubelet、kubectl 和 crictl，並備齊 kubeadm 的前提條件。前提包含 cgroup v2、無 swap、正確的 node-ip，以及一條 service CIDR 的靜態路由。它在 playbooks/k8s/kubeadm.yml 的第一個 play 執行，排在 Role: crio 之後、Role: kubeadm 之前。

role 在 ansible/roles/kubelet/，只負責「裝好套件、備好前提」。kubeadm init 和 join 的邏輯在 kubeadm role。

現在的設定

項目值為什麼
cgroup v2 檢查stat -fc %T /sys/fs/cgroup 必須回 cgroup2fs，否則 assert 中止實際查檔案系統型別，不假設 Ubuntu 24.04 一定是 cgroup v2。image 被改過時，在這裡就明確報錯，不會讓後面的 cgroup driver 設定在錯誤前提下跑出難追的間接錯誤
swapswapoff -a，並在 /etc/fstab 用 regex 註解掉 swap 那一行kubeadm 預設要求無 swap。swapoff 只管當下，fstab 避免重開機後又掛回來。目前這批 VM 沒有 swap 分割區（ansible_swaptotal_mb 為 0），兩步都是 no-op，保留是為了換 image 後仍然正確且冪等
網路工具conntrack、socat、ebtables、ethtoolconntrack 是 kubeadm preflight 的硬性要求。其餘三個是官方列出的 kubelet 依賴，一次裝齊，避免每個 preflight 錯誤各修一次，見 Bug #15
apt repohttps://pkgs.k8s.io/core:/stable:/{{ kubernetes_minor_version }}/deb/URL 綁定 minor 版本，目前是 v1.34
套件kubelet、kubeadm、kubectl、cri-tools，state: latest，裝完 dpkg_selections: holdhold 防止 apt upgrade 把它們升到別的 minor，和 CRI-O 錯開。cri-tools 提供 crictl，oidc_auth role 要用它確認 kube-apiserver container 是否重建
node-ip/etc/default/kubelet 寫 KUBELET_EXTRA_ARGS=--node-ip=<fabric_ip>，例如 10.10.0.20見下一節
service CIDR 路由netplan 90-service-cidr-route.yaml，to: 172.18.0.0/16、scope: link讓 kernel 為 ClusterIP 選對來源位址，見 service-cidr 的靜態路由
服務狀態systemctl enable --now kubelet此時 kubelet 會 crashloop，屬於預期，見最後一節

node-ip 明確指定

kubelet 沒指定 --node-ip 時，會選預設路由所在介面的位址。這些節點有兩張網卡：k8s-net 沒有預設路由，mgmt-net 有。kubelet 自己猜的話，一定會選到 mgmt-net。

架構的前提是節點之間的流量走 k8s-net，mgmt-net 只供維運和對外使用（見雙網卡模型）。所以 role 透過 /etc/default/kubelet 指定 --node-ip，kubelet 的 systemd unit 會讀取這個檔案的 KUBELET_EXTRA_ARGS。值取自每個節點在 inventory 裡的 fabric_ip。

節點上的 /etc/default/kubelet
KUBELET_EXTRA_ARGS=--node-ip=10.10.0.20

版本鎖定與升級

每次執行都先對已安裝的套件做 selection: install 解除鎖定，再用 state: latest 安裝，最後重新 hold。latest 在這裡是安全的，因為 repo URL 已經綁定 minor 版本，只會抓同一個 minor 的最新 patch。

解除鎖定只對 ansible_facts.packages 裡已有的套件執行。全新節點的 dpkg 選擇資料庫沒有這些套件，對不存在的套件設定 selection 會報 Failed to find package 'X' to perform selection。所以 role 先用 package_facts 判斷節點是否安裝過，見 Bug #61。

service-cidr 的靜態路由

這個 role 在每個節點的 fabric_iface 上加一條 service CIDR 的 scope link 路由，唯一目的是讓 kernel 對 ClusterIP 選出 k8s-net 的來源位址。路由本身不轉送任何封包。為什麼 ClusterIP 會選錯來源位址，概念與完整解釋見網路架構總覽 § service-cidr。這裡記錄 kubelet role 的實作和當初的除錯證據。

實作

節點上的 /etc/netplan/90-service-cidr-route.yaml（範本渲染後）
network:
  version: 2
  ethernets:
    ens3:
      routes:
        - to: 172.18.0.0/16
          scope: link

用 scope: link 且不指定 gateway，因為這個網段本來就不會路由到任何地方，只需要佔住路由表項目。封包一定先被 DNAT 成真實 backend，不會照這條路由的字面意思去送。

介面名稱不寫死。實測每台的 fabric NIC 都是 ens3，由 Terraform 的 network {} block 順序決定。role 仍用 ip -4 -o addr show | grep -F '<fabric_ip>/' 查出對應的介面，再代入 netplan 範本。OpenStack 的 NIC 枚舉順序在某台機器不同時，也不會壞。

修法放在 kubelet 這個通用 role，不放進 Role: cilium。受影響的不只 Cilium，任何 hostNetwork 模式、需要連 ClusterIP 的元件都會撞到。

已知限制

  • role 只支援 apt 系的節點，並要求 cgroup v2。不符合時，cgroup 檢查會中止，不會自動修改 kernel 參數或重開機。
  • kubelet 的 apt repo 使用已標示 deprecated 的 apt_repository，原因與 Role: crio 相同。

實測踩到的 bug

#15 · kubeadm init preflight 因缺少 conntrack 失敗

  • 症狀：第一次執行 kubeadm init，preflight 直接 fatal：[ERROR FileExisting-conntrack]: conntrack not found in system path。
  • 根因：節點 image 沒有 conntrack，而它是 kubeadm preflight 的硬性要求。
  • 修法：role 一次安裝 conntrack、socat、ebtables、ethtool。後三者是官方文件列出的 kubelet 依賴，一起裝可避免逐個 preflight 錯誤修了再重跑。
  • 怎麼確認修好：kubeadm init 的 preflight 階段通過。
  • 相關：Bug 事後檢討 #15。

#18 · Cilium init container 連 ClusterIP 逾時

  • 症狀：安裝 Cilium 時，init container 卡在連 10.96.0.1:443 並逾時。當時還是預設 service CIDR，後來改成 172.18.0.0/16。這是 native routing 落地過程中，唯一純屬網路層的 bug，和 Kubernetes、Cilium 本身無關。
  • 根因：Linux 對本機發起的連線，先用改寫前的原始目的地（ClusterIP）做路由查詢決定來源位址，這發生在 kube-proxy 的 DNAT 之前。ClusterIP 網段在 k8s-net 上沒有路由，查詢 fallback 到 mgmt-net 的預設路由，選到 mgmt-net 的位址當來源。封包的目的地雖然已被 DNAT 成真實 master 的 fabric_ip，來源位址卻是 192.168.200.x，對方從 mgmt-net 回覆而連線逾時。
  • 修法：netplan 加一條 service CIDR 的 scope: link 路由，見上方實作。
  • 怎麼確認修好：ip route get 對 service CIDR 內的位址，回報走 k8s-net 的介面，來源位址是 10.10.0.x。
  • 相關：Bug 事後檢討 #18、service-cidr 概念。

#18 的除錯證據

  1. 在受影響節點的 ens3 上用 tcpdump 抓包，SYN 封包的來源位址是 192.168.200.x（mgmt_ip），不是預期的 10.10.0.x（fabric_ip）。此時目的地已被 kube-proxy 正確 DNAT 成某台 master 的 fabric_ip。
  2. 用 ip route get 10.96.0.1 驗證，kernel 回報走 mgmt-net、來源選 192.168.200.x。原因是 ClusterIP 網段 10.96.0.0/12 在 k8s-net 上沒有對應路由，所以 fallback 到 mgmt-net 的預設路由。

#26 · 升級 kubernetes_minor_version 後套件版本沒變

  • 症狀：把 kubernetes_minor_version 從 v1.31 改成 v1.34，repo URL 也指向新版本，但 kubeadm、kubelet、kubectl 實測仍停在 v1.31。
  • 根因：state: present 的語意是「有裝就好」，加上 dpkg_selections: hold 讓 apt 拒絕任何版本變動。兩者疊加後，已安裝的套件永遠不會被這個 task 動到，即使 repo index 已經指向 v1.34。
  • 修法：安裝前先解除鎖定（selection: install），安裝 task 改為 state: latest，裝完再重新 hold。
  • 怎麼確認修好：升級 kubernetes_minor_version 後重跑 playbook，kubelet --version 顯示新的 minor。
  • 相關：Bug #27 是 CRI-O 同樣在升級 minor 時暴露的問題，見 Role: crio。

kubelet 啟動後 crashloop 是預期行為

role 最後一步等同 systemctl enable --now kubelet。這時還沒有 kubeadm init 或 join 產生的 /var/lib/kubelet/config.yaml，kubelet 會持續 crashloop。這與官方 kubeadm 文件描述的流程一致，不需要處理。等 Role: kubeadm 的 init 和 join 完成後，kubelet 才會穩定運作。

驗證方式

在任一 k8s 節點上
$ stat -fc %T /sys/fs/cgroup
$ cat /etc/default/kubelet
$ ip route get 172.18.0.1
$ apt-mark showhold

預期結果：第一行輸出 cgroup2fs。第二行的 --node-ip 是該節點的 10.10.0.x。第三行走 k8s-net 的介面，來源位址是 10.10.0.x。第四行列出 kubelet、kubeadm、kubectl、cri-tools。
