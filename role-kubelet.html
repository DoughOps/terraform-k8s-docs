Ansible 自動化Role: kubelet

在所有 k8s_nodes 上裝 kubeadm/kubelet/kubectl, 並確保三個前提條件:cgroup v2、無 swap、kubelet 用正確的網段當 node-ip。kubeadm init/join 的邏輯不在這裡,見 Role: kubeadm——這個 role 只管 「裝好套件、裝好前提條件」。

前提條件一:cgroup v2,用 assert 直接驗證,不是假設

roles/kubelet/tasks/main.yml
- command: stat -fc %T /sys/fs/cgroup
  register: cgroup_fs_type

- assert:
    that: cgroup_fs_type.stdout == "cgroup2fs"
    fail_msg: "...不是 cgroup2fs,中止讓你確認..."

使用者的原始需求就是「用 cgroup v2」——這裡沒有選擇默默假設 Ubuntu 24.04 一定是 cgroup v2(雖然實務上它就是),而是實際 查一次 /sys/fs/cgroup 的檔案系統類型, cgroup2fs 才是真的 unified hierarchy。如果哪天 image 被客製化過導致不是 cgroup v2,這裡會直接中止並給出明確原因,不是讓 後面 kubelet/CRI-O 的 cgroup driver 設定在一個錯誤前提下繼續跑, 跑出更難追的間接錯誤。

前提條件二:無 swap

kubeadm 預設仍要求節點沒有 swap(kubelet 對 swap 的支援目前還是 alpha/beta 等級的 feature gate)。swapoff -a 只影響 當下的執行期,額外在 /etc/fstab 用 regex 註解掉 swap 掛載那一行,確保重開機後 swap 不會又被掛回來。實測這批 OpenStack VM 本身就沒有配置 swap 分割區(ansible_swaptotal_mb 是 0),這兩步在目前的環境下都是 no-op,但保留是為了讓這個 role 在任何(包含未來換了不同 image 的)環境下都是正確、冪等的。

前提條件三:kubeadm preflight 需要的網路工具

conntrack 是 kubeadm preflight 檢查的硬性要求 ——第一次跑 kubeadm init 時實測直接撞到 [ERROR FileExisting-conntrack]: conntrack not found in system path, preflight 檢查會直接 fatal error、拒絕繼續。socat/ ebtables/ethtool 是官方文件列出的 kubelet/kube-proxy 依賴,一次裝好,不要每個 preflight 錯誤各修一次 再重跑。

kubeadm/kubelet/kubectl 安裝 + 版本鎖定

跟 Role: crio 一樣的 apt repo 模式 (pkgs.k8s.io,GPG key + keyring + apt source), 裝完之後對三個套件都下 dpkg_selections: selection: hold——避免任何一次 apt upgrade 意外把它們升級到不同的 minor version, 跟 CRI-O 版本錯開造成不相容。

Bug:被 hold 鎖住的套件,即使改了 kubernetes_minor_version、repo URL 也指向新版本, state: present 還是不會升級——第一次把 kubernetes_minor_version 從 v1.31 改成 v1.34 時,role 沒有跟著改,實測套件仍然停在 v1.31。根因是 state: present 的語意是 「有裝就好」,而 dpkg_selections: hold 讓 apt 更進一步 拒絕任何版本變動,兩個機制疊加的結果是「已經裝過的套件永遠不會被 這個 task 動到」,就算 repo URL 本身已經指向 v1.34 的 index 也一樣。 修法是在安裝前先解除鎖定(selection: install),再把 安裝 task 從 state: present 改成 state: latest——這裡用 state: latest 是安全的,因為 repo URL 本身已經是版本綁定的(.../v1.34/deb/), 「latest」只會在同一個 minor version 底下抓最新 patch,不會意外 跳到不同的 minor version。

node-ip:kubelet 要明確指定,不能讓它自己猜

/etc/default/kubelet
KUBELET_EXTRA_ARGS=--node-ip=10.10.0.20

不設的話,kubelet 會自動選「預設路由所在的介面」的位址當自己的 node-ip。這台機器有兩張網卡:k8s-net(no_gateway=true, 沒有預設路由)跟 mgmt-net(有預設路由)——kubelet 如果自己猜,一定會選到 mgmt-net 的位址,而這整個架構的設計前提是 「k8s 節點之間的流量走 k8s-net(資料平面),mgmt-net 只給操作/對外用」 (見 網路架構總覽)。這裡 透過 /etc/default/kubelet(kubelet 的 systemd unit 會 source 這個檔案的 KUBELET_EXTRA_ARGS)明確指定 --node-ip,用每個節點各自的 fabric_ip (從 ansible inventory 讀,見 框架 設計)。

最大的一個 bug:service-cidr 需要一條靜態路由

這是整個 native routing 落地過程中唯一一個純網路層級(不是 k8s 也不是 Cilium)的 bug,完整除錯過程值得記錄——裝 Cilium 時, init container 卡在連 10.96.0.1:443(那時候還是預設 service-cidr,後來改成 172.18.0.0/16)逾時。

  1. tcpdump 在受影響節點的 ens3 上抓包, 發現 SYN 封包的來源位址是 192.168.200.x (mgmt_ip),不是預期的 10.10.0.x(fabric_ip) ——即使目的地已經被 kube-proxy 正確 DNAT 成某個真實 master 的 fabric_ip。
  2. 用 ip route get 10.96.0.1 直接驗證: kernel 回報會走 mgmt-net、來源選 192.168.200.x ——因為 10.96.0.0/12(ClusterIP 網段)在 k8s-net 上完全沒有對應路由,查詢 fallback 到 mgmt-net 的預設路由。
  3. 根因是 kernel 決定「來源位址」的時機: Linux 對本機發起的連線,是先用原始目的地(改寫前的 ClusterIP)做一次路由查詢來決定來源位址,這個時機在 kube-proxy 的 DNAT 規則生效之前。ClusterIP 從來不是一個 「路由得到」的位址,DNAT 一定會先把它改寫成真實 backend——但 「決定來源位址」這件事發生得比 DNAT 早,如果 ClusterIP 網段 在本機路由表裡沒有任何專屬條目,就會被一般的 fallback 邏輯 (走預設路由)決定,選到錯的網段。

修法:netplan 加一條 scope link 的「假」路由

/etc/netplan/90-service-cidr-route.yaml(範本渲染後)
network:
  version: 2
  ethernets:
    ens3:
      routes:
        - to: 172.18.0.0/16
          scope: link

這條路由不會真的被拿去轉送任何封包(封包一定會先被 DNAT 成真實 backend,不會照著這條路由的字面意思去送)——它唯一的 作用是讓「決定來源位址」那次路由查詢,對 172.18.0.0/16 這個目的地能查到一個落在 k8s-net 上的 結果,連帶讓 kernel 選中 10.10.0.x 當來源位址。用 scope: link(不指定 gateway)是因為這個網段本來就不是 真的路由到哪裡去,只是要「佔住」這個路由表項目。

介面名稱不是寫死的 ens3——雖然目前 每台機器實測下來 fabric NIC 確實都是 ens3 (Terraform 的 network {} block 順序決定),但 role 裡先用 ip -4 -o addr show | grep -F '{{ fabric_ip }}/' 實際查一次對應到哪個介面名稱,再把結果代入 netplan 範本——不假設 介面命名規則,萬一 OpenStack NIC 枚舉順序在某台機器上不一樣, 這裡不會壞。

這個 bug 影響的不只是 Cilium——任何跑在 hostNetwork 模式、需要連 ClusterIP 的元件都會撞到同樣的問題,所以修法放在 kubelet 這個通用 role 裡,不是塞進 Role: cilium,即使它是在裝 Cilium 時才被實際發現的。

啟用 kubelet:此時預期會 crashloop

role 的最後一步是 systemctl enable --now kubelet 的等價操作。這個階段還沒有 kubeadm init/join 產生的 /var/lib/kubelet/config.yaml,kubelet 會一直 crashloop,這是預期行為,跟官方 kubeadm 文件描述的 流程完全一致——真正讓 kubelet 穩定跑起來,要等 Role: kubeadm 的 init/join 跑完。
