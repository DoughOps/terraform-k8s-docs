專案紀錄 DSR / L4LB 歷史

這頁記錄的 iBGP 加 DSR（Direct Server Return）L4 負載平衡設計目前處於休眠狀態：沒有任何 VM 使用它，外部流量也不走這條路。保留這頁，是因為它驗證出的兩個結論至今仍然決定了架構：fabric port 必須關閉 port security，以及 iBGP fabric 真的做得出 ECMP。

目前的狀態

  • 拓樸已被取代：本頁記錄的 5 台 VM 早已不存在，它們是 tor、node-a、node-b、l4lb-0001、l4lb-0002。現在的拓樸見總覽。
  • 程式碼仍在：frr-init.sh.tftpl 的 node 與 l4lb 角色、Terraform 的 service_vip（172.31.255.1）與 service_port（8080）。terraform.tfvars 裡的 l4-0001、l4-0002 實際是 peer 角色，是一般 worker，只多了 l4lb 節點標籤。見 Terraform / OpenStack。
  • 外部流量改走 Cloudflare Tunnel：路徑是 cloudflared、istio-ingressgateway（ClusterIP）、後端 Pod，見網路架構總覽。原設計的 Floating IP 綁在 tor、tor 上本機 DNAT 到 Service VIP 這兩段，從未實作成 Ansible role。Floating IP 現在綁在 bastion，只供 SSH。

問題意識與驗證拓樸

cloudnative.tw 是一般權限的 OpenStack tenant，沒有 LBaaS，沒有 routed public prefix，也沒有雲廠商替你做好的網路進階功能。這種環境下，「BGP-based L4LB」這類通常需要實體機房 BGP 路由器的架構，到底做不做得出來？

Phase 1 用最少的機器回答這個問題：tor、兩台 node、l4lb-0001 與 l4lb-0002。node 用 Python http.server 模擬「假 Pod」。第二台 l4lb 後來才加入，目的是驗證 ECMP。

DSR 的證明：IPVS Direct Routing

l4lb 節點用 ipvsadm -g 的 gatewaying 模式，也就是 Direct Routing，把 Service VIP（172.31.255.1:8080）的流量分派給 node-a 與 node-b。VIP 直接綁在 realserver 的 lo 上。DR 模式的特性是：去程經過 l4lb，只改目的 MAC，不做 NAT、不改 IP；回程完全不經過 l4lb，realserver 直接用 VIP 當來源位址送回 client。

l4lb-0001:~$ sudo ipvsadm -Ln --stats
Prot LocalAddress:Port               Conns   InPkts  OutPkts  InBytes OutBytes
TCP  172.31.255.1:8080                   4       20        0     1392        0
  -> 10.10.0.20:8080                     2       10        0      696        0
  -> 10.10.0.21:8080                     2       10        0      696        0

OutPkts = 0 是最直接的證據：l4lb-0001 只看到 20 個進來的封包（4 個連線的三向交握加 HTTP 請求），沒有任何回應封包經過它。所有回應都是 realserver 直接用 VIP 當來源位址送回 client。這是在真實 OpenStack 環境上量到的數字。

ECMP 的證明：tor 上的多路徑

兩台 l4lb 都用 network 陳述式宣告同一個 VIP。tor 靠 maximum-paths ibgp 8（見 FRR / iBGP Fabric）把流量用 ECMP 分散到兩台 l4lb。20 個新請求之後，兩台各自的 --stats 都有非零的 Conns，各自的 OutPkts 仍是 0。ECMP 分流與 DSR 回程繞過同時成立，互不干擾。

Conns（累計）2139
OutPkts00

分配不是精準的 50/50，這符合預期。kernel 的雜湊分流不是輪詢，而是「同一個連線固定走同一條路，不同連線可能走不同路」。要驗證的是兩條路都有被用到，不是均勻度。

DSR 與 Neutron conntrack 的衝突

mgmt-net 分離之後，曾嘗試把 fabric port 的 port_security_enabled 從整段關閉改成開啟，並用 allowed_address_pairs 精準放行。部署後 Pod 之間的 ping 正常，但對 VIP 的 curl 全部逾時。在 tor、l4lb、realserver 三個點同時用 tcpdump -e 抓包，才拆出完整真相：

  1. l4lb 正確轉發：SYN 從 tor 進來，l4lb 只改目的 MAC（DR 模式該有的行為），IP layer 完全不動，送到 node-a。
  2. node-a 收到 SYN 並送出 SYN-ACK：直接送給 tor，完全繞過 l4lb，這正是 DSR 該有的樣子。
  3. tor 送出的後續封包全部消失：ACK 與 GET 請求的路徑必須經過 l4lb（那是 tor 到 VIP 的唯一路由），但 node-a 完全沒收到。

根因：Neutron 的 OVS security group 是基於 conntrack 的狀態防火牆。l4lb 這個 port 上，conntrack 只看得到這條連線的去程（SYN），因為 DSR 設計讓回程直接從 realserver 送回 client，不經過 l4lb。l4lb 的 conntrack 永遠等不到 SYN-ACK 通過自己，連線狀態卡在「未完成握手」。tor 後續送來的 ACK 與 GET 被判定為屬於未完成連線的封包，當成 invalid state 丟棄。

這是 DSR（非對稱路由）與 conntrack-based 狀態防火牆的結構性衝突，不是規則寫錯。allowed_address_pairs 處理的是 anti-spoofing（來源位址檢查），對 conntrack 狀態機沒有影響，這條路從一開始就不可能成功。

這個結論決定了 fabric port 至今維持 port_security_enabled = false，決策記錄見 Terraform / OpenStack，登錄為 Bug #6。

ECMP 的隱藏前提：雜湊要包含 L4 資訊

加了第二台 l4lb 之後，第一次分流測試，20 個請求 100% 落在 l4lb-0002，l4lb-0001 完全是零，即使路由表明明有兩個 next-hop。

根因是 net.ipv4.fib_multipath_hash_policy 預設為 0，ECMP 雜湊只取來源 IP 與目的 IP。測試時 client 永遠是 tor（單一來源 IP），目的永遠是同一個 VIP，雜湊輸入從頭到尾沒變，結果自然也不變。這是雜湊函式在這個輸入下的必然結果。

改成 1（L3 加 L4，納入來源與目的埠）後，同一個 client 開的不同 TCP 連線因為來源埠不同，才會分散。這個設定只需要下在 tor 上，因為它是唯一做雜湊決策的節點，登錄為 Bug #7，設定位置見 FRR / iBGP Fabric。

這個發現的意義超出 L4LB 本身：「ECMP 有沒有生效」不能只用單一 client 測試。單一來源在 hash-policy=0 下永遠走同一條固定路徑，會得到假陰性的結果。

這個階段留下的資產

🔒

port_security_enabled = false

三點 tcpdump 實測出 conntrack 與 DSR 衝突後的結論，沿用至今，見 Terraform / OpenStack。

🧭

next-hop-self all 加 route-reflector-client

iBGP route reflector 正確反射路由的兩個必要條件，tor 現在對所有 client 都這樣設定，見 FRR / iBGP Fabric。

📌

network 陳述式需要 connected route

用 dummy0 驗證出的機制，後來在 Role: cilium 的 bgp_announce 重新使用，改讀 Cilium 建的 cilium_host 路由，見 PodCIDR 如何進入 BGP。

⚖️

fib_multipath_hash_policy = 1

tor 專屬設定。路由表有多個 next-hop 不代表流量會自動分散，雜湊必須納入 L4 資訊。
