Lab Docs / DSR / L4LB(歷史階段)
cloudnative.tw · AS 65000

這一頁記錄的拓樸已經被取代——node-a、 node-b、l4lb-0001、l4lb-0002 這幾台機器早就不存在了,現在的拓樸是 總覽頁面畫的 bastion + 3 master + 2 lb + 2 worker。保留這頁是因為這裡驗證出來的兩個結論,直接決定了現在整個 架構的樣子:port_security_enabled = false 的最終原因 (見下方 conntrack 衝突),以及「iBGP fabric 真的可以做出 ECMP」這個 Phase 3 native routing 完全依賴的前提。

歷史階段Phase 1:iBGP + DSR L4LB 驗證

最早的問題意識很單純:cloudnative.tw 是一個一般權限的 OpenStack tenant,沒有 LBaaS、沒有 routed public prefix、沒有任何「雲廠商幫你做好」 的網路進階功能。這種環境下,「BGP-based L4LB」這種通常需要實體機房 BGP 路由器才有的架構,到底做不做得出來?這一頁記錄的 5 台 VM 拓樸(tor + node-a/node-b「假 pod」+ l4lb-0001/0002)就是用最少的機器 回答這個問題。

用什麼證明:IPVS Direct Routing(DSR)

l4lb 節點用 ipvsadm -g(gatewaying/Direct Routing 模式) 把 Service VIP(172.31.255.1:8080)的流量分派給 node-a/node-b 這兩個「假 pod」(用 Python http.server 模擬,VIP 直接綁在 lo 上)。DR 模式的特性是:去程 經過 l4lb(只改目的 MAC,不做 NAT、不改 IP),回程完全 不經過 l4lb——realserver 直接用 VIP 當來源位址把回應送回 client。

l4lb-0001:~$ sudo ipvsadm -Ln --stats
Prot LocalAddress:Port               Conns   InPkts  OutPkts  InBytes OutBytes
TCP  172.31.255.1:8080                   4       20        0     1392        0
  -> 10.10.0.20:8080                     2       10        0      696        0
  -> 10.10.0.21:8080                     2       10        0      696        0

OutPkts = 0 是這個 lab 最直接的鐵證:l4lb-0001 只看到 20 個進來的封包(4 個連線的三向交握 + HTTP 請求),完全沒有 任何一個回應封包經過它。所有回應都是 realserver 直接用 VIP 當來源 位址送回 client——這不是憑空宣稱,是在真實 OpenStack 環境上量出來的 數字。

用什麼證明:tor 上的 ECMP

兩台 l4lb 節點都用 network 陳述式宣告同一個 VIP, 靠 tor 的 maximum-paths ibgp 8(見 FRR / iBGP Fabric)把流量用 ECMP 分散到兩台 l4lb。20 個新請求後,兩台各自的 --stats 都有非零的 Conns,而且各自的 OutPkts 依然是 0——ECMP 分流跟 DSR 回程繞過,兩件事同時成立,互不干擾。

分配不是精準的 50/50,這符合預期——kernel 的雜湊分流本來就不是輪詢, 是「同一個連線固定選同一條路,不同連線可能選不同路」, 「兩條路都真的有被用到」才是這裡要驗證的重點,不是均勻度。

最重要的發現:DSR 跟 Neutron conntrack 防火牆天生衝突

mgmt-net 分離之後,曾經嘗試把 fabric port 的 port_security_enabled 從整段關閉,改成恢復開啟 + 用 allowed_address_pairs 精準放行。部署後 pod-to-pod ping 正常,但 VIP 的 curl 全部逾時。 用 tcpdump -e 在 tor / l4lb / realserver 三個點同時抓包, 才拆解出完整真相:

  1. l4lb 正確轉發——SYN 從 tor 進來,l4lb 只改目的 MAC(DR 模式該有的行為),IP layer 完全不動,送到 node-a。
  2. node-a 收到 SYN、送出 SYN-ACK,直接送給 tor, 完全繞過 l4lb——這正是 DSR 該有的樣子。
  3. 但 tor 送出的後續封包(ACK、GET 請求)全部消失 ——這些封包的路徑必須經過 l4lb(那是 tor 到 VIP 的唯一路由路徑), 但 node-a 端完全沒收到任何一個。

根因:Neutron 的 OVS security group 是基於 conntrack 的狀態防火牆。l4lb 這個 port 上,conntrack 只看得到這條連線的「去程」(SYN)——因為 DSR 設計就是讓回程直接從 realserver 送回 client,完全繞過 l4lb。l4lb 的 conntrack 永遠等不到 它需要的 SYN-ACK 通過自己,連線狀態永遠卡在「未完成握手」。 當 tor 後續送 ACK、GET(這些封包必須經過 l4lb),conntrack 判斷這是屬於一個未完成連線的封包,當成 invalid state 直接丟棄。 這是 DSR(非對稱路由)跟 conntrack-based 狀態防火牆的結構性 衝突,不是規則寫錯——allowed_address_pairs 解決的是 anti-spoofing(來源位址檢查),對 conntrack 狀態機制完全 沒有影響,這條路從一開始就不可能成功。

這個結論直接決定了 Terraform / OpenStack 頁面裡 fabric port 永久維持 port_security_enabled = false 的最終原因——不是「先關著,之後再處理」的 TODO,是一個有明確反例 證明過「開啟會壞」的架構決定。

ECMP 的隱藏前提:雜湊策略要包含 L4 資訊

加了第二台 l4lb 之後,第一次做分流測試,20 個請求 100% 全部落在 l4lb-0002,l4lb-0001 完全零——即使路由表明明白白有兩個 next-hop。 根因是 net.ipv4.fib_multipath_hash_policy 預設是 0,ECMP 雜湊只取「來源 IP + 目的 IP」當輸入。測試時 client 永遠是 tor(單一來源 IP)、目的永遠是同一個 VIP,雜湊輸入 從頭到尾沒變過,結果自然也從頭到尾一樣——這不是運氣不好,是雜湊函式 在這個輸入下的必然結果。改成 1 (L3+L4,納入來源/目的埠)之後,同一個 client 開的不同 TCP 連線因為 來源埠不同,雜湊結果才會分散。這個設定只需要下在 tor 上(唯一做 雜湊決策的節點),完整細節見 FRR / iBGP Fabric。

這個發現的意義超出 L4LB 本身:它證明「ECMP 有沒有生效」不能只用 單一 client 測試,單一來源在 hash-policy=0 下永遠會是 100% 固定路徑的假陰性結果。

這個階段留下的資產

🔒

port_security_enabled = false

不是隨便關的,是三點 tcpdump 實測出 conntrack/DSR 衝突之後的結論, 沿用至今,見 Terraform / OpenStack。

next-hop-self all + route-reflector-client

iBGP RR 要能正確反射路由的兩個必要條件,現在 tor 對所有 k8s_nodes 都這樣設定,見 FRR / iBGP Fabric。

📌

network 陳述式需要一筆 connected route

用 dummy0 驗證出來的機制,後來在 Role: cilium 的 bgp_announce 裡被重新用(拿掉 dummy0,改讀 Cilium 建的 cilium_host route)。

⚖️

fib_multipath_hash_policy = 1

tor 專屬設定,ECMP 真正依連線分散流量的必要條件,不是路由表有多個 next-hop 就自動生效。
