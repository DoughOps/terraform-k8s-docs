cloudnative.tw · AS 65000

開始 總覽

這個 Lab 在 cloudnative.tw 的一般權限 OpenStack tenant 上建成，沒有 LBaaS，也沒有 routed public prefix。一般 tenant 只給你一張扁平網路加 Router NAT。在每台機器上跑 FRR 組成 iBGP fabric 之後，就能拿到接近實體機房才有的東西。這包括 ECMP、DSR 式 L4LB，以及這份文件的主角：不靠 VXLAN／Geneve overlay 的 native routing CNI。

8 個 k8s 節點 + 1 tor + 1 bastion 單一 ASN 65000，全節點 iBGP Cilium native routing，不用 Cilium 自己的 BGP Ansible 全自動化，跑在 bastion 的 Docker 裡 Cilium eBPF 取代 kube-proxy Cloudflare Tunnel 對外，不開任何 inbound port cert-manager + Origin CA，端對端 Full (strict) 加密 Cloudflare Access 擋整個 *.dough-ops.com

現在的拓樸

3 台 master 做 etcd 與 apiserver HA，2 台原本規劃當 L4LB 的節點（l4-）和 3 台 ap- 節點都是 worker。全部節點的資料平面都在同一個扁平網路 k8s-net 上跑 iBGP，管理流量走 mgmt-net。IP 規劃與雙網卡模型見網路架構總覽。

節點拓樸圖 mgmt-net（虛線，管理與對外）+ k8s-net iBGP fabric（實線，tor 扇出）

每個節點的 Pod CIDR（172.16.x.0/24）由 Cilium 分配，由本節點的 FRR 用 network 陳述式廣播出去，tor 反射給其他所有節點。

mgmt-net 192.168.200.0/24（管理與對外） k8s-net 10.10.0.0/24（iBGP fabric） tor 唯一 route reflector bastion 唯一操作入口，也是 iBGP peer

圖上沒畫出來的是對外流量的入口。叢集內 cloudflare namespace 跑著 cloudflared，向 Cloudflare 邊緣建立 outbound-only 連線，所以不佔用拓樸裡的 Floating IP 或任何 inbound port。完整路徑見網路架構總覽 § 對外入口，部署細節見 Role: cloudflare_tunnel。

為什麼要讀這份文件，而不只是 kubectl get all？這個 Lab 的價值不在於有一個能動的 k8s 叢集，minikube 五分鐘就有一個。每個看起來普通的設定背後，都對應一個實測踩到的坑或一個取捨。文件的目標是讓你不用重踩這些坑，就能看懂為什麼這樣設。

八個階段

這個 Lab 分階段疊上去，每一階段先驗證上一階段的假設，再往下走。看過這個順序，就能理解某些設計為什麼「看起來繞了一下」：做那個決定時，後面的階段還沒發生。全站的 Phase 編號與名稱都以這裡為準。

  1. Phase 1 · 驗證 iBGP、ECMP 與 DSR L4LB 用最少的機器證明一般 tenant 做得出 BGP-based L4LB。next-hop-self force 讓 route reflector 正確反射路由，maximum-paths ibgp 做出真正的 ECMP。IPVS DR 模式讓回程流量不經過 L4LB，證據是 ipvsadm --stats 的 OutPkts=0。機器只有 1 台 tor、2 台假 pod 節點和 2 台 L4LB。這個階段也得出 Neutron port security 與 DSR 不相容，之後的 fabric port 全部關閉 port security。DSR／L4LB 設計已被取代，見 DSR / L4LB 歷史，fabric 設計見 FRR / iBGP Fabric。
  2. Phase 2 · 真實拓樸與雙網路 把測試機器換成 bastion、3 台 master、2 台 L4LB（同時也是 worker）和 2 台 worker。網路正式拆成 k8s-net（資料平面，無預設路由）與 mgmt-net（操作與對外，有 SNAT）。細節見 Terraform / OpenStack 與網路架構總覽。
  3. Phase 3 · Ansible、kubeadm 與 Cilium native routing 先建立「本機下指令、在 bastion 的 Docker 裡執行 ansible」的框架，見 Ansible 框架設計。接著依序裝 CRI-O、kubeadm 3-master HA 控制平面和 tor 上的 apiserver haproxy（Role: apiserver-lb），最後裝 Cilium。Cilium 用 native routing，刻意不用自己的 BGP Control Plane。每個節點的 Pod CIDR 由 FRR 宣告進既有的 iBGP fabric，見 Role: cilium。
  4. Phase 4 · 取代 kube-proxy、Istio 與 Cloudflare Tunnel 打開 kubeProxyReplacement，由 Cilium eBPF 完全取代 kube-proxy。接著裝 Istio 當叢集內的 L7 路由層，見 Role: istio。再裝 cloudflared，用 outbound-only 的 Cloudflare Tunnel 當唯一的對外入口，見 Role: cloudflare_tunnel。同一批工作把叢集升到 Kubernetes 1.34。
  5. Phase 5 · 加密、身份驗證、內部工具與 bastion 持久化 cert-manager 加 Cloudflare Origin CA 簽出 wildcard 憑證，整條路徑達到 Full (strict) 加密（Role: cert_manager）。Cloudflare Access 擋在 *.dough-ops.com 前面，只放行指定 GitHub org 的成員，Dashboard、Hubble、Grafana 等內部工具見內部工具。 這個階段也包含 bastion 持久化與重建韌性。bastion 的資料碟在 terraform destroy 後保留，HashiCorp Vault 跑在 bastion 並於重建後自動 unseal，見 Role: vault。監控資料用靜態 PV 撐過整個環境重建。細節見資料碟與全部拆除。
  6. Phase 6 · Dex、Keycloak 與 Cloudflare Access 的聯邦 PoC 在 bastion 上裝獨立的 Keycloak，模擬公司既有的 SSO。叢集內的 Dex 當叢集專屬的 OIDC broker，只透過 Dex 去談 Keycloak，應用程式只認 Dex。Dex 對 Keycloak 的呼叫是機器對機器連線，所以 Cloudflare Access 針對這類流量另開範圍收窄的 bypass。設計見 Role: keycloak / dex，登入流程見身份聯邦登入流程。
  7. Phase 7 · 自架 GitLab CE 與 Runner 在 bastion 上以容器跑 GitLab CE，沿用 Cloudflare Access 做邊緣驗證，再疊加 GitLab 自己的 OmniAuth OIDC，過了邊緣驗證就自動登入。instance-wide 的 Runner 使用 Docker executor，讓 CI pipeline 有地方執行。密鑰集中放在加密的 secrets.yml。細節見 Role: gitlab。
  8. Phase 8 · ArgoCD 串接自架 GitLab ArgoCD 除了公開 GitHub repo，也從私有 GitLab repo 拉 manifests 並自動 sync，驗證 ArgoCD 與 GitLab 之間的認證與連線。登入設計與串接方式見 Role: argocd § 登入與 ArgoCD 與 GitLab 串接。這個階段抓到的 bastion Docker network 撞上 Service CIDR 的問題，記在 Bug #45。
