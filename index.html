cloudnative.tw · AS 65000

在真實 OpenStack 上,用 iBGP fabric 撐起一個 native routing 的 Kubernetes 叢集

這不是教學文件裡的範例架構,是在 cloudnative.tw(一個一般權限、沒有 LBaaS/routed public prefix 的通用 OpenStack tenant)上,從零開始一步步建出來、每個決定都有 實測證據支撐的真實叢集。核心命題很單純:公有雲/一般 OpenStack tenant 通常只給你「一張扁平網路 + Router NAT」,但如果你自己在每台機器上跑 FRR 組一個 iBGP fabric,你其實可以拿到接近「有 BGP 路由器的實體機房」才有的 東西——ECMP、L4LB DR、以及現在這份文件的主角:不靠 VXLAN/Geneve overlay 的 native routing CNI。

7 個 k8s 節點 + 1 tor + 1 bastion 單一 ASN 65000,全節點 iBGP Cilium native routing,不用 Cilium 自己的 BGP Ansible 全自動化,跑在 bastion 的 Docker 裡 Cilium eBPF 取代 kube-proxy Cloudflare Tunnel 對外,不開任何 inbound port cert-manager + Origin CA,端對端 Full (strict) 加密 Cloudflare Access 擋整個 *.dough-ops.com

現在的拓樸

這是目前(2026-07-27)這個 lab 實際跑起來的樣子——3 台 master 做 etcd/apiserver HA、 2 台原本規劃當 L4LB 的節點現在也直接當 k8s worker 用、2 台純 worker, 全部節點的資料平面都在同一個扁平網路(k8s-net)上跑 iBGP。

節點拓樸圖 mgmt-net(虛線,管理/對外)+ k8s-net iBGP fabric(實線,tor 扇出)

每個節點的 Pod CIDR(172.16.x.0/24)由 Cilium 分配,由本節點的 FRR 用 network 陳述式廣播出去,tor 反射給其他所有節點。

mgmt-net 192.168.200.0/24(管理/對外) k8s-net 10.10.0.0/24(iBGP fabric) tor 唯一 route reflector bastion 唯一操作入口,無 k8s-net

圖上沒畫出來的是對外流量的入口:cluster 內 cloudflare namespace 跑著 cloudflared, 對 Cloudflare 邊緣建立 outbound-only 連線,不佔用上面拓樸裡的任何 floating ip/inbound port——完整路徑見 Role: cloudflare_tunnel。

為什麼要看這份文件,不是只看 kubectl get all? 因為這個 lab 的價值不在「有一個能動的 k8s 叢集」——minikube 五分鐘就有一個。 價值在於每一個看起來普通的設定背後,都對應著一個實測踩到的坑,或一個刻意的取捨。 這份文件的目標是讓你不用重踩這些坑就能看懂「為什麼是這樣設」。

建置的五個階段

這個 lab 不是一次到位設計出來的,是分階段疊上去的,每一階段都先驗證上一階段的 假設是對的,再往下一階段走。了解這個順序,能幫助理解為什麼某些設計「看起來繞了一下」 ——因為當初做那個決定時,後面的階段根本還沒發生。

  1. Phase 1 · 驗證 iBGP + ECMP + DSR L4LB 的核心假設(已被取代,見 DSR / L4LB 歷史頁面) 最早的問題是:「cloudnative.tw 這種一般權限 OpenStack tenant,到底有沒有可能做出 BGP-based 的 L4LB?」用最少的機器(tor + 2 個「假 pod」node-a/node-b + 2 台 l4lb) 證明了:next-hop-self force 讓 route reflector 正確反射路由、 maximum-paths ibgp 做出真正的 ECMP、IPVS DR 模式讓 L4LB 回程流量完全不經過負載平衡器本身(用 ipvsadm --stats 的 OutPkts=0 證明)。這個階段也是 Neutron port security 與 DSR 天生不相容這個結論的來源——之後全專案的 fabric port 都 port_security_enabled = false,是這裡驗證出來的,不是隨便關的。
  2. Phase 2 · 換成真實 k8s 拓樸,分離 mgmt-net / k8s-net 驗證完核心假設後,把測試用的 node-a/node-b/l4lb-0001/l4lb-0002 換成真正要跑 k8s 的機器:bastion(操作入口)+ 3 master + 2 lb(仍保留角色但也當 worker)+ 2 worker,並且把原本「單一扁平網路 + Router 做 SNAT」正式拆成 k8s-net(資料平面,無預設路由)+ mgmt-net(操作/對外,有 SNAT), 詳見 Terraform / OpenStack 頁面。
  3. Phase 3 · 用 Ansible 把「裝 k8s」這件事自動化,再用 kubeadm + Cilium native routing 把叢集真的立起來 先建立一套「本機打指令、實際在 bastion 的 Docker 裡執行 ansible」的框架 (Ansible 框架設計),再依序裝 CRI-O → kubeadm 拉起 3-master HA 控制平面 → apiserver 的 haproxy LB (架在 tor 上,見 Role: apiserver-lb)→ 最後裝 Cilium,選 native routing 模式、刻意不用 Cilium 自己的 BGP Control Plane,而是把每個節點的 Pod CIDR 動態塞進既有的 FRR fabric 裡宣告出去(見 Role: cilium)—— 讓 Phase 1 驗證出來的 iBGP fabric 真的變成「production 用途」,不是驗證完就丟掉。
  4. Phase 4 · 拿掉 kube-proxy、裝 Istio + Cloudflare Tunnel, 把叢集變成真的能對外服務 Phase 3 讓叢集自己內部通了,但還沒有對外的路。這個階段做三件 事:把 kubeProxyReplacement 打開、讓 Cilium 的 eBPF 完全取代 kube-proxy(連帶把 Cilium 搬到專屬的 cilium namespace,見 Role: cilium);裝 Istio 當 cluster 內部的 L7 路由層(istio namespace,見 Role: istio);最後裝 cloudflared,建立一條 outbound-only 的 Cloudflare Tunnel 當唯一對外入口(cloudflare namespace,見 Role: cloudflare_tunnel) ——這個階段也踩到一個值得記錄的岔路:第一版方案是走 bastion floating ip + NodePort + nginx,被使用者明確否決、 整個移除,因為使用者已經獨立設定好 Cloudflare Tunnel,不需要 再開任何 inbound port。同一批工作也順手把整個叢集升級到 Kubernetes 1.34。
  5. Phase 5 · 端對端加密 + 身份驗證:cert-manager、 Cloudflare Access,還有一批真正拿來用的內部工具 Phase 4 讓 *.dough-ops.com 對外通了,但 Cloudflare Tunnel 到 Istio Gateway 那一段還是 plain HTTP、 誰都連得到。這個階段裝 cert-manager + Cloudflare 官方的 origin-ca-issuer,簽一張真正被 Cloudflare 信任的 *.dough-ops.com wildcard 憑證,讓 Istio Gateway 也講 HTTPS,cloudflared 用同一張 CA 的 root cert 驗證(見 Role: cert_manager)—— 整條路徑變成 Cloudflare「Full (strict)」等級的端對端加密。 光加密還不夠,因為緊接著裝的三個工具(Kubernetes Dashboard、 Hubble UI、kube-prometheus-stack 的 Grafana/Prometheus/ Alertmanager,見 內部工具) 有一半以上完全沒有內建登入,所以同一批工作也設定了 Cloudflare Access,擋在整個 *.dough-ops.com 萬用字元前面,只有 doughops 這個 GitHub org 的 成員登入後才連得到——一次設定,新增任何服務都自動涵蓋在內。

怎麼讀這份文件

如果你想要自己動手從零建一份一樣的環境,直接看 從零開始建置——那頁是唯一一份「OpenStack 認證設定 → Terraform 建資源 → Cloudflare Terraform → Ansible 裝好整套」的完整 操作清單。如果你只有五分鐘,看 網路架構總覽 就好——那頁把「為什麼整個系統 長這樣」講完整了。如果你要重現或除錯某個具體元件,直接跳對應的 role-*.html 頁面,每頁都是「這個 role 每個設定為什麼這樣寫」 的逐項說明,包含實測踩到的 bug。如果你在找「這個錯誤訊息我好像在哪見過」, 直接去 Bug 事後檢討,那頁把整個專案 實測到的所有 bug 按時間排序,每個都附根因分析跟修法。
