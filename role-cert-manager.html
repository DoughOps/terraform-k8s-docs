對外入口與身份驗證 Role: cert_manager

這個 role 安裝 cert-manager 和 Cloudflare 的 origin-ca-issuer。它簽出一張被 Cloudflare 信任的 *.dough-ops.com wildcard 憑證，讓 Istio Gateway 用真憑證終止 HTTPS。這補上 Full (strict) 加密等級：邊緣到 Gateway 這一段也加密並驗證。在建置順序中接在 Istio 之後，依賴 istio namespace 已存在。Role: cloudflare_tunnel 的 Tunnel 用這張憑證驗證 origin。

為什麼需要 Origin CA 憑證

Universal SSL 只處理瀏覽器到 Cloudflare 邊緣這一段。cloudflared 到 istio-ingressgateway 這一段，如果沒有憑證，只能是 plain HTTP，流量要經過好幾個節點卻沒有加密。要補上這一段，Gateway 必須自己講 HTTPS，而且憑證要是 Cloudflare 信任的，否則 cloudflared 只能用 noTLSVerify: true 關掉驗證，加密就沒有意義。

決策：Gateway 使用 Cloudflare Origin CA 簽發的憑證。

理由：Origin CA 簽出的憑證只被 Cloudflare 信任，正好符合「邊緣到 origin」這一段。不需要處理 Let's Encrypt 的 HTTP-01 或 DNS-01 challenge 怎麼穿過 Tunnel，也讓 cloudflared 能用 caPool 驗證憑證。

考慮過的替代方案：Let's Encrypt 等公開 CA — challenge 要穿過 Tunnel，增加複雜度，不選。自簽憑證 — cloudflared 無法驗證，只能 noTLSVerify，不選。

代價：Origin CA 憑證不被一般瀏覽器信任。直接繞過 Cloudflare 連 origin 的客戶端會看到憑證錯誤，所以這條 origin 只能由 Cloudflare 的流量使用。

元件角色
cert-manager Kubernetes 通用的憑證生命週期管理，負責簽發、續期，並存進 Secret。本身不知道怎麼呼叫 Cloudflare Origin CA 的 API。
origin-ca-issuer cert-manager 的 external issuer 外掛，API group 是 cert-manager.k8s.cloudflare.com。實際呼叫 Cloudflare Origin CA 的 POST /certificates 簽發憑證，是 Cloudflare 官方專案。

安裝順序

roles/cert_manager/tasks/main.yml（順序）
1. assert cloudflare_origin_ca_api_token 已設定
2. helm 裝 cert-manager（cert-manager namespace）
3. 等 cert-manager-webhook ready（下面幾步的資源都要靠它驗證）
4. kubectl apply origin-ca-issuer 的 CRD（2 個）
5. kubectl apply origin-ca-issuer 的 RBAC（3 個）
6. kubectl apply origin-ca-issuer 的 controller（namespace、serviceaccount、deployment）
7. 等 origin-ca-issuer controller ready
8. apply OriginIssuer 與 wildcard Certificate（istio namespace）
9. kubectl wait --for=condition=Ready certificate/dough-ops-com-wildcard

最後一步會等憑證真的簽發完成，不是 apply 完就假設成功。第一次建置就靠這一步，加上 openssl x509 實際印出憑證內容，確認整條鏈路是通的，見驗證方式。

步驟 3 的 webhook 必須先 ready。webhook 沒有運作時，後面 apply 的 OriginIssuer 和 Certificate 會因為連不上它而被拒絕。

這個 playbook 是 playbooks/k8s/cert-manager.yml，前置條件是 playbooks/k8s/istio.yml 已經跑過，因為 TLS Secret 要放在 istio namespace。

OriginIssuer 放在 istio namespace

決策：OriginIssuer、Certificate 和 TLS Secret 都放在 istio namespace。

理由：OriginIssuer 是 namespace-scoped，它簽出的 Certificate 和 Secret 必須與它同一個 namespace。Istio Gateway 只能讀與自己同一個 namespace 的 Secret，所以 Secret 必須在 istio。

考慮過的替代方案：放在 cert-manager 或 origin-ca-issuer namespace — Gateway 讀不到，不選。改用 ClusterOriginIssuer — Secret 仍須在 istio，且目前只有一個 namespace 需要，不增加複雜度。

代價：以後有其他 namespace 的 Gateway 需要憑證時，要各自建 OriginIssuer 或改用 cluster 層級的版本。

認證：scoped API token

決策：用一般 API token，權限只有 Zone → SSL and Certificates → Edit，並限定在 dough-ops.com 這一個 zone。

理由：Cloudflare 在 2026-03-19 棄用了舊版 Origin CA Key（v1.0- 開頭的帳號層級金鑰），官方建議改用 API token。origin-ca-issuer 的 README 兩種方式都支援，但 Origin CA Key 已標註為過時做法。token 限定單一 zone 後，即使外洩，也只能幫這個 zone 簽 Origin CA 憑證，連 DNS 都改不了。

考慮過的替代方案：帳號層級的 Global API Key — 權限過大，不選。Origin CA Key — 已棄用，不選。

代價：token 會長期存放在叢集的 Secret 裡，仍需要妥善保護。

這個 token 由 cloudflare/api_token.tf 自動建立，不用手動到 dashboard 點。值寫進 secrets.yml 的 cloudflare_origin_ca_api_token，約定與 cloudflare_tunnel_token 相同，見 Cloudflare 設定清單 與 Ansible 框架設計 § 密鑰管理。token 換新之後，要重跑 playbooks/k8s/cert-manager.yml，否則新憑證續期會失敗，現有憑證在過期前不受影響。

一張 wildcard 憑證

roles/cert_manager/templates/origin-issuer.yaml.j2（Certificate 部分）
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: dough-ops-com-wildcard
  namespace: istio
spec:
  secretName: dough-ops-com-tls
  dnsNames:
    - "dough-ops.com"
    - "*.dough-ops.com"
  duration: 2160h     # 90 天，Origin CA 允許的天數選項之一
  renewBefore: 360h   # 提早 15 天續期
  issuerRef:
    group: cert-manager.k8s.cloudflare.com
    kind: OriginIssuer
    name: cloudflare-origin-ca

只簽一張涵蓋 *.dough-ops.com 的憑證，不為每個子網域各簽一張。TLS 在共用的 Istio Gateway 一次終止，不論請求去哪個子網域，用的都是同一張憑證。VirtualService 只負責解密後的 HTTP 層路由，見 Role: istio。

已知限制與 workaround

  • originServerName 必須帶子網域：Gateway 的 443 listener 比對 *.dough-ops.com，不接受 apex 名稱。這是 Bug #28 的 workaround，目前使用 gateway.dough-ops.com，只要符合萬用字元語意即可，不需要有對應的服務。
  • origin-ca-issuer 在安裝時從 GitHub 下載：manifest 來自 raw.githubusercontent.com 的固定 tag，bastion 要能連到 GitHub，版本由 origin_ca_issuer_version 固定。
  • 憑證只由 Cloudflare 信任：直接連 origin 的客戶端會看到憑證錯誤，測試後端要自行帶 Origin CA root。

實測踩到的 bug

#28 · 所有 *.dough-ops.com 子網域回 503

  • 症狀：真實瀏覽器或 curl 連 hubble.dough-ops.com、dashboard.dough-ops.com 等子網域，Cloudflare 邊緣回應自己品牌的 503 錯誤頁，不是 Envoy 或 Hubble 產生的。從叢集內部直接對 istio-ingressgateway 送請求（用真實子網域當 SNI）每次都成功。這個差異是排查的線索。
  • 根因：第一版把 originRequest.originServerName 設成 zone apex dough-ops.com。cloudflared 對整條 wildcard ingress 規則只有一份 originRequest，所以不論請求哪個子網域，TLS handshake 送出的 SNI 都是這個固定值，但 HTTP 的 Host header 會照實際請求帶。Gateway 的 443 server block 設定 hosts: ["*.dough-ops.com"]，Istio 轉成 Envoy 的 TLS filter chain server_names 比對規則，語意是子網域萬用字元，至少要有一段 label。它能匹配 hubble.dough-ops.com，不匹配 dough-ops.com 本身。SNI 是 apex 時，Envoy 找不到任何 filter chain 接手，直接斷線。這發生在 TLS 層，早於 HTTP 層的 Host 路由，所以 Host header 正確也救不回來。
  • 修法：把 originServerName 改成任何帶子網域的名字，這裡用 gateway.dough-ops.com。這個名字純粹用來滿足 SNI 比對，不需要有對應的 Service。這項設定在 cloudflare/tunnels.tf，不是 Ansible 管的。
  • 怎麼確認修好：用臨時 curl pod 重現。SNI 和 Host header 故意不一致。TLS 用 SNI 過 filter chain，HTTP 路由用 Host header 送到正確服務。test、hubble、dashboard、grafana、prometheus、alertmanager 六個子網域全部重新驗證，cloudflared 的錯誤日誌不再出現。
  • 相關：Bug #28。影響範圍不只 Hubble，所有掛在同一條 wildcard ingress 規則下的服務都受影響。

cloudflared 的錯誤日誌（症狀）：

cloudflared 的錯誤日誌
ERR error="Unable to reach the origin service. The service may be down or it
may not be responding to traffic from cloudflared: read tcp
172.16.6.161:45672->172.18.84.180:443: read: connection reset by peer"
dest=https://hubble.dough-ops.com/

除錯的關鍵是重現 cloudflared 的實際行為：臨時 curl pod 故意讓 SNI 與 Host header 不一致。

重現：SNI 為 apex，Host header 為 hubble.dough-ops.com
$ curl --resolve dough-ops.com:443:<ingressgateway ClusterIP> --cacert origin-ca-root.pem \
    -H "Host: hubble.dough-ops.com" https://dough-ops.com/
curl: (35) OpenSSL SSL_connect: Connection reset by peer   ← TLS handshake 直接失敗，連 HTTP 層都還沒到

修好之後，SNI 和 Host 不一致但都成功：

修好之後：SNI 為 gateway.dough-ops.com，Host header 為 hubble.dough-ops.com
$ curl --resolve gateway.dough-ops.com:443:<ingressgateway ClusterIP> --cacert origin-ca-root.pem \
    -H "Host: hubble.dough-ops.com" https://gateway.dough-ops.com/
HTTP/2 200   ← TLS 用 SNI 過了 filter chain，HTTP 路由用 Host header 送到 hubble-ui

驗證方式

驗證要檢查憑證鏈，不能只看回應碼。先在叢集內印出簽出來的憑證：

在 bastion 上（首次簽發時的實測輸出）
$ kubectl -n istio get secret dough-ops-com-tls -o jsonpath='{.data.tls\.crt}' \
    | base64 -d | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
subject=O = "CloudFlare, Inc.", OU = CloudFlare Origin CA, CN = CloudFlare Origin Certificate
issuer=C = US, ST = California, L = San Francisco, O = "CloudFlare, Inc.",
       OU = CloudFlare Origin SSL ECC Certificate Authority
notBefore=Jul 27 02:49:00 2026 GMT
notAfter=Oct 25 02:49:00 2026 GMT
X509v3 Subject Alternative Name:
    DNS:*.dough-ops.com, DNS:dough-ops.com

預期結果：issuer 是 CloudFlare Origin SSL ECC Certificate Authority，SAN 包含 *.dough-ops.com 和 dough-ops.com，有效期為 90 天。接著從叢集內部開臨時 curl pod，用同一份 Origin CA root cert 直接打 Gateway 的 443。從內部測是因為外部請求會先被 Cloudflare Access 擋下，測不到後端。

實測：憑證驗證通過，HTTP/2 200
$ curl -sv --resolve test.dough-ops.com:443:<ingressgateway ClusterIP> \
    --cacert origin-ca-root.pem https://test.dough-ops.com/
* subjectAltName: "test.dough-ops.com" matches cert's "*.dough-ops.com"
* OpenSSL verify result: 0
* SSL certificate verified via OpenSSL.
* using HTTP/2
< HTTP/2 200
< server: istio-envoy

預期結果：憑證驗證通過並回 HTTP/2 200。這證明「cloudflared 用 caPool 驗證，Envoy 用 Origin CA 憑證回應，憑證鏈驗證通過」的路徑是加密且經過驗證的。外部 curl 則應回 302，代表 Access 在邊緣擋住了請求，規則見 Cloudflare Access 規則。

演進歷史

這個 role 最初和 Cloudflare Access 一起設定。部分內部工具沒有內建登入，光有 HTTPS 不夠，還需要身份驗證擋在前面。Access 現在由 cloudflare/ Terraform 管理，詳見 Cloudflare Access 規則。

Origin CA 的 scoped token 最初用 Cloudflare API 手動建立。為了讓環境能無人值守地從零建出來，現在改由 cloudflare/api_token.tf 產生。
