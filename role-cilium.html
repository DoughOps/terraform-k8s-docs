cloudnative.tw · AS 65000

叢集元件 Role: cilium

這個 role 把 Cilium 部署成 CNI，使用 native routing，跨節點的 pod 路由完全交給既有的 FRR iBGP fabric。它也取代 kube-proxy，並開啟 Hubble 觀測。在建置順序中，它排在 kubeadm 之後、smoke-test 之前，依賴已經存在的 apiserver 和 tor 上的 haproxy（見 Role: apiserver-lb）。整體網路設計見網路架構總覽，這頁專注在這個 role 怎麼設定，以及實測踩到的問題。

兩段式編排

roles/cilium/tasks/main.yml
1. bastion:   用 helm 裝 Cilium（ipam.mode=cluster-pool）
2. k8s_nodes: 把每個節點實際拿到的 CIDR（CiliumNode）用 vtysh 加進本地 FRR

呼叫這個 role 的 playbook，hosts 要同時涵蓋 bastion 和 k8s_nodes。實際寫法是 hosts: k8s_nodes:bastion。兩段用 when 各自守衛。

Ansible 預設的 linear strategy 會讓每個 task 等所有 host 做完或 skip，才進下一個 task。所以「裝 Cilium」一定在「vtysh 加 CIDR」之前完成，不需要額外的 wait_for 或鎖。

用 helm 安裝

安裝 task 全部用 become: false，以 ubuntu 身份執行。kubeconfig 在 /home/ubuntu/.kube/config，helm 的 repo cache 和 state 也在 ubuntu 的家目錄。用 root 跑會產生另一份 state，之後手動以 ubuntu 身份下 helm 指令就對不起來。

helm 二進位直接從 get.helm.sh 下載 tarball 解壓縮，版本由 group_vars/all/main.yml 的 helm_version 控制（roles/istio 共用同一個值）。只有「把二進位放進 /usr/local/bin」這一步需要 become: true。

roles/cilium/tasks/install.yml（節錄）
kubernetes.core.helm:
  name: cilium
  chart_ref: cilium/cilium
  chart_version: "{{ cilium_chart_version }}"   # 1.19.6
  release_namespace: "{{ cilium_namespace }}"   # cilium
  create_namespace: true
  wait: true
  wait_timeout: 5m0s

Cilium 裝在專屬的 cilium namespace，不使用官方預設的 kube-system，讓 CNI 的資源和其他系統元件分開管理，也和 istio、cloudflare 等其他元件的做法一致。

Cilium 的 chart 沒有寫死 namespace，只要設定 release_namespace 就夠了。這點和 Istio 不同，Istio 還需要另外設定 global.istioNamespace（見 Role: istio）。

helm 的 wait: true 讓 ansible 等到 release 就緒，之後再用 kubectl rollout status daemonset/cilium --timeout=300s 二次確認。

現在的 values

下表逐項對照 roles/cilium/templates/cilium-values.yaml.j2。

欄位值為什麼
routingMode native 不用 VXLAN／Geneve overlay，跨節點封包直接帶 pod 真實 IP 走底層網路。前提是底層知道怎麼路由每個節點的 PodCIDR，這正是 FRR iBGP fabric 在做的事。完整理由見網路架構總覽。
ipv4NativeRoutingCIDR {{ cluster_pod_cidr }}（172.16.0.0/16） 告訴 Cilium 這個範圍的目的地交給底層網路處理，不要自己 masquerade。設成整個叢集的 pod CIDR。
autoDirectNodeRoutes false 關掉 Cilium 判斷節點是否同 L2 網段、自動加直連路由的功能。k8s-net 雖然是同一個 flat subnet，但節點 PodCIDR 的路由刻意交給 FRR／BGP，避免兩邊互相打架。
ipam.mode cluster-pool 由 cilium-operator 配發每個節點的 CIDR，記錄在 CiliumNode 的 .spec.ipam.podCIDRs，不依賴 kube-controller-manager 的 node-ipam-controller。bgp_announce.yml 直接讀這個欄位。
ipam.operator.clusterPoolIPv4PodCIDRList 172.16.0.0/16 配發的來源範圍。套用後不能改既有元素（Cilium 官方文件明講）。
ipam.operator.clusterPoolIPv4MaskSize 24（cluster_pod_cidr_node_mask） 每個節點分到一個 /24。和上一列一樣，套用後不能再改，要改只能用 kubeadm-reset.yml 整個叢集重建。
bgpControlPlane.enabled false 不使用 Cilium 自己的 BGP，見下方的決策紀錄。
kubeProxyReplacement true 用 Cilium 的 eBPF 實作取代 kube-proxy，見 kube-proxy 取代。
bpf.masquerade true kubeProxyReplacement 只決定 Service 負載平衡是否用 eBPF，不會連帶打開 BPF masquerade。chart 預設是 false，masquerade 和 host routing 會停在 legacy iptables／netfilter。kernel 6.8 和 Cilium 1.19.6 都超過 BPF host routing 要求的 5.10 以上。見 Bug #46。
k8sServiceHost／k8sServicePort {{ apiserver_hostname }}（k8s-api.internal）／{{ apiserver_port }} 沒有 kube-proxy 時，Cilium agent 啟動當下需要一個不靠 kube-proxy 就連得到的 apiserver 入口。必須用 hostname，不能用 tor 的 IP，見 Bug #24。
hubble.enabled／relay／ui 全部 true 觀測 eBPF 資料平面實際看到的流量。relay 聚合各節點 agent 的資料，ui 才是對外的網頁介面。對外掛載見 Hubble UI。
extraConfig.enable-remote-node-masquerade "true" 繞過底層 fabric 問題的 workaround，見 remote-node-masquerade。

PodCIDR 如何進入 FRR

每個節點把自己被配發的 CIDR 讀出來，用 vtysh 加一個 network 陳述式到本地 FRR，讓 iBGP fabric 把這個 prefix 廣播出去。這和 Phase 1 用 dummy0 加 network 宣告 Service VIP 是同一招，見 DSR / L4LB 歷史。差別是 PodCIDR 在 Cilium 執行期才決定，沒辦法像 terraform.tfvars 的 announce_prefix 那樣在開機時寫死。

讀取來源是 kubectl get ciliumnode <節點名> -o jsonpath={.spec.ipam.podCIDRs[0]}。cluster-pool 模式下，CiliumNode 是權威來源，Node.spec.podCIDR 不再有值。

roles/cilium/tasks/bgp_announce.yml（精簡）
vtysh -c "configure terminal" \
      -c "ip route 172.16.0.0/24 Null0 200" \
      -c "end" -c "write memory"

vtysh -c "configure terminal" \
      -c "router bgp 65000" \
      -c "network 172.16.0.0/24" \
      -c "end" -c "write memory"

這段做三件事：

  1. 讀取 CiliumNode 的 PodCIDR，並斷言有拿到值。拿不到代表 cilium-operator 沒有正常運作。
  2. 加一條 distance 200 的 Null0 靜態路由，給 zebra 一個「這個 prefix 存在」的憑證。原因見 Bug #19。
  3. 在 router bgp 加 network，讓 fabric 廣播。

兩個寫入步驟都先讀 show running-config，確認設定還不存在才執行，所以重跑不會累加重複設定。

Null0 路由只用來通過 zebra 的驗證，不影響封包轉送。kernel 裡 Cilium 的 route 是 metric 0，這條 blackhole 是 metric 20，實際查詢永遠選中 Cilium 的那條。實測輸出在 Bug #19。

決策紀錄：不使用 Cilium BGP Control Plane

決策：bgpControlPlane.enabled: false，PodCIDR 的宣告由 FRR 負責。

理由：fabric 的 iBGP 已經由 FRR 負責，tor 是 route reflector，見 FRR / iBGP Fabric。再讓 Cilium 跑一套 BGP 實作，就有兩個 daemon 對同一批節點宣告路由，策略和 next-hop 行為會互相打架。

考慮過的替代方案：Cilium BGP Control Plane 直接和 tor 建立 peering — 會與既有的 FRR session 並存。route reflector 要多處理一種 client，BGP 設定也要維護兩套。

代價：要自己維護 bgp_announce.yml 這段 vtysh 流程，並用 Null0 路由繞過 zebra 的限制（Bug #19）。PodCIDR 變動時，宣告不會自動跟著更新，需要重跑 playbook。

kube-proxy 取代

叢集沒有安裝 kube-proxy，Service 的負載平衡全部由 Cilium 的 eBPF 資料平面處理。Cilium 端的設定是 kubeProxyReplacement: true，kubeadm 端對應使用 --skip-phases=addon/kube-proxy（見 Role: kubeadm）。

決策：用 Cilium eBPF 取代 kube-proxy。

理由：Service 轉發只剩一套資料平面，不需要 kube-proxy 的 iptables 規則鏈與 Cilium 的 BPF map 並存。

考慮過的替代方案：保留 kube-proxy（iptables 或 ipvs 模式）搭配 Cilium — 兩套實作都會處理 Service 流量，排錯時要判斷是哪一套在動作。

代價：Cilium agent 啟動時不能依賴 kube-proxy 轉發 ClusterIP，必須明確設定 k8sServiceHost／k8sServicePort，這是標準的 kube-proxy-free bootstrap 問題。這個值用 hostname 而不是 IP，見 Bug #24。

Istio 完全不受影響。它在 L7 對 Kubernetes Service 這個抽象概念操作，不依賴 ClusterIP 是由 iptables 還是 eBPF 轉發（見 Role: istio）。

Hubble UI 的對外掛載

Hubble UI 本身沒有登入機制，只靠 Cloudflare Access 擋在前面。它透過 Istio 的共用 Gateway 對外，網址是 hubble_hostname（hubble.dough-ops.com）。

這個掛載由獨立的 playbooks/k8s/hubble-expose.yml 執行，不在 roles/cilium 的主流程裡。原因是 VirtualService 這個 CRD 由 Istio 提供，而 cilium.yml 排在 istio.yml 之前，從零建置時 CRD 還不存在，直接 apply 會失敗：no matches for kind "VirtualService"。所以 hubble-expose.yml 在 k8s.yml 裡排在 istio.yml 之後。

這個 playbook 用 import_role 搭配 tasks_from: hubble_expose。tasks_from 只在 task 層級的 import_role／include_role 生效。寫在 play 層級的 roles: 清單會被忽略，結果是整個 main.yml 被重跑一次，包含 helm 安裝和 bgp_announce。

已知限制與 workaround

目前唯一偏離「pod 內部一律帶真實 IP」設計的地方，是 enable-remote-node-masquerade。

remote-node-masquerade

這是繞過底層 fabric 問題的 workaround，不是設計意圖。native routing 的前提是 pod 對外一律帶真實 pod IP，只有真正離開叢集的流量才需要 masquerade，叢集內部（pod↔pod、pod→node）完全不 NAT。這個設定讓「pod → 叢集內其他節點的真實 host IP」的來源位址被改寫成發起節點自己的 IP，違反了這個前提。

決策：在 cilium-values.yaml.j2 打開 extraConfig.enable-remote-node-masquerade: "true"。

理由：OpenStack／OVN fabric 會靜默丟棄 pod-CIDR（172.16.0.0/16）來源的封包，除非目的地是 tor。節點自己真實 IP 來源的封包永遠暢通。讓 pod 發往節點真實 IP 的封包先偽裝成節點來源，就能繞過這個問題。

考慮過的替代方案：修底層 fabric — 需要 OVN Southbound DB 或 hypervisor OVS flow table 的權限，租戶身份查不到。僅依賴 ipv4NativeRoutingCIDR — 擋不住這條流量，因為 BPF masquerade 對 remote-node／kube-apiserver identity 的目的地有寫死的豁免，不受這個 CIDR 控制。

代價：apiserver 看到的來源位址不再是發起連線的 pod。同一節點上所有 pod 對 apiserver 的連線，在 audit log 和連線來源欄位都顯示成同一個節點 IP，失去「哪個 pod 打了這次 API」的可追蹤性。

影響範圍
  • 只影響「pod → 叢集內其他節點的真實 IP」。目前唯一踩到的情境是 pod → kubernetes Service：它是 no-selector Service，Endpoints 直接指向三台 master 的 6443。
  • 不影響 pod↔pod，也不影響 pod → 一般有 selector 的 ClusterIP，這些流量繼續帶真實 pod IP。
  • 日後若有其他東西讓 pod 直接連某個節點的真實 IP，也會被悄悄 SNAT。
  • Cilium 官方文件提醒，這個選項會限制 ingress host firewall 對 pod → node 方向的政策執行能力。叢集目前沒有依賴 remote-node entity 的 NetworkPolicy 或 CiliumNetworkPolicy，以後加的話要重新確認。
何時可以拿掉

底層 fabric 的問題修好之後，整段 extraConfig 可以移除，讓 pod 對 apiserver 的連線恢復帶真實 pod IP。這個設定只是繞過症狀，沒有解決根因，所以拿掉之前要先重新驗證底層問題是否真的消失。排錯過程和證據見 Bug #47。

為什麼是這個設定

用分層測試把「pod → apiserver 全新連線逾時」收斂成一個乾淨的規律：

  • pod → tor 本身：暢通。
  • 節點自己真實 IP → 任何其他節點：暢通。
  • pod-CIDR 來源 → 除 tor 以外的任何節點：封包在 OpenStack fabric 消失。

兩端同步 tcpdump，發送端看得到封包送出，接收端零封包，所以問題在線上，不在任何一台 VM 內部。cilium-dbg monitor 證實 Cilium 每次都放行，把封包送上 ens3（action: allow），和 Cilium 的 policy 或 datapath 無關。Neutron port 的 port_security_enabled、MAC、IP 也逐一查過沒有異常。往下需要 OVN Southbound DB 或 hypervisor OVS flow table，共享雲（openstack.cloudnative.tw）只給一般 project 身份，查不到。

這個選項本來的設計目的是讓 remote node 的 firewall 規則能用單一節點 IP 辨識流量，見 Cilium 官方的 masquerading 文件。這裡借用它的效果繞開 fabric 的問題。

Helm 沒有對應欄位

chart 的 values.yaml 沒有把這個 agent flag 包成 camelCase 欄位，所以用 extraConfig 直接把 kebab-case 的 ConfigMap key 塞進去：

roles/cilium/templates/cilium-values.yaml.j2
extraConfig:
  enable-remote-node-masquerade: "true"

改 extraConfig 之後 agent 不會自動重啟。只會更新 ConfigMap，helm upgrade 和 kubectl rollout status daemonset/cilium 都回報成功，但那只代表 DaemonSet 的 pod template 沒變，沒有 pending rollout。這類會改變編譯後 BPF 程式邏輯的設定，agent 不重啟就不會重新載入，ConfigMap 改了也不生效。第一次驗證照標準流程：改 values、跑 k8s/cilium.yml、重測，結果完全沒效果，才發現這個陷阱。套用後要手動重啟：

在 bastion 上
$ kubectl -n cilium rollout restart daemonset/cilium
$ kubectl -n cilium rollout status daemonset/cilium --timeout=180s
怎麼確認生效

用 tcpdump 比較前後：

  • 生效前，pod → 節點真實 IP 的 SYN 來源位址是 pod IP（172.16.1.x）。
  • 生效後，同一條連線的 SYN 來源位址變成發起節點自己的 IP（10.10.0.x），三向交握完成。

原本卡住的 argocd-application-controller-0 不需要重建，就從 0/1 自動恢復成 1/1 Running。

實測踩到的 bug

下列 bug 的完整編號登錄在 Bug 事後檢討。這頁保留和 Cilium 設定直接相關的實測細節。

#19 · FRR 的 network 陳述式一直是 invalid

  • 症狀：network 陳述式要求 prefix 在 zebra 的 RIB 裡有一筆有效（non-blackhole）的 route，才會真的宣告。實際上 BGP 表顯示 invalid, not advertised。
  • 根因：Cilium 為節點 PodCIDR 在 kernel 建了一筆指向 cilium_host 的 route，kernel 看得到，zebra 卻沒有匯入。redistribute kernel 也沒用。懷疑 zebra 對「proto kernel 但帶 via gateway」這種不是單純 connected route 的條目有特殊處理，只有沒有 via、只有 dev 的 connected route 才會被無條件納入。這個懷疑沒有進一步比對 FRR 原始碼。
  • 修法：在 FRR 補一條 Null0 靜態路由，distance 200。Null0 是 blackhole，不指向真實介面，不會影響轉送。distance 刻意設高，確保 kernel 裡 Cilium 的真實 route 永遠贏。不能用 255，那是 FRR 的保留值，語意是「永遠不會被選上」。
  • 怎麼確認修好：show ip bgp 顯示 valid, sourced, local, best，且 ip route get 選中 cilium_host，見下方輸出。
  • 相關：Bug #19

先確認 kernel 有、zebra 沒有：

實測：kernel 有，但 zebra 沒有
$ ip route show 172.16.0.0/24
172.16.0.0/24 via 10.244.0.35 dev cilium_host proto kernel   ← kernel 有

$ vtysh -c "show ip route 172.16.0.0/24"
% Network not in table                                        ← zebra 沒有

第一次嘗試用 distance 255，仍然 invalid：

實測過程：distance 255 先失敗
$ vtysh -c "configure terminal" -c "ip route 172.16.0.0/24 Null0 255" -c "end"
$ vtysh -c "show ip bgp 172.16.0.0/24"
    0.0.0.0 (inaccessible) ... invalid, sourced, local   ← 還是 invalid

255 不只不會裝進 kernel FIB，連 BGP 的 network 驗證都會把它當成不存在。這是實測發現的。改用 200（夠高、但不是保留值）才成功。

distance 200：成功
$ vtysh -c "configure terminal" -c "ip route 172.16.0.0/24 Null0 200" -c "end"
$ vtysh -c "show ip route 172.16.0.0/24"
Routing entry for 172.16.0.0/24
  Known via "static", distance 200, metric 0, best
$ vtysh -c "show ip bgp 172.16.0.0/24"
    ... valid, sourced, local, best
  Advertised to non peer-group peers: 10.10.0.10   ← 真的被宣告出去了

關鍵的驗證是確認這條假路由沒有接管封包轉送：

kernel FIB 兩條路由並存，實際查詢選中 Cilium 的那條
$ ip route show 172.16.0.0/24
172.16.0.0/24 via 10.244.0.35 dev cilium_host proto kernel    # metric 0（隱含）
blackhole 172.16.0.0/24 proto static metric 20                # role 加的這條

$ ip route get 172.16.0.100                                     # 挑一個 PodCIDR 內的位址
172.16.0.100 dev cilium_host src 10.244.0.35                    ← 選的是 cilium_host，不是 blackhole

metric 0 的 Cilium route 比 metric 20 的 blackhole 優先，所以 Null0 路由只提供 zebra 驗證用的憑證，對真實流量透明。

#24 · 移除 kube-proxy 後，k8sServiceHost 設成 tor 的 IP 讓 Cilium 全掛

  • 症狀：所有 cilium pod 卡在 Init:CrashLoopBackOff，錯誤是 TLS 憑證驗證失敗。
  • 根因：kube-apiserver 憑證的 SAN 由 kubeadm init --control-plane-endpoint 傳入的字串和三台 master 各自的 IP 決定，tor 的 IP 從來不在清單裡。tor 上的 haproxy 只轉發 TCP，apiserver 不知道流量經過了誰。Cilium 用 tor 的 IP（10.10.0.10）發起 TLS 時，憑證對不上。
  • 修法：k8sServiceHost 改成 apiserver_hostname（k8s-api.internal），也就是 kubeadm init --control-plane-endpoint 當初傳入的同一個字串，SAN 本來就包含它。
  • 怎麼確認修好：所有 cilium pod 從 Init:CrashLoopBackOff 變成 1/1 Running。hostNetwork 的 pod（Cilium agent 就是）可以透過節點自己的 /etc/hosts（由 apiserver_dns role 寫入）解析這個 hostname，不需要另外處理 pod 專屬的 DNS 設定。
  • 相關：與 #16、#23 同類，都是「憑證 SAN 綁特定字串或 IP，中間節點不能頂替」。見 Role: kubeadm、Bug #24。
實測：cilium pod 的錯誤訊息
Unable to connect to the server: tls: failed to verify certificate: x509:
certificate is valid for 172.18.0.1, 10.10.0.20, 10.10.0.21, 10.10.0.22,
not 10.10.0.10

#46 · Cilium 停在 legacy iptables masquerade

  • 症狀：cilium-dbg status --verbose 顯示 Routing: Host: Legacy、Masquerading: IPTables，叢集明明已拿掉 kube-proxy。
  • 根因：kubeProxyReplacement: true 和 bpf.masquerade 是 chart 裡兩個獨立的開關，values 一直沒設後者，預設 false。
  • 修法：cilium-values.yaml.j2 補上 bpf.masquerade: true。
  • 怎麼確認修好：cilium-dbg status --verbose 不再出現 Legacy／IPTables。
  • 相關：排查 pod → apiserver 逾時時發現，但不是該逾時的根因，根因是 #47。見 Bug #46。

#47 · pod → 節點真實 IP 的新連線逾時

  • 症狀：pod 對 apiserver 的全新連線逾時，已經跑很久的 pod 不受影響。
  • 根因：底層 OpenStack fabric 丟棄 pod-CIDR 來源的封包，詳見 remote-node-masquerade。
  • 修法：打開 enable-remote-node-masquerade，這是 workaround。
  • 怎麼確認修好：tcpdump 看到 SYN 來源位址變成節點 IP，三向交握成功。
  • 相關：Bug #47

#18 · 安裝 Cilium 時 init container 連 ClusterIP 逾時

  • 症狀：Cilium 的 init container 連 ClusterIP 逾時。
  • 根因：hostNetwork 流量的來源位址選擇問題，根因和修法都不屬於這個 role。
  • 修法：見 Role: kubelet。
  • 怎麼確認修好：init container 能連上 ClusterIP，Cilium 正常啟動。
  • 相關：Bug #18

驗證方式

最完整的驗證是 smoke-test，它會確認節點與 pod 就緒、tor 上每個節點恰好一條 PodCIDR 路由，以及跨節點 pod 流量。手動檢查可以用下列指令：

在 bastion 上
$ kubectl -n cilium get pods
$ kubectl get ciliumnode -o custom-columns=NAME:.metadata.name,CIDR:.spec.ipam.podCIDRs
$ kubectl -n cilium exec ds/cilium -- cilium-dbg status --verbose

預期結果：所有 cilium pod 為 Running；每個節點都有一個 /24；cilium-dbg status 沒有 Legacy／IPTables。

在任一 k8s 節點上
$ sudo vtysh -c "show ip bgp 172.16.0.0/24"
$ ip route get 172.16.0.100

預期結果：BGP 表顯示 valid, sourced, local, best；ip route get 選中 cilium_host。

演進歷史

IPAM 從 kubernetes 改成 cluster-pool

早期 IPAM 使用 ipam.mode=kubernetes，權威來源是 Node.spec.podCIDR，由 kube-controller-manager 配發。改成 cluster-pool 後，配發改由 cilium-operator 負責，記錄在 CiliumNode。原本那整段「讓 kube-controller-manager 配發 PodCIDR」的 task 已經刪除，檔案是 roles/cilium/tasks/enable_pod_cidr_allocation.yml，main.yml 也不再呼叫。

這段在當時的做法，是直接編輯 kube-controller-manager 的 static pod manifest 補上三個 flag。kubeadm init 當時故意沒帶 --pod-network-cidr（見 Role: kubeadm），所以沒有任何 Node 物件有 .spec.podCIDR。

/etc/kubernetes/manifests/kube-controller-manager.yaml（補上的部分）
    - --allocate-node-cidrs=true
    - --cluster-cidr=172.16.0.0/16
    - --node-cidr-mask-size=24

補完 flag 之後還要主動等待 kube-controller-manager 重啟並真的完成配發，因為 kubelet 對 static pod 檔案的監控有輪詢間隔：

enable_pod_cidr_allocation.yml（已刪除）
- command: kubectl get nodes -o jsonpath={.items[*].spec.podCIDR}
  delegate_to: bastion
  until: node_pod_cidrs.stdout.split() | length == groups['k8s_nodes'] | length
  retries: 30
  delay: 10
  run_once: true

這是當時唯一依賴另一個 controller 非同步反應的步驟，所以用 until 輪詢直到所有節點都拿到 podCIDR。cluster-pool 模式下不再需要這段等待。

#17 · YAML block 純量讓 3 台 master 的 kube-controller-manager 同時消失

  • 症狀：kubelet 的錯誤訊息是 couldn't parse as pod(yaml: line 28: did not find expected key)。三台 master 的 kube-controller-manager 同時從叢集消失，因為 kubelet 判斷 manifest 無效，不會保留舊容器。leader election 的結果是整個叢集沒有任何 kube-controller-manager 在運作，直到修好為止。
  • 根因：第一版用 block: | 寫那三行。YAML block 純量取每行共同的最小縮排當基準並整段砍掉，三行縮排一樣深，砍完變成 0 縮排，插進 command: 底下的 list 就是語法錯誤。
  • 修法：不用 block 純量，改用單行雙引號字串加手動寫 \n。雙引號字串裡的縮排和換行逐字元照打，不會被 YAML 自動吃掉。blockinfile 以 marker 比對而不是比對內容，所以檔案當下是壞的 YAML 也沒關係，重跑同一個 task 就會換成修好的版本。
  • 怎麼確認修好：3 台 master 的 kube-controller-manager 都恢復運作。
  • 相關：Bug #17，與 #13、#22 同屬 ansible 字串處理陷阱。
enable_pod_cidr_allocation.yml（修復後，已刪除）
block: "    - --allocate-node-cidrs=true\n    - --cluster-cidr={{ cluster_pod_cidr }}\n    - --node-cidr-mask-size={{ cluster_pod_cidr_node_mask }}"
