Ansible 自動化Role: cilium

整個專案最複雜、也最多實測 bug 的一個 role。目標:部署 Cilium 當 CNI,native routing 模式,完全依賴既有的 FRR iBGP fabric 做跨節點的 pod 路由,不使用 Cilium 自己的 BGP Control Plane。這是使用者的明確要求——原文是「不要使用cilium的 bgp, 使用我們已經建好的bgp」。整體設計邏輯見 網路架構總覽,這頁專注在 這個 role怎麼做到,以及過程中撞到的幾個 bug。裝在 cilium namespace(不是官方預設的 kube-system), 而且已經取代 kube-proxy(eBPF kube-proxy replacement),兩者都是後來加上去的架構決定,見下方。

2026-08-06 更新:IPAM 模式從 kubernetes 改成 cluster-pool——使用者明確要求。每個節點的 PodCIDR 現在由 cilium-operator 自己配發,記錄在 CiliumNode 這個 CRD 的 .spec.ipam.podCIDRs, 不再依賴 kube-controller-manager 的 --allocate-node-cidrs/--cluster-cidr、也 不再有 Node.spec.podCIDR 這個欄位。原本「第一段:讓 kube-controller-manager 配發 PodCIDR」那整段(含下面的 Bug #1) 已經整段刪除(enable_pod_cidr_allocation.yml 這個檔案不存在了)——保留在這頁最下面的 歷史紀錄,原因是這是一段真實撞過、 而且教訓仍然通用的 bug(YAML block 純量的縮排陷阱),不是這個 repo 的行事風格會直接刪掉不留痕跡的那種內容。

兩段式編排,靠 ansible 的 linear strategy 保證順序

roles/cilium/tasks/main.yml
1. bastion:   用 helm 裝 Cilium(ipam.mode=cluster-pool)
2. k8s_nodes: 把每個節點實際拿到的 CIDR(CiliumNode)用 vtysh 加進本地 FRR

呼叫這個 role 的 playbook,hosts 要同時涵蓋 bastion、k8s_nodes 兩種身份(實際寫法是 hosts: k8s_nodes:bastion),兩段用 when 各自守衛。這樣寫可以依賴 ansible 預設的 linear strategy ——每個 task 都要等所有 host 做完/skip,才會進下 一個 task——保證「裝 Cilium」一定會在「vtysh 加 CIDR」之前完成, 不需要額外的 wait_for 或鎖機制。

用 helm 裝 Cilium

全部用 become: false(ubuntu 使用者身份跑, 不是 root)——kubeconfig 在 /home/ubuntu/.kube/config, helm 自己的 repo cache/state 也放在 ubuntu 的家目錄,用 root 跑會變成另一份不同的 state,之後手動用 ubuntu 身份下 helm 指令會對不起來。helm 二進位本身用 get.helm.sh 的 tarball 直接下載解壓縮(不是走 apt repo),只有「把二進位放進 /usr/local/bin」這一步才需要 become: true。

roles/cilium/tasks/install.yml(節錄)
kubernetes.core.helm:
  name: cilium
  chart_ref: cilium/cilium
  chart_version: "{{ cilium_chart_version }}"   # 1.19.6
  release_namespace: "{{ cilium_namespace }}"   # cilium,不是 kube-system
  create_namespace: true

release_namespace 明確設成 cilium (使用者明確要求,不是官方預設把 CNI 裝在 kube-system) ——這一步比 Role: istio 的 global.istioNamespace 情況單純,Cilium 的 chart 本身 沒有寫死任何 namespace 假設,只設 release_namespace 就夠了,不需要另外多帶一個變數對齊。

values.yaml 每一個設定為什麼要這樣寫

roles/cilium/templates/cilium-values.yaml.j2
routingMode: native
ipv4NativeRoutingCIDR: "172.16.0.0/16"
autoDirectNodeRoutes: false
ipam:
  mode: cluster-pool
  operator:
    clusterPoolIPv4PodCIDRList:
      - "172.16.0.0/16"
    clusterPoolIPv4MaskSize: 24
bgpControlPlane:
  enabled: false
kubeProxyReplacement: true
k8sServiceHost: "k8s-api.internal"
k8sServicePort: 6443
設定為什麼
routingMode: native 不用 VXLAN/Geneve overlay——完整理由(已經有一個能用的 BGP fabric、k8s-net 本身已經是 OpenStack 的 overlay 不想 疊兩層)見 網路架構總覽。
ipv4NativeRoutingCIDR 告訴 Cilium「這個範圍的目的地,交給底層網路(FRR)處理, 不要自己插手/masquerade」——設成整個叢集的 pod-cidr。
autoDirectNodeRoutes: false 關掉 Cilium 自己「猜」節點是不是同一個 L2 網段、自動加 直連路由的功能——k8s-net 雖然是同一個 flat subnet,但 「這個節點的 PodCIDR 該怎麼路由過去」這件事,刻意選擇交給 FRR/BGP 處理,不要 Cilium 自己插一手,兩邊互相打架。
ipam.mode: cluster-pool 使用者明確要求用 Cilium 自己的 cluster-pool IPAM——cilium-operator 自己配發每個節點的 CIDR,記錄在 CiliumNode 的 .spec.ipam.podCIDRs, 完全不依賴 kube-controller-manager。bgp_announce (下一段)直接讀這個欄位。clusterPoolIPv4PodCIDRList 的既有元素、clusterPoolIPv4MaskSize 都是套用後 就不能再改的參數(Cilium 官方文件明講),跟原本 Node.spec.podCIDR 的「叢集初始化時就固定死」 限制是同一類。
bgpControlPlane.enabled: false 明確關掉 Cilium 自己的 BGP——這是這次 導入 Cilium 最主要的架構決定,不是漏掉沒設。
kubeProxyReplacement: true 用 Cilium 的 eBPF 實作取代 kube-proxy (使用者明確要求)——不再另外裝 kube-proxy,對應的 kubeadm init 也改成 --skip-phases=addon/kube-proxy,見 Role: kubeadm。
k8sServiceHost / k8sServicePort 沒有 kube-proxy 的話,cluster 裡不存在任何東西幫 Cilium 自己把 apiserver 的 ClusterIP 轉成真正的後端位址——Cilium 在 kube-proxy-free 模式下需要一個明確、不靠 kube-proxy 就能連到的 apiserver 入口,直接沿用 apiserver_hostname(k8s-api.internal) /apiserver_port,細節見下方的第四個 bug。

helm 安裝本身用 kubernetes.core.helm 模組, wait: true + wait_timeout: 5m0s 讓 ansible 等到 helm 認定的 release 就緒才算完成這一步,之後再多加 一道 kubectl rollout status daemonset/cilium 做二次確認。

把 PodCIDR 塞進 FRR——最複雜的一個 bug

目標很單純:每個節點把自己被配發的 CIDR 讀出來( kubectl get ciliumnode {{ inventory_hostname }} -o jsonpath={.spec.ipam.podCIDRs[0]},cluster-pool 模式下這是 權威來源,不是 Node.spec.podCIDR),用 vtysh 加一個 network 陳述式到本地 FRR,讓既有 iBGP fabric 把這個 prefix 廣播出去——跟 Phase 1 用 dummy0 + network 宣告 Service VIP 是同一招(見 DSR / L4LB 歷史頁面), 只是這次要宣告的 prefix 是 Cilium 執行期間才動態決定的。

Bug:zebra 不認 Cilium 建的 route

FRR 的 network 陳述式要求「這個 prefix 在 zebra (FRR 的路由管理 daemon)自己的 RIB 裡有一筆有效(non-blackhole) 的對應 route」才會真的宣告出去。天真的假設是:Cilium native routing 模式本來就會在 kernel 裡建一筆整個節點 PodCIDR 指到 cilium_host 的 connected route,這筆 route 應該會被 zebra 自動撿到。

實測:kernel 有,但 zebra 沒有
$ ip route show 172.16.0.0/24
172.16.0.0/24 via 10.244.0.35 dev cilium_host proto kernel   ← kernel 有

$ vtysh -c "show ip route 172.16.0.0/24"
% Network not in table                                        ← zebra 沒有

試過 redistribute kernel(讓 zebra 主動吸收所有 proto kernel 的路由)也沒用,同一個結果。當時的懷疑 (目前沒有進一步深入 FRR 原始碼確認)是 zebra 對「proto kernel 但帶 via gateway」這種不是單純 connected route 的 條目有特殊處理,只有真正的 connected route(沒有 via 、只有 dev)才會被無條件納入。

修法:自己補一條 Null0 靜態路由當「憑證」

既然沒辦法讓 zebra 認得 Cilium 建的 route,就自己在 FRR 裡補一條 route 給 zebra 認——用 Null0(blackhole,不指向任何 真實介面)避免這條 route 真的影響封包轉送,同時設一個刻意偏高的 distance(FRR 的 administrative distance,數字越大 優先權越低),確保 kernel 裡如果同時存在 Cilium 的真實 route 跟 這條假 route,永遠是 Cilium 的那條贏。

實測過程:distance 255 先失敗
$ vtysh -c "configure terminal" -c "ip route 172.16.0.0/24 Null0 255" -c "end"
$ vtysh -c "show ip bgp 172.16.0.0/24"
    0.0.0.0 (inaccessible) ... invalid, sourced, local   ← 還是 invalid!

255 是 FRR 的保留值,語意是「這條路由永遠不會被 選上」——不只不會裝進 kernel FIB,連 BGP 的 network 驗證都會把它當成不存在。這是實測發現的,不是文件先讀到才避開。 改用 200(一個夠高、但不是保留值的數字)才成功:

distance 200:成功
$ vtysh -c "configure terminal" -c "ip route 172.16.0.0/24 Null0 200" -c "end"
$ vtysh -c "show ip route 172.16.0.0/24"
Routing entry for 172.16.0.0/24
  Known via "static", distance 200, metric 0, best
$ vtysh -c "show ip bgp 172.16.0.0/24"
    ... valid, sourced, local, best
  Advertised to non peer-group peers: 10.10.0.10   ← 真的被宣告出去了

關鍵的驗證是確認這條 distance 200 的假路由 沒有真的接管封包轉送:

kernel FIB 裡兩條路由同時存在,但實際查詢選中 Cilium 的那條
$ ip route show 172.16.0.0/24
172.16.0.0/24 via 10.244.0.35 dev cilium_host proto kernel    # metric 0(隱含)
blackhole 172.16.0.0/24 proto static metric 20                # 我們加的這條

$ ip route get 172.16.0.100                                     # 挑一個 PodCIDR 內的位址
172.16.0.100 dev cilium_host src 10.244.0.35                    ← 選的是 cilium_host,不是 blackhole

metric 0(Cilium 的 route)比 metric 20(我們加的 blackhole)低, 實際封包轉送查詢永遠選中前者——這條 Null0 路由的唯一作用是讓 zebra/BGP 的 network 陳述式有東西可以驗證,對真實流量 完全透明。

最終的完整 vtysh 序列

roles/cilium/tasks/bgp_announce.yml(精簡)
vtysh -c "configure terminal" \
      -c "ip route 172.16.0.0/24 Null0 200" \
      -c "end" -c "write memory"

vtysh -c "configure terminal" \
      -c "router bgp 65000" \
      -c "network 172.16.0.0/24" \
      -c "end" -c "write memory"

兩個步驟都先讀一次 show running-config,用字串比對 確認「這條設定還沒存在」才執行——冪等,重跑不會累加重複設定。

另一個間接發現的 bug:service-cidr 路由

裝 Cilium 過程中間接發現、但根因跟修法都不屬於這個 role 的 bug—— Cilium 的 init container 連 ClusterIP 逾時,根因是 hostNetwork 流量的來源位址選擇問題,完整故事見 Role: kubelet。

Bug:kube-proxy 移除後,k8sServiceHost 設成 tor 的 IP 直接讓所有 Cilium pod 掛掉

移除 kube-proxy、改成 kubeProxyReplacement: true 之後,第一版直覺地把 k8sServiceHost 設成 hostvars['tor']['fabric_ip']——邏輯上看起來合理: apiserver 的實際流量本來就是先到 tor 的 haproxy,再轉發給三台 master(見 Role: apiserver-lb), 所以「Cilium 直接連 tor 的 IP」感覺是抄了一個近路,少一次 DNS 查詢。

實測:所有 cilium pod 卡在 Init:CrashLoopBackOff
Unable to connect to the server: tls: failed to verify certificate: x509:
certificate is valid for 172.18.0.1, 10.10.0.20, 10.10.0.21, 10.10.0.22,
not 10.10.0.10

根因:kube-apiserver 憑證的 SAN(Subject Alternative Name)清單,是照 kubeadm init --control-plane-endpoint 當時傳入的字串跟 三台 master 各自的 IP 決定的——tor 的 IP 從來不在這份 清單裡,因為 tor 上的 haproxy 對 apiserver 而言完全透明 (它只是轉發 TCP,apiserver 不知道流量經過了誰)。Cilium 用 k8sServiceHost 直接發起 TLS 連線時,拿到的憑證跟它 連線用的 IP(tor 的 10.10.0.10)對不上,TLS 驗證直接失敗——這跟 Role: kubeadm 裡 kubeadm init phase upload-certs 那個 advertise address 的 bug,本質上是同一類「憑證 SAN 綁的是特定字串/IP, 任何中間節點都不能拿自己的位址頂替」的教訓,只是這次撞在 Cilium 這一側。

修法是把 k8sServiceHost 改成 apiserver_hostname(k8s-api.internal)這個 hostname,不是任何 IP——這也是當初 kubeadm init --control-plane-endpoint 傳入的同一個 字串,SAN 清單本來就包含它。改完之後所有 cilium pod 立刻從 Init:CrashLoopBackOff 變成 1/1 Running。 另外實測確認 hostNetwork 模式的 pod(Cilium 的 agent 就是)可以 正確透過節點自己的 /etc/hosts(apiserver_dns role 寫入的)解析這個 hostname,不需要另外處理 pod 專屬的 DNS/hosts 設定。

歷史紀錄:ipam.mode=kubernetes 時期的第一段(已淘汰)

2026-08-06 之前,PodCIDR 配發走的是 ipam.mode=kubernetes,權威來源是 Node.spec.podCIDR,要靠這裡記錄的這一段先讓 kube-controller-manager 願意配發。改成 cluster-pool 之後這整段已經不存在(roles/cilium/tasks/enable_pod_cidr_allocation.yml 已刪除,roles/cilium/tasks/main.yml 也不再呼叫它), 留在這裡純粹是因為撞到的 YAML 陷阱教訓通用,值得保留。

kubeadm init 當時故意沒帶 --pod-network-cidr (見 Role: kubeadm),所以 kube-controller-manager 沒有 --allocate-node-cidrs, 沒有任何 Node 物件會有 .spec.podCIDR——但當時 ipam.mode=kubernetes 需要這個欄位才能運作。這一段 直接編輯 kube-controller-manager 的 static pod manifest,補上兩個 flag。

/etc/kubernetes/manifests/kube-controller-manager.yaml(補上的部分)
    - --allocate-node-cidrs=true
    - --cluster-cidr=172.16.0.0/16
    - --node-cidr-mask-size=24

Bug:YAML block 純量把 3 台 master 的 manifest 全部搞壞 ——第一版用 block: |(YAML block 純量)寫這三行,結果 YAML 的縮排規則是「取每行共同的最小縮排當基準,整段砍掉」:三行 源碼縮排一樣深,砍完全部變成 0 縮排,插進這個 YAML list (command: 底下)裡直接是語法錯誤。結果是 3 台 master 的 kube-controller-manager 同時壞掉 ——kubelet 的錯誤訊息是 couldn't parse as pod(yaml: line 28: did not find expected key), 這台機器的 kube-controller-manager 直接從叢集裡消失(kubelet 判斷 manifest 無效,不會保留舊的容器)。因為 leader election 機制,這代表 整個叢集沒有任何一個 kube-controller-manager 在運作 ,一直到修好為止。

修法是不用 YAML block 純量,改用單行雙引號字串 + 手動寫 \n:

enable_pod_cidr_allocation.yml(修復後,已刪除)
block: "    - --allocate-node-cidrs=true\n    - --cluster-cidr={{ cluster_pod_cidr }}\n    - --node-cidr-mask-size={{ cluster_pod_cidr_node_mask }}"

雙引號字串裡的縮排跟換行是逐字元照打,不會被 YAML 自動吃掉—— 這是能可靠控制輸出縮排的寫法。blockinfile 本身用 marker 比對(不是比對內容),所以就算檔案當下是壞的 YAML 也沒關係, 它純粹是逐行文字操作,重新執行同一個 task,marker 之間的內容就會被換成修好的版本。

補完 flag 之後,還需要主動等待 kube-controller-manager 真的重啟(kubelet 的 static pod 檔案監控有輪詢間隔,不是立即生效)、 而且真的完成配發:

enable_pod_cidr_allocation.yml(已刪除)
- command: kubectl get nodes -o jsonpath={.items[*].spec.podCIDR}
  delegate_to: bastion
  until: node_pod_cidrs.stdout.split() | length == groups['k8s_nodes'] | length
  retries: 30
  delay: 10
  run_once: true

用 until 輪詢直到 7 個節點都拿到 podCIDR ——這是當時唯一一個「主動等結果」而不是假設立即生效的地方,因為 這是唯一一個依賴另一個 controller(kube-controller-manager)非同步 反應的步驟。cluster-pool 模式下不再需要這一段等待——cilium-operator 自己配發 CiliumNode 的速度不依賴 kube-controller-manager 的 static pod 重啟週期。
