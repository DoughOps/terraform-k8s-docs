總覽全部拆除

這頁是 從零開始建置 的反向操作——把那頁建出來的 東西全部清乾淨,退回到「什麼都沒有」的狀態。跟建置一樣分成兩個獨立的 Terraform state(openstack/、cloudflare/),拆的時候也是兩個獨立的 terraform destroy,順序不像建置那樣嚴格,但有些東西不屬於任何一份 state 管理,得手動清。

這是不可逆操作。 terraform destroy 會刪掉 VM、網路、 floating IP——沒有另外的備份機制,銷毀前自己決定要不要留一份。這個 lab 本身沒有 生產資料,但如果你在上面跑了自己的東西,這是最後提醒。

bastion 的兩顆資料碟(nfs-data 50GB、user-data 80GB)預設不會被 terraform destroy 刪掉—— openstack/main.tf 的 openstack_blockstorage_volume_v3.data_volumes 設了 lifecycle.prevent_destroy = true。nfs-data 撐著 docs-site(這份文件站)以及任何掛在 nfs-csi 這個 StorageClass 上的 PVC,值得特別保護。但這也代表一般的 terraform destroy 現在會直接卡在這兩個 resource 報錯,不會 默默略過——這是刻意的行為,細節跟操作步驟見下面 Step 2。

你要拆的是哪一種?

先想清楚要拆到哪一層,免得拆多了要重新走一次 Step 5~7(手動、綁 GitHub OAuth 授權,最麻煩)。

🔄

只是叢集裝壞了,VM 還能留

不要用這頁。改用 playbooks/kubeadm-reset.yml(見 框架設計)——只清 kubeadm/CNI/FRR 狀態, VM、網路、Cloudflare 全部不動,重跑 k8s/kubeadm.yml → k8s/cilium.yml 就好。改 --service-cidr/ --pod-network-cidr 這種叢集初始化時就固定死的參數才需要這個。

🖥️

VM 全部砍掉,Cloudflare 側留著

只做下面 Step 2(openstack/ 那份 terraform destroy)。 之後想重建,直接跳回 從零開始建置 Step 3~4, Step 5~9 全部不用重做——secrets.yml/main.yml 裡的 Cloudflare 值都還有效。

🧨

整個 lab 收掉,什麼都不留

下面 Step 2~6 從頭做到尾——兩份 terraform destroy、手動清 Cloudflare 側不受 Terraform 管的殘留、決定要不要連本機的 vault/密鑰一起清掉。

Step 1 · 建議的順序(不是硬性依賴)

兩份 state 之間沒有 Terraform 層級的相依(不同 provider,互不引用對方的 resource),理論上先拆哪個都不會報錯。這裡建議先拆 OpenStack、 再拆 Cloudflare:

  1. 先拆 OpenStack(Step 2) VM 消失的同時,跑在 worker 節點上的 cloudflared pod(cluster 內的 tunnel connector)自然跟著消失,Cloudflare 那邊的 tunnel 會顯示「down」,但 不會報錯或卡住——這只是 Cloudflare dashboard 上的狀態顯示,不影響後續清理。
  2. 再拆 Cloudflare(Step 4) 這時候 tunnel 已經沒有活的 connector,刪除 tunnel/DNS/Access 這些 resource 乾淨俐落,不會有「正在使用中」之類的 API 錯誤。

反過來做(先拆 Cloudflare)也可以——差別只是拆完 Cloudflare 之後、還沒拆 OpenStack 之前的這段時間,cluster 內的 cloudflared pod 會一直重連 一個已經不存在的 tunnel,瘋狂 log 錯誤但不影響拆除本身。

Step 2 · 拆 OpenStack 資源

先記下兩顆資料碟目前的 volume ID——不管接下來要保留還是要一起砍掉,都用得到:

openstack/ 目錄
$ cd openstack
$ terraform output data_volume_ids
{
  "bastion__nfs-data" = "33d1c1fa-9f01-40c8-995c-3fae2ddacabc"
  "bastion__user-data" = "51593b7d-6c0d-4a53-8330-c42dcf8001e0"
}

情境 A(建議):保留這兩顆資料碟

先把它們踢出 state(不會呼叫 OpenStack API,volume 本身完全 不受影響,只是 Terraform 不再管它),destroy 才不會被 prevent_destroy 卡住:

openstack/ 目錄
$ terraform state rm \
  'openstack_blockstorage_volume_v3.data_volumes["bastion__nfs-data"]' \
  'openstack_blockstorage_volume_v3.data_volumes["bastion__user-data"]'
$ terraform plan -destroy
# 確認清單裡已經沒有這兩顆 volume,再確認沒有搞錯環境(尤其如果你手上不只一份 clouds.yaml)
$ terraform destroy

會刪掉:9 台 VM(tor/bastion/ms-*/ l4-*/ap-*)、k8s-net/mgmt-net 兩個網路跟對應的 subnet/router、security group、bastion 的 floating IP、 k8s 這個 keypair。.ssh/id_ed25519.pub 本身是本機檔案,不會被刪,但它註冊進 OpenStack 的那份 keypair 會消失—— 之後重新 terraform apply 會用同一份 .pub 重新註冊 同名 keypair,不用重新產生金鑰。兩顆資料碟這時候還在 OpenStack 裡,只是 處於「沒有 instance 掛著、沒有 Terraform 管」的狀態,不會產生額外費用以外 的問題。

之後要重建、想接回同一顆(不是建一顆空白的新 volume)才需要 先 import,再 apply:

重建時,apply 之前先做
$ terraform import 'openstack_blockstorage_volume_v3.data_volumes["bastion__nfs-data"]' 33d1c1fa-9f01-40c8-995c-3fae2ddacabc
$ terraform import 'openstack_blockstorage_volume_v3.data_volumes["bastion__user-data"]' 51593b7d-6c0d-4a53-8330-c42dcf8001e0
$ terraform apply

(上面兩個 ID 換成你自己 Step 2 開頭記下來的值)——這只有「兩份 destroy 之間真的隔了一段時間、volume 已經不在 state 裡」才需要;如果只是單純 VM 被 replace(state 裡的 volume resource沒被動過),不用做這一步,見 從零開始建置「VM 全部重建」那張卡片。

情境 B:連這兩顆資料碟也要一起砍掉

prevent_destroy 會擋掉一般的 terraform destroy, 故意設計成不能「不小心」刪掉——真的要刪,先在 openstack/main.tf 把 openstack_blockstorage_volume_v3.data_volumes 的 lifecycle { prevent_destroy = true } 那段拿掉(或改成 false),再跑一次 terraform destroy。這是刻意 要求「多一個手動步驟」才能刪除——避免下指令的手滑跟「這本來就該被 terraform destroy 清掉」的預期落差,同時造成真的資料遺失。

Step 3 · 拆完 OpenStack 之後,順手清一下 Ansible 端的殘留

這些檔案在下次建置時都會被覆蓋/重新產生,留著也不影響下次 terraform apply,但如果你要交接或封存這個 checkout,清掉比較乾淨:

檔案怎麼處理
ansible/inventory/hosts.ini不用手動清——scripts/ansible.sh 每次執行都會重新產生,已經被 .gitignore 排除。
ansible/inventory/group_vars/all/vault.yml不要刪,除非你要換一把全新的 SSH key。這是全部節點共用私鑰的唯一加密來源,VM 沒了不代表這把 key 失效——下次 terraform apply 出來的新 VM 一樣會信任它。

Step 4 · 拆 Cloudflare 資源

cloudflare/ 目錄
$ export CLOUDFLARE_API_TOKEN="<跟 Step 6 建置時同一組 token>"
$ cd cloudflare
$ terraform plan -destroy
$ terraform destroy

會刪掉:2 條 Cloudflare Tunnel(openstack-k8s、bastion-ssh) 跟對應的 config、2 條 DNS 記錄(萬用字元 + ssh.<你的網域>)、 3 組 Access Application/Policy(wildcard、bastion-ssh、grafana-sso)、 api_token.tf 自動建出來的那個 scoped cloudflare_origin_ca_api_token。

cloudflare_zero_trust_organization 這個 resource 可能會卡住或報錯,是預期狀況。 Zero Trust org 設定是帳號層級的單例(整個 Cloudflare 帳號永遠只有一份), 底層 API 對它沒有真正的「刪除」語意,見 organization.tf 開頭的 註解。如果 destroy 卡在這一個 resource,其他 resource 通常已經 刪除完成、只剩它卡著——重新跑一次 terraform destroy 通常會 再試一次同一個 resource;如果一直失敗,可以用 terraform state rm cloudflare_zero_trust_organization.this 直接把它從 state 裡拿掉(不會真的呼叫 API 刪除,只是讓 Terraform 不再 管它),帳號層級的 org 設定值留著不影響其他資源,也不會產生任何額外 費用或殘留資源。

Step 5 · 不受任何一份 Terraform state 管理的殘留(要不要清,自己決定)

這幾件事是 從零開始建置 Step 5~6 手動做的 「一次性 bootstrap」,兩份 terraform destroy 都不會動它們:

項目要清的話怎麼做建議
網域接進 Cloudflare 這個 zone回註冊商那邊把 nameserver 改回去,再到 Cloudflare dashboard 移除這個 zone。通常不用清——留著不影響任何東西,也不用額外付費,下次重建直接接著用。
Zero Trust 的 GitHub Identity ProviderZero Trust dashboard → Settings → Authentication → 刪除對應的 GitHub 登入方式。不用清,除非要換一個完全不同的 GitHub org 當身份來源——留著的話下次重建直接沿用同一組 github_idp_id。
Step 6 手動建的 CLOUDFLARE_API_TOKENCloudflare dashboard → My Profile → API Tokens → 找到那顆 token → Revoke。如果真的要收掉整個 lab、不打算再用這個帳號,建議撤銷——這顆 token 權限涵蓋整個帳號的 Access/Tunnel 設定。
Step 7 建的 GitHub App(github_app_id 等)GitHub org → Settings → Developer settings → GitHub Apps → 刪除對應的 App。只有 roles/github_runner 在用,跟 Cloudflare/OpenStack 完全無關,通常留著沒有壞處。

Step 6 · (可選)徹底清空本機 state 跟密鑰

如果 Step 2~5 已經把雲端資源都清乾淨,但你還想讓本機 checkout 回到 「完全沒建置過」的狀態(例如要整個資料夾砍掉,或要把這把 SSH key 永久停用), 才需要做這一步——一般情況下建議跳過,留著這些檔案不影響任何 雲端資源,下次要重建也不用重新走一次 Step 1~2 的 keypair 產生流程。

檔案 / 目錄內容清掉的影響
openstack/terraform.tfstate*
openstack/.terraform/		Terraform state + provider plugin cacheState 已經清空(destroy 完是空的),刪掉檔案本身無害;下次要用得重新 terraform init。
cloudflare/terraform.tfstate*
cloudflare/.terraform/		同上,Cloudflare 那份同上。
ansible/inventory/group_vars/all/secrets.ymlStep 7 填進去的 Cloudflare token/secret,destroy 完這些值已經失效不進版控,刪掉不影響任何東西,下次重建照 Step 7 從範本重填就好。
ansible/inventory/group_vars/all/vault.yml
.ssh/id_ed25519.pub
.env		這把 lab 唯一共用 SSH key 的加密來源、公鑰、解密密碼刪掉代表徹底放棄這把 key——下次建置要整套重新走 從零開始建置 Step 2 的 ssh-keygen/make key-encrypt。沒有備份的話這個動作不可逆。

Step 7 · 驗證真的清空了

  • OpenStack:Horizon dashboard 或 CLI(openstack server list/ openstack network list)確認沒有任何 tor/bastion/ms-*/l4-*/ ap-*、k8s-net/mgmt-net 殘留—— terraform destroy 的 exit code 是 0 不代表每個 resource 都真的被雲端確認刪除,值得肉眼再核對一次。openstack volume list 如果選了情境 A,應該還看得到 bastion-nfs-data/ bastion-user-data——這是預期的,不是殘留;選情境 B 的話才 應該完全消失。
  • Cloudflare:Zero Trust dashboard → Networks → Tunnels 確認 2 條 tunnel 都不見了;Access → Applications 確認 3 個 Application 都不見了; DNS 頁面確認萬用字元跟 ssh. 那條記錄都不見了。

之後想重建? 兩份 terraform destroy 都做完 (Step 2、Step 4)、但保留 Step 6 那些本機檔案的話,直接回 從零開始建置 Step 3(檢查 terraform.tfvars)重新 terraform apply 就好, Step 1~2、Step 5~7 全部不用重做。如果情境 A 保留了那兩顆資料碟,記得 apply 之前先照 Step 2 的說明把它們 import 回來,不然會生出兩顆空白的新 volume。如果連 Step 6 都清了,才需要從 Step 1 整套重來。
