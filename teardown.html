開始 全部拆除

這頁是從零開始建置的反向操作：先判斷你要拆到哪一層，再照對應步驟清掉雲端資源與本機殘留。環境由兩份獨立的 Terraform state（openstack/ 與 cloudflare/）加上幾個不屬於任何 state 的手動項目組成，所以拆除也分成幾段。完整拆除約需 15 到 30 分鐘，時間為估計值。

這是不可逆操作。terraform destroy 會刪掉 VM、網路與 Floating IP，沒有備份機制。如果你在上面跑了自己的東西，銷毀前先決定要不要保留。

bastion 的兩顆資料碟（nfs-data、user-data）預設不會被刪。openstack/main.tf 的 openstack_blockstorage_volume_v3.data_volumes 設了 lifecycle.prevent_destroy = true。nfs-data 撐著 docs-site 與所有掛在 nfs-csi StorageClass 的 PVC，user-data 放 Vault、Keycloak、GitLab 的資料。所以一般的 terraform destroy 會直接停在這兩個 resource 並報錯，需要照下面的 Step 1 處理。保護機制的設計見資料碟與 prevent_destroy。

你要拆的是哪一種？

先想清楚要拆到哪一層，免得拆多了，要重新走一遍建置裡手動又綁 OAuth 授權的步驟。

🔄

叢集裝壞了，VM 還能留

不要用這頁。改用 playbooks/kubeadm-reset.yml（見 Ansible 框架設計），只清 kubeadm、CNI、FRR 的狀態，VM、網路、Cloudflare 都不動。接著重跑 k8s/kubeadm.yml 與 k8s/cilium.yml。改 --service-cidr、--pod-network-cidr 這種初始化時固定的參數才需要它。

🖥️

VM 全部砍掉，Cloudflare 留著

只做 Step 1 和 Step 2。之後重建從建置的 Step 2 開始，建置的 Step 4 與 Step 5 不必重做，因為 secrets.yml 與 main.yml 裡的 Cloudflare 值仍然有效。

🧨

整個 lab 收掉，什麼都不留

Step 1 到 Step 6 從頭做到尾：兩份 terraform destroy，手動清 Cloudflare 側不受 Terraform 管理的殘留，再決定要不要連本機的 vault 密碼與密鑰一起清掉。

如果你用 GitLab CD repo 的 pipeline 操作，不必手動下 Terraform 指令。下表對照兩種做法，pipeline 的 EXECUTION 變數說明見 Role: gitlab。

想做什麼手動GitLab CD 的 EXECUTION
清掉叢集狀態，機器保留並重開機kubeadm-reset.yml，另外自行清 kubeconfigdecommission，使用 playbooks/decommission.yml，不碰 Terraform
砍掉 tor 與 bastion 以外的所有 VM本頁 Step 1，但會連 tor 與 bastion 一起拆destroy_vm，用 -target 排除 tor 與 bastion，清單執行時動態計算
把砍掉的 VM 建回來並重裝叢集建置的 Step 3、Step 6 到 Step 9create_cluster，等同 make build 的範圍
不改動任何東西，只檢查terraform plan 加 smoke testverify

EXECUTION 的三個 Terraform 值需要 secrets.yml 中的 CI 專用 OpenStack 與 S3 憑證，設定見建置的 Step 5。

拆除順序

兩份 state 之間沒有 Terraform 層級的相依：它們用不同的 provider，互不引用對方的 resource，先拆哪個都不會報錯。建議先拆 OpenStack，再拆 Cloudflare。

  1. 先拆 OpenStack：VM 消失時，跑在 worker 上的 cloudflared pod 也跟著消失。Cloudflare dashboard 上的 tunnel 會顯示 down，但不影響後續清理。
  2. 再拆 Cloudflare：這時 tunnel 已經沒有活的 connector，刪除 tunnel、DNS、Access 都不會遇到「正在使用中」的 API 錯誤。

反過來做也可以。差別只是兩次拆除之間，叢集內的 cloudflared 會一直重連已不存在的 tunnel，log 很吵，但不影響拆除。

兩份 state 都在 S3 相容的 backend，不在本機。下面所有手動下的 terraform 指令，都要先匯出 AWS_ACCESS_KEY_ID 與 AWS_SECRET_ACCESS_KEY（值和 .env 相同），拆 Cloudflare 時還要 CLOUDFLARE_API_TOKEN。可以在 repo 根目錄用 set -a; . ./.env; set +a 一次匯出。make teardown 會自己讀 .env，不必手動匯出。

Step 1 · 拆 OpenStack 資源

先記下兩顆資料碟目前的 volume ID。不論保留或一起刪除，後面都會用到。

openstack/ 目錄
$ cd openstack
$ terraform output data_volume_ids
{
  "bastion__nfs-data" = "33d1c1fa-9f01-40c8-995c-3fae2ddacabc"
  "bastion__user-data" = "51593b7d-6c0d-4a53-8330-c42dcf8001e0"
}

預期結果：印出兩個 volume ID（上面是範例值）。失敗時看哪裡：data_volume_ids 這個 output 要 apply 過一次才會寫進 state。拿不到時，改用 terraform show -json 讀 state，scripts/teardown.sh 就是這樣做的。

情境 A：保留兩顆資料碟（建議）

先把它們踢出 state。這個動作不會呼叫 OpenStack API，volume 本身完全不受影響，只是 Terraform 不再管它，destroy 才不會被 prevent_destroy 擋住。

openstack/ 目錄
$ terraform state rm \
  'openstack_blockstorage_volume_v3.data_volumes["bastion__nfs-data"]' \
  'openstack_blockstorage_volume_v3.data_volumes["bastion__user-data"]'
$ terraform plan -destroy
# 確認清單裡已經沒有這兩顆 volume，再確認沒有搞錯環境（尤其如果你手上不只一份 clouds.yaml）
$ terraform destroy

預期結果：terraform destroy 要你輸入 yes，之後依序刪除下列資源。

  • 10 台 VM：tor、bastion、ms-*、l4-*、ap-*。
  • k8s-net 與 mgmt-net，以及對應的 subnet 與 router。
  • security group、bastion 的 Floating IP、k8s keypair。

本機的公鑰檔案不會被刪。OpenStack 裡註冊的那份 keypair 會消失，下次 terraform apply 會用同一份公鑰重新註冊同名 keypair，不必重新產生金鑰。兩顆資料碟仍在 OpenStack 裡，處於沒有 instance 掛載、沒有 Terraform 管理的狀態。

失敗時看哪裡：報 prevent_destroy 代表 state rm 沒做成功，重新確認位址字串的引號。卡在其他資源時重跑一次 terraform destroy。

之後重建想接回同一顆資料碟，而不是建出空白的新 volume，要在 apply 之前先 import：

重建時，apply 之前先做
$ terraform import 'openstack_blockstorage_volume_v3.data_volumes["bastion__nfs-data"]' 33d1c1fa-9f01-40c8-995c-3fae2ddacabc
$ terraform import 'openstack_blockstorage_volume_v3.data_volumes["bastion__user-data"]' 51593b7d-6c0d-4a53-8330-c42dcf8001e0
$ terraform apply

ID 換成你自己記下的值。只有兩次操作之間 volume 已不在 state 時才需要 import。如果只是 VM 被 replace、state 裡的 volume resource 沒被動過，就不用。預期結果：apply 的 plan 裡沒有新建 volume 的項目。

情境 B：連資料碟一起刪除

prevent_destroy 故意讓一般的 terraform destroy 無法刪除資料碟，防止手滑造成資料遺失。真的要刪，先在 openstack/main.tf 把 openstack_blockstorage_volume_v3.data_volumes 的 lifecycle { prevent_destroy = true } 拿掉或改成 false，再跑 terraform destroy。Vault、Keycloak、GitLab 的資料也會一併消失，之後重建要重新 init。make teardown 不支援這條路徑。

Step 2 · 清 Ansible 端的殘留

下面這些檔案在下次建置時會被覆蓋或重新產生，留著不影響下次 terraform apply。要交接或封存這個 checkout 時，清掉比較乾淨。

檔案怎麼處理
ansible/inventory/hosts.ini不必手動清。scripts/ansible.sh 每次執行都會重新產生。
.ssh/repo 根目錄下解密私鑰的快取，內容是明碼私鑰。可以直接刪除，下次執行 scripts/ansible.sh 會重新解密。
ansible/files/ssh/id_ed25519除非要換一把全新的 SSH key，否則不要刪。這是全部節點共用私鑰的唯一加密來源，VM 沒了不代表 key 失效，下次建出的新 VM 一樣信任它。

預期結果：.ssh/ 目錄不存在。失敗時看哪裡：下次執行 scripts/ansible.sh 時解密失敗，檢查 .env 的 ANSIBLE_VAULT_PASSWORD，見密鑰管理。

Step 3 · 拆 Cloudflare 資源

cloudflare/ 目錄
$ set -a; . ../.env; set +a
$ cd cloudflare
$ terraform plan -destroy
$ terraform destroy

預期結果：terraform destroy 要你輸入 yes，之後刪除下列資源。完整清單以 terraform plan -destroy 的輸出為準。

  • 2 條 Cloudflare Tunnel：openstack-k8s 與 bastion-ssh，連同各自的 config。
  • 5 條 DNS 記錄：萬用字元、ssh、vault、keycloak、gitlab。
  • 全部 Access Application 與 Policy。
  • api_token.tf 建出的 scoped cloudflare_origin_ca_api_token。

cloudflare_zero_trust_organization 卡住或報錯是預期狀況。Zero Trust org 設定是帳號層級的單例，整個 Cloudflare 帳號只有一份，底層 API 沒有真正的刪除語意，見 organization.tf 開頭的註解。destroy 停在這個 resource 時，其他 resource 通常已刪完。

重跑一次 terraform destroy 通常會再試一次。持續失敗就用 terraform state rm cloudflare_zero_trust_organization.this 把它從 state 拿掉。這不會呼叫 API 刪除，帳號層級的 org 設定留著不影響其他資源，也不產生費用。

失敗時看哪裡：認證錯誤先確認 CLOUDFLARE_API_TOKEN 與 S3 憑證都已匯出。

Step 4 · 不受 state 管理的殘留

下面是建置前置項目裡手動完成的一次性設定，兩份 terraform destroy 都不會動它們。要不要清，由你決定。

項目要清的話怎麼做建議
網域接進 Cloudflare 的 zone回註冊商把 nameserver 改回去，再到 Cloudflare dashboard 移除 zone。通常不用清。留著不影響任何東西，也不用額外付費，下次重建直接沿用。
Zero Trust 的 GitHub Identity ProviderZero Trust dashboard → Settings → Authentication → 刪除 GitHub 登入方式。不用清，除非要換成完全不同的 GitHub org。留著的話下次沿用同一個 github_idp_id。
CLOUDFLARE_API_TOKENCloudflare dashboard → My Profile → API Tokens → Revoke。如果整個 lab 收掉、不再使用這個帳號，建議撤銷。這顆 token 的權限涵蓋整個帳號的 Access 與 Tunnel 設定。
GitHub AppGitHub org → Settings → Developer settings → GitHub Apps → 刪除。只有 github_runner role 在使用，與 Cloudflare、OpenStack 無關，留著通常沒有壞處。
GitHub fine-grained PAT 與 GitLab access tokenGitHub 與 GitLab 的 token 管理頁面分別撤銷。GitLab 資料若隨資料碟刪除，它的 token 已失效。GitHub PAT 有到期日，也可以提前撤銷。
Keystone 簽發的 S3 憑證用 Keystone 的 credentials API 刪除該組 EC2 credential。整個 lab 收掉且不再使用 state bucket 時才需要。

Step 5 · 清本機 state 與密鑰（可選）

Step 1 到 Step 4 已經把雲端資源清乾淨，但你還想讓本機 checkout 回到沒建置過的狀態，例如要整個資料夾刪掉，或永久停用這把 SSH key，才需要這一步。一般建議跳過：留著這些檔案不影響任何雲端資源，下次重建也不必重新產生 key。

檔案或目錄內容清掉的影響
openstack/.terraform/
cloudflare/.terraform/		provider plugin 與 backend 設定的本機快取無害。下次要用得重新 terraform init。state 本身在 S3，不在這裡。
openstack/.data-volume-ids.jsonmake teardown 暫存的資料碟 volume ID刪掉後，make build 不會自動接回同一顆資料碟，需要手動 import。
ansible/inventory/group_vars/all/secrets.yml各服務的 token 與 secret。整檔 ansible-vault 加密並進版控destroy 之後 Cloudflare 的值已失效。可保留密文，或換回範本重填。重建時流程見建置的 Step 5。
ansible/files/ssh/id_ed25519
ansible/files/ssh/id_ed25519.pub
.env		共用 SSH key 的加密私鑰、公鑰，以及 vault 密碼與雲端憑證刪掉代表放棄這把 key。下次建置要整套重走建置的 Step 1。沒有備份的話不可逆，而且沒有 .env 的密碼就解不開任何加密檔。

預期結果：所列檔案不存在。這一步沒有指令可以驗證，直接 ls 確認。

Step 6 · 驗證真的清空了

  • OpenStack：用 Horizon 或 CLI 確認沒有 tor、bastion、ms-*、l4-*、ap-*，也沒有 k8s-net 與 mgmt-net。CLI 可用 openstack server list 與 openstack network list。terraform destroy 回傳 0 不代表每個資源都已被雲端確認刪除，值得肉眼再核對。openstack volume list 在情境 A 應該還看得到 bastion-nfs-data 與 bastion-user-data，這是預期的保留結果。情境 B 才應該完全消失。
  • Cloudflare：Zero Trust dashboard → Networks → Tunnels 確認 2 條 tunnel 都不見了。Access → Applications 確認 Application 都不見了。DNS 頁面確認萬用字元與 ssh 等記錄都不見了。

失敗時看哪裡：有殘留的資源，回到對應 state 目錄重跑 terraform plan -destroy 看是否還在管理，或到 dashboard 手動刪除。

一鍵拆除

make teardown 把情境 A 串成一條指令，也是這支腳本唯一支援的路徑。

repo 根目錄
$ make teardown

它依序做：記下兩顆資料碟的 ID 並存到 openstack/.data-volume-ids.json，把它們從 state 移除，terraform destroy OpenStack，再 terraform destroy Cloudflare。兩次 destroy 都不帶 -auto-approve，仍要輸入 yes。預期結果：結尾印出完成訊息，並提醒 cloudflare_zero_trust_organization 卡住是預期行為。

失敗時看哪裡：找不到 .env 的 CLOUDFLARE_API_TOKEN 時，腳本在 OpenStack 拆完之後停止，補上 token 重跑即可，OpenStack 那段會偵測到資料碟已不在 state 而略過。這條路徑只保留資料碟，Step 4、Step 5 仍要自己判斷。

拆完之後想重建

  • 只拆了 OpenStack：從建置的 Step 2 檢查 terraform.tfvars，接著 terraform apply。情境 A 保留了資料碟的話，apply 之前先照上面的說明 import，否則會建出兩顆空白的新 volume。make build 會自動處理。
  • OpenStack 與 Cloudflare 都拆了：另外要重做建置的 Step 4 與 Step 5，Cloudflare 側所有 token 與 client secret 都會是新的。
  • 連本機密鑰也清了：從建置的 Step 1 整套重來。
  • 資料碟保留時：Vault、Keycloak、GitLab 的資料還在，新的 bastion 重新掛上後會接回既有資料。Vault 只需要 unseal，不必重新 init，見 Role: vault。
