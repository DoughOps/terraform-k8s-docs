平台服務 Role: gitlab

這頁說明 bastion 上自架的 GitLab CE（roles/gitlab_server）、instance-wide 的 GitLab Runner（roles/gitlab_runner），以及放在 GitLab 上的 CD repo（roles/gitlab_cd_repo）。它們與 Role: vault、Role: keycloak / dex 一樣跑在 bastion 上，不是叢集內的 workload，資料放在持久化的 /userap，bastion 重建後自動復原。CD repo 的 EXECUTION 選項包含 destroy_vm，使用前請先讀已知限制。

為什麼用 container，不用 Helm chart

決策：GitLab 以單一 gitlab/gitlab-ce omnibus container 跑在 bastion，與 Kubernetes 無關。

理由：GitLab 提供 Helm chart、Operator、omnibus 套件與 Docker container 幾種安裝模式。這裡的 GitLab 是平台服務的上游：ArgoCD 從它 pull manifests，CD repo 也在它上面。放在叢集內，叢集重建時它會跟著消失。放在 bastion 並把資料放在持久化 volume，叢集重建不影響它。omnibus image 自帶所有元件，不需要額外管理資料庫。

考慮過的替代方案：Helm chart 部署到叢集 — 叢集重建時要連資料一起還原，且 GitLab 不可用時 ArgoCD 與 CD repo 也失去來源。omnibus 套件直接裝在 host — 相依套件與 bastion 其他服務混在一起，升級與回復較難。

代價：GitLab 與 Keycloak、Vault、NFS server 共用 bastion 的資源與信任邊界，所以要調低資源設定。bastion 掛掉時 GitLab 也不可用。

登入設計

gitlab.dough-ops.com 先過既有的萬用字元 Cloudflare Access Application。只有 doughops GitHub org 成員放行，與 dashboard、grafana、vault 同一層。第二層是 GitLab 自己的 OmniAuth OIDC，對應 Cloudflare 另一個 Access for SaaS Application gitlab-sso。兩層互相疊加，與 Vault 的 OIDC 登入是同一種模式。

關鍵設定是 omniauth_auto_sign_in_with_provider。沒有這行，OmniAuth 只是在 GitLab 登入頁多一顆「Sign in with OIDC」按鈕，還要手動點。設了之後，瀏覽器一開 gitlab.dough-ops.com，GitLab 就跳過自己的登入頁，立刻重導向 OIDC provider。外層 Access 通常已有有效 session，整段重導無感，直接落地在 GitLab 首頁。

OIDC 設定走 discovery：只給 issuer 並設 discovery: true，由 omniauth-openid-connect 自己抓 authorization、token 與 jwks 端點。uid_field 是 email，這個 email 同時是 oidc_admin_emails allowlist 比對的依據，名單內的帳號會被設成 GitLab Admin，名單外是一般使用者。

Break-glass 登入

上面的設定會讓 /users/sign_in 直接被導去 OIDC provider，密碼表單不會渲染。GitLab 官方文件記載的 escape hatch 是加 query string：

break-glass 登入網址
https://gitlab.dough-ops.com/users/sign_in?auto_sign_in=false

這個網址跳過的只是 GitLab 自己的自動導向，仍在同一個萬用字元 Access Application 底下，要先過 Cloudflare 的 GitHub org 登入。它適用於 gitlab-sso 這個 OIDC app 本身設定壞掉的情況，救不了 Cloudflare 整層失效。登入帳號是 root，密碼是 secrets.yml 的 gitlab_root_password。

Git 與 API 存取的 bypass

git clone 與以 PAT 呼叫的 API 無法走完 Cloudflare Access 的互動式 GitHub org 登入，萬用字元 Application 會把它們擋在外面。SSH 與 HTTPS 的 clone 都受影響，所以 HTTPS 這條路在 bypass 之前打不通。

做法與 keycloak_direct 相同，見 Role: keycloak / dex。另開一個 path-scoped 的 bypass Application gitlab-direct，只涵蓋 Git over HTTPS 與 REST API 這兩類流量，decision = "bypass"。精確的路徑規則在 cloudflare/access.tf，Access 規則的整體原則見 Cloudflare 設定清單 § Access 規則。其他一般瀏覽頁面不受影響，仍要先過萬用字元 Access。

代價是這兩類流量只剩 GitLab 自己的 PAT 與 HTTP Basic 驗證，不再額外要求通過 GitHub org。TLS 仍由 Cloudflare 終止。

自動化 PAT 的來源

決策：自動化 PAT 的值只存在於加密的 secrets.yml（gitlab_automation_pat），bastion 磁碟上不留任何副本。

理由：GitLab 不會回吐已存在 token 的明碼，所以這組值由誰選都沒有差別。與其讓 bastion 用 openssl rand 產生再存檔，不如在本機用 openssl rand -hex 32 選一次寫進 secrets.yml。這樣要知道或輪替這組值，不需要先 SSH 進 bastion 找檔案；換掉 secrets.yml 裡的值、重跑 playbook，GitLab 那邊就自動同步。

考慮過的替代方案：在 bastion 上產生並存成 /userap/gitlab/secrets/automation-pat（比照 roles/keycloak_server）— 可以運作，但密鑰變成一份只有登入 bastion 才看得到的狀態，難以維護與輪替。

代價：值由人選，強度取決於當時的選擇。這個原則無法套用到所有密鑰，例如 Vault 的 root token 與 unseal key 由 vault operator init 產生，無法預先決定。

實作上，bootstrap_pat.rb 以 Rails console 把 secrets.yml 的值設成 token，每次都無條件 upsert，不是找不到才建：

roles/gitlab_server/templates/bootstrap_pat.rb.j2
user = User.find_by_username('root')
token = user.personal_access_tokens.find_by(name: 'ansible-automation')
token ||= user.personal_access_tokens.create(
  name: 'ansible-automation',
  scopes: [:api],
  expires_at: 365.days.from_now
)
token.set_token('{{ gitlab_automation_pat }}')
token.save!

role 不再有「產生、存檔、讀回」的 task。腳本寫出後執行、執行完立即刪除，明碼只留在 secrets.yml 那一份。權限為何是 0644，見 Bug #39。

secrets.yml 整檔加密並進版控，這個做法沿用 ansible/files/ssh/id_ed25519 的先例，細節見 Ansible 框架設計 § 密鑰管理。

GitLab Runner

roles/gitlab_runner 在 bastion 上另跑一個 gitlab/gitlab-runner:v17.6.0 container，以 root 執行，不額外指定 --user。它掛載主機的 /var/run/docker.sock，註冊成 instance-wide runner，對 doughops 底下所有 project 可見。tags 是 bastion,docker，並接受無 tag 的 job。

註冊是 GitLab 16 起的兩階段流程。先用自動化 PAT 呼叫 POST /api/v4/user/runners，取得只出現一次的 authentication token，再用它執行 gitlab-runner register --non-interactive。這個 token 不存檔，只活在該次 ansible run 的記憶體裡。

掛載的 volume

掛載作用
/var/run/docker.sock讓 job container 也能自己 docker build 與 docker push，不只是 runner 建立 job container 用
/cacheGitLab Runner 建議的 job 間快取路徑，container 內部路徑，不 bind mount 到主機，也不處理快取持久化
/root/.ssh:/root/.ssh讓 job 拿到 bastion 上已解密的 SSH 身份，不必在 CI 重走一次解密流程

三個掛載都在 runner 層級設定。GitLab 的 Docker executor 不讓個別 job 在 pipeline 檔案裡指定額外的主機 volume，這點與 GitHub Actions 不同。

runner 身份不持久化：config.toml 只活在 container 自己的檔案系統，不 bind mount 到 /userap。bastion 重建就是全新註冊一次，比維護「舊 token 是否還有效」的偵測邏輯簡單，CI runner 的身份本來就可以隨時重新發放。concurrent = 20 在註冊後以 sed 改 config.toml，因為 register 不會設定這個值。

container 是否存在是註冊的主要判斷依據。GitLab 側是否已有同名 runner 只是輔助防呆，避免 container 被手動刪掉但後台舊紀錄還在時重複建立。若 container 被手動刪過而後台紀錄沒清，重跑會因為 token 未定義而報錯，這種情境要到 /admin/runners 手動處理。

CD repo

roles/gitlab_cd_repo 在 GitLab 上建立 doughops/k8s-central-cd，放在 doughops group 下而非 root 個人 namespace，內容只有一個 .gitlab-ci.yml。你在 GitLab UI 按「Run pipeline」、填變數後，pipeline 才去 GitHub clone terraform-k8s 的指定 ref 並執行。它與 GitHub Actions 的手動觸發是同一件事的兩個版本，兩者並存，GitHub 版見 Role: github_runner § run-playbook.yml。

role 每次重跑都會對齊下列狀態：

  • group 與 project 的可見度都是 internal，任何登入過的帳號都看得到。
  • .gitlab-ci.yml 的內容與 role 產生的版本不同時，以 Commit API 更新。
  • CI/CD 變數以 upsert 建立，且全部 protected: true，見 CI/CD 變數。
  • 列出 GitLab 上全部使用者，補齊 doughops group 的 membership，等級是 Owner（access_level 50），只升不降，排除 bot 帳號。

bot 帳號要排除，因為 Group 或 Project Access Token 建立時 GitLab 會自動產生對應的 bot 使用者，其權限綁在 token 的 role 上。用 members API 改 bot 的權限，GitLab 會回 403。

pipeline 的 workflow.rules 只接受 $CI_PIPELINE_SOURCE == "web"，也就是 UI 的「Run pipeline」。一般 push 到這個 repo 不會意外觸發 ansible-playbook。

Run pipeline 的變數

三個變數都宣告在 pipeline 頂層 variables。GitLab 的「Run pipeline」畫面只會預先列出頂層變數，也只有頂層支援 {description, value} 擴充寫法，job 層級的變數不會出現在表單，見 Bug #44。

變數預設作用
PLAYBOOK_PATH空相對於 ansible/playbooks/ 的路徑，例如 k8s/smoke-test.yml。只有 EXECUTION 留空時才使用
GIT_REFmain要 clone 的分支或 tag（git clone --branch "$GIT_REF" --single-branch），用於在合併前以 CD repo 測試某個 feature branch 的 playbook。GitHub Actions 版不需要，因為 workflow_dispatch 的 UI 內建分支選擇器
EXECUTION空見 EXECUTION 選項

留空 EXECUTION 時走 PLAYBOOK_PATH 流程。這個流程用 realpath -m 解析路徑，跑到 ansible/playbooks/ 之外就在執行 ansible-playbook 之前失敗，檔案不存在也一樣。

job 的執行環境

  • image 是 ghcr.io/doughops/terraform-k8s-ansible-runner:latest，設為 public，job 不需要任何 pull 認證。image 內只有 Ansible 執行環境，沒有程式碼或密鑰，見 Bug #42。
  • 從 GitHub clone 使用 CI/CD 變數 GITHUB_CLONE_PAT，是 fine-grained PAT。
  • ansible.cfg 寫死的 vault 密碼路徑 /ansible-key/vault-password 在 job container 裡不存在。pipeline 把 CI/CD 變數 ANSIBLE_VAULT_PASSWORD 寫成 $CI_PROJECT_DIR/.vault-password，再以環境變數 ANSIBLE_VAULT_PASSWORD_FILE 覆蓋，環境變數優先於 ansible.cfg，見 Bug #43。
  • SSH 身份來自 runner 層級掛載的 /root/.ssh，pipeline 不另外處理金鑰。
  • job 層級 timeout: 3h。create_cluster 要跑完整套建置，GitLab 預設的 1 小時 job timeout 大機率不夠。

EXECUTION 選項

EXECUTION 在「Run pipeline」畫面是下拉選單，由頂層變數的 options 提供合法值，選錯字在 UI 層就被擋掉，不用等 job script 的 case ... *) 分支報錯。選了任一個非空值，PLAYBOOK_PATH 就不會被讀。

destroy_vm 與 create_cluster 會對 OpenStack 執行 -auto-approve，decommission 會重開機所有 k8s 節點。CI 無人值守，沒有互動式 yes，唯一的確認就是選下拉選單並按「Run pipeline」這個動作。誰能按，見已知限制。

值做什麼破壞性需要的憑證
空執行 PLAYBOOK_PATH 指定的單一 playbook取決於 playbookvault 密碼
verifyterraform plan（不 apply）加 k8s/smoke-test.yml無OpenStack、S3 state
decommission叢集狀態清乾淨、機器留著、重開機清掉所有 k8s 節點的叢集狀態vault 密碼，不碰 Terraform
destroy_vm砍掉 tor 與 bastion 以外的所有 VM高：VM 與其 port、boot volume 被刪除OpenStack、S3 state

verify

非破壞性檢查，可隨時手動觸發，用來確認 CI 的 Terraform 與 Ansible 串接正常，以及叢集有沒有 drift。terraform plan 故意不加 -detailed-exitcode。openstack/ 目前有一筆已知的 drift（bastion 的 user_data 雜湊不符），加了這個旗標會讓它每次都把 verify 變紅，反而蓋掉真正意外的新 drift。維持預設行為，diff 只會印進 job log。

decommission

不砍任何 VM，純 Ansible，執行 playbooks/decommission.yml。它對所有 k8s_nodes 做下列事項，不含 tor 與 bastion：

  1. 執行 kubeadm reset、清除 CNI 與 cilium 網卡殘留、清除該節點在 FRR 宣告的 PodCIDR。這一段以 import_playbook 重用 playbooks/kubeadm-reset.yml，不重複維護。
  2. 刪除 bastion 上殘留、指向已失效叢集的 kubeconfig：/root/.kube/config 與 /home/ubuntu/.kube/config，前者是後者的 symlink，見 playbooks/bastion/kubeconfig.yml。
  3. 重開機所有 k8s 節點。

與 kubeadm-reset.yml 的差別是：後者是準備重新 kubeadm init 的過渡步驟，這個是終態。機器留著、乾淨地停在那裡，之後想裝回來，重跑 playbooks/k8s.yml 即可。它不需要 OpenStack 或 S3 憑證。

destroy_vm

先印一次 terraform plan -destroy 供 job log 稽核，再執行 terraform destroy -auto-approve。-target 清單在執行時以 terraform show -json 加 jq 動態計算，不寫死節點名稱，所以 terraform.tfvars 增減節點不必同步修改 pipeline。

  • 納入：openstack_compute_instance_v2、openstack_networking_port_v2，以及 boot_volumes。
  • 排除：index 是 tor 或 bastion 的資源，以及 data_volumes。後者有 lifecycle.prevent_destroy，誤 target 到會讓整個 destroy 中止，主動排除比較乾淨。
  • 沒有找到任何非 tor／bastion 的資源時，印訊息後略過，視為已刪除過。

create_cluster

用 terraform apply 把 destroy_vm 拿掉、但仍在 terraform.tfvars 的節點建回來。tor 與 bastion 不在 destroy_vm 的 target 內，因此不會被動到。apply 後重新產生 inventory/hosts.ini，因為 openstack/outputs.tf 的 vm_private_ips 讀的是實際存在的 instance，重建後才有新值。接著依序執行 bastion.yml 與 k8s.yml，範圍與 make build 相同。

與 make build 的差別：make build 的 terraform apply 要在終端機互動確認，這裡是 -auto-approve，也沒有 cloudflare apply 與 sync-cloudflare-secrets.sh 這兩步，只重建 OpenStack 上的 VM 與其上的設定。

CI/CD 變數

role 以 upsert 建立下列專案層級變數，全部 protected: true，只在 protected 分支（main）的 pipeline 可用。

變數來源（secrets.yml）用途

三組 Terraform 相關欄位必須一起填，缺一個就整組跳過，不個別 upsert。沒填時 verify、destroy_vm、create_cluster 會在 terraform init 明確失敗，不會誤用空字串。github_cd_clone_pat 沒填時，project 與 .gitlab-ci.yml 照常建立，pipeline 在 git clone 失敗。

OPENSTACK_CLOUDS_YAML 的 masked 是 false，因為 GitLab 的 file 型變數不支援 mask，只能靠 protected: true 限縮。ansible/Dockerfile.ci 另外加裝了 terraform 與 jq，GitHub Actions 的 run-playbook.yml 也用同一張 image，額外的工具對它無害。

已知限制

下面幾項彼此疊加，影響範圍是整個 lab，請當成一組風險閱讀。

能登入 GitLab 的人，等於能操作 bastion 與 OpenStack。四個設計各自合理，疊在一起的結果是：

  • 每個通過 Cloudflare Access 並登入過 GitLab 的帳號，在 doughops group 都是 Owner，可以建立 project 與 pipeline。
  • instance runner 接受無 tag 的 job，且 job container 掛著 docker.sock 與 bastion 的 SSH 身份。docker.sock 等同 bastion 主機 root。
  • CD repo 的 destroy_vm 與 create_cluster 使用的 OpenStack 憑證，權限與維護者的本機相同。這個 OpenStack tenant 只有單一 project，沒有子帳號或縮小範圍的機制。所以 pipeline 能動的是整個 project 的 compute、network 與 volume，不只是叢集的 VM。
  • 預設分支 main 是 protected，Owner 可以推送，也能手動觸發 pipeline。

縮小風險的方向：把預設 membership 從 Owner 降低，並讓 runner 的敏感掛載與 protected 的 runner 或 tag 綁定，只有受信任的 project 才能使用。這些尚未實作。

  • Runner 與 bastion 共享信任邊界：與 GitHub runner 相同，runner 沒有與 bastion 的其他職責隔離。
  • Git 與 API 的 bypass 只剩 PAT 驗證：見 Git 與 API 存取的 bypass。
  • runner 身份不持久化：bastion 重建後會重新註冊，GitLab 後台可能留有 offline 的舊紀錄，需要在 /admin/runners 手動清理。
  • docker.sock 與 /root/.ssh 是 runner 層級的掛載：[runners.docker] 的 volumes 把這兩者掛進每一個 job container。GitLab 的 Docker executor 不像 GitHub Actions，沒辦法讓個別 job 自己指定 host volume。所以 job 腳本能操控整台 bastion，這是刻意接受的取捨。
  • OpenStack 憑證的 masked: false：file 型變數無法 mask，job log 若印出該檔案內容就不會被遮蔽。
  • verify 對已知 drift 不報錯：因為沒有 -detailed-exitcode，新增的 drift 要看 diff 才發現，不會自動變紅。
  • 成員清單最多處理 100 個帳號：role 用 per_page=100 取使用者，不處理分頁，對這個 lab 的規模足夠。

實測踩到的 bug

#72 · 新 project 無法推送 main

  • 症狀：doughops/gitops-demo 直接建在 group 底下，第一次 commit 檔案到 protected 的 main 就被 GitLab 擋下，連自動化帳號（root）也被擋。
  • 根因：membership 迴圈原本只把每個使用者（含 root）升到 Developer，也就是 access_level 30。protected branch 預設要 Maintainer（40）以上才能推。doughops/k8s-central-cd 之前沒撞到，因為它最初建在 root 個人 namespace，建立者自動是 Owner。事後搬進 group 不動 project membership，root 因此保留 Owner。
  • 修法：預設權限從 Developer 提升到 Owner（access_level 50），範圍只限 doughops group，不影響其他 group 或 instance-wide 設定。
  • 怎麼確認修好：doughops 底下新建的 project 可由自動化帳號直接 commit 到 main。
  • 相關：Bug #72。此修法擴大了預設權限，風險見已知限制。

驗證方式

  • 登入流程：用無痕視窗開 gitlab.dough-ops.com。沒有現成 session 時先看到 Cloudflare 的 GitHub org 驗證畫面，接著不出現任何 GitLab 自己的登入頁，直接落地在 GitLab 首頁。
  • Admin 權限：用 oidc_admin_emails 名單內的帳號登入，/admin/users 確認 is_admin: true；名單外的帳號是一般使用者。
  • Break-glass：/users/sign_in?auto_sign_in=false 加 gitlab_root_password 能直接登入，不經 OIDC。
  • Runner：/admin/runners 看得到一個線上（綠燈）的 instance runner。跑一個不指定 image 的最簡單 pipeline，job log 裡 docker version 印出的是主機 Docker daemon 的資訊。
  • 冪等性：重跑 playbooks/bastion/gitlab.yml 與 playbooks/bastion/gitlab-runner.yml 兩次，failed=0，不會重複建立 PAT 或 runner。
  • CD repo：在 UI 按「Run pipeline」，PLAYBOOK_PATH=ping.yml，job log 看得到它 clone GitHub，並對所有節點 ping 成功。把 PLAYBOOK_PATH 填成會跳出 ansible/playbooks/ 的值，pipeline 在執行 ansible-playbook 之前就明確失敗。
  • EXECUTION 的靜態驗證：YAML 以 yaml.safe_load 解析，內嵌 script 以 bash -n 檢查，GitLab CI Lint API 回 valid: true。5 個 CI/CD 變數的型別、masked、protected 對 API 查證過。
  • destroy_vm 的 -target 清單對真實 remote state 做過唯讀測試，抓到 8 個非 tor／bastion 節點、24 筆資源。destroy_vm、create_cluster 與 verify 沒有實際觸發過，最後一步由人在 UI 按「Run pipeline」。
  • .gitlab-ci.yml 語法：POST /api/v4/projects/:id/ci/lint 回 "valid": true，無 errors 與 warnings。

放棄的方案：Pull Mirroring

CD repo 原本想用 GitLab 內建的 Pull Mirroring，把整個 GitHub repo 鏡像過來，不必每次 clone。實測真實的 GitLab CE 後發現，Repository Mirroring 不論 push 或 pull 都屬於 Premium 付費層，CE 完全沒有。所以改成現在的設計：GitLab 上只放 pipeline，執行時才 clone GitHub。

密鑰管理的演進

第一版比照 roles/keycloak_server：openssl rand 在 bastion 上產生 PAT，存成 /userap/gitlab/secrets/automation-pat，之後每次重跑讀回。這個做法可以運作，但密鑰變成一份只在 bastion 磁碟上的狀態。

後來改成現在的設計：所有密鑰都放進 secrets.yml，bastion 檔案系統不保存任何副本；secrets.yml 整檔 ansible-vault 加密後進版控。腳本同時由「找不到才建」改成真正的 upsert，輪替只要換 secrets.yml 的值再重跑。理由與取捨見自動化 PAT 的來源。
