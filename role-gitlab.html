Ansible 自動化Role: gitlab

在 bastion 上跑一套完全自架的 GitLab CE(roles/gitlab_server) 跟一個 instance-wide 的 GitLab Runner(roles/gitlab_runner)。 跟 Role: vault、Role: keycloak / dex 是同一個大方向——服務跑在 bastion,不是叢集內 workload,資料在 bastion 重建後自動復原。這頁涵蓋:為什麼是 container based、Cloudflare Access 怎麼做到「過了邊緣驗證就直接登入 GitLab、不再跳第二次登入畫面」、GitLab Runner 的 Docker executor 怎麼接 host 的 Docker daemon,以及過程中撞到、後來又整個推翻重做一次的 密鑰管理設計。

為什麼是 container based,不是 Helm chart

GitLab 官方提供好幾種安裝模式(Helm chart、Operator、omnibus 套件直接裝 在 host 上、Docker container)。這個 lab 明確選 container based——單一 gitlab/gitlab-ce omnibus image,資料 bind mount 到 /userap/gitlab/{config,logs,data}(bastion 的 user-data 這顆持久化 Cinder volume,同一顆 volume 上 還有 Vault、Keycloak 的資料),跟 Kubernetes 完全無關——這是刻意的 取捨,不是還沒來得及做成 Helm chart。omnibus image 本身已經包了 nginx/puma/postgresql/redis/sidekiq 全部元件,不需要像 Keycloak 那樣額外開一個獨立的 Postgres container。

Cloudflare Access:兩層防線疊加,不是取代

gitlab.dough-ops.com 先過既有的萬用字元 Cloudflare Access Application(doughops GitHub org 成員才放行,跟 dashboard/grafana/vault 是同一層),再疊加 GitLab 自己的 OmniAuth OIDC(對應 Cloudflare 另一個「Access for SaaS」 Application,gitlab-sso)——defense-in-depth,跟 Vault 的 OIDC 登入同一種模式。

關鍵設定是 omniauth_auto_sign_in_with_provider ——沒有這行,OmniAuth 只是在 GitLab 登入頁多一顆「Sign in with OIDC」按鈕,還要手動點。設了之後,瀏覽器一開 gitlab.dough-ops.com,GitLab 直接跳過自己的登入頁、 立刻重導向 OIDC provider,外層 wildcard Access 通常已經有有效 session,整段重導無感,直接落地在 GitLab 首頁。

Break-glass:這個設定同時會讓 /users/sign_in 直接被導去 OIDC provider,密碼表單根本不會渲染——GitLab 官方文件記載的 escape hatch 是加 query string:

break-glass 登入網址
https://gitlab.dough-ops.com/users/sign_in?auto_sign_in=false

這個網址還是卡在同一個萬用字元 Access Application 底下——只是跳過 GitLab 自己的自動導向,不是跳過 Cloudflare 的登入檢查。這條路能用的 前提是 doughops org 成員身份還有效;真的要繞過 Cloudflare 整層, 只能靠這個 role 額外開的 gitlab-direct bypass Application(見下面「Git 存取:一個新的 bypass Application」)。

Git 存取:一個新的 bypass Application

設計最初只打算走 HTTPS + Personal Access Token clone/push,後來在 whole-branch review 才發現一個沒想到的缺口:git clone 跟 PAT-based API 呼叫沒辦法走完 Cloudflare Access 那套互動式 GitHub org 登入,萬用字元 Application 會直接把它們擋在外面——不管走不走 SSH,HTTPS 這條路一樣打不通。

修法是照抄 keycloak_direct(見 Role: keycloak / dex)已經驗證過的 模式:另開一個 path-scoped bypass Application,只放行 gitlab.dough-ops.com/*.git/* 跟 /api/v4/* 這兩組路徑,decision = "bypass"。 這兩條路徑範圍外的一般瀏覽頁面完全不受影響,還是要先過萬用字元 Access。取捨很直接:這兩條路徑底下,GitLab 自己的 PAT/HTTP Basic 驗證變成唯一防線,TLS 還是 Cloudflare 在做,只是不再額外要求先過 GitHub org 這關。

密鑰管理:從「bastion 自動產生存檔案」整個推翻重做

這是這個 role 裡變動最大的一段。GitLab 端需要一組給自動化用的 Personal Access Token(api scope,綁在 root 帳號上), 拿去呼叫 REST API 做 oidc_admin_emails allowlist upsert、幫 GitLab Runner 註冊 CI runner。

第一版比照 roles/keycloak_server 既有的 手法:openssl rand 在 bastion 上產生一次、存成檔案 (/userap/gitlab/secrets/automation-pat),之後每次 重跑都讀回這個檔案。這個做法可以動,但使用者後來提出兩個更嚴格的 要求,把整個機制推翻重做:

  1. 所有密鑰都要放進 secrets.yml,禁止依賴 bastion 的檔案系統——「bastion 上有一個只有 SSH 進去才 看得到的密鑰檔案」本身就是一種難以維護的狀態,想知道/輪替這組值 得先 SSH 進 bastion 找檔案。
  2. secrets.yml 本身要加密後 commit 進 GitHub——不是留在本機、gitignore 排除。

第一點其實有辦法完全做到:GitLab 本來就不會把已存在 token 的明碼 回吐出來,所以「這組值到底是誰選的」根本不重要——第一版讓 bastion 自己 openssl rand 沒有必要,乾脆讓**這組值從一開始就 只存在 secrets.yml**,由人(或這次由 AI)在本機用 openssl rand -hex 32 選一次,直接寫進去:

roles/gitlab_server/templates/bootstrap_pat.rb.j2
user = User.find_by_username('root')
token = user.personal_access_tokens.find_by(name: 'ansible-automation')
token ||= user.personal_access_tokens.create(
  name: 'ansible-automation',
  scopes: [:api],
  expires_at: 365.days.from_now
)
token.set_token('{{ gitlab_automation_pat }}')
token.save!

gitlab_automation_pat 直接引用 secrets.yml 的一般變數,這個 role 不再有任何「產生 → 存檔 → slurp 讀回」的 task。這份腳本同時改成真正的 upsert——不管 GitLab 裡那個名字的 token 存不存在,每次都無條件把值設成 secrets.yml 現在這組,不是「找不到才建」。這代表以後 要輪替這組密鑰,只要換 secrets.yml 裡的值、重跑 playbook,GitLab 那邊會自動同步,不用先手動去後台刪舊的。

第二點沿用這個 repo 已經有的先例——ansible/files/ssh/id_ed25519 整份檔案本身就是 ansible-vault 的加密輸出、進版控,不是 包在某個 YAML 變數裡。同一招套用到 secrets.yml:

整檔加密,從 .gitignore 移除
ansible-vault encrypt ansible/inventory/group_vars/all/secrets.yml
# → $ANSIBLE_VAULT;1.1;AES256 開頭,Ansible 對 group_vars/ 底下任何
#   vault 加密的 YAML 檔案都會透明解密,不用額外設定

這個原則沒辦法無限上綱套用到全部密鑰——HashiCorp Vault 自己的 root token/unseal key,是 vault operator init 當下由 Vault 自己產生、回吐給你的,沒辦法「預先決定」這個值再塞給它,這是 Vault 這個工具本身的機制,不是這個 lab 的設計選擇。gitlab_automation_pat 能這樣做,剛好是因為它從來就不是 GitLab 自己生的,只是我們自己選一個 隨機字串、透過 Rails console 硬塞進去而已。

Bug:bootstrap_pat.rb 用 0600 權限,git 使用者讀不到

第一次對真實 bastion 跑這個 role,gitlab-rails runner 直接回報找不到檔案:

實測錯誤
'load': cannot load such file -- /etc/gitlab/bootstrap_pat.rb (LoadError)

檔案明明存在(docker exec gitlab ls -la /etc/gitlab/ 看得到)。查了 /opt/gitlab/bin/gitlab-rails 這支 wrapper script 才發現:docker exec 預設是 root 身份,但 gitlab-rails 內部用 chpst -u git:git 把 權限從 root 降成 git 這個 unix 使用者才真的去跑 bundle exec rails runner——這份腳本原本是 mode: "0600"(root-only),git 使用者根本 讀不到,Ruby 的 Kernel#load 把「permission denied」誤報 成「檔案不存在」,看起來像路徑錯了,實際上是權限問題。修法是把 mode 改成 0644——這份腳本本來就是一次性的,執行完立刻刪除, 世界可讀的時間窗很短,仍在 /userap 這個已信任的磁碟 邊界內。

Bug:忘了關掉 Let's Encrypt,第一次 reconfigure 差點失敗

final review 抓到的一個潛在地雷,還沒真的炸開就先修掉了:Omnibus 只要看到 external_url 是 https、又沒有另外 設定憑證,預設會自動開 Let's Encrypt、每次 reconfigure 都嘗試續期。這個 lab 的 TLS 是在 Cloudflare 邊緣終止(見 下面 nginx 設定),bastion 也沒有對外開放的 :80 給 ACME http-01 challenge 打,憑證申請一定會失敗、拖垮 甚至卡住 reconfigure。明確關掉:

roles/gitlab_server/templates/gitlab.rb.j2
nginx['listen_port'] = 80
nginx['listen_https'] = false
letsencrypt['enable'] = false

Bug:gitlab_signup_enabled = false 只在第一次 seed 生效

這個 lab 的帳號設計是一律透過 OmniAuth(過 Cloudflare Access 才自動 建立)產生,GitLab 自己的帳密註冊表單理論上該關掉,不然多開一個不受 oidc_admin_emails allowlist 約束的建帳號管道。第一版在 gitlab.rb 裡設定 gitlab_rails['gitlab_signup_enabled'] = false,重跑 reconfigure,admin dashboard 卻還是顯示「Check your sign-up restrictions」的警告。

原因是這個設定只在 ApplicationSettings 這張表第一次 被 seed 出來時生效(GitLab 官方 db:seed_fu 的 行為),既有安裝重跑 reconfigure 不會回頭覆蓋已經存在的設定值。修法 是額外加一個每次都執行的 API upsert,跟 admin allowlist 那段是同一種 取捨:

roles/gitlab_server/tasks/main.yml
PUT /api/v4/application/settings
  signup_enabled: false

GitLab Runner:Docker executor,全域共用

roles/gitlab_runner 在 bastion 上另外跑一個 gitlab/gitlab-runner container,以 root 執行 (不額外指定 --user),直接 mount host 的 /var/run/docker.sock,註冊成 GitLab 的 instance-wide runner——對 doughops 底下所有 project 都可見。註冊流程是 GitLab 16 起的新版兩階段:先用 automation PAT 呼叫 POST /api/v4/user/runners 拿一次性的 authentication token,再拿那個 token 去 gitlab-runner register --non-interactive。

CI job 能自己 docker build/docker push——[runners.docker] 的 volumes 也把 /var/run/docker.sock mount 進每一個 job container,不是只給 gitlab-runner 自己建立 job container 用。這是刻意接受的取捨:job 腳本理論上能操控整台 bastion 共用的同一個 Docker daemon,跟 host 之間沒有隔離,使用者明確要求這個 行為。

不持久化 runner 身份——config.toml 只活在 container 自己的檔案系統裡,不 bind mount 到 /userap。bastion 重建就是全新註冊一次,比維護一份「舊 token 是否還有效」的偵測邏輯 簡單,CI runner 的身份本來就是可以隨時重新發放的東西。 concurrent = 20(全域最大同時執行 job 數,使用者明確 要求的值)。

CD Repo:只放 pipeline、不放程式碼,手動觸發 clone GitHub 來跑

roles/gitlab_cd_repo 在 GitLab 上建一個 doughops/k8s-central-cd project(放在 doughops 這個 group 底下,不是 root 個人 namespace),內容只有一個 .gitlab-ci.yml——手動在 GitLab UI 按「Run pipeline」、 填一個 PLAYBOOK_PATH,pipeline 執行當下才去 GitHub clone terraform-k8s 的最新內容、跑指定的那支 ansible playbook。跟 GitHub Actions 那邊已經有的 手動觸發 playbook 功能是同一件事的 GitLab 版本,兩者並存。

這個方向原本想走 GitLab 內建的 Pull Mirroring(把整個 repo 內容 鏡像過去,不用每次 clone)——實測發現 GitLab CE 完全沒有 Repository Mirroring 這個功能,不管 push 還是 pull 都被整個放進 Premium 付費層,不是設定沒開對,是產品分層問題,這個方向直接 放棄改走現在這個設計。

任何登入過這個 GitLab 的使用者,預設就有這個 group 的 Owner 權限。GitLab 沒有「新帳號自動加入某個 group」的 內建機制,這個 role 用跟 oidc_admin_emails allowlist 同一種 upsert 手法:每次重跑都對一次 GET /api/v4/users 列出的全部使用者清單,查+補齊 doughops group 的 membership(Owner,只升不降)——新登入過的帳號下次重跑這個 role 就會自動補進去,不用手動邀請。Project 跟 group 本身也都設成 internal 可見度,任何登入過的使用者預設就看得到。

Bug:預設只給 Developer,doughops 底下直接建立的新 project 沒辦法 push 進 protected 的 main 分支。原本這個 迴圈只把每個使用者(包含 gitlab_automation_pat 對應 的 root 帳號自己)升到 Developer(access_level 30)。 doughops/k8s-central-cd 沒撞到這個問題,是因為它原本 建在 root 個人 namespace(建立者自動是 Owner),事後 才搬家進 doughops group——搬家不會動到 project membership,root 因此意外保留了 Owner。後來 doughops/gitops-demo(見 Role: argocd)直接建在 group 底下, 第一次 commit 檔案進 protected 的 main 分支就被 GitLab 擋下(protected branch 預設要 Maintainer(40)以上才能推)——連 自動化帳號自己都被卡住。修法:把預設權限從 Developer 提升到 Owner(access_level 50),範圍只限定 doughops 這個 group,不影響其他 group 或 instance-wide 設定。

Bug:fine-grained GitHub PAT 的 Packages 權限不支援真的 pull GHCR image。Pipeline 需要拉 ghcr.io/doughops/terraform-k8s-ansible-runner 這個 private image,原始設計用同一組 fine-grained PAT(Contents +Packages 都 Read-only)當 DOCKER_AUTH_CONFIG 的憑證。實測 docker login ghcr.io 用這組 PAT 會成功 (憑證格式沒問題),但接著 docker pull 仍然回 denied——查證後確認這是 GitHub 目前的產品限制: fine-grained PAT 的 Packages 權限只涵蓋 Packages REST API(列清單、 看 metadata),實際 pull/push container image 目前只認 classic PAT 的 read:packages scope。改法:把這個 image 設成 public(本身只有 ansible 執行環境,沒有程式碼或密鑰,公開沒有 風險),DOCKER_AUTH_CONFIG 整個拿掉,pipeline 不需要 任何認證就能拉到這個 image。

Bug:剛 clone 下來的 ansible.cfg 指向一個 這個 job container 沒有的 vault 密碼路徑。 src/ansible/ansible.cfg 的 vault_password_file 寫死指向 /ansible-key/vault-password——那是 scripts/ansible.sh 自己 docker run 時才會 掛出來的路徑,CD repo 這個 job container 完全沒有這個掛載,直接跑 ansible-playbook 會報「vault password file … was not found」。修法比照 GitHub Actions 那份已經驗證過的做法: 把 ANSIBLE_VAULT_PASSWORD 這個 CI/CD 變數的值寫成一個 檔案,用 ANSIBLE_VAULT_PASSWORD_FILE 環境變數蓋掉 ansible.cfg 那個寫死的路徑(環境變數優先權比 ansible.cfg 高)。

SSH 身份不用另外處理——roles/gitlab_runner 在 runner 層級的 --docker-volumes /root/.ssh:/root/.ssh(GitLab 的 Docker executor 不像 GitHub Actions 那樣讓個別 job 在 pipeline 檔案裡自己指定額外的 host volume mount,只能在 runner 這個層級 設定)讓 job container 直接拿到 bastion 主機自己已經解密好的 SSH 身份,不用在 CI 這邊重新走一次 vault 解密金鑰的流程。端對端驗證 過:手動觸發一次 pipeline,`PLAYBOOK_PATH=ping.yml`,job log 看得到它 clone GitHub、對全部 10 個節點(bastion、tor、3 台 master、2 台 lb、3 台 worker)ping 成功;`PLAYBOOK_PATH` 故意填 路徑跳脫的值,pipeline 在真的執行 ansible-playbook 之前就明確失敗,不是靜默略過。

Bug:「Run pipeline」畫面完全看不到要填什麼。 PLAYBOOK_PATH 原本宣告在 job.variables (job 層級),使用者實測按下「Run pipeline」時回報:畫面上沒有任何 預設欄位或說明。查證後發現 GitLab「Run pipeline」手動觸發畫面的 變數輸入框,只會預先列出宣告在頂層(pipeline 層級)variables 的變數,並且只有頂層才支援 {description, value} 這種擴充物件寫法、被畫面渲染成 說明文字——job 層級的變數完全不會出現在這個表單裡。修法:把 PLAYBOOK_PATH 搬到頂層 variables,加上 description;job 不用重複宣告,頂層變數本來就會自動 傳給底下每個 job。用一次真的觸發的測試 pipeline(暫時放寬 workflow.rules 接受 api 來源)驗證過改完 的語法正確、pipeline 照樣成功執行。

順便加上 GIT_REF 這個頂層變數(預設 main,同樣有 description),讓「Run pipeline」除了指定要跑哪支 playbook 之外,也能指定要從 GitHub clone terraform-k8s 的哪個分支/tag(git clone --branch "$GIT_REF" --single-branch)——方便在合併回 main 之前,先用 CD repo 這條路徑測試某個 feature branch 上的 playbook 改動。GitHub Actions 那邊 (.github/workflows/run-playbook.yml)不需要對應變數, 是因為 workflow_dispatch 手動觸發時 GitHub UI 本身就有 內建的分支選擇器,GitLab 沒有等價的內建機制。用一次真的觸發的測試 pipeline(GIT_REF=main、PLAYBOOK_PATH=k8s/ smoke-test.yml)驗證過 status: success。

驗證方式

  • 登入流程:無痕視窗開 gitlab.dough-ops.com,應該 先看到 Cloudflare GitHub org 驗證畫面(沒有現成 session 的話), 接著不出現任何 GitLab 自己的登入頁,直接落地在 GitLab 首頁。
  • Admin 權限:用 oidc_admin_emails 清單裡的帳號登入, /admin/users 確認該帳號 is_admin: true; 清單外的帳號應該是一般使用者。
  • Break-glass:/users/sign_in?auto_sign_in=false + secrets.yml 的 gitlab_root_password 能直接登入,不經過 OIDC。
  • Runner:/admin/runners 看得到一個線上(綠燈)的 instance runner;跑一個不指定 image 的最簡單 pipeline,job log 裡 docker version 印出的是 host 真正的 Docker daemon 資訊,不是假的。
  • 冪等性:重跑 playbooks/bastion/gitlab.yml、 playbooks/bastion/gitlab-runner.yml 兩次, failed=0,不會重複建立 PAT/runner。
