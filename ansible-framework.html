叢集元件 Ansible 框架設計

這頁說明 Ansible 自動化框架本身的設計：誰執行 ansible、inventory 怎麼產生、私鑰與 secrets.yml 怎麼保管，以及 Makefile 與 playbook 的組織方式。各個 role 的設定細節在後面每一頁。想照步驟從零建置，請看從零開始建置。

執行模型

ansible 實際執行的地方，是 bastion 上的一個臨時 Docker 容器。你的筆電只負責把最新的 ansible/ 目錄同步過去、觸發 bastion 執行，自己不跑任何 task。

你的筆電

→
rsync ansible/ 與 docs/
vault 密碼走 ssh stdin
→
bastion:
docker build
有 cache 時通常秒建
→
bastion:
docker run
容器內執行 ansible
→
輸出即時串流
回你的終端機

bastion 是唯一同時能從外部 SSH 進入、又和所有節點同在 mgmt-net 的機器。筆電只能連到 bastion（透過 Floating IP），所以執行 ansible 的地方只能是 bastion，或經由 bastion 跳。把版本、Python 環境和 collection 全部封裝進一個 Dockerfile，筆電只需要 ssh、rsync、docker 這類本來就有的工具。

決策：用 bastion 上的 Docker 容器當 ansible 控制端，不另外開專用的 controller VM。

理由：bastion 本來就必須存在，是唯一的操作入口。多裝一個 Docker daemon 的邊際成本，遠低於多開一台 VM 的 OpenStack 配額壓力。

考慮過的替代方案：專用 controller VM — 多一份配額，多一台要維護的機器。筆電直接裝 ansible — 筆電連不到 bastion 以外的節點，還要自己維護 ansible 與 collection 版本。

代價：ansible 的成敗綁在 bastion 上。bastion 重建後，kubectl、kubeconfig、/etc/hosts 記錄這類存在開機碟的東西都要重跑 bastion.yml 補回來。

Inventory 自動產生

ansible/inventory/generate_inventory.py 讀 terraform output -json，把 vm_mgmt_ips 當 ansible_host，vm_private_ips 當 fabric_ip，輸出成 INI 格式的 hosts.ini。scripts/ansible.sh 每次執行都會重新產生，不要手動編輯。

分組依節點名稱前綴判斷：ms- 是 masters，l4- 是 lbs，ap- 是 workers。Terraform 的 bgp_role 對 master、lb、worker 全部是同一個 peer，無法用來區分。

# ansible_host 是 mgmt-net 位址，ansible 實際連線用這個
# fabric_ip 是 k8s-net（資料平面）位址，role 需要引用時用這個
bastion ansible_host=192.168.200.11 fabric_ip=10.10.0.11

INI 格式

INI 對「host 加一串 key=value 參數」的結構比 YAML 緊湊，少一層縮排。

👻

tor 與 bastion 是裸 host

寫在任何 [group] 標頭之前的 host 行自動屬於 ungrouped，仍然在 all 之內。不必為它們另開同名 group。

🧩

k8s_nodes 合併 group

[k8s_nodes:children] 把 masters、lbs、workers 合成一個 group，給要動整個叢集的 playbook 用，例如 CRI-O、kubeadm、Cilium。不含 tor 與 bastion，它們是 fabric 與維運節點。

執行環境 Dockerfile

執行環境由 ansible/Dockerfile 定義，在 bastion 上 build。build context 是 scripts/ansible.sh 同步過去的暫存目錄，裡面有 ansible/ 與 docs/ 兩棵樹。

ansible/Dockerfile
FROM python:3.13-slim

RUN echo 'Acquire::ForceIPv4 "true";' > /etc/apt/apt.conf.d/99force-ipv4

RUN apt-get update && apt-get install -y --no-install-recommends \
      openssh-client git sshpass rsync \
    && rm -rf /var/lib/apt/lists/*

RUN pip install --no-cache-dir ansible-core

WORKDIR /ansible

COPY ansible/requirements.yml .
RUN ansible-galaxy collection install -r requirements.yml

COPY ansible/ .
COPY docs/ /docs

Acquire::ForceIPv4

bastion 的 mgmt-net 只有 IPv6 link-local，沒有實際的 IPv6 路由。Debian 預設的 deb.debian.org 是雙棧，傾向先試 IPv6，每個 mirror 連線都要等 30 秒逾時才退回 IPv4，build 會慢到難以使用。強制 apt 只用 IPv4 可以解決這個現象。

這個設定後來證實不是 build 慢的真正根因，真正原因是 Docker MTU（見 Bug #10）。保留它仍然合理，apt 走 IPv4 本身是對的。

requirements.yml 先單獨 COPY

這是 Docker layer cache 的標準手法。先只 COPY ansible/requirements.yml 再安裝 collection，只有這個檔案改動才會重新執行 ansible-galaxy collection install。接著才 COPY ansible/ .，改 playbook 或 role 只會讓最後兩層重建，這兩層只是複製檔案，很快。

collection 裝在 ansible 預設路徑 ~/.ansible/collections，不放在 /ansible 底下。後者會被 COPY ansible/ . 的內容蓋掉。

ansible/ 與 docs/ 在 build 時就複製進 image，容器執行時不依賴 bastion 上的暫存目錄。每次執行用的是這次 build 出來的固定快照。

scripts/ansible.sh 流程

所有 ansible 指令都經由這支腳本執行。它在你的筆電上跑，一次完成下面的步驟。

  1. 解密私鑰快取：第一次執行時把 vault 加密的私鑰解密到 repo 根目錄的 .ssh/id_ed25519，之後重複使用。這份明碼拷貝只給腳本自己的 ssh、scp、rsync 連 bastion 用，.ssh/ 已被 gitignore。
  2. 讀 S3 憑證：從 .env 取出 AWS_ACCESS_KEY_ID 與 AWS_SECRET_ACCESS_KEY，讓 terraform output 連得到 state backend。
  3. 重新產生 inventory：呼叫 generate_inventory.py，所以 VM 的 IP 變了也不必手動改。
  4. 等 bastion 的 cloud-init：執行 cloud-init status --wait。docker 是 cloud-init 裝的，剛建好的 bastion 在 Nova 回報 ACTIVE 時 docker 可能還沒裝完，曾經真的遇過 docker: command not found。已經開機一段時間的環境上，這個指令幾乎立刻回傳。
  5. 同步到暫存目錄：在 bastion 的 /tmp 下用 mktemp 開一個本次專用的隨機目錄，rsync 同步 ansible/ 與 docs/，再經由 ssh stdin 把 vault 密碼寫成該目錄下權限 600 的檔案。密碼不經過筆電的任何暫存檔。
  6. build 並執行：以該目錄為 context build 一個帶隨機後綴的 image，用 docker run --rm 執行你傳入的指令。vault 密碼唯讀掛進容器，路徑對應 ansible.cfg 的 vault_password_file。環境變數 REMOTE_DOCS_DIR 把本次 docs/ 在 bastion 上的位置傳給 docs_site role。
  7. 清理：不論成功或失敗，結束時 trap 都會刪掉暫存目錄與 image。隨機命名讓兩個人同時執行時不會互踩。第 1 步的 .ssh/ 快取刻意保留。
repo 根目錄
$ scripts/ansible.sh ansible all -m ping
$ scripts/ansible.sh ansible-playbook playbooks/ping.yml
$ scripts/ansible.sh ansible-playbook playbooks/k8s/cilium.yml --limit masters -v

預期結果：終端機依序印出 ==> 重新產生 inventory、==> 同步 ansible/ 到 bastion、==> 在 bastion 上執行，接著是 ansible 的即時輸出。ping 每個節點回 pong。

失敗時看哪裡：terraform output 失敗，多半是 .env 缺 S3 憑證，見開始前要準備的東西。解密失敗，檢查 .env 的 ANSIBLE_VAULT_PASSWORD。SSH 連不上，先確認 terraform output bastion_floating_ip 有值。

密鑰管理

專案有四類需要保管的值，各自的來源與保護方式不同。

項目位置保護方式進版控
SSH 私鑰ansible/files/ssh/id_ed25519整檔 ansible-vault 加密是（密文）
SSH 公鑰ansible/files/ssh/id_ed25519.pub非機密是
機密變數ansible/inventory/group_vars/all/secrets.yml整檔 ansible-vault 加密是（密文）
vault 密碼與雲端憑證.env只存在你的筆電否（gitignore）

SSH 私鑰

全部節點（含 bastion）共用同一把 ed25519 key，沒有另外的內部 key。私鑰只有一份來源，就是整檔加密的 ansible/files/ssh/id_ed25519。repo 裡沒有明碼私鑰檔案。

  • 公鑰 ansible/files/ssh/id_ed25519.pub 由 openstack/main.tf 的 openstack_compute_keypair_v2.k8s 讀取並註冊進 OpenStack。Nova 在開機當下把它寫進每台節點的 authorized_keys，不需要事後的 bootstrap 步驟。
  • make key-encrypt KEY=/path/to/private_key 把明碼私鑰加密寫入來源檔，同時更新 .pub。make key-decrypt 解密後把私鑰印到 stdout。背後是 scripts/encrypt_key.sh 與 scripts/decrypt_key.sh。
  • 本機沒有 ansible-vault 時，這兩支腳本改用一個固定名稱的本機 Docker image ansible-vault-local 加解密。image 只建一次，之後靠 layer cache。
  • repo 根目錄的 .ssh/ 是 scripts/ansible.sh 解密後的快取，內容是明碼私鑰，已被 gitignore，絕對不可提交。

私鑰有兩條互相獨立的使用路徑：

  1. 筆電到 bastion：make ssh 與 scripts/ansible.sh 使用解密出來的暫存或快取拷貝連 bastion。
  2. ansible 到所有節點：完全不碰筆電上的拷貝。bastion.yml 的第一個 play 以 connection: local 在容器內執行（不經 SSH），由 bastion_access role 把來源檔解密後寫到 bastion 的磁碟，連線時全部由 ssh config 解析身分。沒有任何 host 或 group 設定 ansible_ssh_private_key_file。

bastion 上的私鑰有兩份，原因是權限需求不同。ansible 容器以 root 執行，人登入 bastion 時是 uid 1000。OpenSSH 要求私鑰屬主必須是讀取者本人，且權限為 0600，單一檔案無法同時滿足兩者。

這兩份存放在 bastion 的持久磁碟，而不是容器內部。ad-hoc 指令（ansible all -m ping）不會跑任何 role，身分若只存在容器內，沒跑過 playbook 前所有 ad-hoc 指令都會連不上。只要跑過一次 bastion.yml，之後就能沿用。落地位置屬於實作細節，以 roles/bastion_access 為準。

共用單一 key 的風險：所有節點信任同一把 key，ssh config 連其他節點一律用 root 帳號，且 bastion 上有解密後的私鑰。bastion 一旦被入侵，攻擊者可以用 root 進入所有節點。這個取捨的前提是 key 只給這個 lab 使用。要降低風險，可以改成每台節點一把 key，或改用短效憑證。

更換 SSH key

換 key 會讓既有節點不再信任新公鑰，所以只在要重建 VM，或已另外更新各節點 authorized_keys 時才做。

repo 根目錄
$ ssh-keygen -t ed25519 -f /tmp/id_ed25519 -N ""
$ make key-encrypt KEY=/tmp/id_ed25519
$ rm /tmp/id_ed25519 /tmp/id_ed25519.pub

預期結果：ansible/files/ssh/id_ed25519 的第一行是 $ANSIBLE_VAULT;1.1;AES256，ansible/files/ssh/id_ed25519.pub 已更新，/tmp 下的明碼副本已刪除。更換 vault 密碼時，用 openssl rand -base64 32 產生新值寫進 .env，再重新加密這兩個檔案。

secrets.yml

ansible/inventory/group_vars/all/secrets.yml 放所有不能明碼進版控的變數：Cloudflare tunnel token、各服務的 OIDC client secret、GitLab 與 GitHub 的 token、oidc_admin_emails 名單等。檔案整檔用 ansible-vault 加密後提交，.gitattributes 把它標成 -diff，因為密文逐行比對沒有意義。

secrets.yml.example 是同目錄下的欄位範本，每個欄位旁有註解說明用途與取得方式。新增欄位時要同步更新範本。

repo 根目錄，修改 secrets.yml（需要本機有 ansible-vault）
$ set -a; . ./.env; set +a
$ ansible-vault edit ansible/inventory/group_vars/all/secrets.yml --vault-password-file <(printf '%s' "$ANSIBLE_VAULT_PASSWORD")
$ head -n 1 ansible/inventory/group_vars/all/secrets.yml
$ANSIBLE_VAULT;1.1;AES256

預期結果：存檔後第一行仍是 $ANSIBLE_VAULT;1.1;AES256。需要解密或重新加密時，以同樣方式帶 --vault-password-file 執行 decrypt 或 encrypt。

欄位還是 REPLACE_ME 時，role 的反應分兩種。cloudflare_tunnel、bastion_ssh_tunnel、cert_manager、github_runner 直接失敗。其餘會安全跳過對應功能，例如 Keycloak 永久管理員、Vault 與 ArgoCD 與 GitLab 的 OIDC、ArgoCD 的 GitLab 憑證、GitLab CD 的 CI 變數。哪些欄位要先填，見開始前要準備的東西。

vault 密碼與 .env

加密私鑰與 secrets.yml 用同一個 vault 密碼，放在 .env 的 ANSIBLE_VAULT_PASSWORD。.env 被 gitignore，是這個 repo 所有明碼憑證的唯一存放處：

變數用途
ANSIBLE_VAULT_PASSWORD解密私鑰與 secrets.yml
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY		Terraform S3 state backend 憑證，見 state backend
CLOUDFLARE_API_TOKENcloudflare/ 的 Terraform 操作，make build 與 make teardown 從這裡讀
OS_PASSWORD可選，覆蓋 clouds.yaml 的 password 欄位

vault 密碼離開筆電的唯一路徑，是 scripts/ansible.sh 經 ssh stdin 寫到 bastion 的本次暫存目錄，再唯讀掛進容器，執行結束就刪除。

換密碼要把私鑰與 secrets.yml 兩個檔案都重新加密（ansible-vault rekey），只改 .env 會讓兩個檔案都解不開。

sync-cloudflare-secrets.sh 與加密檔

這支腳本把 cloudflare/ 的 14 個 Terraform output 寫回同名的 ansible 變數。8 個寫進 secrets.yml，內容是 tunnel token、origin CA token 與各服務的 OIDC client secret。6 個寫進 main.yml，內容是各服務的 OIDC client ID。

secrets.yml 是密文，不能直接 grep 或 sed。腳本改用下面的流程，不用事先手動解密：

  1. 先讀完輸出：所有 terraform output 都讀到才開始動檔案，讀失敗就什麼都不改。
  2. 解密到暫存區：優先放 /dev/shm，只修改暫存副本，結束時刪除。
  3. 重新加密並驗證：解回來比對內容無誤後，才用 mv 換掉 repo 裡的檔案。

內容沒有變動時不重新加密，避免產生沒有意義的 git diff。檔案原本是明碼時，結束後一律變成密文。本機沒有 ansible-vault 時改用 Docker，和 scripts/decrypt_key.sh 相同。任何一步失敗，secrets.yml 都維持原樣。

舊版腳本的問題見 Bug #73。

這個版本尚未在實際環境執行過，第一次使用後請確認 secrets.yml 的檔頭是 $ANSIBLE_VAULT;1.1;AES256。

連線方式

ansible 在 bastion 的容器內執行，bastion 與所有節點同在 mgmt-net（192.168.200.0/24）這個 flat 網段，可以直連，不需要 ProxyJump。整條路徑只有一次 SSH 跳躍：筆電到 bastion。bastion 到其他節點是容器內的直連。

bastion_access role 同時讓人直接登入 bastion 後，也能不經容器手動 SSH 到任何節點除錯。ssh config 設定 StrictHostKeyChecking accept-new，連其他節點一律用 root 帳號。這是操作便利性，和 ansible 怎麼執行是兩件事，所以獨立成一個小 role。

Makefile 指令

make 不帶參數會印出 help（.DEFAULT_GOAL := help），避免誤打指令就觸發 SSH 連線。help 列出所有帶 ## 說明的目標。

repo 根目錄
$ make ssh
# 讀 terraform output -raw bastion_floating_ip，直接 ssh 進 bastion
# 不用每次手動查 IP、拼 ssh 指令

make ssh 使用和 scripts/ansible.sh 相同的私鑰來源，差別是它給你一個互動式 shell。使用者名稱是 ubuntu，從 .env 讀 S3 憑證以便 terraform output 取得 Floating IP。私鑰解密到一個暫存目錄，結束時刪除。

預期結果：出現 bastion 的 shell 提示。失敗時看哪裡：terraform output 失敗代表 S3 憑證缺漏；key 解密失敗代表 ANSIBLE_VAULT_PASSWORD 不對。

指令作用
make help列出所有指令（預設目標）
make sshSSH 到 bastion，唯一的操作入口
make key-encrypt KEY=...加密一份明碼私鑰並更新 .pub，沒帶 KEY 會印用法並結束
make key-decrypt解密私鑰，印到 stdout
make install-hooks安裝 pre-commit hook，每次 commit 前重新產生 hosts.ini 並併入該次 commit
make build一次建好整套環境，見 一鍵建置
make teardown一次拆除整套環境，資料碟預設保留，見 全部拆除
make pingscripts/ansible.sh ansible all -m ping 的捷徑，不在 help 列表內

pre-commit hook 在沒有 Terraform state、沒裝 Terraform 或沒有 OpenStack 存取權時，只印警告並放行 commit，不會擋住只改文件的貢獻者。

├── playbooks/                # 每個 playbook 對應一個你會下的指令
└── roles/                    # 每個 role 對應一個元件

group_vars/all/main.yml 是共用值的單一來源：apiserver_hostname、kubernetes_minor_version、bgp_asn、cluster_pod_cidr、service_cidr、ingress_wildcard_hostname 都只在這裡定義一次，被多個 role 共用。其中 bgp_asn 與 Terraform 的 var.bgp_asn 沒有自動同步，改的時候兩邊要一起改。各服務的 hostname 同理，要和 cloudflare/terraform.tfvars 保持一致。

為什麼是 group_vars/all/ 目錄

ansible 的 group_vars/<name>.yml 自動載入機制，要求 <name> 對應到一個真正存在的 inventory group。機密檔放在 group_vars/ 底下改名叫 secrets.yml，不會被載入，也不會報錯。

改成「每個 group 一個目錄」的寫法：group_vars/all/main.yml 放公開變數，group_vars/all/secrets.yml 放機密。兩個檔案都對應到真實存在的 all group，ansible 會自動合併載入目錄內所有 .yml，不需要 vars_files。

實測踩到：第一版把機密放在 group_vars/secrets.yml，整個叢集重建時直接得到 cloudflare_tunnel_token is undefined。修法是把 all.yml 用 git mv 搬進 all/main.yml，機密放同目錄下的 secrets.yml。

Playbook 一覽

全新環境只需要兩個聚合 playbook 各跑一次：bastion.yml，再跑 k8s.yml。完整順序與每一步的前置條件見建置順序。下面的表格說明每個檔案的用途。

bastion.ymlbastion 的聚合入口，混合 inline play 與 import_playbook。不含 cloudflare-tunnel.yml。不要求叢集已存在，kubeconfig.yml 偵測到叢集不存在時會安全跳過

只重建 bastion

叢集其他節點都還活著、只有 bastion 被替換時，例如改 data_volumes 讓開機碟的 block device 變更而強制重建，新 bastion 開機時 Nova 會自動寫入同一把公鑰。只要公鑰沒換，直接跑一次 bastion.yml 即可，不需要也不應該重跑 k8s.yml。

已知限制

  • 單一 key 與單一 vault 密碼：所有節點共用一把 SSH key，私鑰與 secrets.yml 共用一個 vault 密碼。風險見上方的 SSH 私鑰與 vault 密碼。
  • 共用值要手動同步：bgp_asn 與各服務 hostname 在 Terraform 與 Ansible 之間沒有自動傳遞，改的時候兩邊都要改。
  • ansible 的可用性綁在 bastion：bastion 掛掉時沒有備援控制端。

演進歷史

  • 私鑰從單一 key，到兩把 key，再回到單一 key：2026-07-27 拆成專屬 key，用 BOOTSTRAP=1 與 ansible.posix.authorized_key 佈署信任。切換後以 ansible all -m ping 對 9 台驗證，並比對 bastion 落地檔案的 checksum。2026-07-30 改回單一 key，由 Nova 開機時統一注入。最早直接把私鑰放在 bastion。後來改成另一把與身分無關的內部 key，以免個人私鑰外流。最後評估這把 key 只給這個 lab 使用，外流頂多進入 lab 內部節點，風險可接受，於是改回單一 key，省下多維護一把 key 與一個 bootstrap 步驟。兩把 key 時期，bastion 重建後內部 key 的信任消失，造成連環失敗，見 Bug #34。
  • 私鑰從 YAML 變數改成整檔加密：早期的來源是 vault.yml 裡的加密變數，現在改成整檔加密的 ansible/files/ssh/id_ed25519，bastion_access role 直接複製這個加密來源。
  • Inventory 從 YAML 改成 INI：INI 更緊湊，也不需要為了避開 group 與 host 同名的警告，把 tor 與 bastion 放進 all.hosts。
  • group_vars/all.yml 拆成目錄：加入 Cloudflare Tunnel 時為了放機密而重新組織，原因見為什麼是 group_vars/all/ 目錄。
