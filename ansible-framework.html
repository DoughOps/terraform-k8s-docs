Ansible 自動化整套自動化框架怎麼設計

從這頁開始,文件的重心從「Terraform 建出來的機器長什麼樣子」 轉成「怎麼把 CRI-O/kubeadm/Cilium 裝上去」。這頁講的是框架本身的設計 ——為什麼控制端是 bastion 上的 Docker、inventory 怎麼自動產生、 整條指令執行路徑實際發生了什麼事。個別 role 的設定細節在後面每一頁。

核心設計:你的筆電不執行任何 ansible task

整個框架的第一原則是:ansible 實際執行的地方是 bastion 上的 一個臨時 Docker 容器,不是你的筆電、也不是另外開一台專用機器。 你在筆電上打的指令,只負責「把最新的 ansible/ 目錄同步過去、觸發 bastion 去執行」,自己不跑任何 task。

你的筆電
scripts/ansible.sh ...
→
rsync ansible/ 到 bastion
+ scp 內部 key 另外傳一份
→
bastion:
docker build
(有 cache 通常秒建)
→
bastion:
docker run
容器內執行 ansible-playbook
→
輸出即時串流
回你的終端機

為什麼要繞這一圈,不直接在筆電上裝 ansible 連過去?兩個原因: 第一,bastion 才是唯一在 mgmt-net 上、能直連所有節點的機器 ——你的筆電只能連到 bastion(透過 floating ip),連不到任何其他節點, 所以「執行 ansible 的地方」本來就只能是 bastion 或透過 bastion 跳。 第二,不想讓你的筆電需要裝、維護一套 ansible + collection 環境——版本、Python 環境、collection 版本全部封裝進一個 Dockerfile,筆電只需要有 ssh/rsync/docker client 這種幾乎必然已經有的工具。

為什麼不是「開一台專用的 ansible controller VM」

這是使用者在設計階段明確做的決定,不是預設值:與其為了跑 ansible 多開一台 VM(在 OpenStack quota 吃緊的情況下,多一台就是多一份 配額壓力),不如直接用 bastion 既有的運算資源,用 Docker 隔離執行環境——bastion 本來就必須存在(唯一操作入口), 多裝一個 Docker daemon 的邊際成本遠低於多開一台機器。

Inventory:從 Terraform output 自動產生,INI 格式

ansible/inventory/generate_inventory.py 讀 terraform output -json(vm_mgmt_ips 當 ansible_host、vm_private_ips 當 fabric_ip),依節點名稱前綴分組——不是看 terraform 的 bgp_role,因為 master/lb/worker 目前全部共用 同一個通用的 peer 角色,bgp_role 沒辦法拿來 區分「這台是 master 還是 lb 還是 worker」,只有名稱前綴 (ms-/l4-/ap-)才知道。

為什麼是 INI,不是 YAML

框架最早用 YAML inventory,後來使用者明確要求改成 INI——INI 格式對這種「host + 一串 key=value 參數」的結構更緊湊,少一層縮排。

👻

tor / bastion 是「無 group」的裸 host

INI 格式裡,寫在任何 [group] 標頭之前的 host 行,自動算 ungrouped,仍然屬於 all ——不用額外開一個跟自己同名的 group(YAML 版本一度為了避免 「group 跟 host 同名」的警告,特地把它們放進 all.hosts, INI 格式完全不需要這個繞路)。

🧩

k8s_nodes 是特地加的合併 group

[k8s_nodes:children] 語法把 masters/lbs/workers 合併成一個 group,給「要對整個 k8s 叢集下手」的 playbook 用 (裝 CRI-O、kubelet/kubeadm、Cilium)——不含 tor/bastion, 它們是 fabric/ops 節點,不是 k8s 叢集成員。

Dockerfile:兩個乍看奇怪、其實各自有原因的決定

ansible/Dockerfile
FROM python:3.12-slim

RUN echo 'Acquire::ForceIPv4 "true";' > /etc/apt/apt.conf.d/99force-ipv4

RUN apt-get update && apt-get install -y --no-install-recommends \
      openssh-client git sshpass rsync \
    && rm -rf /var/lib/apt/lists/*

RUN pip install --no-cache-dir ansible-core

WORKDIR /ansible
COPY requirements.yml .
RUN ansible-galaxy collection install -r requirements.yml

1. Acquire::ForceIPv4

bastion 的 mgmt-net 只有 IPv6 link-local、沒有實際的 IPv6 路由(專案只建了 IPv4 的 mgmt_subnet)。Debian base image 預設的 deb.debian.org 是雙棧、傾向先試 IPv6,每個 mirror 連線都要等 30 秒逾時才 fallback 回 IPv4,build 會被拖得非常慢。 強制 apt 只用 IPv4,一行解決。這個修法後來被證明不是真正的 根因(見 Bug 事後檢討裡的 MTU 故事)——但留著當保險無害,而且對「apt 走 IPv4」這件事本身 仍然是對的優化。

2. requirements.yml 先單獨 COPY,不是整包一起複製

這是標準的 Docker layer cache 手法:如果直接 COPY . . 再裝 collection,任何一次改 playbook/role 都會讓這層快取失效, 重新 ansible-galaxy collection install(慢)。先只 COPY requirements.yml,只有這個檔案真的改了才會重新 安裝——playbooks/roles/inventory 之後用 volume mount 蓋掉 /ansible,完全不影響這層快取的有效性。這也是為什麼 collection 要裝到 ansible 預設路徑 (~/.ansible/collections),不能裝進 /ansible 底下——裝進去的話,runtime 的 volume mount 會直接蓋掉,每次執行都要 重裝一次。

私鑰處理:只有一把 key

這個設計來回改過兩次,這裡記錄最終版本、也記錄為什麼: 最早是單一 key(使用者的私鑰直接落地在 bastion 上);後來使用者 要求改成兩把 key(另外一把跟身份無關的「內部 key」,理由是不想讓 自己真正的私密金鑰外流);再後來使用者重新評估,認為 這把 key 只給這個 lab 使用,外流頂多讓人連進 lab 內部節點, 風險可以接受,決定改回只用一把 key——不要為了這個取捨, 多維護一把 key、一個 bootstrap 步驟。目前(也是最終)版本:

  • 只有一把 key,沒有另外的「內部 key」。
  • 它的公鑰(.ssh/id_ed25519.pub,不是機密)透過 main.tf 的 openstack_compute_keypair_v2.k8s 註冊進 OpenStack,由 Nova 在開機當下統一埋進全部 節點(包含 bastion)的 authorized_keys——不需要任何 事後的 bootstrap 步驟,也沒有雞生蛋蛋生雞的問題。
  • 私鑰只有一份加密來源,不是本機檔案: group_vars/all/vault.yml 裡一個叫 vault_ssh_private_key 的 ansible-vault 加密變數, 密碼放在 .env 的 ANSIBLE_VAULT_PASSWORD (同樣被 .gitignore 排除)。以前(舊版)這裡另外還有 一份 .ssh/id_ed25519 私鑰檔案,已經拿掉——兩份加密 內容各自獨立維護,遲早會有一邊改了忘了改另一邊、悄悄不同步的 風險,不值得為了「檔案 vs. 變數」兩種形式各留一份。管理這唯一 來源用 make key-encrypt KEY=/path/to/private_key(順便 重新產生 .ssh/id_ed25519.pub)、 make key-decrypt(印私鑰到 stdout);背後是 scripts/encrypt_key.sh/scripts/decrypt_key.sh, 本機沒裝 ansible-vault 的話會自動 fallback 成用一個 固定 tag、靠 docker layer cache 重跑不用重新 pip install 的一次性 image(ansible-vault-local)來加解密。
  • 這唯一一份來源被兩條完全獨立的路徑消費。第一條:筆電直接 SSH/rsync/scp 到 bastion(make ssh、 scripts/ansible.sh 裡的 SSH_OPTS)—— scripts/decrypt_key.sh 在每次執行時解密出一份用完即丟 的暫存拷貝,只給這兩支工具自己連 bastion 用。
  • 第二條:ansible 內部連任何節點(包含 bastion 自己),完全不會碰上面那份暫存拷貝。vault.yml 這個 檔案本身跟著 ansible/ 整包 rsync/COPY 進 image,不需要 額外掛載;roles/bastion_access 的第一個 play 用 connection: local 執行(不透過 SSH),把 vault_ssh_private_key 這個變數寫進 bastion 掛進容器的 ~/.ssh/id_ed25519、~/.ssh/config—— docker run 把 bastion 的 ~/.ssh 整個 資料夾讀寫掛進容器自己的 ~/.ssh,容器內的本地寫入就 等於直接寫進 bastion 磁碟,避開「還沒有 key 就沒辦法 SSH 連 bastion 去放 key」的雞生蛋問題。之後任何一個 host/group 都不設定 ansible_ssh_private_key_file,連線全部靠這份 ~/.ssh/config 解出私鑰路徑,跟一個人手動從 bastion ssh 到其他節點走的是同一條路。ansible.cfg 的 vault_password_file 指向容器內固定掛載的密碼檔,讓 ansible/ansible-playbook 不管是 scripts/ansible.sh 自動跑、還是手動 docker run 進容器自己下指令,都能解密 vault_ssh_private_key(也可以用 --vault-password-file 明確覆蓋)。

連線用 mgmt-net,不是走 jump host

Ansible 實際上在 bastion 的容器裡執行,而 bastion 跟其他所有節點 都在同一個 mgmt-net(192.168.200.0/24)flat 網段上, 可以直接連,不需要任何 ProxyJump。「需要 jump host」 只發生在「從你的筆電連到 bastion 以外的節點」這種情境——現在整條路徑是 「筆電 → bastion → 容器內直連」,中間只有一次 SSH(筆電到 bastion), bastion 到其他節點是容器內部直連 mgmt-net,不是又跳一次 SSH。

資料夾結構

ansible/
ansible/
├── ansible.cfg               # inventory/roles 路徑、stdout_callback 等
├── requirements.yml           # collection 依賴
├── Dockerfile                 # 執行環境,在 bastion 上 build
├── inventory/
│   ├── generate_inventory.py # 從 terraform output 產生 hosts.ini
│   ├── hosts.ini              # 自動產生(.gitignore 排除)
│   └── group_vars/all/
│       ├── main.yml           # 公開的共用變數(見下方)
│       ├── secrets.yml        # 機密變數,.gitignore 排除
│       └── secrets.yml.example# 範本,提交進 git
├── playbooks/                 # 每個 playbook 對應一個「你會下的指令」
└── roles/                     # 每個 role 對應一個元件,後面每頁一個

group_vars/all/main.yml 是整個框架的「單一事實來源」—— apiserver_hostname、kubernetes_minor_version、 bgp_asn(跟 Terraform 的 var.bgp_asn 手動保持 同步,ansible 沒辦法直接讀 terraform 變數)、cluster_pod_cidr、 service_cidr、ingress_wildcard_hostname 全部 在這裡定義一次,被多個 role 共用,不會出現「同一個值在兩個地方各寫 一份、改一邊忘了改另一邊」的問題——這個原則在 Role: cilium 頁面會看到具體踩過的坑 (CRI-O 版本 vs kubeadm 版本沒對齊)。

為什麼是 group_vars/all/main.yml,不是單一的 group_vars/all.yml

這是加入 cloudflare_tunnel role 時,為了處理 Cloudflare Tunnel token 這種不能進 git 的 機密值,重新拆出來的結構。

Bug:直接把機密另存成 group_vars/secrets.yml 這種扁平檔案,永遠不會被自動載入——第一版直覺地在 group_vars/ 底下(跟原本的 all.yml 同一層) 多開一個 secrets.yml,實測整個叢集重建時直接 cloudflare_tunnel_token is undefined。根因是 ansible 的 group_vars/<name>.yml 自動載入機制, <name> 必須對應到一個真正存在的 inventory group——沒有一個叫做「secrets」的 group,這個 檔案名稱對 ansible 而言毫無意義,靜靜地被忽略,不會報錯提醒你。

修法是改用 ansible 支援的「每個 group 一個目錄」 寫法:把原本的 group_vars/all.yml 用 git mv 搬進 group_vars/all/main.yml, 機密另外放同一個目錄底下的 group_vars/all/secrets.yml ——兩個檔案都對應到真正存在的 all group,ansible 會 自動合併載入 all/ 目錄底下的所有 .yml 檔案,不需要額外的 vars_files include,同時達成「公開變數跟機密變數的檔案分開放、機密檔案單獨 gitignore」的目標。

真正的機密值只存在 group_vars/all/secrets.yml (gitignored),git 裡只留一份 secrets.yml.example 範本,寫變數名稱跟一個明顯的佔位值,不含真正的 token——這個約定 在 Role: cloudflare_tunnel 有完整說明,跟這個專案處理 SSH 私鑰的方式是同一套邏輯。

k8s/nfs-csi.yml部署 csi-driver-nfs,提供 nfs-csi/nfs-csi-retain 兩個 RWX StorageClass,背後接 bastion/nfs-server.yml 的 NFS export
k8s/vault-secrets-operator.yml裝 vault-secrets-operator,讓任何 namespace 都能用 VaultStaticSecret 掛載 bastion/vault.yml 裝的 Vault,見 Role: vault。前置條件是 bastion/vault.yml 已經跑過

裝一個全新叢集,現在只要兩個聚合 playbook 各跑一次: bastion.yml(不要求叢集已存在,kubeconfig.yml 那步會安全跳過)→ k8s.yml(內部順序是 crio.yml(kubeadm 需要先有 container runtime)→ apiserver-lb.yml → kubeadm.yml(結束時把 kubeconfig 裝回 bastion)→ cilium.yml → smoke-test.yml → node-labels.yml → istio.yml → cert-manager.yml(Gateway 的 443 server block 要靠這一步簽出來的憑證才會真的生效)→ bastion/cloudflare-tunnel.yml(叢集現在活了,這裡是它第一次 真的部署成功的時間點)→ dashboard.yml / kube-prometheus-stack.yml / demo-app.yml / showcase.yml(這幾個先後順序不重要,互相獨立,都只是掛一個 新的 VirtualService 到同一個共用 Gateway 上)→ nfs-csi.yml → docs-site.yml(這步要排在 nfs-csi.yml 之後—— 用一顆普通的 nfs-csi 動態佈建 PVC,NFS export 只能經由 PVC 存取,不允許原生 nfs: volume 繞過 roles/nfs_csi_driver 的網路存取限制;內容用 kubectl exec/kubectl cp 經 Kubernetes API 寫進 PVC,不直接碰 bastion 上 PVC 背後實際落地的目錄,細節見 roles/docs_site)→ oidc-auth.yml → oidc-rbac.yml)。不需要在 k8s.yml 跑完後回頭 重跑 bastion.yml。Cloudflare 那邊的 DNS/Tunnel ingress/Access 設定不在這個順序裡——那些是手動用 Cloudflare API 設一次就永久生效,不需要每次重建叢集都重做,見 Cloudflare 手動設定清單。 完整的稽核過程見 bootstrap-order-audit.md。

只有 bastion 單獨重建(叢集其他節點都還活著,例如改 terraform.tfvars 的 data_volumes 導致 bastion 的 boot_index=0 block_device 變了、強制 replace):新的 bastion 開機時 Nova 會自動重新埋進同一把 key(只要 vault_ssh_private_key/.ssh/id_ed25519.pub 沒換),不需要任何額外的信任步驟,直接跑一次 bastion.yml 就好——不需要也不應該重跑整個「全新叢集」順序,叢集本身的狀態 沒有變。

bastion-access:讓 bastion 自己也能 SSH 到所有節點

原本的設計裡,只有你的筆電需要能 SSH 到 bastion,bastion 到其他 節點是靠 ansible-runner 容器內的 key 直連(見上方「私鑰處理」)。 這個 role 額外做的事:把同一把 key(從 vault_ssh_private_key 這個變數讀出來,使用者的真實私鑰)也放一份到 bastion 自己的 ~/.ssh/id_ed25519,並寫一份 ~/.ssh/config (StrictHostKeyChecking accept-new),讓使用者 直接登入 bastion 之後,不透過 ansible-runner 容器,也能 手動 SSH 到任何一台節點做臨時的除錯——這是操作便利性的需求,跟 「ansible 怎麼執行」是兩件事,所以獨立成一個小 role,單獨一個 playbook,不是塞進其他 role 裡。
