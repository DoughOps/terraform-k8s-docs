叢集元件 Role: crio

這個 role 在所有 k8s_nodes 上安裝 CRI-O，這包含 master、l4 和 ap，不含 tor 和 bastion，作為 container runtime。它是 k8s.yml 建置順序的第一步，不依賴其他 role，後面的 kubelet、kubeadm 都要等 CRI-O 起來才能跑。範圍只到「CRI-O 本身裝好、設定對」，kubeadm、kubelet 和 crictl 屬於 Role: kubelet。

playbook 是 playbooks/k8s/crio.yml，role 在 ansible/roles/crio/。CRI-O 和 containerd 都符合 CRI 規範，也都被 kubeadm 支援。CRI 全名是 Container Runtime Interface。這裡選 CRI-O，因為它每個 minor 版本都對應一個 Kubernetes minor，版本相容性很好判斷。

現在的設定

項目值為什麼
kernel moduleoverlay、br_netfilter，並寫入 /etc/modules-load.d/crio.confoverlay 是預設 storage driver 疊檔案系統層需要的。br_netfilter 讓經過 Linux bridge 的封包也會被 netfilter 規則檢查。寫進 modules-load.d 才能在重開機後自動載入
sysctlnet.bridge.bridge-nf-call-iptables = 1、net.bridge.bridge-nf-call-ip6tables = 1、net.ipv4.ip_forward = 1，寫在 /etc/sysctl.d/99-kubernetes-cri.conf這是 Kubernetes 官方列出的 container runtime 共通前提。CRI-O 是第一個需要它們的元件，所以放在這個 role
apt repoisv:/cri-o:/stable:/{version}/deb/（download.opensuse.org 的 OBS 專案）CRI-O 官方現在建議的安裝來源，取代舊的個人 repo
crio_version{{ kubernetes_minor_version }}，目前是 v1.34CRI-O、kubeadm、kubelet 共用同一個版本變數，改一次就同步，不會版本錯配

cgroup driver 要明確設定

kubelet 從 1.22 起，新叢集預設使用 systemd 作為 cgroup driver，這些節點本身也是 cgroup v2。但 CRI-O 不會偵測 kubelet 的選擇，它有自己的預設值。兩邊不一致時，kubeadm init 和 kubeadm join 會直接失敗。

設定放在 crio.conf.d 的 drop-in，不直接改 /etc/crio/crio.conf，因為主設定檔在套件升級時有被覆蓋的風險。檔案變動會 notify 「重啟 crio」handler，讓設定真的生效。

節點上的 /etc/crio/crio.conf.d/10-cgroup-manager.conf
[crio.runtime]
cgroup_manager = "systemd"

ip_forward 設兩次

net.ipv4.ip_forward 在跑 FRR 的節點上，cloud-init 階段已經開過（見 FRR / iBGP Fabric）。這裡用另一個檔案 99-kubernetes-cri.conf 再宣告一次同樣的值，兩份設定不衝突，只是來源不同層。

加入 apt repo

安裝流程是三步：下載 GPG key、轉成 keyring 格式、加入 apt source。

roles/crio/tasks/main.yml（精簡）
- shell: curl -fsSL {{ crio_repo_key_url }} | gpg --dearmor -o {{ crio_apt_keyring }}
  args: { creates: "{{ crio_apt_keyring }}" }   # 冪等：keyring 檔案存在就不重跑
- apt_repository:
    repo: "deb [signed-by={{ crio_apt_keyring }}] {{ crio_repo_url }} /"
    filename: cri-o

已知限制與 workaround

apt_repository 已標示 deprecated

ansible-core 2.19 還支援 apt_repository，但它已標成 deprecated，預計 2.25 移除。官方建議改用 deb822_repository。

目前沒有換。isv:/cri-o:/stable 是 flat repo，URL 結尾是單一 /，沒有 dists/<suite>/<component> 結構。deb822_repository 對這種格式的參數對應尚未驗證，而 apt_repository 已照 CRI-O 官方文件驗證過可以運作。Role: kubelet 的 Kubernetes apt repo 有同樣的取捨。ansible-core 要移除它之前，兩個 role 都要一起改。

實測踩到的 bug

#27 · 升級 CRI-O 1.34 後 crictl pull 短名稱失敗

  • 症狀：k8s/smoke-test.yml 的跨節點 pod 測試開始失敗。手動重現：
    節點上
    $ crictl pull busybox:1.36
short name mode is enforcing, but image name busybox:1.36 returns
ambiguous list
  • 根因：CRI-O 1.34 底層的 containers/image 函式庫，把 short-name-mode 預設改為 enforcing。即使 unqualified-search-registries 只有 docker.io 一個 registry，它也不會替未限定名稱補全成 docker.io/library/busybox:1.36。這是防止同名映像檔在不同 registry 之間被劫持的安全機制，設定本身沒有寫錯。
  • 修法：在 /etc/containers/registries.conf.d/10-short-name-mode.conf 放一個 drop-in，明確設 short-name-mode = "permissive"，遇到 ambiguous 名稱時以搜尋清單的第一個 registry 補全。drop-in 放在獨立檔案，不動 CRI-O 套件自己安裝的 crio.conf，那個檔案是 unqualified-search-registries 的來源，套件升級時可能被覆蓋。修法先用 crictl pull 手動驗證過，才寫進 role，並 notify 重啟 crio。
  • 怎麼確認修好：在節點上重跑 crictl pull busybox:1.36 成功，或重跑 smoke-test。
  • 相關：Bug #26 同樣是升級 minor 版本才暴露，見 Role: kubelet。

驗證方式

role 最後一步執行 crio version，並標記 changed_when: false，只當驗證，不算變更。這步能確認 CRI-O daemon 真的回應，而不只是套件裝好。

預期結果：task 成功，輸出 CRI-O 的版本資訊。版本號的 minor 和 kubernetes_minor_version 一致。完整的叢集層級驗證見測試與 smoke-test。驗證順序是先在單一節點測試，再套用到全部 k8s_nodes，最後二次執行確認冪等。
