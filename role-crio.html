Ansible 自動化Role: crio

在 k8s_nodes(masters/lbs/workers)上安裝 CRI-O 當 container runtime。這個 role 的範圍刻意畫得很窄:只到「CRI-O 本身裝好、 設定對」,kubelet/kubeadm/crictl 是另一個 role 的責任(見 Role: kubeadm)。playbook 是 playbooks/k8s/crio.yml,role 檔案在 ansible/roles/crio/。

為什麼選 CRI-O,不是 containerd

兩者都是符合 CRI(Container Runtime Interface)規範、kubeadm 官方支援的 runtime。這個專案選 CRI-O 是延續 Red Hat/Kubernetes 生態圈常見組合的選擇, 而且 CRI-O 的版本release 節奏直接對齊 Kubernetes minor version(每個 k8s minor 都有一個對應的 CRI-O minor),版本相容性判斷比較直覺 ——見下方版本對齊的設計。

安裝前的兩組前提條件

Kernel module:overlay、br_netfilter

roles/crio/tasks/main.yml
- community.general.modprobe:
    name: "{{ item }}"
    state: present
  loop: [overlay, br_netfilter]

overlay 是 CRI-O 預設的 storage driver 需要的檔案系統模組 (容器的分層檔案系統靠它疊起來);br_netfilter 讓經過 Linux bridge 的封包也會被 iptables/netfilter 規則檢查——沒有這個模組, kube-proxy 之後裝的 iptables 規則對「橋接過去」的封包不會生效。 兩者都用 copy 額外寫進 /etc/modules-load.d/crio.conf, 確保重開機後這兩個模組還是會自動載入,不是只有這次執行當下 load 一次。

sysctl:bridge 流量要過 iptables、開 ip forward

/etc/sysctl.d/99-kubernetes-cri.conf
net.bridge.bridge-nf-call-iptables = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward = 1

這三行是 Kubernetes 官方文件明列的「任何 container runtime 的共通 前提條件」,不是 CRI-O 專屬——放在這個 role 裡是因為時序上 CRI-O 是第一個需要它們的元件(kube-proxy/kubelet 之後才裝)。 net.ipv4.ip_forward 這裡再設一次是保險:k8s-net 上 跑 FRR 的節點在 cloud-init 階段就已經開過(見 FRR / iBGP Fabric),這裡用不同的 sysctl 檔案(99-kubernetes-cri.conf vs cloud-init 寫的 /etc/sysctl.conf)再宣告一次同樣的值,兩份設定不衝突, 只是來源不同層,刻意不去重複利用同一個檔案。

官方 apt repo:isv:/cri-o:/stable

CRI-O 官方現在建議的安裝方式是 download.opensuse.org 底下的 OBS(Open Build Service)專案 isv:/cri-o:/stable:/{version}/deb/,取代舊版文件常見的 個人 repo。標準的三步驟:下載 GPG key、轉成 keyring 格式、 加入 apt source。

roles/crio/tasks/main.yml(精簡)
- shell: curl -fsSL {{ crio_repo_key_url }} | gpg --dearmor -o {{ crio_apt_keyring }}
  args: { creates: "{{ crio_apt_keyring }}" }   # 冪等:keyring 檔案存在就不重跑

- apt_repository:
    repo: "deb [signed-by={{ crio_apt_keyring }}] {{ crio_repo_url }} /"
    filename: cri-o

為什麼用已經 deprecated 的 apt_repository,不是官方建議的 deb822_repository:ansible-core 目前(2.19) 還支援 apt_repository,只是標成 deprecated、預計 2.25 移除。這個專案刻意先不換——deb822_repository 對這種「flat repo」格式(isv:/cri-o:/stable 的 URL 結尾是單一 /,不是傳統 dists/<suite>/<component> 結構)的參數對應還沒把握,而 apt_repository 已經照 CRI-O 官方文件驗證過可以正常動作。這是一個記錄下來的技術債,不是沒注意到 deprecation warning。

cgroup driver 對齊:CRI-O 這邊要明確設,不能靠猜

Kubernetes 的 kubelet 從 1.22 起,新叢集預設用 systemd 當 cgroup driver(這台機器本身就是 cgroup v2,systemd 統一管理 cgroup 資源階層)。但 CRI-O 不會自動偵測、對齊 kubelet 的選擇 ——它有自己的預設值,如果不明確設定,CRI-O 跟 kubelet 可能各自用不同的 cgroup driver 管理同一組容器資源,kubeadm init/join 會直接因為這個不一致而失敗。

/etc/crio/crio.conf.d/10-cgroup-manager.conf
[crio.runtime]
cgroup_manager = "systemd"

用 crio.conf.d 底下的 drop-in 檔案,不是直接改 /etc/crio/crio.conf——drop-in 目錄的設計本來就是給 「套件升級時不想被覆蓋掉的自訂設定」用,直接改主設定檔在套件升級時 有被蓋掉的風險。這個檔案改變時會觸發 notify: 重啟 crio handler,確保設定真的生效,不是寫了檔案但 daemon 還在用舊設定跑。

版本對齊:crio_version 從哪來

roles/crio/defaults/main.yml
crio_version: "{{ kubernetes_minor_version }}"   # 不是寫死的字串

crio_version 直接引用 group_vars/all/main.yml 的 kubernetes_minor_version (目前 v1.34),不是各自寫一份獨立的版本號。CRI-O 的版本節奏跟 Kubernetes minor version 對齊(每個 k8s 1.x 都有對應的 CRI-O 1.x),讓兩邊共用同一個變數來源,改一次 kubernetes_minor_version 就能同時決定 CRI-O 跟 kubeadm/kubelet 要裝哪個版本,不會有「改了 k8s 版本卻忘記同步改 CRI-O 版本」這種版本錯配的風險——這正是後面 Role: cilium 頁面會提到、當初刻意 要避免的那類問題。

安裝 task 也是 state: latest,不是 state: present——CRI-O 套件沒有像 kubelet 那樣被 dpkg_selections 鎖住,但 state: present 一樣是「有裝就好」的語意,升級 kubernetes_minor_version 之後如果安裝 task 不改, 即使 crio_version 已經連動變成 v1.34、repo URL 也指向 v1.34,已經裝好的 v1.31 套件也不會被自動換掉。跟 Role: kubelet 的 kubeadm/kubelet/ kubectl 是同一個模式的 bug,修法也一樣:改成 state: latest,靠版本綁定的 repo URL 保證「latest」 不會跳出預期的 minor version。

CRI-O 1.34 新增的坑:short-name-mode 預設拒絕未限定的 image 名稱

升級到 CRI-O 1.34 之後,k8s/smoke-test.yml (見 測試 / smoke-test)裡原本能跑的 跨節點 pod 測試開始失敗:

$ crictl pull busybox:1.36
short name mode is enforcing, but image name busybox:1.36 returns
ambiguous list

直覺的第一反應是「unqualified-search-registries 裡明明 只設了一個 docker.io,應該不會 ambiguous」——但 CRI-O 1.34(底層是 containers/image 這個 library)的 short-name-mode 這一版預設是 enforcing ,即使搜尋清單裡只有一個 registry,也拒絕自動幫未限定名稱 (像 busybox:1.36,沒有寫完整的 docker.io/library/busybox:1.36)補上完整路徑——這是 containers/image 為了防止「同名映像檔在不同 registry 之間被劫持」 的安全機制,行為變嚴了,不是這個專案的設定寫錯。

/etc/containers/registries.conf.d/10-short-name-mode.conf
short-name-mode = "permissive"

新增一個 drop-in 檔案,把 short-name-mode 明確設回 permissive(遇到 ambiguous 名稱時,直接用搜尋清單的 第一個 registry 補全,不拒絕)。修法先用 crictl pull 手動驗證過才寫進 role,notify: 重啟 crio確保 daemon 真的套用新設定。

驗證步驟

role 的最後一步是 crio version(changed_when: false, 純驗證不算變更),確認 CRI-O daemon 真的有回應,不是只是套件裝了 但服務起不來。完整的驗證紀錄(單一節點先測、再全 k8s_nodes 滾出去、二次執行確認冪等)見 測試 / smoke-test。
