總覽從零開始建置

這頁是整個專案唯一一份「從什麼都沒有,到一個完整能用的叢集」的 操作清單,把散落在 CLAUDE.md、Terraform / OpenStack、ansible/README.md、cloudflare/README.md 裡的片段收斂成一條照著做就能走完的路。請照這頁操作,不要照 repo 根目錄的 README.md。

整條路徑分四段,順序不能跳: ① 本機的 Terraform 建 OpenStack VM/網路 → ② 本機的 Terraform(獨立的 cloudflare/ 目錄)建 Cloudflare 的 DNS/Tunnel/Access → ③ 把 ② 的輸出值填進 ansible 變數 → ④ 透過 scripts/ansible.sh 觸發跑在 bastion 上 Docker 裡的 Ansible,依序把 k8s + 所有周邊裝起來。你的筆電只直接跑 Terraform 和 scripts/ansible.sh,不需要在筆電上裝 Ansible、 kubectl、helm。

前置需求

項目用途
本機裝 Terraform(>= 1.5)建 OpenStack 資源跟 Cloudflare 資源都要用,兩個獨立目錄各自 init。
一個 OpenStack 專案帳號要有建 VM/網路/浮動 IP 的權限。這個 lab 假設的是「一般權限 tenant」,沒有 LBaaS/routed public prefix 也能跑(見 總覽的核心命題)。
一個網域 + 接進 Cloudflare免費方案就夠(Universal SSL 涵蓋第一層萬用字元)。對外入口是 Cloudflare Tunnel,不需要在 OpenStack 開任何 inbound port。
一個 Cloudflare API Token給 cloudflare/ 這個 Terraform module 用,見下面第 4 步的權限範圍。
一個 GitHub organizationCloudflare Access 的登入身份來源(github-organization policy)——也可以換成其他 IdP,但這個 lab 的既有設定是 GitHub。

Step 1 · OpenStack 認證(clouds.yaml)

openstack/main.tf 的 provider "openstack" { cloud = "openstack" } 讀的是標準 OpenStack SDK 的 clouds.yaml,不是 os_username/os_password 這種 variable—— 這個檔案放在 openstack/ 目錄,被 .gitignore 排除,不會進版控。 向你的 OpenStack 服務商要一份 clouds.yaml(通常在 Horizon dashboard 的「API Access → Download OpenStack RC File / clouds.yaml」), 放到 openstack/ 目錄,並確認頂層的 cloud 名稱是 openstack (不是的話要嘛改檔案裡的 key,要嘛改 openstack/main.tf 的 cloud = "..."):

clouds.yaml(結構示意,值換成你自己的)
clouds:
  openstack:
    auth:
      auth_url: https://<your-openstack>:5000
      username: <you>
      password: <your-password>
      project_id: <project-id>
      project_name: <project-name>
      user_domain_name: Default
    region_name: RegionOne
    interface: public
    identity_api_version: 3

Step 2 · SSH Keypair

repo 裡已經有一組 .ssh/id_ed25519.pub(被 .gitignore 排除,不是因為內容敏感,純粹跟著整個 .ssh/ 目錄一起)——這是 所有節點(包含 bastion)共用的唯一一把私鑰的公鑰,沒有另外的 「內部 key」,這是刻意的設計決定(這把 key 只給這個 lab 使用,私鑰之後也會 落地在 bastion 上,外流風險可接受)。私鑰本身不是檔案,只有 一份加密來源:ansible/inventory/group_vars/all/vault.yml 裡的 vault_ssh_private_key 這個 ansible-vault 加密變數,密碼放進 .env 的 ANSIBLE_VAULT_PASSWORD(同樣被 .gitignore 排除)。如果是全新環境,自己產一組新的:

產生 keypair、寫進密碼、加密
$ ssh-keygen -t ed25519 -f /tmp/id_ed25519 -N ""
$ echo 'ANSIBLE_VAULT_PASSWORD="'"$(openssl rand -base64 32)"'"' >> .env
$ make key-encrypt KEY=/tmp/id_ed25519
$ rm /tmp/id_ed25519 /tmp/id_ed25519.pub

make key-encrypt 把明碼私鑰包裝進 vault_ssh_private_key、加密寫進 vault.yml,同時 重新產生 .ssh/id_ed25519.pub(給下面 Step 4 用)——加密之後 /tmp 底下那份明碼副本就用不到了,可以刪掉。反過來要看私鑰內容 (除錯、或想手動 ssh-add)用 make key-decrypt, 私鑰會印到 stdout。

這唯一一份加密來源之後被兩條完全獨立的路徑消費——筆電直接 ssh 到 bastion (scripts/ansible.sh、make ssh)解密出用完即丟的 暫存拷貝;ansible 內部連任何節點另外走一條完全不同的路,不會用到前者解密出來 的暫存檔。細節見 Ansible 框架設計的 「私鑰處理」一節。不需要手動上傳到 OpenStack——openstack/main.tf 的 openstack_compute_keypair_v2.k8s 這個 resource 會在 Step 4 跑 terraform apply 時自動把公鑰註冊進去, 名稱固定是 k8s,對應 terraform.tfvars 裡每個 VM 的 keypair_name。

Step 3 · terraform.tfvars:定義要建哪些 VM

openstack/terraform.tfvars(這個檔案本身有進版控, 跟一般「tfvars 含密鑰不能進版控」的慣例不同——這裡面沒有任何密鑰,只有拓樸定義) 已經是目前這個 lab 實際在跑的拓樸(見 總覽的表格: 1 台 tor、1 台 bastion、3 台 ms-*、 2 台 l4-*、2 台 ap-*)。全新環境的話,檢查/調整每個 VM 的 vm_flavor_name/vm_image_name 對不對得上你的 OpenStack 專案有的 flavor/image,keypair_name 維持 "k8s"(對到 openstack/main.tf 裡 openstack_compute_keypair_v2.k8s 的名稱,見 Step 2), 其餘欄位照抄即可。新增/刪除節點只要改這個檔案裡的 vms map,細節見 Terraform / OpenStack。

Step 3.5 · State backend 的憑證(AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY)

openstack/、cloudflare/ 這兩份 Terraform state 都存在 跟你 OpenStack 帳號同一個環境的 S3 相容 object storage(不是本機檔案), Step 4/Step 6 的 terraform init 都要先有這組憑證才連得上。用 Keystone 的 OS-EC2 credentials API 簽發(跟 Step 1 的 clouds.yaml 帳密是同一個身分,只是換一種呈現形式給 S3 協定用):

簽發 EC2 access/secret key,存進 .env
POST {auth_url}/v3/users/{user_id}/credentials/OS-EC2
Header: X-Auth-Token: <先用 clouds.yaml 帳密換到的 token>
Body:   {"tenant_id": "<project_id>"}
# 回應的 access/secret 兩個欄位,寫進 .env(gitignored):
$ echo 'AWS_ACCESS_KEY_ID=...' >> .env
$ echo 'AWS_SECRET_ACCESS_KEY=...' >> .env

下面 Step 4/Step 6 的指令、以及之後 make ssh/ scripts/ansible.sh/scripts/build.sh/ scripts/teardown.sh/scripts/sync-cloudflare-secrets.sh 這些會呼叫 terraform output/plan/apply 的 script,都會自動從 .env 讀這兩個值、export 出來,不用每次手動 export。細節見 docs/superpowers/specs/2026-08-12-terraform-state-s3-backend-design.md。

Step 4 · 跑 Terraform,建出 OpenStack 資源

openstack/ 目錄
$ cd openstack
$ terraform init
$ terraform plan
$ terraform apply

建出網路(k8s-net/mgmt-net)、每台 VM、bastion 的 floating ip。跑完之後 terraform output bastion_floating_ip 應該有值——這是唯一的 SSH 進入點,後面 make ssh/ scripts/ansible.sh 都靠 terraform output 動態拿 這個值,不用自己記 IP。

Step 5 · Cloudflare 那一側:網域 + Identity Provider(手動,兩件事,只做一次)

這兩件事沒有自動化工具能繞過(原因見下方),要先手動做完,Step 6 的 Terraform 才有東西可以接。但這不影響 CI/CD 自動建環境 ——兩件事都是綁在網域/GitHub org 本身、不是綁在單次環境建置的 一次性 bootstrap:人工做一次,把拿到的 ID 存進 CI 的 secret store,之後每次自動建置只是讀取既有值餵給 Terraform variable, 不用重做。

🌐

1. 網域接進 Cloudflare

Cloudflare dashboard 加入你的網域這個 zone → 把註冊商的 nameserver 改成 Cloudflare 指定的兩個 → 等 zone 狀態變成 active。這是 註冊商那邊的操作,不在 Cloudflare API 管得到的範圍,而且改一次之後 不會再變。

🔑

2. 連接 GitHub Identity Provider

Zero Trust dashboard → Settings → Authentication → 新增 GitHub 登入方式,跑一次瀏覽器 OAuth 授權流程,拿到一組 github_idp_id。 GitHub OAuth App 的 client secret 本來就只能在瀏覽器裡跑一次授權拿到, 不是 Terraform provider 刻意不支援,是 GitHub 平台本身沒有 API-only 的路。

Step 6 · cloudflare/ Terraform:建 DNS/Tunnel/Access

獨立目錄、獨立 state,跟 OpenStack 的 main.tf 完全分開(不同 provider,互不影響)。先填 cloudflare/terraform.tfvars(account_id、 zone_id、zone_name、Step 5 拿到的 github_idp_id、GitHub org 名稱、team name、你要用的子網域),再匯出一個只有必要權限的 API Token(不要用 Global API Key):

PermissionScope
Account → Access: Apps and Policies → Edit整個帳號
Account → Access: Organizations, Identity Providers, and Groups → Edit整個帳號
Account → Cloudflare Tunnel → Edit整個帳號
Zone → DNS → Edit限定你的 zone(不要給全部 zone)
User → API Tokens → Edit這顆 token 自己

最後一個權限(User → API Tokens → Edit)是給 cloudflare/api_token.tf 用的——讓這顆 token 自己建出 Step 7 需要的 cloudflare_origin_ca_api_token,不用另外再去 dashboard 手動點一個 scoped token,CI/CD 無人值守建環境才不會卡在這一步。這是刻意的取捨,細節見 cloudflare/api_token.tf 開頭的說明。

cloudflare/ 目錄
$ export CLOUDFLARE_API_TOKEN="<上面那組 token>"
# 只放進環境變數,不要寫進任何 .tf/.tfvars 檔案
$ cd cloudflare
$ terraform init
$ terraform plan
$ terraform apply

建出 2 條 Cloudflare Tunnel(cluster 內用的 + bastion SSH 用的)、對應的 Access Application/Policy、DNS CNAME、Zero Trust org 設定。完整的變數說明、 resource 對照表見 cloudflare/README.md。

Step 7 · 把 Terraform 的輸出接回 Ansible 變數

先複製範本建立 secrets.yml(這個檔案不進版控):

repo 根目錄
$ cp ansible/inventory/group_vars/all/secrets.yml.example ansible/inventory/group_vars/all/secrets.yml

這 6 個 Terraform output 名稱刻意跟要填入的 ansible 變數名稱完全一致 (見 cloudflare/outputs.tf 開頭的說明),可以直接跑 scripts/sync-cloudflare-secrets.sh 自動讀值寫回去 ——敏感值全程只留在 shell 變數裡,不印到終端機/貼進聊天記錄:

repo 根目錄
$ scripts/sync-cloudflare-secrets.sh

不想用 script、想手動個別貼的話,也可以自己在 cloudflare/ 目錄下用 terraform output -raw <name> 個別讀出來貼進檔案:

Terraform output填進哪個檔案的哪個變數
cloudflare_tunnel_tokensecrets.yml → cloudflare_tunnel_token
cloudflare_bastion_ssh_tunnel_tokensecrets.yml → cloudflare_bastion_ssh_tunnel_token
grafana_oidc_client_secretsecrets.yml → grafana_oidc_client_secret
cloudflare_origin_ca_api_tokensecrets.yml → cloudflare_origin_ca_api_token
cloudflare_access_oidc_client_idmain.yml → cloudflare_access_oidc_client_id
grafana_oidc_client_idmain.yml → grafana_oidc_client_id

cloudflare_origin_ca_api_token 是由 cloudflare/api_token.tf 自動建出來的 scoped token(只有 「Zone → SSL and Certificates → Edit」、範圍限定你的 zone),給 roles/cert_manager 簽 wildcard 憑證用——不是上面 Step 6 那個 CLOUDFLARE_API_TOKEN,是另一個,但現在不用再去 dashboard 手動點,CI/CD 無人值守建環境也能拿到。

另外幾個值目前不在 cloudflare/ 這個 Terraform module 的範圍裡(script 也不會動它們),要另外手動建:

  • secrets.yml → oidc_admin_emails:哪些 email 登入後拿 cluster-admin(其他人自動唯讀),自己列一份清單。
  • secrets.yml → github_app_id / github_app_installation_id / github_app_private_key:bastion.yml 最後一步 bastion/github-runner.yml 一開始就會檢查這三個值,沒填 (還是 REPLACE_ME)Step 9 執行到那一步會直接 fail。逐欄位 的完整建立步驟(Webhook/Permissions/去哪裡找 Installation ID……)見 Role: github_runner,這裡不重複一份 避免兩邊寫的步驟之後對不上。跟 Step 5 的 GitHub Identity Provider 一樣, GitHub App 建立本來就要跑一次瀏覽器授權,沒有自動化工具能繞過——這是 一次性 bootstrap,綁在 GitHub org 本身,不是每次建環境 都要重做:人工建一次,把這三個值存進 CI 的 secret store,之後自動建 環境只要讀取既有值就好。

main.yml 裡的 cloudflare_access_team_domain、 各服務的 hostname(dashboard_hostname、grafana_hostname 等)也要跟 Step 6 cloudflare/terraform.tfvars 填的值對上,細節見 cloudflare/README.md。

Step 8 · 確認全部節點連得到

因為只有一把 key(見 Step 2),而且 Nova 開機時就已經把它的公鑰埋進 每一台節點(包含 bastion)的 authorized_keys,這裡不需要 額外的 bootstrap 步驟——直接確認連得到就好:

repo 根目錄
$ scripts/ansible.sh ansible all -m ping

全部節點都要回 pong,才能往下走。

Step 9 · Ansible:把 k8s + 所有周邊裝起來

你的筆電不需要裝 Ansible/kubectl/helm—— scripts/ansible.sh 會自動把 ansible/ 整包 rsync 到 bastion,在 bastion 上 build 一個 Docker image,在裡面跑你要的指令, 輸出直接串流回你的終端機。每次執行都會先用 terraform output 重新產生 inventory,所以 VM IP 變了也不用手動改。

健檢(第一次跑之前先確認連得到)
$ scripts/ansible.sh ansible all -m ping

確認全部節點都回 pong 之後,現在只要兩個聚合 playbook 各跑一次,不需要再手動記每個子 playbook 的順序:

兩個聚合 playbook,一次跑完全部
$ scripts/ansible.sh ansible-playbook playbooks/bastion.yml

這時候先別急著跑下一步。 bastion.yml 跑完之後,GitLab 的 doughops group 已經建立好了(bastion/gitlab-cd-repo.yml 建的)。 去 https://gitlab.<your-domain> 網頁 UI 登入 → 左側選 doughops group → Settings → Access Tokens → Add new token:名稱例如 argocd-gitops-reader、Role 選 Reporter、 Scopes 只勾 read_repository、Expiration date 選介面 允許的最遠日期(GitLab 16.0 之後強制要選到期日,沒有「永久不過期」 這個選項)。複製產生的 token 值,填進本機 ansible/inventory/group_vars/all/secrets.yml 的 argocd_gitlab_repo_token 欄位,再往下跑 k8s.yml——k8s/argocd.yml 會讀這個值,幫 ArgoCD 註冊讀取這個 GitLab repo 的憑證(細節見 Role: argocd)。這一步沒做也不會讓 k8s.yml 失敗,只是 ArgoCD 裡 gitops-demo 這個 Application 會顯示 repository 不可存取,之後補填、重跑 k8s/argocd.yml 就會恢復正常。

repo 根目錄
$ scripts/ansible.sh ansible-playbook playbooks/k8s.yml

bastion.yml 不要求叢集已經存在——裡面的 kubeconfig.yml 那步會偵測到叢集還沒建立就安全跳過(不會 報錯中斷後面的步驟)。k8s.yml 內部依序是:

  1. 核心叢集(缺一不可,順序固定) k8s/crio.yml → k8s/nfs-client.yml (裝 nfs-common,晚一點的 nfs-csi.yml/ docs-site.yml 掛 NFS volume 要用到)→ k8s/apiserver-lb.yml → k8s/kubeadm.yml(結束時把 kubeconfig 裝回 bastion)→ k8s/cilium.yml → k8s/smoke-test.yml(裝完先跑一次,確認 iBGP fabric + Pod 跨節點連線真的在動,再往下走)→ k8s/node-labels.yml(幫 workers/ lbs 節點補上 node-role.kubernetes.io/* 標籤,kubeadm 預設只會幫 control-plane 節點打)。
  2. L7 路由 + 加密 + 對外入口 k8s/istio.yml → k8s/cert-manager.yml (cert-manager 需要 istio namespace 先存在,才有地方放簽出來的 TLS Secret)→ bastion/cloudflare-tunnel.yml(需要 Step 7 填好的 secrets.yml;叢集現在活了,這裡是它 第一次真的部署成功的時間點——不需要事後回頭重跑 bastion.yml)。
  3. 內部工具(都需要 istio + cert-manager 先跑過) k8s/dashboard.yml → k8s/kube-prometheus-stack.yml (Hubble UI 是 Cilium 內建的,已經在 k8s/cilium.yml 裝過,不用另外跑)。
  4. 可選(掛在同一個共用 Gateway 上,互相獨立) k8s/demo-app.yml(測試用的 nginx,驗證整條對外路徑真的 通)、k8s/showcase.yml(對外成果展示頁,靜態 HTML)。
  5. 儲存 addon(有先後順序) k8s/nfs-csi.yml(部署 csi-driver-nfs,需要 bastion.yml 的 nfs-server.yml 已經先跑過, 匯出目錄才有東西可掛)→ k8s/docs-site.yml(部署這份技術 文件站本身,PVC 用的 nfs-csi StorageClass 要先裝好, 順序要排在 nfs-csi.yml 之後,不能反)。
  6. Cloudflare Access SSO(需要 Step 7 填好的 AUD/client_id) k8s/oidc-auth.yml → k8s/oidc-rbac.yml (RBAC 要在 apiserver 信任 OIDC 之後才有意義,順序不能反)。

這條清單完整對應 playbooks/k8s.yml 的 import 順序,只是 拆開逐項解釋——想單獨重跑某一段除錯,直接照這個順序個別執行 scripts/ansible.sh ansible-playbook playbooks/k8s/xxx.yml 就好,不用整個 k8s.yml 重來。bastion.yml 底下的 bastion/access.yml、bastion/ssh-tunnel.yml、 bastion/tools.yml、bastion/github-runner.yml 跟叢集建置沒有相依性,隨時可以單獨重跑。完整的順序稽核過程見 bootstrap-order-audit.md。

Step 10 · 驗證

  • scripts/ansible.sh ansible-playbook playbooks/k8s/smoke-test.yml ——節點/系統 pod Ready、apiserver haproxy backend UP、BGP PodCIDR 傳播數量、 跨節點 pod-to-pod 連線,全部自動檢查,可重複執行。
  • 對每個受 Cloudflare Access 保護的 hostname 發請求,應該都拿到 302 導到 Cloudflare 登入頁:curl -I https://test.<your-domain>/。
  • 瀏覽器實際登入一次 Dashboard/Grafana,確認 SSO 正常(細節見 內部工具)。

之後只是想加/刪一個節點,或是 VM 全部重建怎麼辦?

➕

加/刪節點

改 openstack/terraform.tfvars 的 vms map → terraform apply(在 openstack/ 目錄下)。新節點開機時 Nova 就已經把 唯一那把 key 的公鑰埋進去(跟其他節點一樣,沒有另外的內部 key、不需要任何 bootstrap 步驟),直接重跑 scripts/ansible.sh(inventory 自動重新產生) 就好,Cloudflare 那邊完全不用動。

🔄

VM 全部重建(IP 換了、bastion 也換了)

在 openstack/ 目錄下 terraform apply 重建 OpenStack 資源後,新的 bastion 開機時一樣會被 Nova 埋進同一把 key(只要 vault_ssh_private_key/.ssh/id_ed25519.pub 沒換),直接連得到,不需要任何 bootstrap 步驟。secrets.yml/main.yml 裡的值都還有效(Cloudflare 那側的 Tunnel/Access 沒有跟著動), 直接重跑 Step 9 的 Ansible 順序就好,不用碰 Step 5~7。

連 Cloudflare 那側也要重建

Step 6 的 Terraform 重新 apply 之後,token/AUD/ client_id/secret 全部會換新的——一定要照 Step 7 重新填一次, 再重跑 bastion/cloudflare-tunnel.yml/ bastion/ssh-tunnel.yml/k8s/oidc-auth.yml/ k8s/kube-prometheus-stack.yml 這四個 playbook,不然 cloudflared/kube-apiserver OIDC/Grafana SSO 會停留在舊的、已經失效的 身份上。完整的 bug 記錄(兩個 ansible role 原本沒設計成支援 token 輪替,後來補上偵測變更才重啟的邏輯)見 Cloudflare 手動設定清單。
