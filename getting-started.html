開始 從零開始建置

這頁是重建整套環境的完整步驟：10 台 OpenStack VM、BGP fabric、Kubernetes、Cilium、Istio、Cloudflare Tunnel 與周邊服務。適合需要重建環境的團隊成員。個人設定約需 20 分鐘，建置本身約需 1.5 到 2.5 小時，其中大部分是等待。時間都是估計值，視 OpenStack 與網路速度而定。

整條路徑分四段：第一段用 Terraform 建 OpenStack 的 VM 與網路。第二段用 cloudflare/ 的 Terraform 建 DNS、Tunnel 與 Access。第三段把第二段的輸出填進 ansible 變數。第四段由 scripts/ansible.sh 觸發 bastion 上 Docker 裡的 Ansible，依序裝好 Kubernetes 與所有周邊。筆電只直接執行 Terraform 與 scripts/ansible.sh，不需要裝 Ansible、kubectl、helm。

.env 內容

repo 根目錄的 .env 被 gitignore，集中放所有明碼憑證。make ssh、scripts/ansible.sh、scripts/build.sh、scripts/teardown.sh 都會自動讀它。

.env（結構示意）

clouds.yaml

openstack/main.tf 的 provider "openstack" 以 cloud = "openstack" 讀標準 OpenStack SDK 的 clouds.yaml，檔案放在 openstack/，已被 gitignore。頂層的 cloud 名稱必須是 openstack，否則要改檔案裡的 key，或改 main.tf 的 cloud 值。

    region_name: RegionOne

    identity_api_version: 3

S3 state 憑證

openstack/ 與 cloudflare/ 的 Terraform state 都存在 S3 相容的 object storage，不在本機。terraform init 之前必須有這組憑證。它用 Keystone 的 OS-EC2 API 簽發，身分和 clouds.yaml 的帳號相同。

簽發 EC2 access／secret key
POST {auth_url}/v3/users/{user_id}/credentials/OS-EC2
Header: X-Auth-Token: <先用 clouds.yaml 帳密換到的 token>
Body:   {"tenant_id": "<project_id>"}
# 回應的 access 與 secret 兩個欄位，寫進 .env

預期結果：回應含 access 與 secret，分別填入 .env 的 AWS_ACCESS_KEY_ID 與 AWS_SECRET_ACCESS_KEY。失敗時看哪裡：terraform init 回報 backend 認證錯誤時，先確認這兩個值，bucket 與端點的設定見 Terraform state backend。

Step 1 · 確認可以解密

全部節點共用一把 ed25519 key，私鑰與 secrets.yml 都已加密進版控。repo 根目錄的 .ssh/ 只是 scripts/ansible.sh 解密後的快取。設計與風險見密鑰管理。

repo 根目錄
$ make key-decrypt > /dev/null

預期結果：指令成功結束，沒有錯誤訊息。

失敗時看哪裡：找不到 .env 或 裡面沒有 ANSIBLE_VAULT_PASSWORD 代表 .env 還沒設好。本機沒有 ansible-vault 時，第一次執行會多花時間 build ansible-vault-local image。

不需要手動把公鑰上傳到 OpenStack。Step 3 的 terraform apply 會以 openstack_compute_keypair_v2.k8s 自動註冊，名稱固定是 k8s，對應 terraform.tfvars 每個 VM 的 keypair_name。

Step 2 · 確認 terraform.tfvars

openstack/terraform.tfvars 進版控，只含拓樸定義，沒有密鑰。裡面是實際運行的拓樸：1 台 tor、1 台 bastion、3 台 ms-*、2 台 l4-*、3 台 ap-*。只有要加減節點或換 flavor 時才需要修改，keypair_name 維持 "k8s"。

預期結果：git status 顯示這個檔案和團隊的版本一致，或只有你要做的改動。失敗時看哪裡：Step 3 的 terraform plan 會在名稱對不上時報錯。可以用 openstack flavor list、openstack image list、openstack volume type list 確認，節點的設計與加減節點方式見 Terraform / OpenStack。

Step 3 · 建 OpenStack 資源

openstack/ 目錄
# 手動執行 terraform 前，先把 .env 的 AWS_* 匯出到目前 shell
$ set -a; . ../.env; set +a
$ cd openstack
$ terraform init
$ terraform plan
$ terraform apply
$ terraform output bastion_floating_ip

預期結果：terraform apply 需要輸入 yes 確認，約 5 到 10 分鐘完成。建出 k8s-net 與 mgmt-net、10 台 VM、bastion 的 Floating IP。terraform output bastion_floating_ip 印出一個 IP，這是唯一的 SSH 入口，後面的腳本都會動態讀取它。

失敗時看哪裡：bastion 加資料碟時的 400 錯誤與 volume boot 問題見 Bug #31、#32、#33。資源設計與資料碟保護見 資料碟與 prevent_destroy。如果上次是用 make teardown 拆的，資料碟要先 import 回來，見全部拆除。

Step 4 · 建 Cloudflare 資源

cloudflare/ 是獨立的 Terraform module，state 也獨立，和 OpenStack 互不影響。cloudflare/terraform.tfvars 已進版控，內含 account_id、zone_id、zone_name、github_idp_id、github_org_name、team_name 與各服務的 hostname，不用修改。完整變數見 cloudflare/variables.tf。token 放在 .env，不要寫進任何 .tf 或 .tfvars。

cloudflare/ 目錄
$ set -a; . ../.env; set +a
$ cd cloudflare
$ terraform init
$ terraform plan
$ terraform apply

預期結果：約 2 分鐘完成，需要輸入 yes。建出 2 條 Cloudflare Tunnel，一條給叢集，一條給 bastion SSH。也建出 DNS 記錄、各服務的 Access Application 與 Policy、Zero Trust org 設定，以及 scoped 的 cloudflare_origin_ca_api_token。Access 規則的原則見 Access 規則與 bypass 原則。

失敗時看哪裡：Unable to find your Access organization 這類 org 名稱不同步的錯誤，見 Bug #30。token 權限不足時回頭檢查上方權限表。cloudflare/README.md 有變數與資源的完整對照。

Step 5 · 把 Terraform 輸出接回 Ansible 變數

Terraform 輸出有 14 個，名稱刻意和要填入的 ansible 變數相同。8 個進 secrets.yml，內容是 tunnel token、origin CA token 與各服務的 OIDC client secret。6 個進 main.yml，內容是各服務的 OIDC client ID。scripts/sync-cloudflare-secrets.sh 自動讀值寫回，值只留在 shell 變數，不印到終端機。

Step 4 沒有建出新的 Tunnel 或 Application 時，輸出不變，這一步可以跳過。

腳本會自動解密 secrets.yml，更新後重新加密，不用事先解密。機制見密鑰管理。

repo 根目錄
$ scripts/sync-cloudflare-secrets.sh
$ head -n 1 ansible/inventory/group_vars/all/secrets.yml
$ANSIBLE_VAULT;1.1;AES256

預期結果：終端機印出 14 行 已寫入 <name> → ...，最後一行輸出是 vault 檔頭。腳本結尾提示的手動欄位已經填好，不用理會。main.yml 的 client ID 有變動時要一併提交。失敗時看哪裡：terraform output 失敗代表 .env 缺 S3 憑證，或 Step 4 尚未完成。解密失敗代表 ANSIBLE_VAULT_PASSWORD 不對。這些情況下 secrets.yml 都不會被更動。

Step 6 · 執行 bastion.yml

repo 根目錄
$ scripts/ansible.sh ansible-playbook playbooks/bastion.yml

預期結果：第一次執行會先解密私鑰、等 bastion 的 cloud-init 裝完 docker、build 執行環境 image，多花幾分鐘。整體約 20 到 30 分鐘，其中 GitLab 第一次 reconfigure 可能等到約 10 分鐘。結尾 failed=0。叢集尚未建立，kubeconfig.yml 會安全跳過，不算失敗。完成後 bastion 具備 NFS server、Vault、Keycloak、GitLab、GitLab Runner、GitHub runner 與 doughops group。順序與依賴見建置順序。

失敗時看哪裡：github_app_id 這類 REPLACE_ME 的失敗訊息，回 Step 5 補欄位。各 role 的細節見 Role: vault、Role: keycloak / dex、Role: gitlab、Role: github_runner。

第一個 play 寫入的 SSH 身分在 bastion 的磁碟上，之後任何 ad-hoc 指令與 playbook 都沿用同一份。

Step 7 · 確認全部節點連得到

容器連其他節點所用的 SSH 身分，由 bastion.yml 的第一個 play 寫入 bastion。ad-hoc 指令不會執行任何 role，所以這個檢查必須在 Step 6 之後。Nova 開機時已把公鑰寫進每台節點的 authorized_keys，不需要其他 bootstrap。

repo 根目錄
$ scripts/ansible.sh ansible all -m ping

預期結果：10 台節點全部回 pong。失敗時看哪裡：UNREACHABLE 且 Permission denied (publickey)，代表 Step 6 沒有成功跑完 bastion_access，或 ansible/files/ssh/id_ed25519.pub 與建 VM 時註冊的公鑰不同。流程細節見 scripts/ansible.sh 流程。

Step 8 · 建立 GitLab group access token

argocd_gitlab_repo_token 還有效時跳過這一步。需要重建 token 時，這一步必須在 Step 6 之後、Step 9 之前。bastion.yml 的 gitlab-cd-repo.yml 建立 doughops group，token 要掛在這個 group 上。ArgoCD 用它讀取 GitLab 上的私有 repo。

  1. 用瀏覽器開 https://gitlab.dough-ops.com 並登入，選 doughops group → Settings → Access Tokens → Add new token。
  2. 名稱例如 argocd-gitops-reader，Role 選 Reporter，Scopes 只勾 read_repository。
  3. Expiration date 選介面允許的最遠日期。GitLab 16.0 之後強制要選到期日，沒有永久不過期的選項。
  4. 複製產生的 token，用 ansible-vault edit 更新 secrets.yml 的 argocd_gitlab_repo_token。

預期結果：secrets.yml 的 argocd_gitlab_repo_token 已更新，檔案仍是加密狀態。失敗時看哪裡：找不到 doughops group 代表 gitlab-cd-repo.yml 沒跑成功，重跑 scripts/ansible.sh ansible-playbook playbooks/bastion/gitlab-cd-repo.yml。

這一步沒做也不會讓 k8s.yml 失敗，只是 ArgoCD 的 gitops-demo Application 會顯示 repository 不可存取。之後補填，重跑 k8s/argocd.yml 就會恢復。設計見 ArgoCD 與 GitLab 串接。

Step 9 · 執行 k8s.yml

repo 根目錄
$ scripts/ansible.sh ansible-playbook playbooks/k8s.yml

預期結果：約 40 到 70 分鐘，結尾 failed=0。中途的 k8s/smoke-test.yml 會先驗證 BGP fabric 與跨節點 pod 連線，通過才繼續往下。完成後所有周邊服務都在叢集內運行。

失敗時看哪裡：找 Bug 事後檢討搜尋錯誤訊息。想只重跑某一段，直接執行 scripts/ansible.sh ansible-playbook playbooks/k8s/<name>.yml，不必整個 k8s.yml 重來。

Step 10 · 驗證

  1. smoke test：scripts/ansible.sh ansible-playbook playbooks/k8s/smoke-test.yml。預期全部 task 成功，檢查項目見測試與 smoke-test。
  2. Cloudflare Access：curl -I https://test.dough-ops.com/。預期收到 302 導向 Cloudflare 登入頁。
  3. 實際登入：用瀏覽器登入 Dashboard 或 Grafana。預期通過 Cloudflare Access 後直接進入服務，各服務與權限見叢集使用手冊。

失敗時看哪裡：302 以外的回應，檢查 Step 4 的 Access Application 與 Step 9 的 cloudflare-tunnel.yml。登入流程問題見身份聯邦登入流程。

建置順序

全新環境只需要兩個聚合 playbook 各跑一次：先 bastion.yml，再 k8s.yml。下面的順序直接來自這兩個檔案的 import_playbook 與 play 排列，各檔案可以單獨執行。

bastion.yml

不要求叢集已存在，叢集尚未建立時，kubeconfig.yml 偵測到會安全跳過。

  1. bastion_access：寫入 bastion 的 SSH 身分，以 connection: local 在容器內執行，是整條鏈能成立的前提。
  2. bastion_ssh_tunnel：bastion 專用的 Cloudflare Tunnel，提供 web SSH。
  3. nfs_server：把資料碟設成 NFS server。k8s/nfs-csi.yml 依賴它。
  4. vault.yml：HashiCorp Vault。k8s/vault-secrets-operator.yml 依賴它。
  5. keycloak.yml：Keycloak，並寫入 /userap 下的 client secret。k8s/dex.yml 等依賴它。
  6. kubeconfig.yml：安裝 kubectl，取得 admin kubeconfig，叢集不存在就跳過。
  7. apiserver_dns、bastion_tools：/etc/hosts 記錄與 k9s、alias。
  8. github_runner：需要 Step 5 的 GitHub App 三個值。
  9. gitlab.yml → gitlab-runner.yml → gitlab-cd-repo.yml → gitlab-gitops-demo.yml：GitLab 與其周邊，依賴關係是鏈狀的。排在最後，是因為它沒有被其他 play 依賴，且等待時間長，不應拖累前面的步驟。

k8s.yml

  1. 核心叢集，順序固定：crio.yml → nfs-client.yml → apiserver-lb.yml → kubeadm.yml → cilium.yml → smoke-test.yml → node-labels.yml。kubeadm.yml 結束時會把 kubeconfig 裝回 bastion。kubeadm 需要先有 container runtime；smoke test 在這裡先確認 fabric 與跨節點連線真的通。
  2. L7 路由與對外入口：istio.yml → hubble-expose.yml → cert-manager.yml → bastion/cloudflare-tunnel.yml。Gateway 的 443 要靠 cert-manager 簽出的憑證才生效。叢集在 tunnel 這步才第一次真正活著，所以它排在這裡，不需要事後回頭重跑 bastion.yml。
  3. 儲存：nfs-csi.yml。必須在 kube-prometheus-stack.yml 與 docs-site.yml 之前，兩者的 PV 都由 nfs.csi.k8s.io driver 掛載，順序反過來會 apply 失敗或 pod 卡在 Pending。
  4. 內部工具與展示：dashboard.yml、kube-prometheus-stack.yml、demo-app.yml、showcase.yml、docs-site.yml。除了儲存的前置關係，彼此獨立。
  5. 身分與權限：oidc-auth.yml → oidc-rbac.yml。RBAC 要在 apiserver 信任 OIDC 之後才有意義。
  6. 平台服務：vault-secrets-operator.yml → argocd.yml → dex.yml → dex-test-app.yml。前兩者分別需要 bastion/vault.yml 與 istio.yml。dex.yml 讀 bastion/keycloak.yml 寫出的 secret，dex-test-app.yml 讀 dex.yml 產生的 secret。
  7. Keycloak 測試 app：keycloak-test-app.yml、keycloak-native-app.yml。各自只依賴 bastion.yml 與 istio.yml，排在最後是因為沒有更合適的位置。

每個 playbook 的用途見 Playbook 一覽。Cloudflare 的 DNS、Tunnel、Access 在 Step 4 一次建好，不在這個順序裡，也不必每次重建叢集都重做。

要改 pod／service CIDR 或 Kubernetes minor version 這類初始化時固定的參數，必須清掉叢集狀態再依序重跑，不能直接重跑 k8s.yml：

repo 根目錄（破壞性）
kubeadm-reset.yml → k8s/kubeadm.yml → k8s/cilium.yml → k8s/smoke-test.yml

kubeadm-reset.yml 刻意不在 k8s.yml 內，避免例行的「全部部署」意外清掉活的叢集。

一鍵建置

前面的步驟準備好之後，make build 把 Step 3 到 Step 9 串成一條指令。它不替你做個人設定、Step 1、Step 2 與 Step 8。

repo 根目錄
$ make build

make build 依序執行：openstack terraform apply、cloudflare terraform apply、scripts/sync-cloudflare-secrets.sh、bastion.yml、ansible all -m ping、k8s.yml。兩次 terraform apply 都不帶 -auto-approve，仍要手動輸入 yes。如果上次用 make teardown 拆除，腳本會在 apply 之前把保留的資料碟 import 回來。

預期結果：結尾提示可以執行 smoke test。失敗時看哪裡：腳本找不到 .env 的 CLOUDFLARE_API_TOKEN 時會停在 cloudflare 那段。Step 8 的 token 不在這條路徑內，make build 跑完後補填，再重跑 k8s/argocd.yml。

常見情境

➕

加減節點

改 openstack/terraform.tfvars 的 vms map，在 openstack/ 執行 terraform apply。新節點開機時 Nova 已寫入同一把公鑰，不需要 bootstrap。直接重跑 scripts/ansible.sh，inventory 會自動重新產生，Cloudflare 完全不用動。

🔄

VM 全部重建

在 openstack/ 重新 terraform apply。只要公鑰沒換，新的 bastion 開機時一樣被寫入同一把 key。secrets.yml 與 main.yml 的 Cloudflare 值仍然有效，直接重跑 Step 6 與 Step 9，不用碰 Step 4 與 Step 5。

☁️

連 Cloudflare 也重建

Step 4 重新 apply 後，token、AUD、client ID、secret 全部換新。必須重做 Step 5，再重跑 bastion/cloudflare-tunnel.yml、bastion.yml 內的 bastion_ssh_tunnel、k8s/oidc-auth.yml、k8s/kube-prometheus-stack.yml，否則 cloudflared、kube-apiserver OIDC 與 Grafana SSO 會停在已失效的舊身分。

🧨

拆除或部分重建

叢集裝壞、只砍 VM、整個 lab 收掉，各有不同的最小操作。見全部拆除。
