Ansible 自動化Role: argocd

roles/argocd 用 helm 把 ArgoCD 裝進叢集 自己裡面(GitOps 持續部署),透過 argocd_applications 清單管理要同步哪些 Application——預設帶官方 guestbook 範例(GitHub 公開 repo),Phase 8 加了 gitops-demo (自架 GitLab 的私有 repo),證明 ArgoCD 不是只能接公開的 GitHub。這頁涵蓋:為什麼裝在叢集自己裡面、 OIDC 怎麼直接對 Cloudflare Access 講、Application 清單怎麼讓部署 內容在叢集重建後自動復原,以及串接 GitLab 私有 repo 時,認證方式 為什麼刻意選手動建立而不是自動產生。

概述:裝在自己要管理的叢集裡

ArgoCD 天生就是設計成可以裝在它要管理的叢集裡——裝完會自動帶一個 內建的 in-cluster target(指向 https://kubernetes.default.svc,用 in-cluster ServiceAccount 認證),不需要額外手動註冊 cluster,裝在哪個叢集 就直接能管哪個叢集。用 helm 裝,fullnameOverride: argocd ——不用官方 chart 預設的 fullname helper(release name 含 chart name 才會收斂成乾淨名稱,這裡 release name argocd 不包含 chart name argo-cd,兩者字面不一樣,不覆寫的話 Service/Deployment 名稱會變成醜的 argocd-argo-cd-server), 直接覆寫成大家熟悉、官方文件範例也是這樣稱呼的 argocd-server 這組名稱。

dex.enabled: false——Dex 是 ArgoCD 內建、可選的 SSO federation 元件,專門用來讓 ArgoCD 接不支援原生 OIDC 的來源 (LDAP、SAML……)。Cloudflare Access 本身已經是合格的 OIDC provider (跟 Grafana/Vault 用的是同一種「Access for SaaS」機制),ArgoCD 自己的 auth/oidc 可以直接對它講 OIDC,不需要 Dex 這層轉譯——裝著 不用純粹多一個 pod、多一分攻擊面。注意這個「Dex」是 ArgoCD chart 內建、可選關掉的元件,跟這個 repo 另外裝的 叢集專屬 OIDC broker Dex 是同名但完全不同的兩個東西,沒有關聯。

server.insecure: true——argocd-server 只講 plain HTTP,不是自己再包一層自簽憑證的 TLS。跟 Dashboard/Grafana 是同一個 模式:TLS 已經在 Istio Gateway 那一層用真憑證終止過一次(見 Role: cert_manager),沒有必要 讓流量進到 argocd-server 又是一層自簽憑證。ArgoCD CLI/Web UI 用的 gRPC-Web 在這個模式下一樣正常運作,這是官方文件明講給「前面有 TLS-terminating ingress」的部署方式用的建議設定。

OIDC:直接對 Cloudflare Access 講,權限一律 admin

只在 argocd_oidc_client_id/argocd_oidc_client_secret 都填了值(不是預設的 REPLACE_ME)才疊加 OIDC 設定—— 沒填就裝一個沒有 SSO 的 ArgoCD,登入方式退回自己的 admin/密碼。 configs.cm.url(https://{{ argocd_hostname }}) 是實測撞到才確認必要的欄位:ArgoCD 自己組 OIDC/Dex 的 redirect_uri 是拿這個值當底,不是從瀏覽器的 request Host header 動態推——沒設這個值,登入時 Cloudflare 那邊會直接拒絕, 回「Invalid redirect URL」,因為 ArgoCD 送出去的 redirect_uri 跟 Cloudflare 那邊登記的 https://argocd.dough-ops.com/auth/callback 對不起來。

使用者明確要求:任何通過 Cloudflare Access(doughops GitHub org 成員)登入的人直接有完整權限——不是 Dashboard/Grafana 那種「預設唯讀 + oidc_admin_emails 才有完整權限」的 分層模式,是跟 Vault 的 oidc-admin policy 同一個決定。ArgoCD 這邊對應的設定是 configs.rbac.policy.default: role:admin(RBAC 的預設 fallback role,ArgoCD 內建角色,不用另外定義 policy.csv)。

argocd_applications 清單:讓部署內容在叢集重建後自動復原

這份清單(defaults/main.yml)就是「ArgoCD 裡應該有 哪些 Application」的來源,不是單純的範例展示——ArgoCD 的 Application/AppProject 本質上是一般的 k8s CRD,存在 etcd 裡,這個 叢集除了 bastion 以外的節點都沒有掛任何持久化 volume,叢集重建 (kubeadm-reset.yml 或整個 openstack/ 重新 apply)etcd 就是全新的,透過 ArgoCD 網頁 UI/CLI 手動建的東西 會全部消失。之後要新增一個 Application:在這份清單多加一項,重跑 scripts/ansible.sh ansible-playbook playbooks/k8s/argocd.yml (或整個 k8s.yml)就會套用,不用去 ArgoCD UI 手動建。

只會「新增/更新」,使用者明確要求不要自動清掉「清單裡拿掉、但 叢集上還留著」的 Application——單向套用,想移除一個 Application 要自己手動 kubectl delete,不會因為改這份清單、重跑 playbook 就意外被清掉。目前兩項:

namerepo_url用途
guestbookgithub.com/argoproj/argocd-example-apps官方文件/教學長期在用的範例,證明裝好的 ArgoCD 真的能同步/部署東西——跟 roles/demo_app 證明 Istio ingress 路徑真的通是同一個用意
gitops-demogitlab.dough-ops.com/doughops/gitops-demoPhase 8 新增,證明 ArgoCD 也能接自架 GitLab 的私有 repo,不是只能接公開 GitHub

套用 syncPolicy 全自動(automated.prune/selfHeal: true + syncOptions: [CreateNamespace=true])——套用 Application manifest 之後不需要在 ArgoCD UI 裡手動點 Sync,目標 namespace 也會自動建立,兩個範例共用同一份 argocd-applications.yaml.j2 模板產生。

GitLab 整合:gitops-demo 這個 Application 怎麼認證

gitops-demo project 本身(建立 project + commit manifests/app.yaml)由 roles/gitlab_gitops_demo 負責,排在 CD Repo 建立的 doughops group 之後跑——只查 group、不建 group,查不到 就整個 role fail(正常情況下不會發生,因為 bastion.yml 裡的 import 順序保證了先後)。project 建立、manifest 檔案的 upsert 邏輯,跟 gitlab_cd_repo 的 .gitlab-ci.yml 是完全一樣的手法(GET 查現在內容 → 404 就 POST 建立、200 且內容不 一樣就 PUT 更新)。這個 role 讓 GitLab 那邊「有東西可以被同步」,跟 roles/argocd 自己(讓 ArgoCD「能認證、能連進去」)是 分開的兩個 role。

roles/argocd 這邊只多做一件事:註冊一個 argocd.argoproj.io/secret-type: repo-creds 類型的 Secret(argocd-gitlab-repo-creds.yaml.j2)——這個類型 用「URL prefix 比對」套用憑證,不是綁單一 repo,url 設成 https://gitlab.dough-ops.com/doughops/,涵蓋 doughops 底下所有 repo,之後要是再加別的 GitLab repo 給 ArgoCD 用,不用再建新 Secret。username: oauth2 (GitLab 官方文件建議:HTTPS git 操作搭配 Project/Group Access Token 時,username 可以是任意非空字串,oauth2 是常見 慣例,跟這個 repo 已經用在 GitHub PAT 認證的 oauth2:${GITHUB_CLONE_PAT}@github.com 是同一個慣例), password 直接引用 argocd_gitlab_repo_token 這個 secrets.yml 變數。跟這份 Secret 有關的 task 都帶 no_log: true,不進 ansible 執行紀錄。

認證方式的決策過程:為什麼是手動建立 token,不是 Ansible 自動產生。原本設計是 Ansible 自動呼叫 GitLab API 產生一組 Group Access Token(gitlab_automation_pat 是 api scope 的 root PAT,足夠呼叫 POST /groups/:id/access_tokens)。但這條路撞到一個 架構限制:secrets.yml 是使用者筆電上的檔案,透過 scripts/ansible.sh 單向 rsync 到 bastion——如果產生 token 的邏輯放在跑在 bastion 上的 Ansible role 裡,寫回的只會是 bastion 那份「下次 rsync 就被覆蓋」的暫存複本, 使用者筆電上真正的 secrets.yml 永遠拿不到這個值。要 解決要嘛(a)另外寫一支跑在筆電本機、直接打 GitLab API(這條路徑 本來就對 PAT 認證公開,見 cloudflare/access.tf 的 gitlab_direct)的 script,仿照 scripts/sync-cloudflare-secrets.sh 的模式;要嘛 (b)手動建。使用者明確選擇(b)——先用手動建立的方式,(a)那條路 留給之後真的需要自動化時再做。

GitLab 16.0 之後沒有「永久不過期」這個選項。 使用者原本要求 token 有效期限設定「永久」,查證後確認做不到:GitLab 從 16.0 版開始,Personal/Project/Group Access Token 一律強制要選 到期日,self-managed 也一樣,不是能關掉的實例設定。接受退而求其次: 手動建立時選 GitLab UI 允許的最遠日期。到期前需要手動去 doughops group 的 Settings → Access Tokens 重新產生、 更新 secrets.yml、重跑 k8s/argocd.yml。

手動建立的完整步驟(doughops group → Settings → Access Tokens → 名稱 argocd-gitops-reader、Role Reporter、Scopes 只勾 read_repository)見 從零開始建置 Step 9。這份 Secret 沒建之前不會讓 k8s/argocd.yml fail—— argocd_gitlab_repo_token_configured 這個旗標檢查值 是不是還是 REPLACE_ME,沒填就整個跳過 Secret 相關 task,改印一則 ansible.builtin.debug 提醒;ArgoCD 裡 gitops-demo 這個 Application 會顯示 repository 不可 存取,之後補填、重跑同一支 playbook 就會恢復正常,不需要重新跑 整個 k8s.yml。

初始 admin 密碼

ArgoCD 自己(不是這個 helm chart)在第一次啟動時,幫 admin 使用者 產生一組隨機密碼、存進 argocd-initial-admin-secret 這個 Secret——這個名字是 argocd-server 自己寫死的,不受 fullnameOverride 影響。跟這個專案處理 Grafana admin 密碼是同一種謹慎程度:role 裡的對應 task 不印出實際內容、不寫進 ansible 執行紀錄。有設定 OIDC 的話,這組帳密不會自動失效,保留當 SSO 出問題時的備援登入路徑(跟 Grafana 的帳密登入是同一種考量)。

查詢初始 admin 密碼
$ kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d

驗證方式

  • 登入:https://argocd.dough-ops.com/(Cloudflare Access 擋著,doughops org 成員才能連到登入頁);有 設定 OIDC 的話登入頁會多一個選項,選了免密碼直接進、直接是 admin 權限。
  • kubectl -n argocd get application 兩個 Application 都 Synced/Healthy。
  • gitops-demo:kubectl -n gitops-demo get pod -o wide 確認 pod Running,kubectl -n gitops-demo port-forward svc/gitops-demo 8080:80 之後 curl localhost:8080 應該看得到 pod/node 名稱,證明 流量真的到達、內容來自 GitLab 而不是 GitHub。
  • 冪等性:重跑 playbooks/k8s/argocd.yml、 playbooks/bastion/gitlab-gitops-demo.yml 兩次, failed=0,不會重複建立 Application/project。
