平台服務 Role: argocd

roles/argocd 用 helm 把 ArgoCD 裝進叢集本身，由 argocd_applications 清單決定要同步哪些 Application。它在 k8s.yml 的 dex.yml 之前、vault-secrets-operator 之後執行，依賴 Istio Gateway、cert-manager 和 Cloudflare 的 argocd-sso Application。預設帶官方 guestbook（公開 GitHub repo）和 gitops-demo（自架 GitLab 的私有 repo）。

這裡的 Dex 是 ArgoCD chart 內建的可選元件，和叢集專屬的 Dex broker 同名，但是兩個互不相關的部署。

登入設計

ArgoCD 不直接對 Cloudflare Access 講 OIDC，而是經由自己內建的 Dex 轉一手。原因是 Cloudflare 的 id_token 只有 5 分鐘效期，直連會每 5 分鐘被登出。登入流程全貌見身份聯邦登入流程，這裡只說明 ArgoCD 這一段。

Dex 對 Cloudflare 的連線只在你互動登入的那一刻用一次，換到身份之後，Dex 自己簽發 id_token 給 ArgoCD。這個 token 的效期由 role 變數 argocd_dex_id_token_expiry（8760h，一年）決定，不受 Cloudflare 那邊的限制，也不需要 refresh_token。

Dex connector 的設定

Dex 設定寫在 configs.cm["dex.config"]，Cloudflare 的 client secret 放在 argocd-secret 的 dex.cloudflare.clientSecret，connector 內以 $dex.cloudflare.clientSecret 引用。

欄位值為什麼

Cloudflare 側的 argocd_sso Application 登記兩條 redirect_uris：Dex 使用的 /api/dex/callback，以及直連 OIDC 時代留下的 /auth/callback。後者保留是為了把 dex.enabled 撥回 false 時不必重跑 Terraform。access_token_lifetime 設 24h、session_duration 設 730h，前者對這個整合模式沒有作用，後者只決定你多久要對 GitHub org 重新認證一次。

決策：ArgoCD 經內建 Dex 串 Cloudflare Access，id_token 由 Dex 簽發，效期設 8760h。

理由：Cloudflare 的 Access for SaaS 核發的 id_token 固定 5 分鐘，且協定層面不發 refresh_token，ArgoCD 的靜默續期機制（refreshTokenThreshold）用不上。ArgoCD Web UI 在 id_token 到期時也不會自動重新導向，直連 OIDC 等於每 5 分鐘要手動登入一次。

考慮過的替代方案：拉高 access_token_lifetime 和 session_duration — 實測對 id_token 效期無效。改用 refresh_token — saas_app.scopes 只接受 openid、groups、email、profile 四種，offline_access 連送都送不出去。

代價：多一個 Dex pod 和一份攻擊面；id_token 外流後一年內有效，而且持有者是 admin。細節見已知限制。

Application 清單

argocd_applications 定義在 defaults/main.yml，是「ArgoCD 裡應該有哪些 Application」的唯一來源。Application 和 AppProject 是存在 etcd 的 CRD，而 bastion 以外的節點沒有持久化 volume。叢集重建後 etcd 是全新的，不論是跑 kubeadm-reset.yml 還是整個 openstack/ 重新 apply，在 UI 或 CLI 手動建的東西會全部消失。

新增 Application 的做法是在清單多加一項，重跑 scripts/ansible.sh ansible-playbook playbooks/k8s/argocd.yml，或重跑整個 k8s.yml。套用只會新增和更新，不會刪除「清單已拿掉但叢集上還在」的項目。要移除就手動 kubectl delete，避免改清單時意外清掉東西。

namerepo_url用途
guestbookgithub.com/argoproj/argocd-example-apps證明裝好的 ArgoCD 真的能同步和部署，和 demo app 證明 Istio ingress 路徑是同一個用意
gitops-demogitlab.dough-ops.com/doughops/gitops-demo證明 ArgoCD 也能接自架 GitLab 的私有 repo

兩個 Application 共用 argocd-applications.yaml.j2，syncPolicy 全自動：automated.prune: true、automated.selfHeal: true、syncOptions: [CreateNamespace=true]。套用後不需要在 UI 點 Sync，目標 namespace 也會自動建立。

與 GitLab 的串接

串接分成兩個 role。roles/gitlab_gitops_demo 讓 GitLab 那邊「有東西可以同步」：它在 CD Repo 建好的 doughops group 底下建立 gitops-demo project，並 commit manifests/app.yaml。它只查 group、不建 group，查不到就整個 role 失敗，正常情況下 bastion.yml 的 import 順序會避免這件事。upsert 手法與 gitlab_cd_repo 的 .gitlab-ci.yml 相同：GET 現況，404 就 POST 建立，200 且內容不同就 PUT 更新。

roles/argocd 負責讓 ArgoCD 能認證。它用模板 argocd-gitlab-repo-creds.yaml.j2 註冊一個 argocd.argoproj.io/secret-type: repo-creds 的 Secret：

  • url 是 https://gitlab.dough-ops.com/doughops/。repo-creds 以 URL prefix 比對套用憑證，涵蓋 doughops 底下所有 repo，之後加別的 repo 不必再建 Secret。
  • username 是 oauth2。GitLab 的 Project 或 Group Access Token 用於 HTTPS git 操作時，username 只要是非空字串。oauth2 是慣例，和本專案 GitHub PAT 使用的 oauth2:${GITHUB_CLONE_PAT}@github.com 一致。
  • password 是 secrets.yml 的 argocd_gitlab_repo_token。相關 task 都帶 no_log: true。

Group Access Token 為什麼手動建立

決策：argocd_gitlab_repo_token 由你在 GitLab 的 doughops group 手動建立 Group Access Token，再填進 secrets.yml。

理由：自動產生的邏輯會跑在 bastion 的 Ansible role 裡，但 secrets.yml 的正本在你的筆電，由 scripts/ansible.sh 單向 rsync 到 bastion。role 寫回的只是下次 rsync 就被覆蓋的暫存複本，筆電上的正本永遠拿不到 token。

考慮過的替代方案：由 Ansible 呼叫 GitLab API — gitlab_automation_pat 的 api scope 足以呼叫 POST /groups/:id/access_tokens，但受上述單向同步限制。另寫一支在筆電本機執行的 script，仿 scripts/sync-cloudflare-secrets.sh — 可行，GitLab API 路徑本來就對 PAT 認證開放，見 cloudflare/access.tf 的 gitlab_direct。自動化留到真的需要時再做。

代價：token 到期要手動換，見下方。

建立步驟：doughops group → Settings → Access Tokens，名稱 argocd-gitops-reader、Role 選 Reporter、Scopes 只勾 read_repository。這是建置前的一次性手動項目，列在從零開始建置 § 開始前要準備的東西。

GitLab 從 16.0 起，Personal、Project、Group Access Token 一律強制選到期日，self-managed 也不能關。所以選 UI 允許的最遠日期，到期前要重新產生 token、更新 secrets.yml、重跑 k8s/argocd.yml。

token 還沒填時，k8s/argocd.yml 不會失敗。argocd_gitlab_repo_token_configured 旗標發現值仍是 REPLACE_ME，就跳過 Secret 相關 task 並印出提醒。此時 gitops-demo 會顯示 repository 不可存取，補填後重跑同一支 playbook 即可恢復，不必重跑整個 k8s.yml。

初始 admin 密碼

ArgoCD 第一次啟動時為 admin 產生隨機密碼，存進 argocd-initial-admin-secret。這個名稱是 argocd-server 寫死的，不受 fullnameOverride 影響。role 內對應的 task 只印出查詢方式，不印出密碼，也不寫進 ansible 執行紀錄。設定了 OIDC 後這組帳密不會失效，保留作為 SSO 故障時的備援登入。

在 bastion 上
$ kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d

已知限制與 workaround

  • 通過 Cloudflare Access 的人都是 admin。policy.default: role:admin 讓 doughops org 成員登入後直接擁有 ArgoCD 完整權限，不像 Dashboard 和 Grafana 以 oidc_admin_emails 名單分層。Vault 的 oidc-admin policy 是同一個決定（見 Role: vault）。權限矩陣見叢集使用手冊 § 權限。
  • id_token 一年有效。8760h 的代價是 token 外流後一年內都能用，而且持有者是 admin。ArgoCD 管理整個叢集的部署，影響範圍等於叢集管理權限。要縮短就調低 argocd_dex_id_token_expiry，代價是更常被要求重新登入。
  • admin 帳號保留。備援用的 admin 密碼登入沒有被關閉，密碼存在 argocd-initial-admin-secret。官方建議登入後刪除該 Secret。
  • 多一個 Dex pod。為了繞過 Cloudflare 的 5 分鐘上限，多了一個 pod 和一份攻擊面，目前沒有找到同時滿足「透過 Cloudflare Access 單一登入」與「session 長度自行決定」的其他做法。
  • 清單單向套用。移除 Application 要手動 kubectl delete。
  • Group Access Token 會過期。見 上方。

實測踩到的 bug

這四個問題都在接上 Cloudflare Access 的過程中遇到，編號 #68 到 #71，登錄在 Bug 事後檢討。另有一筆組裝 oidc.config 時的 Jinja 字串陷阱，見 Bug #67。

#69 · 登入後每 5 分鐘被登出

  • 症狀：ArgoCD 登入後不到半小時就被強制登出。同一套 Cloudflare Access SSO 的 Grafana 和 Vault 沒有這個問題。
  • 根因：Access for SaaS 核發的 id_token 固定 5 分鐘，而且不發 refresh_token。ArgoCD Web UI 在 id_token 到期時不會自動重新導向，所以每 5 分鐘要手動登入一次。這是已知行為，見 argoproj/argo-cd issue #10126、#24807、#27041。
  • 修法：改走 ArgoCD 內建 Dex，見登入設計。
  • 怎麼確認修好：登入一次，在 argocd-server log 讀 Dex 簽發的 claims，exp - iat 等於 31536000 秒（365 天），iss 變成 https://argocd.dough-ops.com/api/dex。Settings → Accounts 等管理頁面可正常進入，policy.default: role:admin 不受影響。
  • 相關：Bug #69。第一版的錯誤方向見演進歷史。

#68 · 登入時 Cloudflare 回 Invalid redirect URL

  • 症狀：登入被 Cloudflare 拒絕，訊息是 Invalid redirect URL: the protocol and host (including port) must match。
  • 根因：ArgoCD 組 redirect_uri 時以 configs.cm.url 為底，不從 request 的 Host header 推。沒設這個值，送出的 redirect_uri 和 cloudflare/access.tf 的 argocd_sso 登記的清單對不起來。
  • 修法：base values 一律設 configs.cm.url: https://{{ argocd_hostname }}。這個值也影響 UI、CLI 和通知連結的對外網址，所以放 base values，不是只在 OIDC 疊加。
  • 怎麼確認修好：登入頁選 Cloudflare Access 後不再被 Cloudflare 擋下。
  • 相關：Bug #68。

#70 · Dex 登入失敗：missing "name" claim

  • 症狀：第一次接上 Dex 登入就失敗，argocd-dex-server log 印 failed to authenticate err="missing \"name\" claim"。
  • 根因：Dex 的 oidc connector 預設要求 name claim，檢查寫在 connector/oidc/oidc.go 的 createIdentity()，沒有 skip 開關。Cloudflare 核發的 id_token 中，這個帳號的 name 是 null，因為 GitHub 帳號沒有設公開顯示名稱。
  • 修法：connector 設 userNameKey: email。email claim 一定有值，因為 Access policy 本來就用 email 過濾 org 成員。
  • 怎麼確認修好：重新登入，log 不再印這個錯誤，會接著遇到下一個 bug。
  • 相關：Bug #70。

#71 · Dex 登入失敗：missing "email_verified" claim

  • 症狀：修完 name 之後，log 換成 failed to authenticate err="missing \"email_verified\" claim"。
  • 根因：Dex 預設還要求 email_verified claim 存在且為 true。Cloudflare 的 id_token 只有 email，沒有這個 claim，無從映射。
  • 修法：connector 設 insecureSkipEmailVerified: true，整個略過檢查。oauth2-proxy 那邊為同樣原因加了對應的 flag。
  • 怎麼確認修好：重新登入成功，並完成上面的 exp - iat 驗證。
  • 相關：Bug #71。

#67 · ArgoCD 的 oidc.config 內換行變成字面的 \n

  • 症狀：用 Jinja 字串串接組 oidc.config，這個 key 的值本身是多行 YAML。字串裡的換行變成字面的 \ 加 n 兩個字元，ArgoCD 解析成壞掉的 YAML。
  • 根因：第一版用 'name: ...\n' ~ 'issuer: ...' 串接，整個 set_fact 包在 >- 折疊純量裡，折疊純量不會把 \n 轉成換行字元。部署前在本機單獨測這段才抓到。
  • 修法：改用 YAML 的 | 區塊純量放真正的換行，搭配 vars: 與一般 YAML dict，再用 combine(..., recursive=True) 組完整的 helm values。
  • 怎麼確認修好：本機重測，結果是 dict 型別，換行是真正的換行字元，之後才套用到叢集。
  • 相關：Bug #67，與 #13、#17、#22 同屬字串處理陷阱。

驗證方式

  • 瀏覽器開 https://argocd.dough-ops.com/。先過 Cloudflare Access（doughops org 成員），有設 OIDC 的話登入頁會多一個選項，選了免密碼直接進，權限是 admin。
  • kubectl -n argocd get application：兩個 Application 都是 Synced 和 Healthy。
  • gitops-demo：kubectl -n gitops-demo get pod -o wide 確認 pod Running；kubectl -n gitops-demo port-forward svc/gitops-demo 8080:80 之後 curl localhost:8080 應該看到 pod 和 node 名稱，證明流量到達，內容來自 GitLab 而不是 GitHub。
  • 冪等性：重跑 playbooks/k8s/argocd.yml 和 playbooks/bastion/gitlab-gitops-demo.yml 兩次，failed=0，不會重複建立 Application 或 project。

演進歷史

  • 2026-08-12featPhase 8：串接自架 GitLab，新增 gitlab_gitops_demo role、repo-creds Secret 和 gitops-demo Application；token 決定手動建立（Changelog）
  • 2026-08-12fixArgoCD 登入由直連 Cloudflare OIDC 改為內建 Dex，解決 5 分鐘登出（登入設計）

直連 OIDC 是原本的設計：dex.enabled: false，ArgoCD 的 oidc.config 直接對 Cloudflare Access 講 OIDC。Cloudflare 本身是合格的 OIDC provider，Dex 看起來只是多餘的一層。上線後登入不到半小時就被登出，排查過程如下。

  1. 查 Terraform state，確認 argocd-sso 的 access_token_lifetime 沒設，吃預設的 5 分鐘。
  2. 把 access_token_lifetime 拉到上限 24h、session_duration 拉到 730h，套用後症狀不變。登入一次直接看 argocd-server log，id_token 的 exp - iat 仍是 300 秒，證明這個欄位對 Access for SaaS 沒有作用。
  3. 嘗試接 ArgoCD 的 refreshTokenThreshold 靜默續期，需要 offline_access scope。terraform validate 直接報 Invalid Attribute Value Match，saas_app.scopes 只能是 openid、groups、email、profile。結論是這個整合模式在協定層面不發 refresh_token，5 分鐘是平台硬限制。
  4. 改用內建 Dex，由 Dex 自己簽發 id_token，效期由 role 控制。
