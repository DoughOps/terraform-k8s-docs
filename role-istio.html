Ansible 自動化Role: istio

部署 Istio service mesh 的 control plane(istiod)+ ingress gateway,全部裝在 istio namespace——使用者明確要求,不是 官方預設的 istio-system。這個 role 只負責「cluster 內部 從 ingress gateway 到 pod」這一段路由,真正的對外入口是 Role: cloudflare_tunnel, 兩者刻意切開,職責不重疊。

為什麼需要 Istio,cluster 內部不是本來就有 Service 可以路由? 因為對外入口只有一條 Cloudflare Tunnel,但 cluster 裡可能有很多個 服務,各自要用不同的子網域區分——Istio 的 Gateway/VirtualService 提供「一個共用的 L7 進入點,靠 Host header 分流到不同服務」的機制, 不需要每個服務各自開一個對外可連的位址。

三個 chart,靠 helm 依序裝,順序不能反

istio-base
CRD + cluster 角色
→
istiod
control plane
→
istio-ingressgateway
gateway chart

istiod 一定要先 ready,gateway 才能真的動起来 ——istio/gateway 這個 chart 部署出來的 pod 本身只是一個 帶 sidecar.istio.io/inject: true 注記的空殼 Deployment,實際的 Envoy container 是靠 istiod 的 mutating webhook 動態注入進去的。順序反過來的話,gateway pod 會卡在 沒有 Envoy container 的狀態,永遠不會真正監聽任何 port。這也是為什麼 role 裡在裝完 istiod 後,會先kubectl rollout status deployment/istiod 等它完全 ready,才進下一步裝 gateway。

global.istioNamespace 一定要明確帶

roles/istio/tasks/main.yml(精簡)
kubernetes.core.helm:
  name: istio-base
  chart_ref: istio/base
  release_namespace: "{{ istio_namespace }}"
  create_namespace: true
  values:
    global:
      istioNamespace: "{{ istio_namespace }}"

istio-base/istiod 這兩個 chart 預設寫死 指向 istio-system,不會自動對齊 release_namespace——只設 release_namespace 而不同時設 global.istioNamespace,實際部署出來的 control plane 元件仍然會去找 istio-system 底下的 資源(像 CA 憑證的 Secret),在 istio namespace 裡 根本找不到,啟動會失敗。兩個值必須一起帶,是實測驗證過的,不是 看文件猜的。

ingress gateway 的 Service:ClusterIP,不是 NodePort

roles/istio/templates/gateway-values.yaml.j2
service:
  type: ClusterIP

早期版本曾經規劃 NodePort(固定 30080/30443), 對應的是「透過 bastion 的 floating ip + NodePort 對外 expose」這個 被使用者明確否決的方案(見 Role: cloudflare_tunnel 關於這段決策轉折的完整說明)。現在對外入口是 cloudflared 從 cluster 內部直接用 ClusterIP DNS 連過來 (istio-ingressgateway.istio.svc.cluster.local:80), 完全不需要任何對外開放的 port,ClusterIP 就是最小權限 的正確選擇——不多開一個攻擊面。

叢集共用的入口 Gateway:一個,不是每個服務各開一個

roles/istio/templates/k8s-gateway.yaml.j2
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: k8s-gateway
  namespace: istio
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "{{ ingress_wildcard_hostname }}"   # 目前 *.dough-ops.com

這個 Gateway 放在 istio namespace,不是 放進某個 app 自己的 namespace——目的是讓任何 app 的 VirtualService,不管自己在哪個 namespace,都可以用 gateways: [istio/k8s-gateway] 這種跨 namespace 引用 的語法掛上來(見下方 demo app 的例子),不用每個 app 各自重複定義 一個 Gateway、重複佔用 80 port。

hosts 設成整個 ingress_wildcard_hostname 萬用字元,不代表任何子網域都被對外開放——這裡只影響 Istio 內部比對 Host header 的範圍,真正「外面連得到哪個名稱」完全由 Cloudflare 那邊的 DNS/Tunnel ingress 設定決定(見 Role: cloudflare_tunnel)。 設寬一點純粹是省得每加一個新服務、新子網域,都要回來改這個共用 Gateway。

demo app 怎麼掛上這個共用 Gateway

用來證明「Cloudflare Tunnel → Istio ingress gateway → VirtualService → Service → Pod」這條路徑真的通的最小測試服務,由 roles/demo_app 部署(獨立的 role,跟 roles/istio 分開,因為一個是「共用基礎設施」、一個是「一個具體 app」)。

roles/demo_app/templates/demo-app.yaml.j2(VirtualService 部分)
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: web
  namespace: demo
spec:
  hosts:
    - "{{ ingress_hostname }}"        # 目前 test.dough-ops.com
  gateways:
    - "{{ istio_namespace }}/k8s-gateway"   # 跨 namespace 引用
  http:
    - route:
        - destination:
            host: web.demo.svc.cluster.local
            port:
              number: 80

nginx pod 回應的內容特意帶上 pod 名稱、pod IP、node 名稱(用 downward API 注入的環境變數),方便肉眼確認流量真的有到達、而且 看得出來是哪個 pod 處理的——不是只看到一個「200 OK」就假設整條 路徑通了。

實測驗證
$ curl -s -m 15 https://test.dough-ops.com/

命名空間注入:classic label,不是 revision-based

demo namespace 上加的是 istio-injection: enabled 這個傳統 label,不是 istio.io/rev=<revision> ——因為 roles/istio 裝 istiod 時沒有設 --set revision=,走的是預設的單一 revision 安裝模式, sidecar injection webhook 認的也是 classic label,兩邊要對齊。

kube-proxy 移除後,這個 role 有沒有受影響

叢集後來移除了 kube-proxy、改用 Cilium 的 eBPF kube-proxy replacement(見 Role: cilium)——這對 Istio 完全透明:Istio 的 Gateway/VirtualService 是 L7(HTTP)層面的 路由,操作對象是 Kubernetes Service 這個抽象概念,不直接依賴 kube-proxy 或任何特定的 Service 實作機制。無論 ClusterIP 的流量是 靠 iptables(kube-proxy)還是 eBPF(Cilium)轉發,Istio 這一層的 設定完全不用改。
