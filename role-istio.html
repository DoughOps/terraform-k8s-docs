叢集元件 Role: istio

這個 role 部署 Istio 的 control plane（istiod）和 ingress gateway，全部裝在 istio namespace。它只負責叢集內從 ingress gateway 到 pod 的 L7 路由，真正的對外入口是 Role: cloudflare_tunnel，兩者職責不重疊。在建置順序中，它排在 cilium 之後，cert_manager 和 cloudflare_tunnel 之前。

為什麼需要 Istio？對外入口只有一條 Cloudflare Tunnel，叢集裡卻有很多服務，各自用不同子網域區分。Istio 的 Gateway 和 VirtualService 提供一個共用的 L7 進入點，靠 Host header 分流到不同服務，每個服務不需要各自開一個對外可連的位址。整條對外路徑見網路架構總覽。

三個 chart 的安裝順序

istio-base
CRD + cluster 角色
→
istiod
control plane
→
istio-ingressgateway
gateway chart

三個 chart 的版本都由 istio_chart_version 控制（1.30.3）。順序不能反。

istiod 必須先 ready，gateway 才能運作。istio/gateway chart 部署出來的 pod 只是一個帶 sidecar.istio.io/inject: true 注記的空殼 Deployment。實際的 Envoy container 由 istiod 的 mutating webhook 動態注入。順序反過來，gateway pod 會卡在沒有 Envoy container 的狀態，永遠不監聽任何 port。所以 role 在裝完 istiod 後，先執行 kubectl rollout status deployment/istiod 等它完全 ready，才裝 gateway。

istio namespace 與 global.istioNamespace

Istio 裝在 istio namespace，不使用官方預設的 istio-system。每個元件各自一個 namespace，例如 cilium、istio、cloudflare，比較好追蹤資源歸屬。所有引用這個 namespace 的 role 和模板都要使用 istio_namespace 變數，不要寫死名稱。這個變數定義在 group_vars/all/main.yml。

roles/istio/tasks/main.yml（精簡）
kubernetes.core.helm:
  name: istio-base
  chart_ref: istio/base
  release_namespace: "{{ istio_namespace }}"
  create_namespace: true
  values:
    global:
      istioNamespace: "{{ istio_namespace }}"

istio-base 和 istiod 這兩個 chart 預設寫死指向 istio-system，不會自動對齊 release_namespace。只設 release_namespace 而不同時設 global.istioNamespace，control plane 元件仍然會去 istio-system 找資源，例如 CA 憑證的 Secret。這些資源在 istio namespace 裡不存在，啟動就會失敗。

所以 istio-base 和 istiod 兩個 release 都要同時帶這兩個值，這是實測驗證的結果。Cilium 的 chart 沒有這個問題，見 Role: cilium。

ingress gateway 的 Service 型態

roles/istio/templates/gateway-values.yaml.j2
service:
  type: ClusterIP

決策：ingress gateway 的 Service 使用 ClusterIP。

理由：對外入口是 Cloudflare Tunnel。cloudflared 跑在叢集內的 cloudflare namespace，直接用 cluster DNS 連 istio-ingressgateway.istio.svc.cluster.local。不需要任何從叢集外打進節點的機制，也不多開一個對外 port。

考慮過的替代方案：NodePort（固定 30080／30443）搭配 bastion Floating IP — 多開對外 port 和攻擊面，且與 Cloudflare Tunnel 的入口重複。LoadBalancer — 這個 OpenStack tenant 沒有 LBaaS，Service 會永遠停在 <pending>。

代價：gateway 無法從叢集外直接連線。除錯時要從叢集內才能打到它，例如用 kubectl port-forward 或另一個 pod。

叢集共用的入口 Gateway

roles/istio/templates/k8s-gateway.yaml.j2
apiVersion: networking.istio.io/v1
kind: Gateway
metadata:
  name: k8s-gateway
  namespace: istio
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 80
        name: http
        protocol: HTTP
      hosts:
        - "{{ ingress_wildcard_hostname }}"   # *.dough-ops.com
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: SIMPLE
        credentialName: dough-ops-com-tls
      hosts:
        - "{{ ingress_wildcard_hostname }}"

整個叢集只有一個 Gateway，放在 istio namespace，不放進任何 app 自己的 namespace。這樣任何 namespace 的 VirtualService 都能用 gateways: [istio/k8s-gateway] 這種跨 namespace 語法掛上來，不用每個 app 重複定義 Gateway，也不會重複佔用同一個 port。

443 與 80

  • 443 是實際使用的路徑。cloudflared 對這個 port 發起 HTTPS，TLS 在 gateway 終止，憑證是 dough-ops-com-tls，由 cert_manager 簽發（Cloudflare Origin CA）。
  • cloudflared 用同一個 Origin CA 的 root cert 驗證，檔名是 origin-ca-ecc-root.pem，由 cloudflare_tunnel 掛入。整條路徑是 Cloudflare 的 Full (strict) 等級加密，不只有 Cloudflare 邊緣到瀏覽器那一段。
  • 80 保留給叢集內部和除錯使用，例如直接用 ClusterIP 打 HTTP 測試，不需要處理憑證。Cloudflare Tunnel 目前不經過這個 port。

hosts 設成整個萬用字元，只影響 Istio 內部比對 Host header 的範圍。外面實際連得到哪個名稱，完全由 Cloudflare 的 DNS 和 Tunnel ingress 設定決定（見 Role: cloudflare_tunnel）。設寬一點，是為了每加一個新服務或子網域時，不必回頭改這個共用 Gateway。

Demo app

roles/demo_app 部署一個最小的測試網頁服務。它用來證明「Cloudflare Tunnel → Istio ingress gateway → VirtualService → Service → Pod」整條路徑真的通。它是獨立的 role，不放進 roles/istio：前者是共用基礎設施，後者是一個具體的 app。

role 只在 bastion 上執行，渲染 demo-app.yaml.j2 後用 kubectl apply，再等 deployment/web rollout 完成。模板包含四個資源，都在 demo namespace：

資源設定
Namespace demo帶 istio-injection: enabled label
Deployment web2 個 replica，nginx:1.27-alpine
Service webport 80
VirtualService webhost 是 ingress_hostname（test.dough-ops.com），掛在 istio/k8s-gateway
roles/demo_app/templates/demo-app.yaml.j2（VirtualService 部分）
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: web
  namespace: demo
spec:
  hosts:
    - "{{ ingress_hostname }}"        # test.dough-ops.com
  gateways:
    - "{{ istio_namespace }}/k8s-gateway"   # 跨 namespace 引用
  http:
    - route:
        - destination:
            host: web.demo.svc.cluster.local
            port:
              number: 80

nginx 回應的內容特意帶上 pod 名稱、pod IP 和 node 名稱（用 downward API 注入環境變數）。這樣可以肉眼確認流量真的到達，也看得出是哪個 pod 處理的，不會只看到一個 200 就假設整條路徑通了。

實測驗證
$ curl -s -m 15 https://test.dough-ops.com/
<html><body style="font-family: sans-serif; padding: 2rem;">
<h1>Istio demo — it works</h1>
<p>Served by pod web-74cb8d9cbf-tvfhl (172.16.5.36) on node ap-0002

預期結果：回應內容顯示處理請求的 pod 名稱和節點。多次重送，可以看到兩個 replica 輪流出現。

sidecar 注入

demo namespace 使用傳統的 istio-injection: enabled label，而不是 istio.io/rev=<revision>。roles/istio 安裝 istiod 時沒有設定 --set revision=，走預設的單一 revision 模式，sidecar injection webhook 認的也是 classic label，兩邊要對齊。

這個 label 會影響在 demo namespace 建立的所有 pod。裸 busybox 測試 pod 會被注入一個 istio-proxy sidecar，它的 startup probe 永遠連不上，把整個 pod 的 Ready 狀態卡住。在這個 namespace 跑測試 pod 時，要加上 annotation sidecar.istio.io/inject: "false" 跳過注入。見 Bug #35。

驗證方式

在 bastion 上
$ kubectl -n istio get pods
$ kubectl -n istio get gateway k8s-gateway
$ kubectl -n demo get pods,virtualservice

預期結果：istiod 和 istio-ingressgateway 為 Running；k8s-gateway 存在；demo 的兩個 web pod 是 2/2 Running（nginx 加 sidecar）。接著用上面的 curl 確認整條外部路徑。

與 kube-proxy 取代的關係

叢集沒有 kube-proxy，Service 轉發改由 Cilium eBPF 處理，見 Role: cilium 的 kube-proxy 取代。這對 Istio 完全透明。Gateway 和 VirtualService 在 L7 操作 Kubernetes Service 這個抽象概念，不依賴 ClusterIP 由 iptables 還是 eBPF 轉發。
