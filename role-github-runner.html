平台服務 Role: github_runner

這個 role 在 bastion 上用 Docker container 跑一個 GitHub Actions self-hosted runner。它註冊成 doughops org 共用的 runner，歸在 doughops-cd 這個 Runner Group。它屬於 bastion.yml 的一環，依賴 secrets.yml 裡的 GitHub App 憑證。這個 runner 與 bastion 共享信任邊界，所以部署或把新 repo 加進 Runner Group 之前，請先讀完下面的限制。

不要把這個 Runner Group 開放給任何 public repo。GitHub 官方文件寫道：

「Self-hosted runners should almost never be used for public repositories on GitHub, because any user can open pull requests against the repository and compromise the environment.」

doughops org 底下多數 repo 是 public。只要有 workflow 能跑在這個 runner 上，任何能對該 repo 開 PR 的人都可能讓程式碼在 bastion 上執行。bastion 持有所有節點的 SSH 存取、Vault 與 Keycloak 的資料，以及 Cloudflare tunnel token，外洩的影響遠大於這個 lab 的其他風險。

doughops-cd 目前只放一個 private repo，且只有少數 admin 有 push 權限。加入新 repo 之前，先確認它是 private、collaborator 名單受控，並且你信任它現在與未來的每一位 collaborator 都有能力操作 bastion。

使用前必讀的限制

下面五項是這個設計的固有取捨。決定是否把新 repo 排進 Runner Group 之前，先確認你接受這些限制。

👥

信任邊界是 push 權限

能觸發 workflow 的人就是有 repo 寫入權限的人，與誰能開 PR 無關。這個 private repo 沒有分支保護可用（GitHub 免費版不支援），有 push 權限的人可以直接推到 main，不經 PR review。

因此任何一位被加進 push 權限的人，等同被授權對 bastion 執行 root 級操作。

🗝️

docker.sock 等於主機 root

runner container 掛載 /var/run/docker.sock，才能執行 container: job。能呼叫這個 socket 的程序可以起一個掛載主機根目錄的 container，取得 bastion 的完整檔案系統。

這是支援 container: job 的必要代價，沒有可以再收緊的設定。

🛡️

隔離只有軟性防護

GitHub Actions 沒有 runner 層級的「強制所有 job 在 container 裡跑」設定，要不要隔離由每個 workflow 自己決定。

本 repo 有兩道防護：靜態掃描與執行期自我檢查（見防止漏寫 container 的檢查）。兩者都能被有 push 權限的人修改或刪除，真正的邊界仍是對這些 admin 的信任。

🖥️

單一、共用、非一次性

這台 runner 常駐在 bastion，一次只跑一個 job。.runner、.credentials 與 bind mount 的工作目錄在多次執行之間持續存在，不會自動清空。

上一個 job 留下的殘留，下一個 job 可能讀得到。

🏚️

與 bastion 共享信任邊界

runner 與 bastion 上的 NFS server、Vault、Keycloak，以及對所有節點的 SSH 存取之間，沒有網路或權限隔離。

影響範圍是整個 lab：runner 上的任何一次不受信任的執行，都可能影響 bastion 的全部職責。長期改法見開放給其他 CD repo 之前。

為什麼用 GitHub App

決策：用 GitHub App 取得註冊 runner 所需的 org 層級權限，不用個人 PAT。

理由：註冊 org 層級 runner 需要 org 管理層級的 API 權限。網頁上「New self-hosted runner」給的 registration token 只能手動貼一次，每次 bastion 重建都要有人回去複製，無法自動註冊。App 是 org 的資產，不會因為某人離開或停用帳號而失效，也沒有強制過期日，不會因為忘記續期而突然斷掉。

考慮過的替代方案：Classic PAT（admin:org）— 權限遠大於「只管 runner」，且綁在個人帳號。Fine-grained PAT — 範圍可以鎖到只剩 Self-hosted runners，設定也比 App 簡單（不用簽 JWT），但強制設過期日（最長 1 年）且綁在個人帳號。

代價：App 需要簽 JWT 與換 installation token，設定步驟較多。App 的 private key 長期有效，外洩時只能靠手動撤銷。org 只有少數成員時，與 fine-grained PAT 的差距不大；若覺得 App 不划算，可以把 mint_registration_token.py 的 JWT 段拿掉，直接用 PAT 當 installation token。

方式範圍會不會過期綁在誰身上
Classic PAT（admin:org）整個 org 管理權限依設定，可以永不過期個人帳號
Fine-grained PAT可鎖到只剩 Organization → Self-hosted runners強制設過期日，最長 1 年，需手動續期個人帳號
GitHub App（採用）同樣鎖到只剩 Organization → Self-hosted runnersApp 本身不過期，只有 private key 的撤銷問題org 資產

建立 GitHub App

下面每一步都對應 GitHub 網頁上實際會看到的欄位。做完後你會拿到三個值：github_app_id、github_app_private_key、github_app_installation_id。

  1. 1. 開新 App 的頁面 網址直接打 https://github.com/organizations/doughops/settings/apps/new，或手動走 doughops org → Settings → Developer settings → GitHub Apps → New GitHub App。
  2. 2. GitHub App name 名稱在全 GitHub 唯一，不只在 doughops org 內，與別人的 App 撞名會建立失敗。建議取一個包含 doughops 的名字，例如 doughops-bastion-runner。
  3. 3. Homepage URL 必填，但不需要真的能用。填 https://github.com/doughops 即可通過表單驗證。
  4. 4. Callback URL、Setup URL 兩者都留空。它們用於讓使用者跑 OAuth 登入流程，這個 App 只使用對 org 的權限，不會有人登入它。
  5. 5. Webhook 把 Active 取消勾選。不需要 webhook 事件；勾著又沒填 URL，GitHub 有時會擋你儲存，或在背景不斷嘗試投遞失敗的 webhook。
  6. 6. Permissions → Repository permissions 整組維持預設的 No access。註冊 runner 與 repo 內容無關。
  7. 7. Permissions → Organization permissions 找到 Self-hosted runners，下拉選 Read and write。注意是下方 Organization permissions 這一組，不是 repository permissions 那組同名的項目。其他 Organization permissions（Members、Administration 等）全部維持 No access。
  8. 8. Permissions → Account permissions 全部維持 No access。這組用於存取使用者個人帳號資料，與這個 App 無關。
  9. 9. Where can this GitHub App be installed? 選 Only on this account（doughops）。「Any account」是給公開發佈的 App 用的。
  10. 10. 按 Create GitHub App，記下 App ID 建立後會跳到 App 自己的設定頁，最上面印著 App ID: 123456 這類數字，這就是 github_app_id。
  11. 11. 產生 private key 同一頁往下捲到 Private keys，按 Generate a private key，瀏覽器會下載一個 <App 名稱>.<日期>.private-key.pem 檔案。檔案的完整內容就是 github_app_private_key，包含 -----BEGIN RSA PRIVATE KEY----- 與 -----END RSA PRIVATE KEY----- 兩行，並保留原本的換行。這個檔案只會下載這一次，遺失了要在同一頁重新產生一把新的，舊的可以在旁邊按 Delete 撤銷。
  12. 12. Install 到 doughops org 左側選單點 Install App，找到 doughops 後按 Install。Repository access 選哪個都不影響安全性，因為這個 App 沒有要任何 repo 權限，有意義的只有前面設定的 Organization permission。選 Only select repositories 隨便選一個，或選 All repositories 都可以。
  13. 13. 取得 Installation ID 按完 Install 後，網址列會變成類似 https://github.com/organizations/doughops/settings/installations/12345678，結尾那串數字就是 github_app_installation_id。事後要找時，走 doughops org → Settings → 左側選單 GitHub Apps → 找到你的 App → 按 Configure，網址列會帶出同一串數字。這個選單在 org 主 Settings 裡，不是 Developer settings 底下同名的項目。

不從網址列找 Installation ID：拿到 App ID 與 private key 之後，可以直接用下面的指令查。它是 mint_registration_token.py 簽 JWT 那段的純 bash 版本，不需要先跑完整個 role。

APP_ID=12345          # 換成實際的 App ID
KEY=doughops-bastion-runner.2026-07-27.private-key.pem   # 換成你下載的檔名

NOW=$(date +%s)
HEADER=$(printf '{"alg":"RS256","typ":"JWT"}' | openssl base64 -e -A | tr '+/' '-_' | tr -d '=')
PAYLOAD=$(printf '{"iat":%s,"exp":%s,"iss":"%s"}' "$((NOW-60))" "$((NOW+540))" "$APP_ID" | openssl base64 -e -A | tr '+/' '-_' | tr -d '=')
SIG=$(printf '%s.%s' "$HEADER" "$PAYLOAD" | openssl dgst -sha256 -sign "$KEY" | openssl base64 -e -A | tr '+/' '-_' | tr -d '=')
JWT="$HEADER.$PAYLOAD.$SIG"

curl -s -H "Authorization: Bearer $JWT" \
     -H "Accept: application/vnd.github+json" \
     https://api.github.com/app/installations

預期結果：回應是一個 JSON 陣列，每個元素的 id 欄位就是 installation ID。這個 JWT 組法已實測能產生格式正確的 token。

填入 secrets.yml

三個值填進加密的 ansible/inventory/group_vars/all/secrets.yml。加密檔的編輯方式與 vault 密碼見 Ansible 框架設計 § 密鑰管理。

group_vars/all/secrets.yml
github_app_id: "12345"
github_app_installation_id: "12345678"
github_app_private_key: |
  -----BEGIN RSA PRIVATE KEY-----
  ……（.pem 檔案的完整內容，保留每一行換行）……
  -----END RSA PRIVATE KEY-----

接著執行：

repo 根目錄
$ scripts/ansible.sh ansible-playbook playbooks/bastion/github-runner.yml

預期結果：playbook 全部 task 成功，GitHub 的 org 設定頁出現一個線上的 bastion runner。三個值沒填時，role 開頭的 ansible.builtin.assert 會直接報錯，不會拖到某個看不懂的 API 401。

mint_registration_token.py

GitHub App 的標準認證流程有三步。先用 private key 簽 JWT（RS256），再拿 JWT 換 installation access token，最後用 token 呼叫實際的 API。這支腳本不裝任何 pip 套件。JWT 的組裝與 base64url 編碼用標準函式庫，RSA-SHA256 簽章則直接呼叫 openssl dgst -sha256 -sign。這樣 image 保持精簡，也少一條要跟著維護版本的相依鏈。

腳本在 entrypoint.sh 每次 container 啟動、且尚未註冊時執行。是否已註冊，看 bind mount 出來的主機目錄 /home/ubuntu/actions-runner 裡有沒有 .runner。除了領 token，它還做兩件事：

  • 確保 doughops-cd Runner Group 存在。不存在就建成 visibility: selected、selected_repository_ids: []，一開始不放任何 repo。
  • 清掉同名的舊 runner。bastion 被 Terraform 重建，或 bind mount 目錄被清掉重新註冊時，GitHub 仍留著上一份紀錄，狀態是 offline。不清掉的話，紀錄會一直堆積在 org 的 runner 清單裡。

Docker 存取權

container 內只裝 Docker CLI（docker.io 套件），不啟動自己的 dockerd。tasks/main.yml 起 container 時掛載 -v /var/run/docker.sock:/var/run/docker.sock，並用 --group-add 加入主機 docker 群組，群組 GID 在執行時用 getent group docker 動態查詢，不寫死數字。

需要這個存取權，是因為 .github/workflows/run-playbook.yml 使用 GitHub Actions 原生的 container: job，讓有寫入權限的人手動選一支 Ansible playbook 在 bastion 上執行。GitHub 官方規定 self-hosted runner 執行 container: job 時，runner 本身要能呼叫 Docker 另外起一個 job container。

這是 docker-outside-of-docker（DooD），不是巢狀的 Docker-in-Docker。job 用的 container 是 bastion Docker daemon 上的平輩 sibling container，不在 github-runner container 裡面。沒有 socket 掛載，run-playbook.yml 連 actions/checkout 都跑不起來。

決策：接受 runner container 擁有等同 bastion root 的 Docker 存取權，並把觸發權限限制在有 repo 寫入權限的 admin。

理由：workflow_dispatch 要求對 repo 有寫入權限才按得下去。能觸發 run-playbook.yml 的人，本來就是有完整寫入權限的 admin。這些人本來就能直接 SSH 進 bastion、修改 Terraform 與 Ansible。透過 workflow 對 bastion 下 root 級操作沒有擴大信任範圍，只是多開一個觸發介面。

考慮過的替代方案：不掛 docker.sock — 無法執行 container: job，也就無法讓 job 在隔離的 image 內跑。runner 與 bastion 網路隔離 — 見開放給其他 CD repo 之前，尚未實作。

代價：真正要防的是「這些 admin 以外的人」能否間接讓 job 跑到 bastion 上，這由 Runner Group 的 repo 範圍與下一節的檢查負責。沒有分支保護，admin 帳號本身的安全就是整條路徑的上限。

為什麼用 bind mount

runner 的安裝與工作目錄使用主機上的真實路徑 /home/ubuntu/actions-runner，不用 Docker named volume。這是 GitHub 對 container: job 的硬性要求。runner 會把自己的 _work 與 externals 目錄 bind mount 進 job container，主機與 container 內必須是完全相同的路徑。DooD 模式下，這個路徑由主機的 Docker daemon 解析。

runner 若掛的是 named volume，daemon 找不到對應的主機路徑，job container 只會拿到空目錄，actions/checkout 直接失敗。role 只掛這個子目錄，不掛整個 /home/ubuntu，避免把 .ssh 與 .github-app-key.pem 等敏感檔案暴露給 container。

bind mount 不像 named volume 會用 image 內容填充空目錄，所以 entrypoint.sh 在啟動時檢查 /home/ubuntu/actions-runner/run.sh，不存在才從 image 內建的 /opt/actions-runner-seed 複製一份。沒有這一步，全新安裝或 bastion 重建後，container 連 entrypoint.sh 都找不到而啟動失敗。

升級 runner 版本或 docker run 參數

改 github_runner_version 或 docker run 指令本身，不會自動替換舊 container。因為 seed 只在目錄是空的時候做，舊版 runner 執行檔已經留在主機目錄裡，換新 image 後舊 binary 仍會勝出。所以版本升級要做兩件事：

  1. 執行 docker stop github-runner 與 docker rm github-runner。
  2. 清空主機的 /home/ubuntu/actions-runner 目錄內容，再重跑 playbook。

這會強制 runner 重新註冊，mint_registration_token.py 清除同名舊 runner 的邏輯本來就處理這個情境。

防止漏寫 container 的檢查

上面的邊界只有在 job 真的帶 container: 欄位時才成立。某個 job 若打到 bastion runner 卻漏寫 container:，它的每個 step 會直接在 runner container 裡執行，包括 actions/checkout 這類第三方 action。該 container 掛著 docker socket，結果比「job container 裡能碰 docker.sock」更直接。沒有分支保護，就沒有 PR review 能擋下這種疏忽，所以另有兩道檢查。

靜態掃描

.github/workflows/lint-bastion-workflows.yml 搭配 .github/scripts/check_bastion_jobs_use_container.py，掃描 .github/workflows/ 底下每個檔案。只要有 job 的 runs-on 打到 bastion 卻沒有 container:，檢查就失敗。

  • 觸發條件：push 到 main、開 PR、手動觸發，不依賴任何人記得手動加防護。
  • 執行環境：ubuntu-latest，不碰 bastion。
  • paths 過濾涵蓋 .github/workflows/** 與 .github/scripts/**。掃描腳本只讀 .github/workflows/ 底下的 .yml，把腳本路徑也列入觸發條件，是為了讓只改檢查腳本、沒動任何 workflow 的變更，也會重新觸發一次掃描。

執行期自我檢查

run-playbook.yml 的第一個 step 檢查 $GITHUB_WORKSPACE 是否以 /__w/ 開頭。GitHub Actions 只在 job container 裡才把 workspace 掛到這個路徑。外層的 github-runner container 沒有這個路徑，所以能分辨 job 有沒有帶 container:。這是最後一道保險，不取代靜態掃描。

最初的版本檢查 /.dockerenv 是否存在，但 runner 程序本身就跑在 container 裡，兩種情況都摸得到這個檔案，檢查形同無效，所以改成現在的路徑判斷。

run-playbook.yml 的行為

這個 workflow 只有 workflow_dispatch 觸發。輸入 playbook 是相對於 ansible/playbooks/ 的路徑，選填的 extra_args 會原樣接在 ansible-playbook 後面。job 在 ghcr.io/doughops/terraform-k8s-ansible-runner:latest 內執行，掛載 bastion 的 /root/.ssh 與 /home/ubuntu/.ssh。

步驟做什麼
1檢查 $GITHUB_WORKSPACE 以 /__w/ 開頭（見上）
2actions/checkout@v4
3用 realpath -m 解析輸入，路徑跑到 ansible/playbooks/ 外面或檔案不存在就拒絕執行
4把 repo secret ANSIBLE_VAULT_PASSWORD 寫成 workspace 內 mode 600 的 .vault-password
5設定 ANSIBLE_VAULT_PASSWORD_FILE 與 REMOTE_DOCS_DIR，執行 ansible-playbook
6if: always() 刪除 .vault-password

第 5 步以環境變數 ANSIBLE_VAULT_PASSWORD_FILE 覆蓋 ansible.cfg 寫死的 /ansible-key/vault-password，因為 job container 沒有 scripts/ansible.sh 掛出的那個路徑。REMOTE_DOCS_DIR 把 container 內的 /__w/... 換成主機上的 /home/ubuntu/actions-runner/_work/...，因為 roles/docs_site 的 kubectl cp 在 bastion 主機本身執行，讀的是主機路徑。這個字串替換是 bash 專屬語法，所以 step 要明確寫 shell: bash，否則 GitHub Actions 會落回 sh 而報 Bad substitution。

CI 能執行哪些 playbook

CI checkout 出來的 repo 帶有整檔 ansible-vault 加密的 secrets.yml，Ansible 載入 group_vars 時會自動解密。所以 repo secret ANSIBLE_VAULT_PASSWORD 必須等於 .env 的同名值。

值正確時，bastion.yml 和碰 Cloudflare、Keycloak、OIDC 的 k8s/* 也能透過這個 workflow 執行。值不對時，所有 playbook 都會在載入變數時失敗，連 ping.yml 也一樣。

repo secret 的值無法從 GitHub 讀回，這條路徑也還沒實際驗證。透過 CI 跑破壞性 playbook 之前，先跑一次 ping.yml 確認能解密。

開放給其他 CD repo 之前

run-playbook.yml 解決的是窄範圍需求：這個 repo 自己的 admin 手動觸發 Ansible playbook。信任邊界就是已經有 push 權限的人，上面的 ADR 說明了為什麼這個範圍可以接受 root 級風險。

讓另一個 repo（例如某個應用程式的 CD pipeline）也用這個 runner 部署到 k8s，是不同量級的問題。那個 repo 的維護者不一定是現在的 admin，它依賴的 Action 與套件也不在這裡能掌控。把 repo 加進 doughops-cd 只決定誰能觸發，不決定被觸發的內容是否可信。就算只放行一個白名單內的 repo，該 repo 的維護者帳號或依賴被攻破，同樣會讓不受信任的程式碼跑到 runner 上。

因此設計方向是假設某次執行不可信，把它能造成的影響壓到最小，而不只是設法讓不可信的執行不發生。下面四項尚未實作，等實際的 CD repo 出現、需求明確後，再依它要部署的內容組合。

🎫

短命、範圍窄的部署憑證

每個 job 用 Kubernetes 的 TokenRequest API 領一個 ServiceAccount token，TTL 15 到 30 分鐘，RBAC 只綁該 repo 自己的 namespace。不把 admin.conf 或長期 kubeconfig 放進 GitHub secret。

🧱

Runner 與 bastion 網路隔離

bastion 持有太多敏感資產（內部 SSH key、對所有節點的連線）。長期應該改成獨立的 runner VM，只開一條路連 kube-apiserver，不再與 bastion 共享信任邊界。

🔀

只允許 push 與 workflow_dispatch 觸發部署

pull_request 不應該碰 self-hosted runner。deploy job 只在 push 到 main（代表已過 PR review）或 workflow_dispatch 時執行，build 與 test 這種每個 PR 都會跑的 job 交給 GitHub-hosted runner。

♻️

Ephemeral runner

每個 job 現生一個一次性 runner，做完自動銷毀，用 generate-jitconfig 加 --ephemeral 實作。任何一次執行的殘留都不會留到下一個 job。

已知限制

  • 上面「使用前必讀的限制」列出的信任邊界問題，在實作 四項改法之前都存在。
  • run-playbook.yml 透過 workflow_dispatch 實際執行一支 playbook 的完整路徑，尚未做過端對端驗證。
  • bastion 這一側已在真實環境驗證：新版 image build、bind mount 加自我 seed、向 GitHub 註冊，以及 docker exec github-runner docker ps 能連到主機的 Docker daemon。
  • GitHub App 的 private key 以 0600 寫在主機 /home/ubuntu/.github-app-key.pem，以唯讀 bind mount 進 container。能在 runner 上執行程式碼的人讀得到它。
  • 容器內 runner 以 UID 1000 執行，而 UID 1000 同時擁有 docker 群組權限。

實測踩到的 bug

下面兩筆在 role 建置期間發現，已登錄為 Bug #59 與 Bug #60。另有一筆 runner 相關的 bug 已在總表：job container 的動態 Docker network 沒有繼承 daemon 的 MTU，造成 git fetch 失敗，見 Bug #38。

#59 · 全綠燈但看不到 runner

  • 症狀：playbook 的所有 task 顯示 ok 或 changed，沒有失敗，但「起 github-runner container」被跳過，runner 從未建立或註冊。
  • 根因：確認 container 是否存在的 task 用 docker inspect github-runner，沒帶 --type。docker inspect 預設搜尋所有種類的物件，包括 container、image、volume 與 network。上一步 docker build -t github-runner 剛好建出同名的 image。檢查從 build 完成後一路命中那個 image，永遠回報「已存在」，docker run 因 when 條件被擋掉。
  • 修法：加上 --type container，把搜尋範圍限定在 container。
  • 怎麼確認修好：重跑 playbook 後 docker ps 看得到 github-runner，log 出現 √ Runner successfully added。
  • 相關：roles/gitlab_runner 的同類檢查也帶 --type container。

#60 · openssl 讀不到 private key

  • 症狀：openssl 回報 Permission denied，讀不到掛載進去的 GitHub App private key。
  • 根因：Dockerfile 原本用 useradd -m runner 建立新使用者，但 ubuntu:24.04 base image 已內建 UID 1000 的 ubuntu，新使用者被擠到 UID 1001。key 檔案以 -v /home/ubuntu/.github-app-key.pem:...:ro 從主機 bind mount 進來，屬於主機 ubuntu（UID 1000）、mode 0600。bind mount 的權限檢查比對的是 UID 數字，不是使用者名稱，UID 1001 讀不到。
  • 修法：不放寬檔案權限，也不再自己建使用者，直接沿用 base image 內建、UID 與主機相符的 ubuntu。
  • 怎麼確認修好：container 內 mint_registration_token.py 能簽出 JWT，runner 成功註冊。
  • 相關：與上一筆同屬 bind mount 與 container 內外差異的問題類型。

驗證方式

  • 在 bastion 上 docker inspect --type container github-runner，確認 Status: running、RestartCount: 0。
  • docker logs github-runner 依序出現 √ Runner successfully added、√ Connected to GitHub、Listening for Jobs。
  • GitHub 的 org 設定頁，doughops-cd Runner Group 底下有一個線上的 bastion runner。
  • 上線前的驗證：Dockerfile 在 bastion 實際 build 過，下載、checksum 與 installdependencies.sh 都成功。用假的 RSA key 測過 JWT 簽章，確認是三段式結構且 payload 正確。REPLACE_ME 佔位值會讓 assert 清楚報錯。
  • GitHub App 建立之前，installation token 交換、Runner Group 建立與註冊這幾個 API 呼叫沒有端對端測過。PyJWT 與 cryptography 刻意不裝，簽章只靠標準函式庫與 openssl。
  • docker exec github-runner docker ps 能列出主機 Docker daemon 上的 container，證明 socket 掛載與群組權限正確。
  • 在已加入 Runner Group 的 repo 手動觸發 run-playbook.yml，輸入 ping.yml，確認 ansible-playbook step 成功。
