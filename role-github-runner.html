Ansible 自動化Role: github_runner

在 bastion 上跑一個獨立的 Docker container,註冊成 doughops 這個 GitHub org 共用的 self-hosted runner。這頁記錄的除了「怎麼接上」,更多篇幅在「這台 runner 實際 上有哪些限制、什麼情況下絕對不能用它」,因為這正是設計這個 role 時花最多時間討論的部分——讀這頁的人,請先看完下面這個警告框跟 「這台 runner 的限制」那節,再決定要 不要把新的 repo 加進 doughops-cd 這個 Runner Group。

🚫 絕對不可以把這個 Runner Group 開放給任何 public repo——doughops 底下 9 個 repo 有 8 個是 public。GitHub 官方文件的原句是:「Self-hosted runners should almost never be used for public repositories on GitHub, because any user can open pull requests against the repository and compromise the environment.」翻成白話:只要有 workflow 檔案能跑 在這個 self-hosted runner 上,任何人(不用是 collaborator,對那個 public repo 開一個 PR 就有機會)理論上都能讓 程式碼在 bastion 上執行。bastion 身上背的東西(對所有節點的 SSH 存取、Vault/Keycloak 的資料、Cloudflare tunnel token)一旦落入 不受信任的人手上,代價遠大於這個 lab 目前處理過的任何風險。 doughops-cd 這個 Runner Group 目前只放了 terraform-k8s 這一個 private repo, 而且只有下面「這台 runner 的限制」提到、目前僅有 3 個的 push 權限持有者能觸發 workflow——之後要加任何新 repo 進這個 Runner Group 之前,先確認那個 repo 是 private、collaborator 名單受控、而且你真的信任「這個 repo 目前跟未來的每一個 collaborator」有能力直接操作 bastion,不是只信任 repo 目前的 維護者。

這台 runner 的限制(部署/使用前務必先讀)

下面每一項都是設計這個 role、以及後來加上 run-playbook.yml 時實際討論、確認過的取捨,不是 理論上的擔心——確認要不要把新 repo 排進這個 Runner Group 之前, 先確認自己接受這些限制。

👥

信任邊界是「誰能 push 這個 repo」,不是「誰能開 PR」

terraform-k8s 目前只有 3 個人有 push 權限 (khchiang1121、hwchiu、 ShannonHung),而且這個 private repo 沒有 分支保護可用(GitHub 免費版不支援)——這 3 個人可以 直接推到 main,不需要 PR review。任何一個人被 加進某個 repo 的 push 權限,只要那個 repo 排進了這個 Runner Group,就等於直接被信任「有能力對 bastion 下 root 級操作」, 不是比喻,是右邊「docker.sock = 主機 root」那項的直接後果。

🗝️

docker.sock = bastion 主機 root,沒有妥協空間

runner container 為了支援 container: job,一定 要掛 /var/run/docker.sock——這個 socket 本身就是 無條件的主機 root 存取權(docker run -v /:/host chroot /host 一行指令就能拿到完整主機檔案系統),跟 runner 自己有沒有包 container、包幾層都無關。這是支援 container: job 的必要代價,不是可以再收緊的 設定。

🛡️

「沒帶 container: 就直接跑在 bastion 上」只有軟性防護

GitHub Actions 不像 GitLab 的 Docker executor,沒有 runner 層級「強制所有 job 都要在 container 裡跑」的設定——要不要隔離 是每個 workflow 檔案自己決定。這裡有兩道防護(見下方 run-playbook.yml 自己的執行期自我檢查跟 lint-bastion-workflows.yml 的靜態掃描),但兩者 都只是「防手滑」的軟性防護,不是硬性技術邊界——任何有 push 權限的人都做得到繞過或直接把這兩道防護刪掉,真正的邊界始終是 「信任這幾個 admin 不會這麼做」。

🖥️

單一、共用、非一次性的 runner,不是乾淨的一次性環境

這不是 GitHub-hosted runner 那種「每個 job 全新 VM、跑完銷毀」 的模型——這一台 runner 常駐在 bastion 上,一次只能跑一個 job,狀態(.runner/.credentials、 bind mount 的工作目錄)在多次執行之間持續存在,不會自動清空。 上一個 job 留下的任何殘留,理論上都可能被下一個 job 看到。

🏚️

Runner 中毒 = bastion 中毒 = 整個 lab 淪陷

runner 直接跑在 bastion 上,沒有跟 bastion 其他職責(NFS server、Vault、Keycloak、對所有節點的 SSH 存取)做網路或權限 隔離。這是已知、接受的架構侷限,不是這次順便解決的問題——見 下方「還沒解決的部分」那節列的長期改法(短命憑證、runner 跟 bastion 網路隔離、ephemeral runner)。

為什麼是 Docker container,不是 systemd

跟 bastion_ssh_tunnel 那種常駐服務不一樣,這裡故意選 Docker——bastion 上已經有 Docker 在跑(scripts/ansible.sh 自己就是靠它建置、執行 ansible-runner container),多一個獨立的 github-runner image 是同一套既有工具鏈,不用再多學一種服務管理方式。版本/ 執行環境完全封裝在 image 裡,重跑這個 role 不會跟 host 上其他 東西的相依套件打架。

實際跑起來了——container 已經在 bastion 上跑, log 印出 √ Runner successfully added → √ Connected to GitHub → Listening for Jobs,docker inspect 確認 RestartCount: 0、Status: running,不是 卡在重啟迴圈裡假裝正常。過程中抓到兩個實測才會冒出來的 bug,記錄 在下面。

Bug 記錄:第一次跑完全綠燈,但 GitHub 上完全看不到 runner——「確認 github-runner container 存不存在」這個 task 用 docker inspect github-runner(沒帶 --type)判斷要不要建立 container,但 docker inspect 預設會搜尋所有種類的 物件(container、image、volume、network……),而上一步 docker build -t github-runner 剛好也建出一個同名的 image——所以這個檢查從第一次跑完 docker build 之後就一路命中那個 image,永遠回報「已經存在」, docker run 因此永遠被 when 擋掉跳過, runner 從來沒有真的被建立、註冊過,ansible 卻全部顯示 ok/沒有失敗。修法是加上 --type container,把搜尋範圍限定在容器,不讓同名的 image 混進來。

Bug 記錄:第二個問題——container 起來了,但 openssl 讀不到掛進去的 private key——Dockerfile 原本 自己 useradd -m runner 造一個新使用者,但 ubuntu:24.04 這個 base image 本身就內建一個 UID 1000 的 ubuntu 使用者,所以新造的 runner 被 擠到 UID 1001。GitHub App 的 private key 檔案是用 -v /home/ubuntu/.github-app-key.pem:...:ro 從 host bind mount 進去的,host 上這個檔案屬於 UID 1000(bastion 的 ubuntu 使用者),bind mount 進 container 之後權限檢查 是照 UID 數字比對、不是看使用者名稱——container 裡的 UID 1001 讀不到 UID 1000 擁有的 mode 0600 檔案, openssl 直接 Permission denied。修法不是放寬檔案 權限,是乾脆不要自己造新使用者,直接沿用 base image 內建、UID 剛好 對得上 host 的 ubuntu 使用者。

為什麼是 GitHub App,不是個人帳號的 PAT

註冊 org 層級的 runner 需要 org 管理層級的 API 權限。最簡單的做法 是 GitHub 網頁上「New self-hosted runner」直接給的 registration token——但那是給人手動貼一次用的,每次 bastion 重建都要有人回來 網頁上重新複製一次,不符合「自動註冊」的需求,所以一定要換成腳本 能拿到的憑證。

能腳本化的選項其實有三種,誠實列出取捨,不是只有「用了才知道」:

方式範圍會不會過期綁在誰身上
Classic PAT(admin:org)整個 org 管理權限,遠大於「只管 runner」看設定,可以是永不過期個人帳號
Fine-grained PAT可以鎖到只剩 Organization → Self-hosted runners強制設過期日(最長 1 年),要記得手動續期個人帳號
GitHub App(這裡選的)一樣鎖到只剩 Organization → Self-hosted runnersApp 本身不設過期,只有要不要主動撤銷 private key 的問題org 資產,不屬於任何一個人

Fine-grained PAT 其實已經解決了「範圍太寬」的問題,設定也比 App 簡單得多(不用簽 JWT、不用管 installation token,直接拿 token 打 API)——選 App 純粹是為了另外兩個屬性:不會因為忘記手動續期而 某天突然斷掉,以及它是 doughops 這個 org 的資產,不會因為某個人 離開/停用帳號而跟著失效。在只有 3 個人的 org 現階段,這個差異其實 沒有很大,是刻意選「對團隊長期比較對」的做法,不是唯一能動的做法 ——如果你之後覺得 App 的設定成本不划算,fine-grained PAT 是完全 合理的替代方案,程式碼只要把 mint_registration_token.py 的 JWT 那段拿掉、直接拿 PAT 當 installation token 用就好。

建立 GitHub App:逐欄位的完整步驟

下面每一步都是 GitHub 網頁上實際會看到的欄位,照著填就好——這頁 第一版只寫了「建一個 App,勾 Self-hosted runners 權限」,漏了一堆 表單上真的會卡住人的欄位(Webhook、Installation ID 去哪找……), 這次補齊。

  1. 1. 開新 App 的頁面 網址直接打 https://github.com/organizations/doughops/settings/apps/new (或手動走 doughops org → Settings → Developer settings → GitHub Apps → New GitHub App)。
  2. 2. GitHub App name 這個名字是全 GitHub 唯一,不是只在 doughops org 內唯一——跟別人的 App 撞名會建立失敗。建議取一個包含 doughops 的名字,例如 doughops-bastion-runner。
  3. 3. Homepage URL(必填,但不需要真的能用) 這個 App 不會真的被誰拿去點連結,填 https://github.com/doughops 就夠,只是通過表單 驗證。
  4. 4. Callback URL、Setup URL 都留空——這兩個是給「App 要讓使用者跑 OAuth 登入流程」用的, 這裡完全用不到(我們只用 App 對 org 的權限,不會有人「登入」 這個 App)。
  5. 5. Webhook 把 Active 這個勾選框取消勾選 ——我們不需要 webhook 事件,勾著又沒填 URL,GitHub 有時候會 擋你儲存,或是背景一直嘗試投遞失敗的 webhook,乾脆關掉。
  6. 6. Permissions → Repository permissions 整組全部維持預設的 No access,一個都不用勾—— runner 註冊跟 repo 內容完全無關。
  7. 7. Permissions → Organization permissions 在清單裡找到 Self-hosted runners(注意不是 repository permissions 那組同名的項目,是下面 Organization permissions 這一組),下拉選單選 Read and write。其他 Organization permissions(Members、Administration……)全部維持 No access。
  8. 8. Permissions → Account permissions 維持全部 No access——這組是給存取使用者個人帳號 資料用的,跟這個 App 的用途無關。
  9. 9. Where can this GitHub App be installed? 選 Only on this account(doughops)——不要選 「Any account」,那個是給要公開發佈給別人裝的 App 用的。
  10. 10. 按 Create GitHub App,記下 App ID 建立完成後會跳到 App 自己的設定頁,最上面就印著 App ID: 123456 這種數字——這是 github_app_id。
  11. 11. 產生 private key 同一頁往下捲到 Private keys 區塊,按 Generate a private key——瀏覽器會自動下載一個 <App 名稱>.<日期>.private-key.pem 檔案。這個檔案的完整內容(整份,含 -----BEGIN RSA PRIVATE KEY-----/ -----END RSA PRIVATE KEY----- 那兩行,保留原本的 換行)就是 github_app_private_key,只會 讓你看到/下載這一次,遺失了要在同一頁重新產生一把新的(舊的 可以在旁邊按 Delete 撤銷)。
  12. 12. Install 到 doughops org 左側選單點 Install App,找到 doughops → 按 Install。跳出來的 Repository access 選哪個 都不影響安全性(這個 App 完全沒有要任何 repo 權限,唯一有意義 的是前面設定的 Organization permission)——選 Only select repositories 隨便選一個,或乾脆選 All repositories 都可以。
  13. 13. 拿 Installation ID 按完 Install 之後,瀏覽器網址列會變成類似 https://github.com/organizations/doughops/settings/installations/12345678 ——結尾那串數字就是 github_app_installation_id。 如果那個當下沒注意到,事後找的路徑是:doughops org → Settings → 左側選單 GitHub Apps(在 org 主 Settings 選單裡,不是 Developer settings 底下那個同名項目)→ 找到你的 App → 按 Configure,網址列一樣會帶出同一串 數字。

不想用瀏覽器網址欄找 Installation ID? 拿到 App ID + private key 之後,可以直接用指令查(這是 mint_registration_token.py 簽 JWT 那段的純 bash 版本, 不需要先跑完整個 ansible role):

APP_ID=12345          # 換成你的 App ID
KEY=doughops-bastion-runner.2026-07-27.private-key.pem   # 換成你下載的檔名

NOW=$(date +%s)
HEADER=$(printf '{"alg":"RS256","typ":"JWT"}' | openssl base64 -e -A | tr '+/' '-_' | tr -d '=')
PAYLOAD=$(printf '{"iat":%s,"exp":%s,"iss":"%s"}' "$((NOW-60))" "$((NOW+540))" "$APP_ID" | openssl base64 -e -A | tr '+/' '-_' | tr -d '=')
SIG=$(printf '%s.%s' "$HEADER" "$PAYLOAD" | openssl dgst -sha256 -sign "$KEY" | openssl base64 -e -A | tr '+/' '-_' | tr -d '=')
JWT="$HEADER.$PAYLOAD.$SIG"

curl -s -H "Authorization: Bearer $JWT" \
     -H "Accept: application/vnd.github+json" \
     https://api.github.com/app/installations

回應是一個 JSON 陣列,每個元素的 id 欄位就是 installation ID(這串指令已經照這個實際的 JWT 組法測過,確認能 產生格式正確的 token,不是憑印象寫的)。

三個值都拿到之後,填進 ansible/inventory/group_vars/all/secrets.yml (複製自 secrets.yml.example,這個檔案不進版控):

group_vars/all/secrets.yml
github_app_id: "12345"
github_app_installation_id: "12345678"
github_app_private_key: |
  -----BEGIN RSA PRIVATE KEY-----
  ……(.pem 檔案的完整內容,保留每一行換行)……
  -----END RSA PRIVATE KEY-----

填完跑 scripts/ansible.sh ansible-playbook playbooks/bastion/github-runner.yml ——沒填之前跑會被 role 開頭的 ansible.builtin.assert 擋下來,清楚報錯而不是卡在某個看不懂的 API 401。

mint_registration_token.py:只用標準函式庫 + openssl

GitHub App 認證的標準流程是:用 App 的 private key 簽一個 JWT(RS256)→ 拿 JWT 換一個 installation access token → 用這個 token 呼叫實際的 API。這一步通常會用 PyJWT/ cryptography 這類套件,但這裡故意不裝任何 pip 套件 ——JWT 的 header/payload 組裝、base64url 編碼,標準函式庫就夠; 唯一需要真正密碼學運算的 RSA-SHA256 簽章,直接呼叫系統的 openssl dgst -sha256 -sign,讓 image 保持精簡,也 減少一條「pip 套件版本又要跟著維護」的相依鏈。

這支腳本除了現領 token,也在 entrypoint.sh 每次 container 啟動、還沒註冊過的時候(.runner 檔案不 存在,靠 bind mount 出去的主機真實目錄 /home/ubuntu/actions-runner 裡有沒有這個檔案判斷,見 下方「為什麼這個 container 現在有 Docker 存取權」關於 bind mount 的說明)順便做兩件事:

  • 確保 doughops-cd 這個 Runner Group 存在——如果不存在,建成 visibility: selected、 selected_repository_ids: [],一開始不放任何 repo 進去。
  • 清掉同名的舊 runner——bastion 被 terraform 重建過、或這個 bind mount 的主機目錄被清掉重新註冊的話,GitHub 那邊還留著上一份 的紀錄(狀態會是 offline),不清掉會一直堆積在 org 的 runner 清單裡。

為什麼這個 container 現在有 Docker 存取權

這頁最早的版本寫的是「這個 container 完全沒有 Docker 存取權」——那時候 runner 存在的唯一目的是把自己接上 GitHub,還沒有 任何東西會真的排工作給它跑。現在不一樣了:Dockerfile 多裝了 docker.io(只裝 CLI,不啟動自己的 dockerd),tasks/main.yml 起 container 的時候多掛了 -v /var/run/docker.sock:/var/run/docker.sock 跟 --group-add(動態查 bastion 上 docker 群組的 GID,把這個 container 裡的 ubuntu 使用者塞進 那個群組,才讀寫得到 socket)。理由是新加的 .github/workflows/run-playbook.yml:它用 GitHub Actions 原生的 container: job 機制,讓人能手動選一支 Ansible playbook、在 bastion 上跑——而 GitHub 官方文件講得很明白, self-hosted runner 要執行 container: job,runner process 本身要能呼叫 Docker,幫這個 job 另外起一個獨立 container。這不是巢狀的 Docker-in-Docker,是 docker-outside-of-docker(DooD):job 用的 container 是 bastion Docker daemon 上的平輩 sibling container,不是 跑在 github-runner 這個 container 裡面。沒有這一段, run-playbook.yml 的 container: job 連 actions/checkout 都跑不起來。

terraform-k8s 已經被加進 doughops-cd 這個 Runner Group,repo secret ANSIBLE_VAULT_PASSWORD 也已經設定好。bastion 這一側(新版 image build、container 用 bind mount + 自我 seed 起來、成功跟 GitHub 註冊、 docker exec github-runner docker ps 確認摸得到 bastion 主機真正的 Docker daemon)已經在真實環境測過一輪、全部 符合預期。run-playbook.yml 這支 workflow 本身透過 workflow_dispatch 真的被觸發、實際跑一支 playbook 這條路徑,還沒有做過端到端驗證——這裡描述的是這個機制「怎麼 運作」跟「為什麼需要 Docker 存取權」,不是在宣稱已經端到端測試 過。

取捨:這等於給了這個 container 跟 bastion 主機 root 一樣大的權限——能對 /var/run/docker.sock 下指令的人,就能起一個把 host 根目錄掛進去的 privileged container,等於直接在 bastion 上用 root 執行任意指令,不是「有限 的容器隔離」。這不是沒注意到的疏漏,是討論過後接受的風險:這個 private repo 現在只有 3 個人有 push 權限,沒有 branch protection 強制走 PR review;而 workflow_dispatch 這個觸發方式 本身就要求「對這個 repo 有寫入權限」才按得下去——換句話說,能 觸發 run-playbook.yml 的人,本來就是這 3 個對 repo 有完整寫入權限的 admin,不是任何外部貢獻者或開 PR 的人。把「這 3 個人能透過 workflow 對 bastion 下 root 級操作」跟「這 3 個人 本來就能直接 SSH 進 bastion、改 Terraform、改 Ansible」放在一起 看,並沒有真的擴大信任範圍,只是多開了一個觸發介面。真正需要 提防的是「這 3 人以外的人」有沒有辦法間接讓 job 跑到 bastion 上——這正是下面 lint-bastion-workflows.yml 要擋的事。

為什麼 runner 的安裝/工作目錄要從 Docker named volume 改成 host 上一個真實路徑的 bind mount (/home/ubuntu/actions-runner,見 tasks/main.yml「建立 runner 安裝目錄」那個 task)——這不是效能或方便的考量,是 GitHub 官方對 container: job 的硬性要求:self-hosted runner 執行 container: job 時,會把自己的 _work/externals 目錄用「host 跟 container 內完全相同的路徑」bind mount 進 job container,DooD 模式下這個路徑是 host 自己的 docker daemon 在解析——如果 runner 自己是掛 named volume(不是一個 host 上真的看得到路徑的目錄)在 跑,daemon 根本找不到對應的主機路徑,job container 只會拿到一個 空目錄,actions/checkout 這一步就直接失敗。改成 bind mount 之後多一個原本沒有的新問題:bind mount 不像 named volume 會自動用 image 內容 seed 空目錄,所以 role 裡多了一個 「只在目錄是空的時候,用一次性 container 把 image 內建的 runner 檔案複製到主機目錄」的 seed 步驟(tasks/main.yml 「把 image 內建的 runner 檔案複製到主機的 bind mount 目錄」那 段),不做這一步的話,全新安裝或 bastion 重建之後 container 連 entrypoint.sh 都找不到,直接啟動失敗。

lint-bastion-workflows.yml:防止有人忘記加 container:

上面那個 root 級風險只在「job 真的帶 container: 欄位」的前提下才有邊界——如果某支 workflow 的 job 打到 bastion 這個 self-hosted runner,卻忘記加 container:,那個 job 的每個 step(包括 actions/checkout 這類第三方 action)都會直接在 bastion 主機上執行,沒有任何隔離,結果比「container 裡能碰 docker.sock」還更直接。因為這個 repo 只有 3 個人有 push 權限、 沒有 branch protection 可用,沒有 PR review 能強制擋下這種疏忽, 所以另外加了一支獨立的 workflow (.github/workflows/lint-bastion-workflows.yml + .github/scripts/check_bastion_jobs_use_container.py) 掃描 .github/workflows/ 底下每一個檔案,只要有 job 的 runs-on 打到 bastion、卻沒有 container: 欄位,就讓檢查失敗——不依賴任何人記得 手動加防護,repo 裡任何 push 到 main、開 PR、或手動 觸發都會自動掃過全部 workflow 檔案。它本身跑在 ubuntu-latest 上,不用碰 bastion;觸發條件 (push/pull_request 的 paths 過濾)涵蓋 .github/workflows/** 跟 .github/scripts/** 兩個路徑——不是說掃描的內容包含 .github/scripts/(check_bastion_jobs_use_container.py 本身只讀 .github/workflows/ 底下的 .yml 檔案),而是把腳本路徑也算進觸發條件,這樣有人只改動檢查腳本、 沒動任何 workflow 檔案時,這支 lint 還是會被觸發重新跑一次—— 篡改腳本這件事本身不會因為沒碰 workflow 檔案就漏掉。 run-playbook.yml 自己第一個 step 還多做一次執行期的自我檢查(確認 $GITHUB_WORKSPACE 是 /__w/ 開頭—— GitHub Actions 只在 job container 裡才會把 workspace bind mount 到這個路徑,外層的 github-runner container 本身沒有 這個路徑,所以能真正分辨出「這個 job 有沒有帶 container:」;原本檢查 /.dockerenv 存在的版本是個 no-op,因為 github-runner 這個 runner process 本身也是跑在 container 裡,兩種情況都摸得到 /.dockerenv),是最後一道保險,不是取代這支 lint。

還沒解決的部分:怎麼安全地開放給第一個 CD repo

run-playbook.yml 設計上要解決的是「這個 repo 自己的 3 個 admin 手動觸發 Ansible playbook」這個窄範圍需求(實際能不能 觸發還要看上面提到的 Runner Group 手動步驟),信任邊界就是 「本來就有 push 權限的人」,上面已經討論過為什麼這個範圍可以接受 root 級風險。這裡要談的是完全不同量級的問題:未來如果要讓 另一個 repo(例如某個應用程式的 CD pipeline)也能 用這個 runner 部署到 k8s,那個 repo 的維護者不一定是這 3 個 admin,程式碼/依賴的 Action 也不是這裡能掌控的——不能直接比照 run-playbook.yml 的信任假設。把 repo 加進 doughops-cd 這個 Runner Group,只是 解決「誰可以觸發」——真正的問題是「觸發的東西被信任嗎」:就算 只放行一個白名單內的 repo,那個 repo 本身被攻破(維護者帳號被盜、 用到的某個 Action/套件被下毒)一樣能讓惡意程式碼跑到 runner 上。討論下來,真正該做的是把「假設某次執行是惡意的」當前提,讓 它能造成的傷害趨近於零,而不是只想辦法讓惡意執行不要發生:

🎫

短命、範圍極窄的部署憑證

每個 job 用 Kubernetes 的 TokenRequest API 現領 一個 ServiceAccount token,TTL 15-30 分鐘,RBAC 只綁該 repo 自己的 namespace——不是把 admin.conf 或長期 存在的 kubeconfig 放進 GitHub secret。

🧱

Runner 跟 bastion 網路隔離

bastion 身上背了太多敏感資產(內部 SSH key、對所有節點的 連線)——長期應該是一台獨立、只開一條路連 kube-apiserver 的 runner VM,而不是繼續疊加在 bastion 上,把「runner 中毒」跟 「整個 lab 淪陷」畫上等號。

🔀

只允許 push/workflow_dispatch 觸發部署

pull_request 永遠不該碰 self-hosted runner ——deploy job 只在 push 到 main (代表已經過 PR review 才會發生)或 workflow_dispatch 觸發,build/test 這種在任何 PR 都會跑的 job 留給 GitHub-hosted runner。

♻️

Ephemeral runner

每個 job 現生一個一次性 runner、做完自動銷毀 (generate-jitconfig + --ephemeral) ——避免任何一次執行的痕跡留到下一個 job,不管下一個 job 是 不是同一個 repo 的。

這些都還沒實作——先把 runner 本身接好、Runner Group 鎖成空的, 等實際的 CD repo 出現、需求明確之後,再依那個 repo 實際要部署的 東西決定怎麼組合上面這幾層。
