Ansible 自動化Role: vault

HashiCorp Vault,當整個叢集共用的 secrets backend。跟這個專案其他 服務不一樣的地方是它跑在 bastion 上,不是叢集內的 workload ——兩個獨立的 role 分工:roles/vault_server 在 bastion 裝 Vault 本身,roles/vault_secrets_operator 在叢集裡裝 vault-secrets-operator(VSO),讓任何 namespace 都能把 Vault 的 secret 同步成一般的 k8s Secret。實際怎麼用見 叢集使用手冊,這頁專注在怎麼做到、 過程中撞到的三個 bug。

為什麼 Vault 跑在 bastion,不是叢集內

這是刻意的選擇,不是預設值——資料要能在 bastion 重建之後自動 復原,而 bastion 剛好已經有一顆完全符合這個需求的資源: user-data 這顆持久化 Cinder volume(prevent_destroy + delete_on_termination = false,bind mount 到 /userap,見 CLAUDE.md「Bastion 的兩個資料 volume 存活」 那段)。Vault 的 storage backend 直接指到 /userap/vault/data——bastion 被 terraform destroy/ apply 重建之後,這個 role 重跑會偵測到「storage 裡已經有 init 過的資料」,直接 unseal 接回去,不會重新 init。

單一 unseal key:換完全自動化,不是隨便放寬安全性

Vault 預設用 Shamir secret-sharing 把 unseal key 拆成 5 把、湊齊 3 把 才能 unseal——這個信任模型假設「多個人各自保管一把,任何單一個人都 不能單獨解鎖」。這個 lab 只有單一 operator,這個假設沒有對應的受益者, 換來的只是「每次重開機/重建都要手動貼 3 把 key」的麻煩。

roles/vault_server/defaults/main.yml
vault_key_shares: 1
vault_key_threshold: 1

換成單一 key 之後,vault operator init/unseal 整段都能安全自動化——這個 role 每次執行都會檢查目前是不是 sealed,是的話就自動用存下來的 key unseal 一次,重開機/ 重建之後不需要人介入。

unseal key + root token 存在跟資料同一顆 volume 上 (/userap/vault/init.json,root-only)——這不是 分開存放的最佳實務(一般建議 key 要跟它解鎖的資料分開放),是刻意 的取捨:如果分開放,bastion 重建之後資料雖然還在,但沒有 key 就永遠 打不開,直接牴觸「重建可以還原」這個要求。這個 lab 只有單一 operator,分開存放換來的安全性沒有實際受益者。

Bug #1:HashiCorp 的 GPG key 沒有 dearmor

裝 vault 這個 apt 套件要先加 HashiCorp 的官方 repo + 簽章金鑰。第一版直接把 curl .../gpg 的輸出存成 .gpg 檔案:

錯誤版本
curl -fsSL https://apt.releases.hashicorp.com/gpg \
  -o /usr/share/keyrings/hashicorp-archive-keyring.gpg

實測直接炸開:apt-get update 報 NO_PUBKEY、the repository is not signed。 HashiCorp 的 /gpg 端點回傳的是 ASCII-armored 的公鑰 (-----BEGIN PGP PUBLIC KEY BLOCK-----),不是已經 dearmor 過的二進位 keyring——apt 的 signed-by= 讀不出 有效的 key。

修法是比照 roles/kubectl_cli 裝 Kubernetes apt repo 那份已經寫對的做法,先 pipe 給 gpg --dearmor:

修復後
curl -fsSL https://apt.releases.hashicorp.com/gpg \
  | gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg

Bug #2:handler 排在 unseal 之後,把 unseal 結果蓋回 sealed

Vault 的設定檔(vault.hcl)改了要重啟服務,用 ansible 標準的 notify: 重啟 vault handler 模式。問題是 Ansible 的 handler 預設要等整個 play 全部 task 跑完才會 執行,不是緊接在觸發它的那個 task 後面——這個 role 的第一次 執行(設定檔本來不存在,一定會觸發這個 handler),task 順序是:

寫設定檔
notify: 重啟(排進佇列)
→
init + unseal
成功,sealed: false
→
開 KV v2
→
handler 這時才執行
重啟 → 回到 sealed!

實測結果:整個 play 跑完、failed=0,但直接查 vault status 卻是 sealed: true——unseal 明明成功過,卻被排在後面才執行的 restart 蓋掉。修法是在寫完設定檔 後立刻強制 flush:

roles/vault_server/tasks/main.yml
- name: 寫 vault 的 server 設定
  ansible.builtin.template: ...
  notify: 重啟 vault

- name: 如果上面設定檔真的換了,現在就重啟(不要拖到整個 play 跑完)
  ansible.builtin.meta: flush_handlers

這樣「這次設定檔有沒有換」永遠是這個 role 裡最先 處理完的事,之後才判斷 init/unseal——不會有「先 unseal 成功、後面又 被重啟蓋回去」的順序問題。

Bug #3:VSO 的「共用身份」不是想像中的那樣

目標是讓所有 namespace 共用同一組 Vault 身份/政策,不用每個 namespace 各自申請。用 VSO chart 內建的 defaultVaultConnection/defaultAuthMethod 建一個共用的 VaultAuth,kubernetes.serviceAccount: default ——第一版直覺假設,這個 default 是 vault-secrets-operator 這個 namespace 底下的 default,所以 Vault 那邊的 kubernetes-auth role 寫死 bound_service_account_namespaces=vault-secrets-operator。

實測:VSO controller log
Failed to get NewClientWithLogin ... auth/kubernetes/login
Code: 403. Errors: * namespace not authorized

查了 hashicorp/vault-secrets-operator#827 才確認實際行為:defaultAuthMethod.kubernetes.serviceAccount 這個名字,是拿去消費這個 VaultAuth 的那個資源 (VaultStaticSecret……)自己所在的 namespace 裡面找同名 SA,不是去 VaultAuth 自己的 namespace 找——每個 namespace 其實都是拿自己的 default SA 去登入 Vault,不是全部借用 operator 的身份。這樣反而更符合「所有 namespace 都可以用」的字面意思,所以 Vault 那邊的 role 要放行萬用 字元 namespace,不能寫死:

修復後
vault write auth/kubernetes/role/k8s-shared \
  bound_service_account_names=default \
  bound_service_account_namespaces=* \
  policies=k8s-shared-read

修完之後端對端驗證:在一個全新建立的 namespace 建 VaultStaticSecret,一個 reconcile 週期內同步出正確內容 的 k8s Secret,SecretSynced: True。

對外曝露:借用既有的 bastion-ssh tunnel,不是另開一條

Vault 監聽在 fabric_ip:8200(k8s-net,tls_disable = true——跟 roles/nfs_server 的 NFS export 同一套「網段本身當信任邊界」的既有安全模型)。要讓 vault.dough-ops.com 對外可達,不需要在 bastion 上另外裝 第二個 cloudflared 實例——bastion-ssh 這條 tunnel 本來就跑在 bastion 上,config_src = "cloudflare" 代表 它的 ingress 規則是從 Cloudflare 那邊即時抓的,直接在 Terraform 幫 它多加一條 ingress 規則就生效,bastion 上完全不用動:

cloudflare/tunnels.tf(新增的規則)
{
  hostname = "vault.dough-ops.com"
  service  = "http://10.10.0.11:8200"
}

vault.dough-ops.com 沒有另外建專屬的 Cloudflare Access Application——它自動落在既有的萬用字元 Application (*.dough-ops.com)底下,跟 dashboard/grafana/prometheus 這些工具是同一個模式,見 內部工具。

OIDC 登入:仿 Grafana,不是仿 Dashboard

Vault 沒辦法比照 Dashboard 那套 被動驗證 Cf-Access-Jwt-Assertion header 的做法—— Dashboard 能這樣做,是因為 kube-apiserver 本身有 --oidc-issuer-url 這種「被動驗證任意 bearer JWT」的 內建能力,Vault 的 API 沒有對應機制,一律要求自己 發的 X-Vault-Token。改仿 Grafana 那套真正的 OIDC relying party(auth/oidc),對應 Cloudflare 這邊獨立的 「Access for SaaS」OIDC application(vault-sso,跟 grafana-sso 同一個機制,不同 app)。

使用者明確要求:OIDC 登入之後直接有完整權限 ——不像 Dashboard/Grafana 那樣分「預設唯讀 + oidc_admin_emails 才有完整權限」兩層。任何通過邊緣 Cloudflare Access(doughops org 成員)、OIDC 登入 Vault 的人,都拿到 oidc-admin 這個自訂政策(path "*", 全部 capability)——不是綁 Vault 內建的 root policy 名稱(技術上可以,但那個名字有特殊含義,寫一個效果等價、獨立可 撤銷/可稽核的政策比較乾淨)。這是刻意的選擇,風險自負,不是這個 role 自己的預設值。

Vault UI 登入頁自動選中 OIDC(不用先點方法選單),靠兩個條件湊滿: 掛載路徑等於 oidc(跟 auth method 的 type 同名)+ listing_visibility=unauth:

roles/vault_server/tasks/main.yml
vault auth enable oidc
vault auth tune -listing-visibility=unauth oidc/

效果等同 Grafana 的 auto_login: true——瀏覽器開 vault.dough-ops.com,先過邊緣萬用字元 Access(用掉既有 team session,免重新登入),Vault UI 自動跳 OIDC,再過一次 vault-sso 這個 SaaS Application(同一個 team session, 一樣免重新登入),直接進 Vault。

redirect_uris 兩條,UI 登入跟 CLI 登入(vault login -method=oidc)分開列:

cloudflare/access.tf(vault_sso Application)
redirect_uris = [
  "https://vault.dough-ops.com/ui/vault/auth/oidc/oidc/callback",
  "http://localhost:8250/oidc/callback",
]

驗證方式

  • Vault 健康狀態:curl http://<fabric_ip>:8200/v1/sys/health 確認 sealed: false。
  • OIDC discovery:curl <oidc_discovery_url>/.well-known/openid-configuration 確認回傳合法的 authorization_endpoint/token_endpoint/jwks_uri。
  • 端對端 secret 同步:建一個測試 namespace + VaultStaticSecret, 確認同步出來的 Secret 內容正確、事後清乾淨。
  • 外部曝露:curl -I https://vault.dough-ops.com/ui/ 確認 302 導去 doughops.cloudflareaccess.com 的登入頁。
