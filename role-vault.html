對外入口與身份驗證 Role: vault

HashiCorp Vault 是整個叢集共用的 secrets backend，跑在 bastion 上，不是叢集內的 workload。兩個 role 分工。roles/vault_server 屬於 bastion.yml，在 bastion 裝 Vault 本身。roles/vault_secrets_operator 屬於 k8s.yml，在叢集內裝 vault-secrets-operator（VSO），讓任何 namespace 把 Vault 的 secret 同步成一般的 k8s Secret。Vault 要先於 VSO 就位。使用方式見叢集使用手冊，這頁說明設計與實測踩到的三個 bug。

現在的設定

項目設定為什麼
位置bastion，監聽 fabric_ip:8200，tls_disable = true沿用 roles/nfs_server 的做法，以 k8s-net 網段本身當信任邊界
storagefile backend，路徑 /userap/vault/data/userap 是 user-data 持久化 volume，bastion 重建後資料還在
unsealvault_key_shares: 1、vault_key_threshold: 1讓 init 和 unseal 能完全自動化
init 結果unseal key 和 root token 存在 /userap/vault/init.json（root-only）重建後才能自動 unseal，見已知限制
OIDCauth/oidc，掛在預設路徑 oidc/，role vault-oidc對接 Cloudflare Access for SaaS 的 vault-sso Application
OIDC 權限policy oidc-admin（path "*"，全部 capability）見已知限制
VSO 共用身份role k8s-shared、policy k8s-shared-read所有 namespace 共用同一組 Vault 政策，不必各自申請

為什麼跑在 bastion

資料要在 bastion 重建後自動復原。bastion 已經有一顆符合需求的資源，就是 user-data 這顆 Cinder volume。它帶 prevent_destroy 和 delete_on_termination = false，bind mount 到 /userap。說明見 Terraform / OpenStack § 資料碟。bastion 被 terraform destroy 再 apply 重建後，role 重跑會偵測到 storage 內已有 init 過的資料，直接 unseal 接回去，不會重新 init。

單一 unseal key

決策：vault_key_shares 和 vault_key_threshold 都設 1，init 和 unseal 全部自動化。

理由：Vault 預設的 Shamir 做法把 unseal key 拆成 5 份、湊齊 3 份才能解鎖，前提是多人各自保管一份。這個 lab 只有單一 operator，這個前提不成立，換來的只是每次重開機或重建都要手動貼 3 把 key。單一 key 之後，role 每次執行都檢查是否 sealed，是就用存下來的 key 自動 unseal。

考慮過的替代方案：預設的 5 取 3 — 只有單一 operator，沒有人分攤保管；key 與資料分開存放 — bastion 重建後資料還在但沒有 key，永遠打不開，與「重建可還原」衝突。

代價：拿到 bastion 上 /userap 讀取權限的人，同時拿到資料與解鎖資料的 key，見已知限制。

對外曝露

要讓 vault.dough-ops.com 對外可達，不需要在 bastion 另裝一個 cloudflared。bastion-ssh tunnel 本來就跑在 bastion 上。它的 config_src = "cloudflare" 表示 ingress 規則從 Cloudflare 即時抓取。在 Terraform 多加一條規則就生效，bastion 上不用動，也不必重跑 Ansible。

cloudflare/tunnels.tf（新增的規則）
{
  hostname = "vault.dough-ops.com"
  service  = "http://10.10.0.11:8200"
}

vault.dough-ops.com 沒有專屬的 Access Application，自動落在萬用字元 Application（*.dough-ops.com）底下，和 Dashboard、Grafana、Prometheus 同一個模式，見內部工具。Access 規則的整體說明見 Cloudflare 設定清單 § Access 規則。

OIDC 登入

Vault 的 API 一律要求自己發的 X-Vault-Token，沒有像 kube-apiserver 的 --oidc-issuer-url 那種被動驗證任意 bearer JWT 的機制，所以不能像 Dashboard 那樣驗證 Cf-Access-Jwt-Assertion header。Vault 改用真正的 OIDC relying party（auth/oidc），對接 Cloudflare 的獨立 Access for SaaS Application vault-sso，機制和 grafana-sso 相同。

要讓 Vault UI 登入頁自動選中 OIDC，需要兩個條件：auth method 的掛載路徑等於 type 名稱 oidc，並且 listing_visibility=unauth。

roles/vault_server/tasks/main.yml
vault auth enable oidc
vault auth tune -listing-visibility=unauth oidc/

效果等同 Grafana 的 auto_login: true。瀏覽器開 vault.dough-ops.com 時，先過邊緣萬用字元 Access，Vault UI 再自動跳 OIDC，過 vault-sso。兩段共用同一個 team session，不需要重新輸入帳密。

redirect_uris 分兩條，UI 登入和 CLI 登入（vault login -method=oidc）各一條。Vault 端 role 的 allowed_redirect_uris 必須和這裡完全一致。

cloudflare/access.tf（vault_sso Application）
redirect_uris = [
  "https://vault.dough-ops.com/ui/vault/auth/oidc/oidc/callback",
  "http://localhost:8250/oidc/callback",
]

已知限制與 workaround

  • unseal key 和 root token 與資料放在同一顆 volume。一般建議 key 要跟它解鎖的資料分開保管。這裡放在一起，是為了讓 bastion 重建後能自動 unseal。代價是任何能讀取 /userap/vault/init.json 的人，都能解鎖 Vault 並取得 root token。保護這個檔案的只有 root-only 的檔案權限，以及 bastion 本身的存取控制（SSH 為唯一入口）。
  • 單一 key 沒有多人制衡。Shamir 5 取 3 的保護不存在，也無法做到「單一個人不能獨自解鎖」。這個 lab 只有單一 operator，所以接受。
  • 通過 Cloudflare Access 的人都是 Vault 全權限。任何通過邊緣 Access（doughops org 成員）並以 OIDC 登入 Vault 的人，都拿到 oidc-admin policy（path "*"，全部 capability）。這和 Dashboard、Grafana 的「預設唯讀，oidc_admin_emails 才有完整權限」兩層模式不同，ArgoCD 是同一個決定（見 Role: argocd）。影響範圍涵蓋 Vault 裡的所有 secret，風險要自己承擔。
  • 用自訂的 oidc-admin，不綁內建的 root policy。技術上可以綁，但 root 名稱有特殊含義，不建議經由認證方式取得。獨立的 policy 效果等價，並且能單獨撤銷和稽核。
  • 明碼 HTTP。tls_disable = true，Cloudflare tunnel 到 Vault 這一段是 bastion 對自己 fabric 位址的本機連線，不經過其他網路跳點。k8s-net 網段本身是信任邊界。
  • VSO 的共用身份其實是各 namespace 自己的 default ServiceAccount。共用 VaultAuth 由 VSO chart 內建的 defaultVaultConnection 與 defaultAuthMethod 建立，原以為 default 指 vault-secrets-operator namespace 底下的那個，才把 role 綁成 bound_service_account_namespaces=vault-secrets-operator。Vault 端 role 的 bound_service_account_namespaces=* 因此放行所有 namespace，任何 namespace 的 default ServiceAccount 都能讀 k8s-shared-read policy 涵蓋的 secret。細節見 #55。

實測踩到的 bug

#53 · apt 加 HashiCorp repo 後 NO_PUBKEY

  • 症狀：裝 vault 套件時，apt-get update 報 NO_PUBKEY 和 the repository is not signed。
  • 根因：第一版把 curl .../gpg 的輸出直接存成 .gpg 檔。HashiCorp 的 /gpg 端點回傳 ASCII-armored 公鑰，開頭是 -----BEGIN PGP PUBLIC KEY BLOCK-----。它不是 dearmor 過的二進位 keyring，apt 的 signed-by= 讀不出有效的 key。
  • 修法：比照 roles/kubectl_cli 裝 Kubernetes apt repo 的寫法，先 pipe 給 gpg --dearmor。
  • 怎麼確認修好：apt-get update 不再報簽章錯誤，vault 套件能安裝。
  • 相關：完整故事見 Bug #53。
錯誤版本
curl -fsSL https://apt.releases.hashicorp.com/gpg \
  -o /usr/share/keyrings/hashicorp-archive-keyring.gpg
修復後
curl -fsSL https://apt.releases.hashicorp.com/gpg \
  | gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg

#54 · play 跑完 failed=0，Vault 卻是 sealed

  • 症狀：整個 play 成功，failed=0，但 vault status 顯示 sealed: true。unseal 明明成功過。
  • 根因：Ansible 的 handler 預設等整個 play 全部 task 跑完才執行。第一次執行時設定檔不存在，一定觸發「重啟 vault」handler。順序變成：寫設定檔並排入 handler，init 和 unseal 成功，開 KV v2，最後 handler 才執行。重啟讓 Vault 回到 sealed。
  • 修法：寫完設定檔後立刻用 meta: flush_handlers 強制執行。「設定檔有沒有換」永遠是 role 裡最先處理完的事，之後才判斷 init 和 unseal。
  • 怎麼確認修好：全新環境跑完 role 後，vault status 顯示 sealed: false。
  • 相關：roles/gitlab 沿用同樣處理。完整故事見 Bug #54。
寫設定檔
notify: 重啟（排進佇列）
→
init + unseal
成功，sealed: false
→
開 KV v2
→
handler 這時才執行
重啟 → 回到 sealed!
roles/vault_server/tasks/main.yml
- name: 寫 vault 的 server 設定
  ansible.builtin.template: ...
  notify: 重啟 vault

- name: 如果上面設定檔真的換了，現在就重啟（不要拖到整個 play 跑完）
  ansible.builtin.meta: flush_handlers

#55 · VSO 登入 Vault 回 403 namespace not authorized

  • 症狀：VSO controller log 出現 Failed to get NewClientWithLogin ... auth/kubernetes/login，Code: 403. Errors: * namespace not authorized。
  • 根因：目標是讓所有 namespace 共用同一組 Vault 身份。第一版假設 defaultAuthMethod.kubernetes.serviceAccount: default 指的是 vault-secrets-operator namespace 的 default，所以把 Vault 端 role 的 bound_service_account_namespaces 寫死成 vault-secrets-operator。實際行為是這個名稱會在消費該 VaultAuth 的資源自己所在的 namespace 找同名 ServiceAccount，這類資源例如 VaultStaticSecret。上游的說明見 hashicorp/vault-secrets-operator#827。每個 namespace 其實都拿自己的 default ServiceAccount 登入 Vault。
  • 修法：Vault 端 role 改放行萬用字元 namespace。
  • 怎麼確認修好：在全新建立的 namespace 建 VaultStaticSecret，一個 reconcile 週期內同步出正確內容的 k8s Secret，狀態 SecretSynced: True。
  • 相關：完整故事見 Bug #55。
修復後
vault write auth/kubernetes/role/k8s-shared \
  bound_service_account_names=default \
  bound_service_account_namespaces=* \
  policies=k8s-shared-read

驗證方式

  • Vault 健康狀態：curl http://<fabric_ip>:8200/v1/sys/health，確認 sealed: false。
  • OIDC discovery：curl <oidc_discovery_url>/.well-known/openid-configuration，確認回傳合法的 authorization_endpoint、token_endpoint、jwks_uri。
  • 端對端 secret 同步：建一個測試 namespace 和 VaultStaticSecret，確認同步出來的 Secret 內容正確，事後清乾淨。
  • 外部曝露：curl -I https://vault.dough-ops.com/ui/，確認回 302 導向 doughops.cloudflareaccess.com 的登入頁。
