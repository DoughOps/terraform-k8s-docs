Cloudflare 手動設定完整設定清單

這份 repo 裡 ansible/ 管的是叢集內部, Cloudflare 那一側的設定不在 ansible 的範圍裡(見 Role: cloudflare_tunnel、Role: cert_manager 裡「這步不是 ansible 管的」的說明)。這頁存在的 目的很單純:把 Cloudflare 那一側需要什麼設定完整記下來, 不然重建一個新環境、或是換一個網域的時候,不會知道要動哪些東西。

DNS / Tunnel / Access Application / Zero Trust org 設定現在改用 Terraform 管了——獨立的 cloudflare/ 目錄、獨立的 state,跟 main.tf 管的 OpenStack 資源完全分開(不同 provider、 不會互相影響)。這頁下面的「實際 API 呼叫」步驟仍然保留,是給 理解設計、或是需要手動排查問題時參考用的, 但不要再照著這頁手動用 API 建立/修改這些資源 ——實際操作一律透過 cloudflare/ 裡的 Terraform 跑,不然會跟 state 對不上。完整的使用說明(terraform init/plan/apply、outputs 怎麼接回 ansible 變數、從零重建 的完整流程)見 cloudflare/README.md。

仍然留給手動處理的只有兩件事,原因見下面「身份提供者」小節: (1)GitHub Identity Provider 的連接 (client secret 要在瀏覽器裡跑一次 OAuth 授權流程,Terraform provider 沒辦法自動化這步);(2)網域接進 Cloudflare (買網域、改 nameserver,這本來就是註冊商那邊的操作,不是 Cloudflare API 管得到的範圍)。

用 Terraform 重建之後,ansible 這邊要跟著做什麼

Terraform 重建 Tunnel/Access Application 之後,token、AUD、 client_id/secret 全部會換成新的值——這些值同時被 ansible 管理的 東西吃進去用(cloudflared 的 token、kube-apiserver 的 --oidc-client-id、Grafana 的 auth.generic_oauth),所以光是 terraform apply 完不會自動生效,還要照順序重跑四個 playbook(完整 指令、每個值該填進 group_vars/all/{main,secrets}.yml 哪個變數,見 cloudflare/README.md):

  1. playbooks/bastion/cloudflare-tunnel.yml——套新的 cloudflare_tunnel_token。
  2. playbooks/bastion/ssh-tunnel.yml——套新的 cloudflare_bastion_ssh_tunnel_token。
  3. playbooks/k8s/oidc-auth.yml——只有萬用字元 Application 的 AUD 換了才需要,套新的 cloudflare_access_oidc_client_id。
  4. playbooks/k8s/kube-prometheus-stack.yml——只有 grafana-sso 的 client_id/secret 換了才需要。

Bug 記錄:光是把新 token 寫進 secrets.yml 重跑 playbook 不夠——兩個角色原本都 不是為「token 會換」設計的,實際做這次 token 輪替時發現:

(1)roles/cloudflare_tunnel 把 token 放進 Kubernetes Secret,cloudflared Deployment 用 env.valueFrom.secretKeyRef 讀——Secret 內容更新後, 已經在跑的 Pod 不會自動拿到新值(env var 只在 Pod 啟動當下讀一次)。修法是在 apply 完 manifest 之後檢查 apply 的 輸出,如果偵測到 Secret 物件真的被改到(configured, 不是 unchanged),就多跑一次 kubectl rollout restart deployment/cloudflared-deployment。

(2)roles/bastion_ssh_tunnel 原本用 cloudflared service install <token> 裝 systemd service,這個指令不是冪等的——service 已經裝過會直接報錯,所以整個 task 用「systemd unit 存不存在」當 guard,只在第一次跑。這代表 token 換了之後單純重跑 playbook, guard 會判斷「已經裝過」直接跳過,新 token 完全不會被 套用。修法是把「裝 token」拆成獨立的一步(用 ansible.builtin.copy 把 token 內容寫進 /etc/cloudflared/token,每次都跑、靠內容 diff 判斷 有沒有變),搭配一個 handler 在真的偵測到內容變了的時候才重啟 cloudflared systemd service。

建置順序:如果要從零開始重建

這是這批東西實際被建立的順序,也是重建時建議照著走的順序—— 前面的步驟是後面步驟的前提。

  1. 1. 網域接進 Cloudflare 買網域(這裡是 dough-ops.com)→ Cloudflare dashboard 加入這個 zone → 把網域註冊商的 nameserver 改成 Cloudflare 指定的兩個 → 等 zone 狀態變成 active。 可以用 GET /zones?name=dough-ops.com 確認。
  2. 2. 設定 Zero Trust 身份提供者 Zero Trust dashboard → Settings → Authentication → 加 GitHub(或其他 IdP)→ 走一次 OAuth 授權流程拿到 client_id/client_secret。記下這個 IdP 的 identity_provider_id,後面建 Access policy(github-organization 規則)要用。
  3. 3. 建 Cloudflare Tunnel(每個「入口」各一條) POST /accounts/{id}/cfd_tunnel, config_src: "cloudflare"(remotely-managed, ingress 規則在 Cloudflare 那邊設定,不是本地 config.yaml)。 這個專案目前有兩條,刻意分開、互不影響:
    • openstack-k8s——跑在 cluster 內 (Role: cloudflare_tunnel),給 *.dough-ops.com 所有對外服務用。
    • bastion-ssh——跑在 bastion 主機本身 (systemd service,不是 k8s pod),只給 ssh.dough-ops.com 用。
    建立後用 GET /accounts/{id}/cfd_tunnel/{tunnel_id}/token 拿 token,填進 ansible/inventory/group_vars/all/secrets.yml 對應的變數(cloudflare_tunnel_token / cloudflare_bastion_ssh_tunnel_token,格式見 secrets.yml.example)。
  4. 4. 設定每條 Tunnel 的 ingress 規則 PUT /accounts/{id}/cfd_tunnel/{tunnel_id}/configurations ,見下方「Tunnel 現況」表格的實際內容。

    如果 origin 是 HTTPS,originRequest.originServerName 一定要帶「子網域形狀」的值,不能是 zone apex ——這裡曾經真的因為設成 dough-ops.com(沒有子 網域)導致所有真實流量 503,細節跟根因見 Role: cert_manager 的 Bug 記錄跟 Bug #28。

  5. 5. DNS:每個對外入口一筆 CNAME,指到對應 Tunnel <hostname> CNAME <tunnel_id>.cfargotunnel.com,proxied: true(一定要 proxied,不然 Cloudflare 邊緣不會接手這個 請求,Access/Tunnel 都不會生效)。見下方「DNS 紀錄」表格。
  6. 6. 建 Origin CA API token(給 cert-manager 用) Dashboard → My Profile → API Tokens → Create Token,或直接 POST /user/tokens,permission 只給 Zone → SSL and Certificates → Edit,Zone Resources 限定在 dough-ops.com 這一個 zone(不要 用帳號等級的 Global API Key,也不要用已經被 2026-03-19 棄用的 Origin CA Key)。token 值填進 secrets.yml 的 cloudflare_origin_ca_api_token,細節見 Role: cert_manager。
  7. 7. 建 Access Application + Policy 每個要保護的 hostname(或萬用字元)各建一個 Access Application,再幫它掛一個 policy。特別注意瀏覽器內建 終端機(SSH/RDP/VNC)要用對應的 type (ssh/rdp/vnc,不是 一般的 self_hosted)——這是這次真的踩到的坑,見 下方 Bug 記錄。完整步驟見下一節「建 Access Application:實際 API 呼叫」。

建 Access Application:實際 API 呼叫

建 Application 跟建它的 Policy 是兩次分開的 API 呼叫 (POST /accounts/{account_id}/access/apps 建 Application,拿到回傳的 id 之後再 POST /accounts/{account_id}/access/apps/{app_id}/policies 建 Policy)——這個專案目前建了兩個 Application,分別對應「一般 HTTP 服務」跟「瀏覽器 SSH 終端機」兩種完全不同的用途。

一般 HTTP 服務:萬用字元 self_hosted Application

涵蓋 *.dough-ops.com 底下所有服務(Dashboard、 Hubble、Grafana……),一個 Application 涵蓋全部,新增服務不用 回來重建:

POST /accounts/{account_id}/access/apps
{
  "name": "dough-ops.com (all apps)",
  "type": "self_hosted",
  "domain": "*.dough-ops.com",
  "destinations": [{ "type": "public", "uri": "*.dough-ops.com" }],
  "session_duration": "24h",
  "app_launcher_visible": true,
  "allowed_idps": ["<github idp 的 identity_provider_id>"],
  "auto_redirect_to_identity": true
}
POST /accounts/{account_id}/access/apps/{app_id}/policies
{
  "name": "Allow doughops GitHub org",
  "decision": "allow",
  "include": [
    {
      "github-organization": {
        "identity_provider_id": "<github idp 的 identity_provider_id>",
        "name": "doughops"
      }
    }
  ]
}

github-organization 規則只需要 org 名稱字串, Cloudflare API 會在建立當下實際去驗證這個 org 是不是真的存在 (回傳結果裡會多一個解析出來的 GitHub 數字 org id)——打錯字的話 這一步就會失敗,不會等到真的有人登入才發現規則設錯。

瀏覽器 SSH 終端機:精確匹配的 ssh Application

刻意用精確 hostname(不是萬用字元)另外建一個 Application,型別是 ssh——這是 Cloudflare「Browser- Rendered Terminal」功能專屬的型別,跟一般的 self_hosted 是兩套不同的渲染邏輯(細節見下方 Bug 記錄)。因為是精確匹配,優先權比上面的萬用字元 Application 高, 兩者不衝突:

POST /accounts/{account_id}/access/apps
{
  "name": "bastion-ssh",
  "type": "ssh",
  "domain": "ssh.dough-ops.com",
  "destinations": [{ "type": "public", "uri": "ssh.dough-ops.com" }],
  "session_duration": "24h",
  "app_launcher_visible": true
}

Policy 建法跟上面完全一樣的格式(github-organization 規則,或改用 email 規則放行特定帳號,見下方「使用者 自己的 Access policy 調整」)。

Policy 的 include 規則不是只有這兩種 ——常見的還有 email(單一 email)、 email_domain(整個網域)、everyone (任何登入的人)、ip_ranges。選哪一種純粹看想放行的 對象是「特定幾個人」還是「一整個 GitHub org/團隊」,兩者可以在 同一個 Application 換掉重建,不影響 Tunnel/DNS 那一層的設定。

應用層自己做 OIDC 登入:type: "saas"

前面兩種(self_hosted、ssh)都是 Cloudflare Access 攔在 app 前面的模式。有些 app 自己就有原生的 OIDC 登入支援(像 Grafana 的 auth.generic_oauth)——這種情況可以讓 Cloudflare Access 反過來扮演一個真正的 OIDC provider,app 自己發起標準的 authorization code flow,不是被動驗證一個既有的 JWT:

POST /accounts/{account_id}/access/apps
{
  "name": "grafana-sso",
  "type": "saas",
  "saas_app": {
    "auth_type": "oidc",
    "redirect_uris": ["https://grafana.dough-ops.com/login/generic_oauth"],
    "grant_types": ["authorization_code"],
    "scopes": ["openid", "email", "profile"]
  }
}

回應裡的 client_id/client_secret 只在這次 POST 回應裡出現一次,要當場存下來(這個 專案存進 secrets.yml)。OIDC discovery 端點的網址 規則固定是:

實測查證(不是憑印象拼字串)
$ curl https://doughops.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<client_id>/.well-known/openid-configuration
{
  "authorization_endpoint": ".../authorization",
  "token_endpoint": ".../token",
  "userinfo_endpoint": ".../userinfo",
  "jwks_uri": ".../jwks"
}

跟其他兩種 Application 一樣,還是要另外掛一個 policy(這裡一樣是 github-organization: doughops)——saas 類型的 Application 一樣受 Access policy 管制,只是使用者通過 policy 之後拿到的不是「直接放行」,而是一組真正的 OAuth code/token,可以被 app 自己的原生登入機制消費。細節見 內部工具的 Grafana SSO 章節, 包含一個被使用者否決的設計(想幫 Grafana 的 hostname 開一個 bypass policy 跳過邊緣檢查,被明確擋下來,因為 「所有網站都需要通過 Cloudflare Access」是刻意的 defense-in-depth 要求,不能因為省一次跳轉就讓步)。

Access Application 現況

名稱typeDomainPolicy

dough-ops.com (all apps) 跟 bastion-ssh/grafana-sso 這幾個都涵蓋到 同一個 hostname(前者是萬用字元,後兩者是精確匹配)——這不是衝突, Cloudflare Access 精確匹配的規則優先權高於萬用字元,行為跟 DNS 的 exact-match 優先於 wildcard 是同一個邏輯(見 Role: cloudflare_tunnel 提到的網域選擇那段)。grafana-sso 比較特別——它不是 攔在 grafana.dough-ops.com 前面「取代」萬用字元那層, 是疊加在 Grafana 自己的 OIDC 登入流程上面(見上方 說明),兩層同時存在是刻意的設計,不是還沒清乾淨的重複設定。

Bug 記錄:一般的 self_hosted Application 保護不了 瀏覽器內建 SSH 終端機——Cloudflare 有兩套外觀很像但完全 不同的功能:type: "infrastructure"(Access for Infrastructure,需要另外註冊 target/connector,是給企業級 SSH 憑證代管用的)、type: "ssh"/"rdp"/ "vnc"(Browser-Rendered Terminal,搭配一條指到 ssh://localhost:22 的 Cloudflare Tunnel,這個專案 實際用的是這一種)。一開始沿用舊的 self_hosted wildcard Application 涵蓋 ssh.dough-ops.com,Access 登入本身沒問題(對 curl 測試看起來完全正常,回應正確的 302),但 瀏覽器打開後不會出現終端機——因為 self_hosted 沒有 啟用瀏覽器渲染。修法是額外建一個 type: "ssh" 的 Application,精確匹配 ssh.dough-ops.com,才會真的 渲染出終端機介面。

使用者自己的 Access policy 調整

建立 bastion-ssh Application 時,原本設定的是 「只放行兩個特定 email」的政策(比其他服務更嚴格,畢竟是完整 shell 存取)。使用者後來自己在 Cloudflare dashboard 把它換成跟 其他服務一樣的 doughops GitHub org 政策——這是 使用者自己在 dashboard 上做的調整,不是這裡的自動化流程改的,寫在 這裡純粹是讓這份文件跟目前 Cloudflare 上的實際狀態保持一致(每次 要確認 Cloudflare 現況時,直接查 API 拿即時資料,不要照這份文件 的「建立當下」的舊值假設現況——這份清單記錄的是怎麼從零 建立的步驟,不是即時同步的狀態鏡像)。

新增一個對外服務,完整清單要做什麼(常見情境)

如果只是在既有的 *.dough-ops.com 萬用字元底下加一個新服務(像 內部 工具那幾個),Cloudflare 這邊完全不用動 ——DNS、Tunnel ingress、Access Application 都已經是萬用字元涵蓋, 只要在 ansible 那邊加 VirtualService 就好,這正是這個架構故意這樣 設計的目的。只有以下情境才需要回來動 Cloudflare 設定:

🌐

換一個全新網域

整個「建置順序」章節重來一次——新 zone、新 DNS 紀錄(可以沿用 既有 tunnel,不用重建)、新的 origin-ca-issuer wildcard Certificate。

🖥️

要瀏覽器內建終端機(SSH/RDP/VNC)

一定要精確匹配的 type: ssh/rdp/vnc Application ——不能只靠萬用字元的 self_hosted Application,見 上面的 Bug 記錄。

🔑

要更嚴格/不同的存取政策

新增一個 Access Application 用精確 hostname 覆蓋萬用字元的 預設政策(跟 bastion-ssh 一開始的做法一樣),不用 去改整個萬用字元 Application 的政策影響到其他服務。
