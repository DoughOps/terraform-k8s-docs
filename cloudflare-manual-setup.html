對外入口與身份驗證 Cloudflare 設定清單

這頁整理 Cloudflare 那一側需要哪些設定：哪些由 cloudflare/ 的 Terraform 建立，哪些只能手動做一次，以及 Cloudflare Access 的整體規則。適合要排查 Cloudflare 側問題或輪替憑證的團隊成員。Ansible 只管叢集內部，Cloudflare 側的資源不在它的範圍內。

DNS、Tunnel、Access Application 和 Zero Trust 組織設定都由 cloudflare/ 管理，使用獨立的 state，與 openstack/ 的資源互不影響。不要用 API 或 dashboard 手動修改這些資源，否則會和 state 對不上。本頁的 API 範例只用來理解設計和排查問題。

Terraform 與手動的分工

Cloudflare 側的設定分成三類：Terraform 建立的資源、只能手動一次的前置、Ansible 管的叢集內部設定。

項目誰管為什麼
DNS 紀錄、2 條 Tunnel 與 ingress 規則Terraformtoken 由 Terraform 本地計算，不依賴 cloudflared 或叢集存在
Access Application 與 PolicyTerraform規則版本化，重建時不用回想要點哪些設定
Zero Trust 組織名稱Terraform讓 team name 有宣告式來源，避免漂移（見 Bug #30）
cert-manager 用的 Origin CA API tokenTerraform無人值守建環境時不需要人去 dashboard 點
Smart Tiered CacheTerraformzone 層級設定一併納入版控

GitHub Identity Provider手動，一次OAuth app 的 client secret 要在瀏覽器走一次授權
Terraform 用的 CLOUDFLARE_API_TOKEN手動，一次Terraform 本身需要的憑證，無法自己建立自己
Terraform state 的 S3 憑證手動，一次見 Terraform state backend
Terraform 輸出值搬進 Ansible 變數sync-cloudflare-secrets.sh輸出名稱與 Ansible 變數同名，逐一寫回

只能手動一次的前置

以下項目已經完成，重建環境時不用重做。只有這些資源被刪除或要輪替時才需要回來看。團隊共用資源的總表見從零開始建置 § 團隊共用資源。

  1. 1. 網域接進 Cloudflare 買網域，在 Cloudflare dashboard 新增這個 zone，把註冊商的 nameserver 改成 Cloudflare 指定的兩個，等 zone 狀態變成 active。用 GET /zones?name=dough-ops.com 確認。zone 的 ID 之後要填進 cloudflare/terraform.tfvars 的 zone_id。
  2. 2. 連接 GitHub Identity Provider 在 Zero Trust dashboard 的 Settings → Authentication 新增 GitHub，走一次 OAuth 授權。記下這個 IdP 的 identity_provider_id，填進 github_idp_id。這個 module 只引用 IdP，不管理它的生命週期。這一步是一次性 bootstrap，GitHub org 與 Zero Trust 帳號不變就不用重做。
  3. 3. 準備 CLOUDFLARE_API_TOKEN token 需要以下權限：Access Apps／Policies:Edit、Access Organizations:Edit、Cloudflare Tunnel:Edit。另外要有這個 zone 的 DNS:Edit，以及 User 層級的 API Tokens:Edit。最後一項用來讓 Terraform 建立 cert-manager 的 scoped token，見已知限制。token 只用環境變數傳遞，不寫進 terraform.tfvars 或任何進版控的檔案。
  4. 4. 準備 state 的 S3 憑證 AWS_ACCESS_KEY_ID 和 AWS_SECRET_ACCESS_KEY 是 state 存放位置的認證，與 Cloudflare 的 token 是兩件事。兩者都放在 .env，make build 等腳本會自動讀取。
  5. 5. 填寫 cloudflare/terraform.tfvars 沒有預設值、必須填的變數有 5 個：account_id、zone_id、zone_name、github_idp_id、bastion_fabric_ip。

用 Terraform 建立或重建

make build 已包含 Cloudflare 的 apply 與輸出值同步。只想單獨處理 Cloudflare 側時，手動執行：

cloudflare/ 目錄
$ terraform init
$ terraform plan
$ terraform apply

預期結果：plan 列出的 Tunnel、DNS、Access Application 與預期一致，apply 後沒有錯誤。接著把輸出值搬進 Ansible：

repo 根目錄
$ scripts/sync-cloudflare-secrets.sh

腳本讀取 Terraform 輸出，寫進 ansible/inventory/group_vars/all/secrets.yml（token 與 client secret）和 main.yml（client ID 與 AUD）。值全程只留在 shell 變數，不印出。輸出名稱與 Ansible 變數同名，所以不需要維護對照表。

腳本會自動解密 secrets.yml，更新後重新加密，機制見 Ansible 框架設計 § 密鑰管理。

換掉 token 或 client 之後重跑的 playbook

Terraform 重建 Tunnel 或 Access Application 後，token、AUD、client ID 與 secret 都會換新。這些值被 Ansible 管理的元件讀進去，所以 terraform apply 之後還要照順序重跑：

  1. playbooks/bastion/cloudflare-tunnel.yml：套用新的 cloudflare_tunnel_token。
  2. playbooks/bastion.yml：其中的 bastion_ssh_tunnel role 套用新的 cloudflare_bastion_ssh_tunnel_token。
  3. playbooks/k8s/oidc-auth.yml：萬用字元 Application 的 AUD 換掉才需要，套用新的 cloudflare_access_oidc_client_id。
  4. playbooks/k8s/kube-prometheus-stack.yml：grafana-sso 的 client ID 與 secret 換掉才需要。
  5. playbooks/k8s/cert-manager.yml：Origin CA 的 scoped token 換掉才需要。

Vault、ArgoCD、Keycloak、GitLab 的 SaaS Application 換掉 client 後，同樣要重跑各自的 role，見對應的 role 頁。叢集內的 cloudflared 在 Secret 變更時要執行 kubectl rollout restart deployment/cloudflared-deployment，才會讀到新 token。兩個 role 處理 token 輪替的做法見 Role: cloudflare_tunnel § token 輪替。

Cloudflare Access 規則

這一節是全站 Cloudflare Access 規則的權威說明。其他頁提到 Access 時，只摘要並連到這裡。精確的 Application 定義、路徑比對與 Policy 都在 cloudflare/access.tf，本節只說明原則與類別。

基本原則

  • 預設全擋：一個萬用字元的 self_hosted Application 涵蓋 *.dough-ops.com，Policy 只放行 doughops GitHub org 的成員，session 為 24 小時。新增服務不需要回頭加 Access 設定。
  • 精確匹配優先：Access 的精確 hostname 規則優先於萬用字元，行為和 DNS 的 exact-match 優先於 wildcard 相同。需要不同處理的 hostname，另外建一個精確匹配的 Application 即可，不必改萬用字元那份。
  • 所有網站都要先過邊緣檢查：自帶登入機制的服務也不例外，邊緣檢查和服務自己的登入是兩層。
  • 權限只到 org 成員層級：通過 Access 代表是 org 成員。進入服務後拿到什麼權限，見權限矩陣。

Application 的四種類別

類別type用途設計重點

應用層 OIDC 與邊緣檢查疊加

決策：有原生 OIDC 登入的服務，同時保留萬用字元的邊緣檢查，不為它們開 bypass。

理由：邊緣檢查擋在服務前面，服務本身出現漏洞時，未登入的人仍然到不了它。服務自己的 OIDC 登入再負責身份與權限。代價只是登入時多一次跳轉。同一個 Cloudflare team 的 session 還有效時，第二層是無感的。

考慮過的替代方案：為這些 hostname 開 bypass，省掉一次跳轉 — 服務一旦有漏洞就直接暴露在公網，不選。

代價：每個 SaaS Application 各有一組 client ID 與 secret，Application 重建後要同步更新到 Ansible 並重跑對應 role。

Access for SaaS 核發的 id_token 效期固定 5 分鐘，也拿不到 refresh_token。這會影響直接串接它的服務，ArgoCD 的處理方式見 ArgoCD 登入設計。

bypass 的原則

bypass 是例外。只有符合下列條件的流量才考慮放行，並且逐一收斂範圍：

  • 對象無法互動登入：例如 OIDC 身份代理之間的 discovery 與 token 呼叫，以及用 personal access token 的 Git 傳輸和 REST API。這些 client 只看 HTTP 狀態碼，被導去登入頁就直接失敗。
  • 範圍限定在路徑：只放行機器對機器需要的端點，不放行整個 hostname。管理後台、其他 realm 的認證端點、網頁介面都不在放行範圍內。
  • 服務自己的認證是唯一防線：被放行的路徑不再有邊緣的 GitHub org 檢查，只剩服務自己的帳密或 token。TLS 仍由 Cloudflare 終止，只是跳過身份檢查，加密不受影響。
  • 瀏覽器的使用路徑不受影響：使用者的瀏覽器流程仍要先通過萬用字元保護。
  • 不出現在 App Launcher：這類 Application 沒有登入頁，隱藏起來避免誤導。

目前有兩個服務使用 bypass，屬於上面前兩種對象。要新增 bypass 時，先評估該路徑能做的事（是否有未限流的密碼驗證、是否暴露管理功能），再決定範圍。精確的路徑與 Policy 定義在 cloudflare/access.tf。

對應的 API 形狀

以下是 Terraform 底層送出的 API 內容，用於理解欄位或手動排查。建 Application 與建 Policy 是兩次獨立的呼叫：先 POST /accounts/{account_id}/access/apps，拿到 id 後再 POST /accounts/{account_id}/access/apps/{app_id}/policies。

萬用字元 self_hosted

POST /accounts/{account_id}/access/apps
{
  "name": "dough-ops.com (all apps)",
  "type": "self_hosted",
  "domain": "*.dough-ops.com",
  "destinations": [{ "type": "public", "uri": "*.dough-ops.com" }],
  "session_duration": "24h",
  "app_launcher_visible": true,
  "allowed_idps": ["<github idp 的 identity_provider_id>"],
  "auto_redirect_to_identity": true
}
POST /accounts/{account_id}/access/apps/{app_id}/policies
{
  "name": "Allow doughops GitHub org",
  "decision": "allow",
  "include": [
    {
      "github-organization": {
        "identity_provider_id": "<github idp 的 identity_provider_id>",
        "name": "doughops"
      }
    }
  ]
}

Policy 的 include 規則還有 email、email_domain、everyone、ip_ranges。放行對象是特定幾個人或整個 org，決定用哪一種。換規則不影響 Tunnel 與 DNS 層。

瀏覽器 SSH：精確匹配的 ssh

POST /accounts/{account_id}/access/apps
{
  "name": "bastion-ssh",
  "type": "ssh",
  "domain": "ssh.dough-ops.com",
  "destinations": [{ "type": "public", "uri": "ssh.dough-ops.com" }],
  "session_duration": "24h",
  "app_launcher_visible": true
}

ssh 是 Browser-Rendered Terminal 專屬的 type，與 self_hosted 是兩套渲染邏輯。精確匹配的優先權高於萬用字元 Application，兩者不衝突。Policy 的格式與上一節相同。

應用層 OIDC：saas

POST /accounts/{account_id}/access/apps
{
  "name": "grafana-sso",
  "type": "saas",
  "saas_app": {
    "auth_type": "oidc",
    "redirect_uris": ["https://grafana.dough-ops.com/login/generic_oauth"],
    "grant_types": ["authorization_code"],
    "scopes": ["openid", "email", "profile"]
  }
}

回應裡的 client_id 和 client_secret 只在建立當下出現一次。透過 Terraform 建立時，它們是 Terraform 的輸出值。OIDC discovery 端點的網址規則固定，以下是實測：

實測查證
$ curl https://doughops.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<client_id>/.well-known/openid-configuration
{
  "authorization_endpoint": ".../authorization",
  "token_endpoint": ".../token",
  "userinfo_endpoint": ".../userinfo",
  "jwks_uri": ".../jwks"
}

saas 類的 Application 同樣受 Access Policy 管制。通過 Policy 之後，使用者拿到的是一組真正的 OAuth code 與 token，由服務自己的登入機制使用。Grafana 的設定見 Grafana 登入與密碼。

已知限制

  • CLOUDFLARE_API_TOKEN 權限偏大：為了讓 Terraform 自動建立 cert-manager 的 scoped token，它需要 User 層級的 API Tokens:Edit。這個權限能建立與管理其他 token，接近帳號層級的控制力。這個 token 只存在於執行環境的環境變數，用完即丟，不像 Origin CA token 要長期留在叢集的 Secret 裡，所以邊際風險可接受。
  • token 範圍稽核只涵蓋兩顆：CLOUDFLARE_API_TOKEN 與 cloudflare_origin_ca_api_token 都限定在 dough-ops.com 一個 zone，帳號層級只有 Tunnel 與 Access 權限。這兩個 Zero Trust 功能沒有 zone-scoped 版本。實測對帳號底下另一個 zone 發請求，確實被拒絕。稽核只含這兩顆，兩組憑證都沒有 API Tokens Read 權限，無法清查整個帳號的所有 token。
  • 刪掉重建會換掉下游引用的值：影響如下。
    • 兩條 Tunnel 的 ID 與 token 換新，cloudflared 在重跑 Ansible 之前連不上。
    • 萬用字元 Application 的 AUD 換新，kube-apiserver 的 --oidc-client-id 指向舊值，所有 OIDC 登入失敗，直到重跑 oidc-auth.yml。該 playbook 逐台 master 更新，client cert 認證不受影響。
    • SaaS Application 的 client 換新，對應服務的 SSO 失效，帳密登入不受影響。
    • Origin CA token 換新，新憑證續期失敗，現有憑證在過期前不受影響。
  • bypass 路徑只剩服務自己的認證：見 bypass 的原則。
  • 手動改動會被覆蓋：在 dashboard 改過的 Policy，Terraform 下次 apply 會依 access.tf 的定義覆蓋。

實測踩到的 bug

#29 · 瀏覽器 SSH 登入正常但沒有終端機

  • 症狀：瀏覽器打開 ssh.dough-ops.com，Access 登入沒問題（curl 測試回應正確的 302），但畫面上沒有出現終端機。
  • 根因：一開始沿用萬用字元的 self_hosted Application 涵蓋這個 hostname，它沒有啟用瀏覽器渲染。Cloudflare 有兩套外觀相近的功能。 type: "infrastructure" 是 Access for Infrastructure，需要另外註冊 target 與 connector，用於企業級 SSH 憑證代管。 type: "ssh"、"rdp"、"vnc" 是 Browser-Rendered Terminal，搭配指向 ssh://localhost:22 的 Tunnel。本專案用的是後者。
  • 修法：另建 type: "ssh"、精確匹配 ssh.dough-ops.com 的 Application。
  • 怎麼確認修好：瀏覽器登入後出現終端機介面。
  • 相關：Bug #29。

#30 · 登入出現「Unable to find your Access organization」

  • 症狀：瀏覽器 SSH 的登入流程出現 Unable to find your Access organization。
  • 根因：team name 曾經從 31lab 改成 doughops。查 GET /accounts/{id}/access/organizations 發現 auth_domain 已是 doughops.cloudflareaccess.com，但 name 欄位還停在舊的 31lab.cloudflareaccess.com。Cloudflare 社群論壇有多筆相同案例，都指向改名後部分畫面沒有跟著更新。
  • 修法：PUT /accounts/{id}/access/organizations，把 name 改成正常的顯示名稱 doughops。現在由 cloudflare/organization.tf 宣告這個值。
  • 怎麼確認修好：重新登入不再出現該錯誤。之後遇到類似的「找不到 Access organization」，先查這個欄位，再排查瀏覽器快取與 incognito。
  • 相關：Bug #30。

Cloudflare 側還有一個相關的踩坑：cloudflared 連 HTTPS origin 時的 originServerName 必須帶子網域。它的完整調查見 Role: cert_manager。

新增服務時要不要動 Cloudflare

在既有的 *.dough-ops.com 底下加一個新服務，Cloudflare 側完全不用動。DNS、Tunnel ingress 和 Access Application 都已經由萬用字元涵蓋，只要在叢集內加 VirtualService。只有下列情境才需要回來改 cloudflare/。

🌐

換一個全新網域

重做 只能手動一次的前置。新 zone、新 DNS 紀錄可以沿用既有 Tunnel，並簽發新的 wildcard Certificate（見 Role: cert_manager）。

🖥️

要瀏覽器內建終端機

必須用精確匹配的 type: ssh/rdp/vnc Application，不能只靠萬用字元的 self_hosted。

🔑

要更嚴格或不同的存取政策

新增一個用精確 hostname 的 Application 覆蓋萬用字元的預設政策，不必改萬用字元那份，也不影響其他服務。
