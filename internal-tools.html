Ansible 自動化內部工具:Kubernetes Dashboard / Hubble UI / kube-prometheus-stack / ArgoCD

四組跟叢集本身的網路/運算架構無關,純粹是「裝好、 透過同一條 Istio Gateway + Origin CA 憑證 expose 出去、擋在 Cloudflare Access 後面」的 維運/觀測/部署工具。前三組(Hubble/Dashboard/kube-prometheus-stack) 共用同一個模式,所以放在同一頁,不是各自獨立成頁;ArgoCD (roles/argocd)也是同一個 「helm 裝 + VirtualService」模式,一起收在這頁,細節見下方獨立 一節。

「內建登入」欄位刻意列出來,是因為這正是為什麼裝完 cert-manager 之後緊接著設定 Cloudflare Access 的原因 (見 Role: cert_manager)—— 五個裡面有三個完全沒有任何形式的身份驗證,如果沒有 Access 擋著, 這些頁面對外就是完全公開的。

VirtualService 跨 namespace 引用共用 Gateway 的寫法,直接沿用 demo app 當初立下的模式 (gateways: [istio/k8s-gateway])——每加一個新工具, 重複同一個模式就好,不用碰 Role: istio 或 Role: cert_manager 任何一行。

Hubble:不是獨立安裝,是 Cilium chart 內建的 flag

跟其他兩個不一樣,Hubble不是另外裝一個 chart ——它是 roles/cilium 的 cilium-values.yaml.j2 多加兩行:

roles/cilium/templates/cilium-values.yaml.j2(新增部分)
hubble:
  enabled: true
  relay:
    enabled: true
  ui:
    enabled: true

relay 是聚合每個節點 Cilium agent 觀測資料的元件, ui 才是真正對外的網頁介面(hubble-ui Service)。VirtualService 的 apply 邏輯放進 roles/cilium/tasks/hubble_expose.yml,由 roles/cilium/tasks/main.yml 在 bastion 那一段 include——放在 cilium role 裡而不是獨立一個 role,因為 Hubble 本質上是 Cilium 的一部分,不是一個獨立安裝的 app。

Kubernetes Dashboard:避開一個已知的 Kong TLS port bug

Dashboard 的 helm chart 內建用 Kong 當前置反向代理,預設 只開 HTTPS(自己簽自簽憑證,kong.proxy.http.enabled: false)。這個專案已經在 Istio Gateway 那一層用真憑證終止過 一次 TLS 了(見 Role: cert_manager),沒有必要讓流量進到 Dashboard 這邊又是一層自簽 憑證的 TLS——上游專案本身有一個已知的 bug/behavior (kubernetes/dashboard#9861): 就算想關掉 HTTPS,實際的 Service port 選擇也不一定照預期運作。

這裡選擇最乾淨的繞法:明確打開 kong.proxy.http.enabled: true,讓 Kong 同時開一個 plain HTTP 的 port 80(targetPort: 8000),VirtualService 直接打 這個 port,完全不碰 HTTPS 那一側,避開整個已知問題,而不是去對抗 它。實測驗證這條路徑確實回應 200,不是靠猜的。

上游專案 kubernetes/dashboard 已經被 CNCF/社群標成 retired(GitHub 倉庫實際搬到 kubernetes-retired/dashboard,helm repo URL 也跟著換了 ——舊的 kubernetes.github.io/dashboard 現在回 404)。chart 本身還能正常裝、正常用,只是往後不會再有官方安全更新 ——這是使用者明確要求裝這個工具時就該知道的取捨,不是隱藏起來的 風險,用哪個工具的決定權在使用者。

Dashboard 的真正 SSO:過了 Cloudflare Access 直接可以用,讀寫權限照身份決定

1. kube-apiserver 直接信任 Cloudflare Access 的 JWT

新增 roles/oidc_auth,幫三台 master 的 apiserver static pod manifest 補上:

/etc/kubernetes/manifests/kube-apiserver.yaml(補上的部分)
- --oidc-issuer-url=https://doughops.cloudflareaccess.com
- --oidc-client-id=<wildcard Access Application 的 AUD>
- --oidc-username-claim=email
- --oidc-username-prefix=-

--oidc-issuer-url 能不能用,關鍵是這個網域要有正常 的 OIDC discovery——用 curl https://doughops.cloudflareaccess.com/.well-known/openid-configuration 實際查證過會回傳合法的 issuer/jwks_uri, 才動手改,不是查了 Cloudflare 文件說「JWT 可以驗證」就假設 apiserver 的 OIDC 認證器一定吃得下去。--oidc-username-prefix=- 關掉 apiserver 預設會加的 issuer 前綴,讓 RBAC 的 User subject 可以直接寫 email 本身。

這是控制平面層級的認證變更,影響整個 apiserver,不只是 Dashboard——用 serial: 1 一台一台改,每台 都先記錄舊的 container id,改完 manifest 之後等 crictl ps 確認 container id 真的換了(不是只看 /livez 回 200——manifest 改完的當下舊 container 通常還在跑,單看 /livez 會誤判成已經套用新設定)、 再確認新 container 的 /livez 真的回 200,才動下一台 master。

2. RBAC:預設唯讀 + 三個明確放行的寫入,個別 email 才有完整 write

roles/oidc_rbac
ClusterRoleBinding cloudflare-access-oidc-view
  subjects: [Group system:authenticated]
  roleRef:  ClusterRole/view                     # 內建,刻意不含 secrets

ClusterRoleBinding cloudflare-access-oidc-default
  subjects: [Group system:authenticated]
  roleRef:  ClusterRole/cloudflare-access-default # 自訂,疊加在 view 之上

ClusterRoleBinding cloudflare-access-oidc-admin
  subjects: [User <email>, ...]   # oidc_admin_emails,secrets.yml
  roleRef:  ClusterRole/cluster-admin

system:authenticated 是 Kubernetes 內建的群組 ——任何用任何方式(client cert、service account token、這裡新加的 OIDC……)成功通過 apiserver 驗證的使用者都自動屬於這個群組,不用 手動維護成員名單。這個群組疊加綁了兩個 ClusterRole:內建的 view(唯讀大多數 namespaced 資源),加上自訂的 cloudflare-access-default (唯讀 view 沒涵蓋到的 cluster-scope 資源如 nodes,外加明確放行三個寫入操作:刪 pod、改 configmap、scale deployment,方便日常操作又不用給完整 write)。 要完整 write 權限的 email 清單放在 oidc_admin_emails(group_vars/all/secrets.yml, 不進版控)——這不是傳統意義上的密鑰,但是使用者的私人帳號資訊, 一樣不該出現在任何會進 git 歷史的檔案裡。

Bug 記錄:自訂角色一開始寫成 resources: ["*"],等於整個 org 都能讀 Secrets ——原始版本想用一個 wildcard ClusterRole 完全取代 view, 理由是 view 涵蓋不到 nodes 這種 cluster-scope 資源。但 RBAC 沒有「排除」語法, resources: ["*"] 沒辦法只排除 secrets ——這代表任何通過 Cloudflare Access 登入的人(目前是整個 doughops GitHub org,不只是 oidc_admin_emails 名單)都能 kubectl get secret -o yaml 讀到 Grafana admin 密碼、TLS 私鑰、Cloudflare tunnel token 等機密——這正是 內建 view 角色刻意排除 secrets 的原因。 部署前發現這個問題,改成兩個 ClusterRoleBinding 疊加:繼續綁 view(沿用官方已經審查過、刻意排除 secrets 的 curation),自訂角色改成明確列舉需要額外補上的 cluster-scope 資源類型(nodes/namespaces/ persistentvolumes/storageclasses)加三個 寫入 verb,完全不碰 wildcard。

3. EnvoyFilter:讓 Dashboard 自動略過登入畫面

Dashboard 官方文件明講:請求裡已經帶著有效的 Authorization header,登入畫面會直接跳過(v7 拿掉了 原本內建的 skip-login 開關,這是官方維護者在 kubernetes/dashboard#8497 明確給的取代方案)。Cloudflare Access 本身在每個通過驗證的請求上 已經自動帶了 Cf-Access-Jwt-Assertion header—— roles/dashboard 新增一個 EnvoyFilter,掛一段 Lua 腳本,把這個 header 的值複製一份、加上 Bearer 前綴、蓋到 Authorization 上:

roles/dashboard/templates/dashboard-cf-jwt-envoyfilter.yaml.j2(Lua 部分)
function envoy_on_request(request_handle)
  local host = request_handle:headers():get(":authority")
  if host == "dashboard.dough-ops.com" then
    local jwt = request_handle:headers():get("cf-access-jwt-assertion")
    if jwt ~= nil then
      request_handle:headers():replace("authorization", "Bearer " .. jwt)
    end
  end
end

用 :authority(Host header)判斷只在 dashboard_hostname 生效,是刻意的——這個 EnvoyFilter 掛在整個 ingress gateway 上(沒辦法只綁定某一條 VirtualService),不加這個判斷會蓋掉 Grafana 等其他服務自己可能 在用的 Authorization header,那些服務不預期被硬蓋 這個值。

驗證這個機制真的有效,不能只靠 curl 測試 ——帶假的 Cf-Access-Jwt-Assertion 值送測試請求,跟 完全不帶這個 header,對 apiserver 來說都是同一種「沒有效的 bearer token」,回應的 401 一模一樣,測不出 Lua 腳本到底有沒有把 header 複製過去。真正的驗證方法是暫時在 Lua 腳本裡加 request_handle:logInfo(...),把 istio-ingressgateway 的 log level 臨時調到 info,送一次測試請求,直接在 Envoy 自己的 log 裡看到「host 判斷對了→ 讀到 header 值 → 真的 執行了 replace」三行紀錄,才確認 Lua 邏輯本身正確,再把 debug 版本換回乾淨版本。

目前 oidc_admin_emails 是空的(使用者要另外提供 email,不透過會留紀錄的管道),所以現在任何過了 Cloudflare Access 的人都只有上面那組預設權限(唯讀 + 三個放行的寫入,不含 secrets)——這是預期的中間狀態,不是漏做,加了 email 重跑 playbooks/k8s/oidc-rbac.yml 就會生效。

kube-prometheus-stack:release name 刻意取跟 chart 同名

Prometheus/Alertmanager/Grafana 三個 Service 的名稱,取決於這個 chart 的 fullname helper 邏輯——如果 release name 跟 chart name(kube-prometheus-stack)不一樣, Service 名稱會疊成 <release>-kube-prometheus-stack-alertmanager 這種重複又長的名字。這裡故意把 helm release 也取名 kube-prometheus-stack,讓 helper 判斷「release name 已經包含 chart name」,自動省掉重複的部分,得到乾淨的 kube-prometheus-stack-grafana / -prometheus / -alertmanager ——VirtualService 裡硬寫的目標 Service 名稱才對得上,這個對應關係 是先用 helm template 實際算出來、確認過名稱,才寫進 ansible role 的,不是照著猜的慣例寫。

持久化:靜態 PV,不是動態佈建,目的是撐過整個環境重建

一開始的決定是「可以不用掛 PVC」(chart 的 prometheusSpec.storageSpec、 alertmanagerSpec.storage、 grafana.persistence.enabled 三個本來就預設關閉)—— 後來使用者問「grafana, alert manager跟prometheus都有掛pvc了嗎? 確保我將環境全部拆除重建後 這些資料還在」,才改成現在這個做法。

不是直接掛 roles/nfs_csi_driver 那兩顆既有的動態 StorageClass(nfs-csi / nfs-csi-retain, docs_site 在用的那種)——動態佈建每次都會在 NFS export 底下建一個 全新、隨機命名的子目錄,reclaimPolicy: Retain 只保護「PVC 被誤刪但叢集還活著」這個情境,保護不了「整個 openstack 環境重建、k8s etcd 全新」:這種情況下舊 PVC 根本不存在 了,新裝的 Prometheus/Grafana 只會拿到一個全新空目錄,接不回舊 資料。改用靜態 PV:固定名字的 NFS 子目錄 (/srv/nfs/k8s/kube-prometheus-stack/{prometheus-db, alertmanager-db,grafana},由 roles/kube_prometheus_stack/tasks/main.yml 直接在 bastion 上建)配上固定名字的 PV (templates/persistent-volumes.yaml.j2),再讓 values.yaml.j2 裡對應的 PVC 用 volumeName 欄位 手動指定要綁哪一顆 PV、storageClassName: "" 關掉動態佈建路線——子目錄名字不變,叢集整個重建後新裝的 Prometheus/Alertmanager/Grafana 會自動接回同一批舊資料,跟 bastion 自己那兩顆 prevent_destroy 的 Cinder data volume 是同一種「資料生命週期不跟著運算資源走」設計。

Prometheus/Alertmanager 走的是 Prometheus Operator 的 StatefulSet + volumeClaimTemplate,實際 產生的 PVC 名稱是 operator 自己組的(不是 chart 直接控制),先查了 prometheus-operator 原始碼確認組合規則,而不是用猜的——但這其實不影響綁定是否成功: 只要 volumeClaimTemplate.spec 裡的 volumeName 設對,Kubernetes 會直接把 operator 產生的那個 PVC(不管它叫什麼 名字)預先綁定到指定的 PV,不需要事先知道或手動建立那個 PVC。 Grafana 走一般 Deployment,chart 本身就有 persistence.volumeName 這個欄位可以直接用,更簡單。 三顆都用 ReadWriteMany(NFS 天生支援,也順便避開 Grafana Deployment 用 RollingUpdate 策略時,新舊 pod 同時搶佔同一顆 ReadWriteOnce volume 卡住的問題)。

先用本機 helm template 對著真正的 chart 版本 (87.19.2)驗證過 values 渲染出來的 PVC/CR 內容跟預期 一致,才實際套用到叢集——套用後直接查 kubectl get pv/pvc 確認三顆都 Bound,再到 bastion 上看 NFS 子目錄底下 確實有 grafana.db、Prometheus/Alertmanager 的 TSDB 目錄,而且擁有者自動變成跟 pod 的 fsGroup (Prometheus/Alertmanager 是 2000、Grafana 是 472)一致——這是 csi-driver-nfs 4.13.4(chart 4.0.0 以後預設開啟 fsGroupPolicy: File)自動做的 recursive chown,不需要 額外手動管理 NFS 子目錄權限。

Grafana 密碼:helm 自動產生,不印進 ansible 執行紀錄

沒有在 values 裡指定 grafana.adminPassword——讓 chart 自己產生一組隨機密碼,存進 kube-prometheus-stack-grafana 這個 Secret 的 admin-password 欄位。role 的最後一步只印一段「怎麼自己 查」的說明(kubectl get secret ... -o jsonpath=... | base64 -d),不會把密碼實際印出來或寫進 ansible 的執行紀錄——密碼這種東西能不落地就不落地,跟這個專案處理 SSH 私鑰、tunnel token、Origin CA API token 是同一種謹慎程度。

Grafana 的 SSO:原生支援,不用碰 Istio

使用者接著問「grafana也串接sso 假如可以原生支援的話 如果要做 大量客製化修改則先停下讓我決定」——跟 Dashboard 不一樣,Grafana 本身就有一等公民的 auth.generic_oauth 功能,Cloudflare 也有對應的原生功能可以配對:Access for SaaS 這種 OIDC application 類型(跟前面 kube-apiserver/Dashboard 用的 self_hosted Application 完全不同機制——這種類型讓 Cloudflare Access 本身扮演一個真正的 OIDC provider,發 authorization code、發 token,不是被動驗證一個既有的 JWT)。兩邊都是原生功能, 不需要像 Dashboard 那樣另外掛 EnvoyFilter/Lua 複製 header 的 workaround(Dashboard v7 是因為拿掉了官方內建的 skip-login 開關 才需要那條路,見 Role: cert_manager；Grafana 沒有這個限制)。

roles/kube_prometheus_stack/templates/values.yaml.j2(grafana.ini 部分)
auth.generic_oauth:
  enabled: true
  allow_sign_up: true
  auto_login: true
  client_id: <grafana-sso 這個 SaaS app 的 client_id>
  scopes: "openid email profile"
  auth_url:  https://doughops.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<client_id>/authorization
  token_url: https://doughops.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<client_id>/token
  api_url:   https://doughops.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<client_id>/userinfo
  role_attribute_path: "contains([<oidc_admin_emails>], email) && 'Admin' || 'Viewer'"

auth_url/token_url/api_url 這三個網址,是先用 curl https://doughops.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<client_id>/.well-known/openid-configuration 實際查出來的正確端點,才填進去——不是照著網路上的網址規則猜著拼。 role_attribute_path 重用 roles/oidc_rbac(見上方 Dashboard SSO 的說明)那份 oidc_admin_emails 清單——同一批人在 Dashboard(K8s RBAC)跟 Grafana(Org Admin)都是管理者,只維護一份名單;清單是 空的話這個表達式直接退化成固定字串 'Viewer',所有人 預設唯讀。client_secret 不寫進 grafana.ini (那份設定會存成一個 plaintext 的 ConfigMap),改用 envValueFrom 從另外建的 Secret 讀,對應到 Grafana 認得的環境變數覆寫規則(GF_AUTH_GENERIC_OAUTH_CLIENT_SECRET 蓋過 ini 裡同一個設定)。

被否決的設計:讓 grafana.dough-ops.com 略過邊緣的 Cloudflare Access——裝完之後發現 grafana.dough-ops.com 同時被兩層擋著:邊緣的萬用字元 Access Application(涵蓋整個 *.dough-ops.com)先擋 一次,Grafana 自己的 auth.generic_oauth 又擋一次, 兩層要求的其實是同一件事(doughops GitHub org)。原本想幫 grafana.dough-ops.com 另外建一個 decision: bypass 的精確匹配 Application,讓邊緣那層 對這個 hostname 讓開,只留 Grafana 自己的 OIDC 當唯一關卡——被 使用者明確否決:「所有網站都需要通過cloudflare access, 否則你的 方法萬一grafana有漏洞 網站會被攻破」。這是刻意的 defense-in-depth 要求:兩層各自獨立擋,即使 Grafana 自己的認證 邏輯哪天出現漏洞,邊緣那一層依然完整擋著,不會因為省一次跳轉就 把這道防線拆掉。維持現況(兩層都在),兩層共用同一個 Cloudflare team session,實測瀏覽器只需要登入一次——第二層是無感的重新 導向,不是真的要求使用者重新輸入帳密。

Grafana 密碼:帳密登入還在,當 SSO 之外的備援

沒有在 values 裡指定 grafana.adminPassword——讓 chart 自己產生一組隨機密碼,存進 kube-prometheus-stack-grafana 這個 Secret 的 admin-password 欄位。role 的最後一步只印一段「怎麼自己 查」的說明(kubectl get secret ... -o jsonpath=... | base64 -d),不會把密碼實際印出來或寫進 ansible 的執行紀錄——密碼這種東西能不落地就不落地,跟這個專案處理 SSH 私鑰、tunnel token、Origin CA API token 是同一種謹慎程度。裝了 SSO 之後這組帳密不會自動失效(auth.generic_oauth 是 加裝一種登入方式,不是取代原本的帳密登入),保留 當作 SSO 出問題時的備援登入路徑。

ArgoCD:in-cluster target,裝完自動能管自己

ArgoCD(GitOps 持續部署)裝在叢集自己裡面,管理它自己所在的這個 叢集——ArgoCD 天生支援這種部署方式,裝完會自動帶一個內建的 in-cluster target(server: https://kubernetes.default.svc, 用 in-cluster ServiceAccount 認證),不需要額外手動註冊 cluster。

roles/argocd/tasks/main.yml(helm values 節錄)
fullnameOverride: argocd   # 見下方說明
dex:
  enabled: false            # 還沒接 SSO,先不裝這個可選元件
configs:
  params:
    server.insecure: true   # TLS 已經在 Istio Gateway 那層終止過,見 Role: cert_manager

fullnameOverride: argocd 是必要的,不是講究命名習慣 而已——官方 argo-cd chart 的 fullname helper 邏輯是 「release name 包含 chart name 才收斂成乾淨名稱」,這裡 release name 取 argocd(沒有連字號)並不包含 chart name argo-cd(有連字號)這個字串,兩者字面不同,不覆寫的話 Service/Deployment 名稱會變成 argocd-argo-cd-server 這種重複又醜的名字。

dex.enabled: false——dex 是 ArgoCD 內建、可選的 SSO federation 元件,專門用來讓 ArgoCD 接不支援原生 OIDC 的來源 (LDAP、SAML……)。Cloudflare Access 本身已經是合格的 OIDC provider(跟 Grafana/Vault 用的是同一種「Access for SaaS」機制), ArgoCD 自己的 auth/oidc 可以直接對它講 OIDC,不需要 Dex 這層轉譯,裝著不用純粹多一個 pod、多一分攻擊面。ArgoCD 自己的 admin 帳號 + 隨機產生的初始密碼(存在 argocd-initial-admin-secret 這個 Secret)保留當 SSO 出問題時的備援登入路徑,跟這個專案處理 Grafana admin 密碼是同一種 謹慎程度:role 執行完只印一段「怎麼自己查」的說明,不會把密碼 實際印出來。

argocd_applications:讓 Application 撐過叢集重建

ArgoCD 的 Application/AppProject 本質上是一般的 Kubernetes CRD,存在 etcd 裡——這個叢集除了 bastion 以外的節點都沒有掛任何持久化 volume(見 openstack/terraform.tfvars),叢集重建 (kubeadm-reset.yml 或整個 openstack/ 重新 apply)etcd 就是全新的,透過 ArgoCD 網頁 UI/CLI 手動建的 Application 會全部消失。roles/argocd 的 argocd_applications 是這個問題的解法:一份清單, 列出「ArgoCD 裡應該有哪些 Application」,每次跑這個 role 都會 重新套用——加一個 Application,只要在清單多加一項、重跑 playbooks/k8s/argocd.yml,不用去 ArgoCD UI 手動建, 這樣它才會在下次叢集重建後自動回來。

預設清單只有一項:ArgoCD 官方文件/教學長期在用的 guestbook 範例——一個帶 syncPolicy.automated + CreateNamespace=true 的 Application,不用 手動點 Sync 就會自動同步、自動建 guestbook namespace,跟 roles/demo_app 證明 Istio ingress 路徑真的通是同一個用意——證明「裝好的這個 ArgoCD 真的能同步/部署東西」,不是只有裝好一個空殼。

這份清單只會新增/更新,使用者明確要求不要自動 清掉「清單裡拿掉、但叢集上還留著」的 Application——單向套用, 移除一個 Application 要自己手動 kubectl delete application,不會因為改清單、重跑 playbook 就意外被清掉。 (中途試過「清單刪掉,重跑就自動清掉叢集上的」這個更嚴格的版本, 實測驗證過兩個方向都正確運作,但使用者不想要這種每次重跑都可能 觸發刪除的行為,改回單向。)

ArgoCD OIDC:仿 Vault(登入即 admin),不是仿 Grafana

使用者明確要求:任何通過邊緣 Cloudflare Access(doughops org 成員)、OIDC 登入 ArgoCD 的人,直接有完整權限——不是 Dashboard/ Grafana 那種「預設唯讀 + oidc_admin_emails 才有完整 權限」的分層模式,是跟 Vault 的 oidc-admin policy 同一個決定。ArgoCD 這邊對應的設定是 configs.rbac.policy.default: role:admin——RBAC 的 預設 fallback role,用 ArgoCD 內建角色,不用另外定義 policy.csv。redirect_uri 用 ArgoCD 直連 OIDC(非 Dex)固定的回呼路徑 /auth/callback,跟 Dex 模式的 /api/dex/callback 不一樣。

Bug:Jinja 字串串接塞 \n,在 >- 折疊純量裡不會變成真正的換行——第一版想用 'name: ...\n' ~ 'issuer: ...' ~ ... 這種字串串接,湊出 oidc.config(ArgoCD ConfigMap 裡一個值本身是多行 YAML 的 key)的內容,整個 set_fact 包在 >- 折疊純量裡。部署前先在本機用 ansible-playbook 單獨 測這段(沒有直接套到叢集上賭運氣)才發現:結果字串裡的換行是照 字面呈現的兩個字元 \ + n,不是真正的 換行字元——套進 ArgoCD 會直接把 oidc.config 解析成一坨 壞掉的 YAML。改成用一般的 YAML | 區塊純量(裡面直接 放真正的換行)組這段字串,搭配 vars: + 一般 YAML dict + combine(..., recursive=True) 組完整的 helm values, 本機重新測過確認結果是 dict 型別、換行是真正的換行, 才套用到叢集。

Bug:沒設 configs.cm.url,登入時被 Cloudflare 拒絕「Invalid redirect URL」——本機測完 Jinja/YAML 那段、 叢集上 argocd-cm/argocd-rbac-cm 的內容也 逐項核對過都對,以為沒事了,結果使用者實際登入時被 Cloudflare 那邊擋下來,錯誤訊息是 「Invalid redirect URL: the protocol and host (including port) must match and the path must be within allowed URLs if provided」。根因是 ArgoCD 組 OIDC(跟 Dex)的 redirect_uri 時,是拿 argocd-cm 的 url 這個欄位當底組出來的,不是從 瀏覽器實際請求的 Host header 動態推——這個欄位當時完全沒設, ArgoCD 送出去的 redirect_uri 跟 argocd_sso 這個 Access Application 登記的 https://argocd.dough-ops.com/auth/callback 兜不起來。 補上 configs.cm.url: https://argocd.dough-ops.com 解決——這個值不只 OIDC 需要,ArgoCD 的 UI/CLI/通知連結一般情況下 也要靠它才能組出正確的對外網址,所以放進 base values,不是只有 OIDC 設定才加。這個 bug 的教訓是:內部逐項核對設定值「看起來都對」 不能取代「真的登入一次」——redirect_uri 匹配是 IdP 那一側的邏輯, 光看 ArgoCD 這邊的 ConfigMap 內容看不出問題所在。

驗證方式:內部用真憑證驗證,外部確認被 Access 擋住

每個工具都用跟 Role: cert_manager 一樣的兩段式驗證:先在叢集內部開一個臨時 curl pod,帶 Origin CA root cert 直接打 istio-ingressgateway 的 443 port(繞過 Cloudflare Access,證明「後端這一段」真的通、憑證真的驗證得過);再從外部 直接 curl https://<子網域>.dough-ops.com/,確認 回應是 302 導去 doughops.cloudflareaccess.com 的 GitHub 登入頁,不是 200 或任何其他狀態——兩段都要各自驗證,只測 外部的話測不到「後端到底通不通」,只測內部的話又證明不了「Access 真的擋住了」。
