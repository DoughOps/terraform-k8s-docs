平台服務 內部工具

這頁整理叢集的內部維運工具。範圍是 Hubble UI、Kubernetes Dashboard，以及 kube-prometheus-stack 的 Prometheus、Alertmanager、Grafana。它們共用同一個模式。Helm 安裝後，用 VirtualService 掛到共用的 Istio Gateway，最外層由 Cloudflare Access 擋住。ArgoCD 屬於同一類，但設計集中在 Role: argocd。

工具總表

下表的「登入方式」欄連到各工具的權威說明。所有工具都先通過邊緣的 Cloudflare Access（GitHub org 成員），再看工具自己有沒有第二層驗證。誰登入後拿到什麼權限，統一寫在叢集使用手冊 § 權限。

Hubble UI

現在的設定

Hubble 是 Cilium chart 內建的元件，沒有獨立的 Helm release。roles/cilium/templates/cilium-values.yaml.j2 開啟三個 flag：

roles/cilium/templates/cilium-values.yaml.j2（hubble 部分）
hubble:
  enabled: true
  relay:
    enabled: true
  ui:
    enabled: true

relay 負責聚合每個節點 Cilium agent 的觀測資料，ui（hubble-ui Service）才是對外的網頁介面。

VirtualService 的 apply 邏輯在 roles/cilium/tasks/hubble_expose.yml，由 playbooks/k8s/hubble-expose.yml 以 import_role 的 tasks_from: hubble_expose 呼叫。VirtualService 掛在 cilium role 裡，是因為 Hubble 本來就是 Cilium 的一部分。

已知限制

  • Hubble UI 沒有內建驗證，全靠邊緣的 Cloudflare Access。
  • hubble-expose.yml 必須排在 istio.yml 之後。VirtualService 這個 CRD 由 Istio 提供，更早 apply 會直接報 no matches for kind VirtualService 並中止整個 k8s.yml。這不屬於「Gateway 晚點出現，istiod 自己會撿起來」的軟引用情況。
  • tasks_from 只在 task 層級的 import_role 或 include_role 生效。寫在 play 層級的 roles: 會被忽略，整個 main.yml 會重跑一次。重跑的內容包括 PodCIDR 配發、helm 裝 Cilium 與 bgp_announce。

實測 bug

#28 · 真實請求 503，叢集內測試正常

  • 症狀：從外部開 https://hubble.dough-ops.com/ 回 Cloudflare 品牌的 503 錯誤頁，叢集內部直接測試一直是 200。
  • 根因：Cloudflare Tunnel 的 originRequest.originServerName 設成 zone apex。Istio Gateway 443 listener 的 SNI 比對是 *.dough-ops.com，apex 不匹配任何 filter chain。TLS handshake 在 HTTP 層之前就被 Envoy 斷線。
  • 修法：改成帶子網域的 gateway.dough-ops.com，不需要是真實存在的服務。
  • 相關：Bug #28、Role: cloudflare_tunnel。

驗證

用兩段式驗證。Hubble UI 的後端 Service 是 hubble-ui.cilium:80。

Kubernetes Dashboard

現在的設定

roles/dashboard 用 Helm 裝 kubernetes-dashboard chart 7.14.0（dashboard_chart_version），namespace 為 kubernetes-dashboard，chart repo 是 https://kubernetes-retired.github.io/dashboard/。唯一覆寫的 values 是 kong.proxy.http.enabled: true。

chart 內建 Kong 當前置反向代理，預設只開自簽憑證的 HTTPS。TLS 已經在 Istio Gateway 用真憑證終止過一次，流量進 Dashboard 再包一層自簽 TLS 沒有意義。上游對這個行為有已知問題（kubernetes/dashboard#9861），就算想關掉 HTTPS，Service port 的選擇也不一定照預期運作。所以 Kong 同時開一個 plain HTTP 的 port 80（targetPort: 8000），VirtualService 直接打這個 port，完全不碰 HTTPS 那一側。

SSO：過了 Access 就能用，權限依身份

Dashboard 只有一個網址 dashboard.dough-ops.com，沒有「唯讀網址」與「管理網址」之分。能不能寫入由登入者的身份決定，所以 kube-apiserver 必須認得「這個請求是誰發的」，不能讓所有人共用一顆固定 token。完整鏈路由三個 role 組成：

Dashboard v7 拿掉了內建的 skip-login 開關。取代方案由官方維護者給出：請求已帶有效的 Authorization header 時，登入畫面直接跳過。
Cloudflare Access 會在每個通過驗證的請求上帶 Cf-Access-Jwt-Assertion header。roles/dashboard 因此新增 EnvoyFilter dashboard-cf-jwt-to-authorization，放在 istio_namespace。它掛一段 Lua，把 header 加上 Bearer 前綴後蓋到 Authorization：

roles/dashboard/templates/dashboard-cf-jwt-envoyfilter.yaml.j2（Lua 部分）
function envoy_on_request(request_handle)
  local host = request_handle:headers():get(":authority")
  if host == "dashboard.dough-ops.com" then
    local jwt = request_handle:headers():get("cf-access-jwt-assertion")
    if jwt ~= nil then
      request_handle:headers():replace("authorization", "Bearer " .. jwt)
    end
  end
end

Lua 用 :authority（Host header）判斷，只在 dashboard_hostname 生效。這個 EnvoyFilter 掛在整個 ingress gateway 上，沒辦法只綁定單一 VirtualService。沒有 host 判斷的話，Grafana 等其他服務自己使用的 Authorization header 會被蓋掉。

Dashboard 的 EnvoyFilter 只負責把 JWT 送到 apiserver。apiserver 認不認得，取決於 oidc-auth；認得之後能做什麼，取決於 oidc-rbac。三者缺一，Dashboard 都不會有預期的行為。

已知限制

  • 上游已退役。kubernetes/dashboard 被標為 retired，倉庫搬到 kubernetes-retired/dashboard，舊的 kubernetes.github.io/dashboard helm repo 回 404。chart 還能正常安裝使用，但不會再有官方安全更新。這個工具的所有攻擊面修補都只能靠外層的 Cloudflare Access 與 RBAC 最小權限。
  • EnvoyFilter 是全 gateway 範圍。它掛在整個 ingress gateway 上，只靠 Lua 的 host 判斷把影響限縮在 Dashboard。
  • SSO 依賴 apiserver 設定。k8s.yml 裡 oidc-auth.yml 排在 dashboard.yml 之後。在它跑完之前，apiserver 會判定 Dashboard 送出的 bearer token 無效。

實測 bug

Dashboard 自己沒有登錄在總表的 bug，RBAC 相關的問題見 oidc-rbac。

驗證

先照兩段式驗證確認路徑通。再確認 Lua 真的把 header 複製過去，這件事不能只靠 curl：

帶假的 Cf-Access-Jwt-Assertion 值，和完全不帶這個 header，對 apiserver 來說都是「無效的 bearer token」，回應同樣是 401，測不出 Lua 有沒有執行。要在 Lua 裡暫時加 request_handle:logInfo(...)，並把 istio-ingressgateway 的 log level 臨時調到 info。送一次請求，在 Envoy 的 log 裡看到「host 判斷正確、讀到 header 值、執行了 replace」三行紀錄，才算確認。確認後換回沒有 debug 的版本。

oidc-auth：apiserver 信任 Cloudflare Access

現在的設定

roles/oidc_auth 在三台 master 的 /etc/kubernetes/manifests/kube-apiserver.yaml 補上四個參數：

/etc/kubernetes/manifests/kube-apiserver.yaml（補上的部分）
- --oidc-issuer-url=https://doughops.cloudflareaccess.com
- --oidc-client-id=<wildcard Access Application 的 AUD>
- --oidc-username-claim=email
- --oidc-username-prefix=-

--oidc-issuer-url 要能用，該網域必須有正常的 OIDC discovery。用 curl https://doughops.cloudflareaccess.com/.well-known/openid-configuration 確認會回傳合法的 issuer 與 jwks_uri 之後才動手。--oidc-username-prefix=- 關掉 apiserver 預設加在使用者名稱前面的 issuer 前綴，讓 RBAC 的 User subject 可以直接寫 email。

這是控制平面層級的認證變更，影響整個 apiserver，不只是 Dashboard。playbook 用 serial: 1 逐台修改，每台的流程是：

  1. 記錄舊的 kube-apiserver container id，指令是 crictl ps --name kube-apiserver -q --state Running。
  2. 修改 manifest，等 container id 真的換掉。
  3. 直接打該台的 https://localhost:6443/livez，回 200 才換下一台。

只看 /livez 會誤判。manifest 剛改完時舊 container 通常還在跑，/livez 仍回 200，但新設定尚未套用。直接打 localhost 而不經 tor 的 haproxy，是為了驗證「這一台」真的活過來，而不是剛好被導去另外兩台。

已知限制

  • apiserver 只認得這一個 OIDC issuer。Cloudflare Access 簽發的 JWT 效期與可用性，就是 kubectl OIDC 身份與 Dashboard 的上限。
  • 不使用 Dex 或 Keycloak 作為 apiserver 的 issuer。那兩者屬於聯邦登入 PoC，見 Role: keycloak / dex。

驗證

每台 master 改完後的 /livez 與 container id 檢查已內建在 role 裡。Playbook 全部成功，代表三台都已重啟並回到健康狀態。

oidc-rbac：預設唯讀，個別 email 管理

現在的設定

roles/oidc_rbac 建立三個 ClusterRoleBinding：

roles/oidc_rbac
ClusterRoleBinding cloudflare-access-oidc-view
  subjects: [Group system:authenticated]
  roleRef:  ClusterRole/view                     # 內建，刻意不含 secrets

ClusterRoleBinding cloudflare-access-oidc-default
  subjects: [Group system:authenticated]
  roleRef:  ClusterRole/cloudflare-access-default # 自訂，疊加在 view 之上

ClusterRoleBinding cloudflare-access-oidc-admin
  subjects: [User <email>, ...]   # oidc_admin_emails，secrets.yml
  roleRef:  ClusterRole/cluster-admin

system:authenticated 是 Kubernetes 內建群組。client cert、service account token、OIDC 等任何方式驗證成功的使用者都屬於它，不用維護成員名單。這個群組同時綁兩個 ClusterRole：

  • 內建 view：唯讀大多數 namespaced 資源，刻意排除 secrets。
  • 自訂 cloudflare-access-default：唯讀 nodes、namespaces、persistentvolumes、storageclasses 這幾個 view 沒涵蓋的 cluster-scope 資源，另外明確放行三個寫入：刪 pod、改 configmap（update／patch）、scale deployment（deployments/scale）。

要完整 write 權限的人，把 email 放進 oidc_admin_emails，設定檔是 ansible/inventory/group_vars/all/secrets.yml。加入後重跑 playbooks/k8s/oidc-rbac.yml 就會生效。預設是空陣列，此時所有人只有上面那組預設權限。名單屬於帳號資訊，放在加密的 secrets.yml，不寫進文件。

各角色對每個工具實際能做什麼，見叢集使用手冊 § 權限。

已知限制

  • 預設群體是整個 Access 允許的 org。任何通過 Cloudflare Access 的成員都有預設那組寫入權限，影響範圍涵蓋所有 namespace。三個寫入分別是刪 pod、改 configmap 與 scale deployment。
  • RBAC 沒有排除語法。想讓某個角色「讀所有東西但不含 secrets」，只能疊加內建 view 再明確列舉額外項目，不能用 resources: ["*"]。
  • oidc_admin_emails 同時管 Dashboard 與 Grafana。同一份名單決定 Kubernetes 的 cluster-admin 和 Grafana 的 Admin，只維護一處，但也代表兩邊的管理權限一起生效。

實測 bug

#58 · wildcard 角色放行 Secrets 讀取

  • 症狀：部署前檢查發現，自訂 ClusterRole 的唯讀規則寫成 apiGroups: ["*"], resources: ["*"]。
  • 根因：原意是用一個 wildcard 角色完全取代 view，因為 view 涵蓋不到 nodes 這種 cluster-scope 資源。但 RBAC 沒有排除語法，wildcard 連 secrets 一起放行。
    結果是任何通過 Cloudflare Access 的人，也就是整個 GitHub org 而不只 oidc_admin_emails 名單，都能 kubectl get secret -o yaml。可讀到的內容包括 Grafana admin 密碼、TLS 私鑰與 Cloudflare tunnel token。內建 view 刻意排除 secrets，就是為了避免這件事。
  • 修法：改成兩個 ClusterRoleBinding 疊加。繼續綁內建 view，沿用官方已審查、排除 secrets 的範圍；自訂角色只明確列舉需要補上的 cluster-scope 資源與三個寫入 verb，完全不用 wildcard。
  • 怎麼確認修好：部署後用 kubectl auth can-i ... --as=system:authenticated 逐項驗證。get pods、delete pods、get nodes、patch configmaps 為 yes；get secrets、delete configmaps、update deployments 為 no。
  • 相關：Bug #58。

驗證

在 bastion 上
$ kubectl auth can-i get secrets --as=someone@example.com --as-group=system:authenticated
no
$ kubectl auth can-i delete pods --as=someone@example.com --as-group=system:authenticated
yes

預期結果：secrets 為 no，三個放行的寫入為 yes，其餘寫入為 no。

kube-prometheus-stack

現在的設定

roles/kube_prometheus_stack 用 Helm 裝 kube-prometheus-stack chart 87.19.2，namespace 為 monitoring。內容包含 Prometheus Operator、Prometheus、Alertmanager、Grafana、node-exporter 與 kube-state-metrics。三個 VirtualService 分別把 Grafana、Prometheus、Alertmanager 掛在各自的子網域。

Helm release name 刻意取成 kube-prometheus-stack，和 chart 同名。chart 的 fullname helper 發現 release name 已包含 chart name，就不再重複拼接，Service 名稱才會是乾淨的 kube-prometheus-stack-grafana、-prometheus、-alertmanager。release name 不同的話，會變成 <release>-kube-prometheus-stack-alertmanager 這種重複名稱，VirtualService 裡寫死的目標也就對不上。這個對應關係是先用 helm template 算出實際名稱才寫進 role。

資料持久化見 監控資料的靜態 PV，Grafana 的登入見 Grafana。

已知限制

  • Prometheus 與 Alertmanager 沒有內建驗證機制，只有 Cloudflare Access 擋在前面。
  • PV 容量（10Gi、2Gi、2Gi）只是綁定檢查用的宣告值。NFS 沒有 per-share quota，這些數字不是磁碟上限。
  • 資料存在 bastion 的 NFS export 上，bastion 的資料碟故障就會一起失去監控歷史。碟的保護機制見 基礎設施 § 資料碟。

實測 bug

這個 role 本身沒有登錄在總表的 bug。與儲存相關的 NFS CSI 問題見 監控資料的靜態 PV § 已知限制。

驗證

用兩段式驗證分別測三個子網域。Service 名稱可用 helm template 先算出再比對 VirtualService。

Grafana

Grafana 有兩條登入路徑：Cloudflare Access for SaaS 的 OIDC SSO，以及 chart 自動產生的 admin 帳密。SSO 是日常路徑，帳密當作備援。登入後的角色由 oidc_admin_emails 決定：名單內是 Org Admin，其餘一律是 Viewer。

現在的設定

SSO。Grafana 原生支援 auth.generic_oauth。Cloudflare 的 Access for SaaS 是一種 OIDC application。它讓 Access 扮演真正的 OIDC provider，發 authorization code 與 token。
這和 Dashboard 用的 self_hosted Application 是不同機制，後者只被動驗證一個既有 JWT。兩邊都是原生功能，所以 Grafana 不需要 Dashboard 那套 EnvoyFilter 與 Lua。

roles/kube_prometheus_stack/templates/values.yaml.j2（grafana.ini 部分）
auth.generic_oauth:
  enabled: true
  allow_sign_up: true
  auto_login: true
  client_id: <grafana-sso 這個 SaaS app 的 client_id>
  scopes: "openid email profile"
  auth_url:  https://doughops.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<client_id>/authorization
  token_url: https://doughops.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<client_id>/token
  api_url:   https://doughops.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<client_id>/userinfo
  role_attribute_path: "contains([<oidc_admin_emails>], email) && 'Admin' || 'Viewer'"
  • 三個端點網址是用 curl https://doughops.cloudflareaccess.com/cdn-cgi/access/sso/oidc/<client_id>/.well-known/openid-configuration 查出來的，不是照網址規則拼的。
  • role_attribute_path 重用 oidc-rbac 的 oidc_admin_emails。名單是空的，表達式退化成固定字串 'Viewer'，所有人預設唯讀。
  • allow_sign_up: true 讓第一次登入的人自動建帳號。能走到 OAuth 流程的人都已通過 Access，Grafana 不再另外限制網域。
  • client_secret 不寫進 grafana.ini，因為那份設定會存成明文 ConfigMap。改用 envValueFrom 從 Secret grafana-oidc-secret 讀，對應 Grafana 的環境變數覆寫 GF_AUTH_GENERIC_OAUTH_CLIENT_SECRET。

admin 帳密備援。values 沒有指定 grafana.adminPassword，chart 自己產生隨機密碼，存在 Secret kube-prometheus-stack-grafana 的 admin-password 欄位。role 最後只印出「怎麼自己查」的指令，不印密碼，密碼因此不會進 ansible 執行紀錄：

在 bastion 上
$ kubectl -n monitoring get secret kube-prometheus-stack-grafana -o jsonpath='{.data.admin-password}' | base64 -d

auth.generic_oauth 是額外加上的登入方式，不會取代帳密登入，所以安裝 SSO 後這組密碼仍然有效。保留它是為了 SSO 出問題時還有備援路徑。

決策：grafana.dough-ops.com 維持兩層驗證，邊緣的萬用字元 Access Application 與 Grafana 自己的 OIDC 都保留。

理由：兩層各自獨立。即使 Grafana 的認證邏輯日後出現漏洞，邊緣那層仍完整擋住，所有網站都必須先通過 Cloudflare Access 才能到達。

考慮過的替代方案：為 grafana.dough-ops.com 另建一個 decision: bypass 的精確匹配 Application，只留 Grafana 的 OIDC — 省一次跳轉，但拆掉縱深防禦，Grafana 本身的漏洞會直接暴露在公網。

代價：多一次重新導向。兩層共用同一個 Cloudflare team session，實測瀏覽器只需要登入一次，第二層是無感的重新導向。

已知限制

  • admin 密碼存在 Secret。能讀 monitoring namespace Secret 的人可以拿到。預設角色不含 secrets（見 oidc-rbac），只有 cluster-admin 能讀。
  • SSO 的 client_id／secret 變更。換掉 Cloudflare 那端的 SaaS app 之後，要更新 grafana_oidc_client_id 與 secret，並重跑 playbooks/k8s/kube-prometheus-stack.yml，否則 SSO 會失效。

實測 bug

Grafana SSO 沒有登錄在總表的 bug。上面的雙層驗證是設計上的取捨，不是 bug。

驗證

  1. 無痕視窗開 https://grafana.dough-ops.com/，先登入 Cloudflare Access，應自動導向 Grafana 並登入，不出現 Grafana 登入表單。
  2. 確認登入後的角色：oidc_admin_emails 內的 email 是 Admin，其他是 Viewer。
  3. 變更 values 後，Grafana pod 會自動重建；到 pod 內確認 grafana.ini 的 client_id 是新值。

監控資料的靜態 PV

現在的設定

Prometheus、Alertmanager、Grafana 的資料用靜態 PV，綁在 bastion NFS export 底下固定名字的子目錄。整個環境重建後，新裝的 chart 會自動接回同一批資料。

元件NFS 子目錄PV 名稱容量宣告
Prometheus/srv/nfs/k8s/kube-prometheus-stack/prometheus-dbkube-prometheus-stack-prometheus-pv10Gi
Alertmanager/srv/nfs/k8s/kube-prometheus-stack/alertmanager-dbkube-prometheus-stack-alertmanager-pv2Gi
Grafana/srv/nfs/k8s/kube-prometheus-stack/grafanakube-prometheus-stack-grafana-pv2Gi

子目錄由 roles/kube_prometheus_stack/tasks/main.yml 直接在 bastion 上建立（nfs_export_path 底下），PV 由 templates/persistent-volumes.yaml.j2 產生，persistentVolumeReclaimPolicy: Retain、mountOptions 為 nfsvers=4.1 與 hard，CSI driver 是 nfs.csi.k8s.io。

決策：監控資料用固定名字的靜態 PV，不使用 nfs-csi、nfs-csi-retain 這兩個動態 StorageClass。

理由：動態佈建每次都在 NFS export 底下建全新、隨機命名的子目錄。reclaimPolicy: Retain 只保護「PVC 被誤刪但叢集還活著」的情境。整個 OpenStack 環境加 kubeadm 重建後，etcd 是全新的，舊 PVC 根本不存在，新裝的 Prometheus 與 Grafana 只會拿到一個空目錄，接不回舊資料。靜態 PV 指向不變的子目錄名字，資料的生命週期就不跟著運算資源走，和 bastion 那兩顆 prevent_destroy 的 Cinder 資料碟是同一種設計，只是在上一層。

考慮過的替代方案：使用 nfs-csi-retain — 擋不住整個叢集重建；不掛 PVC — chart 預設就是關閉的，但資料在 pod 重建時就會消失。

代價：PV 要自己宣告和維護；子目錄由 Ansible 建立，不受 CSI 管理，刪掉環境時不會自動清理。

綁定靠 PVC 這一側的兩個欄位，三者的 values 寫在 templates/values.yaml.j2：

  • volumeName：指定這個 PVC 要綁哪一顆 PV，由它決定綁定結果。
  • storageClassName: ""：關掉動態佈建路線，避免這組 PV／PVC 被當成要走 StorageClass。chart 的 Grafana 樣板對空字串會整個省略這個欄位，效果等同 nil，叢集沒有預設 StorageClass，也不會被 admission 補上。
  • accessModes: [ReadWriteMany]：NFS 原生支援 RWX。Grafana 的 Deployment 用 RollingUpdate，新舊 pod 在更新期間會同時掛同一顆 volume，ReadWriteOnce 會卡住。

Prometheus 與 Alertmanager 由 Prometheus Operator 管理，用 StatefulSet 加 volumeClaimTemplate。實際的 PVC 名稱由 operator 組成（見 prometheus-operator 原始碼），chart 無法控制。但只要 volumeClaimTemplate.spec 內的 volumeName 設對，Kubernetes 就會把 operator 產生的 PVC，不論名字，預先綁到指定的 PV，不需要事先知道或手動建立那個 PVC。Grafana 是一般 Deployment，chart 直接提供 persistence.volumeName。

已知限制

  • NFS 子目錄權限。pod 的 fsGroup 會讓 csi-driver-nfs 4.13.4 對掛載的目錄做遞迴 chown。Prometheus 與 Alertmanager 的 fsGroup 是 2000，Grafana 是 472。chart 4.0.0 以後預設開啟 fsGroupPolicy: File，所以不需要手動管理子目錄權限。
  • 依賴 NFS CSI 與 bastion。k8s/nfs-csi.yml 要先跑，所以在 k8s.yml 裡排在 dashboard 與 kube-prometheus-stack 之前。NFS export 只開給 nfs_export_allowed_cidr（10.10.0.0/24）。
  • NFS CSI 的網路政策影響整個叢集。NFS CSI 附帶一條 CiliumClusterwideNetworkPolicy，名稱是 deny-nfs-mount-except-csi-node。它只用 egressDeny，擋住非 CSI node plugin 連 bastion 的 NFS port，也就是 TCP 2049。egressDeny-only 規則若沒有明講 enableDefaultDeny.egress: false，會把被選到的每個 endpoint 變成 egress 整個 default-deny。第一版漏掉這行，造成全叢集 pod 的 DNS 和對外連線約 10 小時中斷。現在的 manifest 已明確設定這行，詳情見 Bug #36。同一個驗證過程另一個踩到的問題是 Bug #35。demo namespace 的 Istio sidecar 注入，讓裸測試 pod 卡住。
  • 兩個 StorageClass 的由來。nfs-csi（Delete）與 nfs-csi-retain（Retain）共用同一個後端，差別只在 reclaimPolicy。Kubernetes 的 PVC 沒有宣告 reclaimPolicy 的欄位，這是 StorageClass 與 PV 層級的屬性，PVC 只能靠 storageClassName 選。
  • NFS 的存取控制是 IP range-based。它不受 Kubernetes RBAC 管，沒有那條 policy 時，任何能以 root 連到 10.10.0.0/24 的 pod 都能直接 mount 整個 export，看到所有 namespace 的 PV 資料。
  • CSI node／controller plugin 是 hostNetwork。Cilium 對 hostNetwork pod 的 per-pod policy 不生效（叢集未開 hostFirewall），這條規則擋不住刻意設 hostNetwork: true 的其他 pod。補強有三個選項：接受並標註、替其他 namespace 全部加 Pod Security baseline、開 Cilium Host Firewall。目前選第一個，因為叢集本來就沒有針對 hostPath 或 privileged pod 的防護，NFS 多一個同類缺口沒有讓情況更差；補齊屬於獨立的叢集安全加固。

實測 bug

#35 與 #36 是 NFS CSI 部署時踩到的問題，與靜態 PV 本身無關，詳見總表。

驗證

  1. 先用本機 helm template 對著 chart 87.19.2 渲染，確認 PVC 和 CR 的 volumeName 與預期一致。
  2. 套用後，在 bastion 上確認三顆 PV 與 PVC 都是 Bound：kubectl get pv,pvc -A。
  3. 到 bastion 看 NFS 子目錄，應有 grafana.db、Prometheus 與 Alertmanager 的 TSDB 目錄，擁有者與 pod 的 fsGroup 一致。

預期結果：重建環境後重跑 k8s/kube-prometheus-stack.yml，Grafana 與 Prometheus 的歷史資料仍在。

ArgoCD

ArgoCD 的安裝、登入設計、Application 持久化清單和 GitLab 串接，都在 Role: argocd；登入與 token 效期的取捨見 Role: argocd § 登入。

兩段式驗證

每個工具用和 Role: cert_manager 相同的兩段式驗證：

  1. 內部：在叢集內開一個臨時 curl pod，帶 Origin CA root cert 直接打 istio-ingressgateway 的 443 port。這一步繞過 Cloudflare Access，證明後端這一段通、憑證驗證得過。
  2. 外部：從外部 curl https://<子網域>.dough-ops.com/，確認回應是 302，導去 doughops.cloudflareaccess.com 的 GitHub 登入頁，不是 200 或其他狀態。

兩段必須各自驗證。只測外部，測不出後端通不通；只測內部，證明不了 Access 真的擋住。
