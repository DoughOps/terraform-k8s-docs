網路架構 網路架構總覽

這頁用一張圖加幾張表，把整個網路的形狀講完：五段互不重疊的位址空間、兩張網卡各管什麼、Pod 封包靠 iBGP 學到的路由直接送達，以及外部流量現在從哪裡進來。看完後，你應該能判斷任何一個 IP 屬於哪個網段、為什麼它存在，以及封包到每個決策點會發生什麼事。逐跳的封包實例在封包路徑實例。

網段與 IP 規劃

叢集用到 4 個彼此不重疊的位址空間，各由不同層級擁有。最容易混淆的是 k8s-net 和 pod-cidr：前者是 OpenStack 管的真實 subnet，後者是 Cilium 管的軟體位址空間，OpenStack 完全不知道它存在。

網段CIDR擁有者用途誰知道它存在
k8s-net 10.10.0.0/24 Terraform / Neutron 所有節點（含 tor、bastion）的資料平面位址，iBGP peering 全部發生在這個網段 OpenStack（真實 subnet）；每個節點的 ens3
mgmt-net 192.168.200.0/24 Terraform / Neutron Ansible／SSH 操作，以及 apt、helm、image pull 等對外存取；唯一有 SNAT 出口的網段 OpenStack；每個節點的 ens4
pod-cidr 172.16.0.0/16 cilium-operator 整個叢集的 Pod IP 空間，依節點切成 /24（ipam.mode=cluster-pool、clusterPoolIPv4MaskSize=24）。每個節點的那一份記錄在 CiliumNode 的 .spec.ipam.podCIDRs Kubernetes CRD 欄位、kernel 路由表與 FRR；OpenStack 不知道這個網段
service-cidr 172.18.0.0/16 kube-apiserver ClusterIP 的位址空間，由 kubeadm init --service-cidr 設定 只存在於 Cilium 的 eBPF Service 表；不會出現在任何網卡上，純靠位址轉換兌現

Pod 的 CIDR 記在 CiliumNode，不是 Node.spec.podCIDR。後者要靠 kube-controller-manager 的 node-ipam-controller 配發，這個叢集改由 cilium-operator 配發，原因見 Role: cilium。

各節點的 IP

mgmt-net 位址沿用 k8s-net 位址的最後一碼，只為了方便對照，兩個網段之間沒有路由關係。

節點k8s-net（ens3）mgmt-net（ens4）備註
tor10.10.0.10192.168.200.10route reflector、apiserver haproxy
bastion10.10.0.11192.168.200.11Floating IP 綁在這張 mgmt 網卡
ms-0001 ~ ms-000310.10.0.20 ~ 22192.168.200.20 ~ 22control plane
l4-0001 ~ l4-000210.10.0.30 ~ 31192.168.200.30 ~ 31一般 worker，帶 l4lb 標籤
ap-0001 ~ ap-000310.10.0.40 ~ 42192.168.200.40 ~ 42worker

四個網段不重疊是硬性要求：如果 pod-cidr 或 service-cidr 落在 k8s-net 或 mgmt-net 的範圍內，kernel 查路由時就無法分辨。它分不出目的位址是某個真實節點，還是 Pod 或 Service 的虛擬位址。這個專案選 10.10.0.0/24、192.168.200.0/24、172.16.0.0/16、172.18.0.0/16 四個 RFC1918 區塊，就是為了避開這個歧義。

bastion 上 Docker 自建 network 用的位址池 10.99.0.0/16 也要遵守同一條規則。Docker 預設會依序配發 172.17、172.18⋯⋯，曾經與 service-cidr 撞在一起，詳見 Bug #45。

雙網卡模型

每個節點都有兩張網卡。ens3 接 k8s-net，是資料平面；ens4 接 mgmt-net，是操作平面。兩者的信任邊界與流量特性不同，混在同一個網段會互相拖累。這個決定的 Terraform 實作見 Terraform / OpenStack。

🔒

k8s-net 沒有預設路由

subnet 設 no_gateway=true，沒有 Neutron Router，DHCP 也不發預設路由。節點之間的可達性完全靠 iBGP 學到的具體路由，FRR 掛了，連線能力就跟著降級，BGP 的健康狀態直接反映在實際連線上。

🌍

mgmt-net 負責對外

mgmt-net 接 Neutron Router，Router 連到外部網路並做 SNAT，是整個架構唯一的 SNAT 出口。預設路由只在這張網卡上，apt、helm、image pull 全部走這裡。對 k8s-net 做任何網路實驗，都不會切斷 SSH 與 Ansible 這條管理路徑。

🔑

Port Security 只在 mgmt-net 保留

k8s-net 的 fabric port 全部關閉 port security，因為 Neutron 的 conntrack 防火牆與動態路由、非對稱路由天生衝突。mgmt-net 的 port 維持預設防護，兩個網段的風險面互相隔開。決策與證據見 fabric port 關閉 port security。

幾個直接的後果：

  • kubelet 用 --node-ip 指定 k8s-net 位址。沒指定時它會挑預設路由所在的網卡，也就是 mgmt-net。
  • Ansible 連線用 mgmt-net 位址（ansible_host）。需要引用「這台在資料平面上的位址」時，才用 fabric_ip。
  • 兩個網段的實體 MTU 都是 1442，因為 Neutron 本身是一層 overlay。bastion 上的 Docker 也要把 MTU 設成 1442，見 Bug #10。

各角色的路由表

下面是穩態時，也就是 BGP session 全部 established 時，每種角色實際看到的路由表。直接看 kernel 怎麼決定，比推測封包怎麼走更可靠。

tor（route reflector，10.10.0.10）

tor · ip route show
10.10.0.0/24 dev ens3 proto kernel scope link src 10.10.0.10        # 直連 k8s-net
192.168.200.0/24 dev ens4 proto kernel scope link src 192.168.200.10# 直連 mgmt-net
default via 192.168.200.1 dev ens4                                  # 預設路由只在 mgmt-net
172.16.0.0/24 via 10.10.0.40 dev ens3   # BGP 學到：ap-0001 的 PodCIDR
172.16.1.0/24 via 10.10.0.21 dev ens3   # BGP 學到：ms-0002 的 PodCIDR
172.16.2.0/24 via 10.10.0.30 dev ens3   # BGP 學到：l4-0001 的 PodCIDR
# ...其餘節點的 /24，每個 k8s 節點各一條

tor 自己的路由表保留原始發起節點的真實位址當 next-hop。next-hop-self 只改 tor 反射給其他 client 的宣告，不改 tor 本地的 RIB。haproxy 監聽 10.10.0.10:6443，把 apiserver 流量轉給 3 台 master，見 Role: apiserver-lb。

bastion（10.10.0.11、192.168.200.11）

bastion · ip route show
10.10.0.0/24 dev ens3 proto kernel scope link src 10.10.0.11        # 直連 k8s-net
192.168.200.0/24 dev ens4 proto kernel scope link src 192.168.200.11# 直連 mgmt-net
default via 192.168.200.1 dev ens4                                  # 預設路由：SNAT 對外，Floating IP 對內
172.16.0.0/24 via 10.10.0.10 dev ens3 proto bgp                     # BGP 學到：next-hop 是 tor
# ...每個 k8s 節點的 PodCIDR 各一條，next-hop 都是 tor

bastion 以通用的 peer 角色加入 iBGP：它跑 FRR、與 tor 建 session、學到所有 PodCIDR，但不宣告任何 prefix。所以 bastion 連得到節點位址，也連得到 Pod IP。在 bastion 上執行 curl 172.16.x.x 會依 BGP 路由經 tor 送達。它不需要被別人路由到，只需要能出去，這是它與 control plane 節點唯一的差別。

Master／LB／Worker（以 ms-0001 為例）

ms-0001 · ip route show
10.10.0.0/24 dev ens3 proto kernel scope link src 10.10.0.20        # 直連 k8s-net
192.168.200.0/24 dev ens4 proto kernel scope link src 192.168.200.20# 直連 mgmt-net
default via 192.168.200.1 dev ens4                                  # 預設路由只在 mgmt-net（image pull 走這條）
172.18.0.0/16 dev ens3 scope link                                  # service-cidr，netplan 加的靜態路由（見下一節）
172.16.4.0/24 via 172.16.4.X dev cilium_host proto kernel          # 自己的 PodCIDR，Cilium 建的路由
172.16.0.0/24 via 10.10.0.10 dev ens3 proto bgp                    # BGP 學到：ap-0001 的 PodCIDR，next-hop 是 tor
172.16.1.0/24 via 10.10.0.10 dev ens3 proto bgp                    # BGP 學到：ms-0002 的 PodCIDR，next-hop 是 tor
# ...其餘節點的 /24，每個 k8s 節點各一條（自己那條是 cilium_host）

這張表是 native routing 的核心證據。要送到任何 Pod IP，查完路由表就知道下一步是 tor 的 ens3，tor 再依自己的 RIB 轉給目標節點。整條路徑沒有 VTEP mapping，也沒有 VXLAN header，路由本身是靠 iBGP 動態學來的。所有跨節點的 Pod 流量都先到 tor，原因見 next-hop-self。

service-cidr 的靜態路由

每個 k8s 節點都有一條 172.18.0.0/16 dev ens3 scope link，它看起來多餘，因為任何送往 ClusterIP 的封包，都會先被轉換成真實 backend 位址才離開主機。這條路由不轉送任何封包，它只影響一件事：kernel 為連線挑選來源位址。

Linux 決定「用哪張網卡、哪個來源 IP」的時間點，在位址轉換生效之前。kernel 拿原始目的地（172.18.x.x）查一次路由來選來源位址，這時不管是 iptables DNAT 還是 eBPF 的 socket 層轉換，都還沒套用。

tcpdump 實測：SYN 的來源位址是 192.168.200.30（mgmt_ip），不是預期的 10.10.0.30（fabric_ip），即使目的地已經正確轉換成某台 master 的 fabric_ip。

修法是用 netplan 在每個 k8s 節點加一條 172.18.0.0/16 走 k8s-net 網卡的 scope: link 靜態路由，檔案是 /etc/netplan/90-service-cidr-route.yaml。有了它，選來源位址的那次查詢會落在 k8s-net 上，kernel 因此選 10.10.0.x。這個修法對 kube-proxy 的 iptables 與 Cilium 的 eBPF 轉換都成立，所以移除 kube-proxy 後不需要回頭改。Ansible 實作見 Role: kubelet，除錯過程見 Bug #18。

選擇 native routing

Cilium 預設用 VXLAN 或 Geneve 把 Pod 封包再包一層。這個叢集改用 native routing：Pod 封包帶著真實 Pod IP，直接走 k8s-net。

決策：Cilium 使用 routingMode: native，Pod CIDR 由 FRR 以 iBGP 散佈。Cilium 自己的 BGP 關閉，設定是 bgpControlPlane.enabled: false。

理由：fabric 已經存在，native routing 讓它真正承載 Pod 流量，而不只是展示用途。k8s-net 本身已是 Neutron 的 overlay（MTU 1442）。Cilium 再疊一層就是 overlay 疊 overlay，每個封包封裝兩次，有效 MTU 繼續下降，節點 CPU 也要多做一輪封裝。只維護一個 BGP 實作（FRR）也讓狀態機、設定與除錯路徑各只有一套。

考慮過的替代方案：Cilium VXLAN／Geneve overlay — 不依賴底層網路，但與上述理由衝突。Cilium BGP Control Plane（GoBGP）— 每個節點會同時有 FRR 與 GoBGP 兩個 speaker 各自與 tor 維持 session。

代價：Pod CIDR 必須能被整個 fabric 路由，所以 FRR 要把 Cilium 動態配發的 PodCIDR 注入 BGP（見 PodCIDR 如何進入 BGP）。同時，Pod 到「其他節點真實 IP」的流量要靠 masquerade workaround，見下方已知限制。

Cilium、FRR、Service 轉換的分工

native routing 能動，靠的是三個獨立系統各司其職、只透過 kernel 路由表溝通，沒有任何一個直接呼叫另一個的 API。

系統負責什麼怎麼跟其他系統溝通
Cilium（agent + operator） eBPF 資料平面：Pod 網卡（veth）、cilium_host、本節點 PodCIDR 的路由、NetworkPolicy operator 把 PodCIDR 寫進 CiliumNode；在 kernel 路由表留下一筆路由，被動地等 FRR 讀取。Cilium 不知道 FRR 存在
FRR（每個節點的 iBGP peer） 把本節點的 PodCIDR 宣告給 fabric，並把學到的其他節點 PodCIDR 裝進本地 kernel 路由表 Ansible 用 vtysh 注入 network 陳述式（見 Role: cilium 的 bgp_announce）；zebra 把學到的路由寫回 kernel
Cilium eBPF Service 轉換 ClusterIP 到真實 backend 的轉換，取代 kube-proxy，與 Pod 之間的路由無關 讀 Service／EndpointSlice 物件；只有目的地是 ClusterIP 的連線會經過它，見 kube-proxy 取代

三條獨立的除錯路徑：Pod 之間不通，先看 FRR 有沒有學到對方的 PodCIDR（vtysh -c "show ip bgp"）。Service 不通，先看 Cilium 的 Service 表。Pod 卡在 ContainerCreating，先看 /etc/cni/net.d 有沒有 Cilium 寫的設定。三個系統可以各自除錯、各自重啟。

對外入口的現況路徑

外部流量走 Cloudflare Tunnel，完全不經過 Floating IP、tor 或任何負載平衡節點。Floating IP 只綁在 bastion，只供 SSH 與維運。

  • cloudflared 跑在 cloudflare namespace，主動撥出到 Cloudflare 邊緣，叢集不需要任何對外開放的入站埠。Tunnel 的 ingress 規則把 *.dough-ops.com 導向 Istio ingress gateway，見 Role: cloudflare_tunnel。
  • istio-ingressgateway 的 Service 類型是 ClusterIP。這個 OpenStack tenant 沒有 LBaaS，LoadBalancer 類型只會停在 <pending>，而 tunnel 本來就不需要 NodePort 或 LoadBalancer。見 Role: istio。
  • 內部工具共用同一個萬用字元 Gateway，由 Cloudflare Access 擋在前面，規則見 Cloudflare 設定清單。
  • bastion 上另有第二條獨立的 tunnel（bastion-ssh），由 bastion 本機的 cloudflared 提供瀏覽器 SSH，也代理 bastion 上的 Vault、Keycloak 與 GitLab。它不經過叢集。

邊界之後的流量是真實路由：cloudflared Pod 到 gateway Pod 再到後端 Pod，全部走 Cilium native routing，沒有額外的 NAT。整個架構的 NAT 只有 mgmt-router 的 SNAT，以及 Floating IP 對 bastion 的 1:1 NAT。逐跳實例見封包路徑實例的情境五。

已知限制

  • Pod 到其他節點真實 IP 會被 masquerade。來源是 Pod CIDR 的封包，在 OpenStack underlay 中除了送往 tor 以外都會被靜默丟棄，來源是節點自己 IP 的封包則不受影響。Cilium 因此設定 enable-remote-node-masquerade，把這類流量的來源改成節點 IP。它只影響 Pod 到節點 IP，目前實際會踩到的是 Pod 連 kubernetes Service，它的 backend 是 3 台 master 的 6443。細節見 Role: cilium 與 Bug #47。
  • tor 是單點。單一 route reflector 同時兼任 apiserver 的 haproxy。所有跨節點 Pod 流量的 next-hop 都是 tor，tor 掛掉時，跨節點 Pod 通訊與 apiserver 入口會一起中斷。
  • k8s-net 是共用 L2。節點之間「只能經過 tor」靠協定層強制，做法是 next-hop-self all 加關閉 ICMP redirect。實體拓樸並沒有隔離，細節見 FRR / iBGP Fabric。

演進歷史

kube-proxy 的兩階段移除

Cilium 導入之初，kubeProxyReplacement 明確設成 false，保留 kube-proxy。那一階段的範圍只有 CNI 與 native routing 整合，kube-proxy 取代被視為需要另外評估的獨立決定。

後來決定移除 kube-proxy 改用 Cilium eBPF。設定是 kubeProxyReplacement: true，並讓 kubeadm init 帶 --skip-phases=addon/kube-proxy，一開始就不部署它。移除後，Cilium 在 bootstrap 期需要一個不依賴 kube-proxy 的 apiserver 入口，也就是 k8sServiceHost 與 k8sServicePort。實作時在這裡撞到 TLS SAN 不匹配的問題，完整過程見 Role: cilium。

對外入口的演進

最初的設計把 Floating IP 綁在 tor，用本機 DNAT 把流量導向內部 Service VIP，再由 L4LB 節點以 ECMP 加 DSR 分流到 Pod。這條路徑在 OpenStack 上驗證可行，但從未接上實際服務，後來改走 Cloudflare Tunnel，原設計保留為休眠狀態。驗證過程與保留原因見 DSR／L4LB 歷史。
