網路架構整個 k8s 網路是怎麼拼起來的

這頁的目標是把「為什麼整個系統長這樣」一次講完整,不是逐一介紹元件用途。 看完這頁,你應該能自己回答:任何一個 IP 屬於哪個網段、為什麼那個網段存在、 一個封包從 A 到 B 實際上會經過哪些決策點。逐步的封包路徑實例在 封包路徑實例 頁面。

四個 IP 網段,四種完全不同的權責

這個系統裡總共有 4 個不重疊的 IP 網段,分別由不同的層級擁有、管理、決定內容。 搞混這四個網段是最容易迷路的地方——尤其是 k8s-net 跟 pod-cidr 常常被誤以為是同一件事,但它們的權責層完全不同。

網段CIDR擁有者用途誰知道這個網段的存在
k8s-net 10.10.0.0/24 Terraform / Neutron 所有節點(含 tor、bastion)的「資料平面」身分位址,iBGP peering 全部發生在這個網段上 OpenStack(這是一個真實 subnet);每個節點的 ens3
mgmt-net 192.168.200.0/24 Terraform / Neutron Ansible/SSH 操作、對外(apt/helm/image pull)網路存取,唯一有 SNAT 出口的網段 OpenStack;每個節點的 ens4
pod-cidr 172.16.0.0/16 cilium-operator 整個叢集的 Pod IP 位址空間,依節點切成 /24(ipam.mode=cluster-pool 的 clusterPoolIPv4MaskSize=24),每個節點拿到自己那一份,記錄在 CiliumNode 的 .spec.ipam.podCIDRs(不是 Node.spec.podCIDR——後者要靠 kube-controller-manager 的 node-ipam-controller,這裡刻意不用,見 Role: cilium) Kubernetes CRD 物件裡的欄位;OpenStack/Neutron 完全不知道這個網段存在 ——這是純軟體層(kernel 路由表 + FRR)在管的位址空間
service-cidr 172.18.0.0/16 kube-apiserver ClusterIP 的位址空間,kubeadm init --service-cidr 設定 只存在於 iptables/ipvs 規則裡,從來不會真的出現在任何一條實體/虛擬網卡上 ——它是純粹靠 DNAT 兌現的「虛擬」位址

為什麼四個網段互不重疊是硬性要求,不是巧合: 如果 pod-cidr 或 service-cidr 剛好落在 k8s-net/mgmt-net 的範圍內,kernel 的路由表查詢會產生歧義——一個目的地位址到底該解讀成「這是某個真實節點的位址, 直接送到那個介面」還是「這是一個 Pod/Service 的虛擬位址,要先查 iptables/BGP」,kernel 沒有辦法區分。這個專案選 10.10.0.0/24、192.168.200.0/24、172.16.0.0/16、 172.18.0.0/16 四個彼此不重疊的 RFC1918 區塊,純粹是刻意避開這個歧義, 不是隨便挑的數字。

為什麼要有兩個實體網段(k8s-net / mgmt-net),不是一個就好

這是整個基礎設施最早、也最根本的一個決定(詳細背景見 Terraform / OpenStack 頁面),這裡只講網路架構 的角度:「資料平面」跟「操作平面」的信任邊界跟流量特性完全不一樣, 混在同一個網段會互相拖累。

🔒

k8s-net 沒有預設路由(no_gateway=true)

資料平面的節點彼此之間不需要、也不應該有對外上網的能力——它們互相之間的 可達性完全靠 iBGP fabric 決定,不靠 Router。這個網段上的任何一個節點, 如果 FRR 掛了,它跟其他節點(除了直接相鄰、同一個 subnet 的那些)的連線 也應該跟著斷,這是刻意的:讓 BGP fabric 的健康狀態直接反映在實際連線能力上。

🌍

mgmt-net 有 SNAT(enable_snat=true)

Ansible 需要 apt/curl/helm/container image pull 這些對外網路存取, 這些流量完全不需要、也不應該經過刻意設計成「沒有預設路由」的 k8s-net。 把這兩種流量分開,表示之後要對 k8s-net 做任何實驗性的網路調整(例如 fib_multipath_hash_policy 這種會影響整個路由行為的 kernel 參數), 都不會不小心把 SSH/ansible 這條管理路徑也弄斷。

🔑

Port Security 只在 mgmt-net 保留

k8s-net 上所有 fabric port 都是 port_security_enabled = false ——Neutron OVS 的 conntrack-based 防火牆跟 BGP 動態路由、DSR 非對稱路由天生衝突(見 DSR 歷史頁面 的完整 除錯過程)。這個決定只影響 k8s-net,mgmt-net 上的 port 維持預設安全機制, 兩個網段的風險面被完全隔開。

每一種節點角色的完整路由表

下面是「穩態」(所有節點都正常運作、BGP session 都 established)時, 每一種節點角色實際會看到的路由表。這是理解整個系統最直接的方式——不用猜 「封包會怎麼走」,直接看 kernel 真的怎麼決定。

tor(route reflector,10.10.0.10)

tor · ip route show
10.10.0.0/24 dev ens3 proto kernel scope link src 10.10.0.10        # 直連 k8s-net
192.168.200.0/24 dev ens4 proto kernel scope link src 192.168.200.10# 直連 mgmt-net
default via 192.168.200.1 dev ens4                                  # 預設路由只在 mgmt-net
172.16.0.0/24 via 10.10.0.40 dev ens3   # BGP 學到:ap-0001 的 PodCIDR
172.16.1.0/24 via 10.10.0.21 dev ens3   # BGP 學到:ms-0002 的 PodCIDR
172.16.2.0/24 via 10.10.0.30 dev ens3   # BGP 學到:l4-0001 的 PodCIDR
# ...其餘 4 個節點的 /24,總共 7 條(每個 k8s 節點各一條)

tor 身兼 route reflector,所以它自己的 BGP table 裡看到的 next-hop 是 原始發起節點的真實位址(不是被改寫過的)——next-hop-self 只影響 tor 反射給其他 client 時宣告出去的 next-hop,tor 自己的本地 RIB 裡保留原始資訊。haproxy 監聽在 10.10.0.10:6443,把 apiserver 流量轉給 3 台 master,細節見 Role: apiserver-lb。

bastion(操作入口,10.10.0.11 + 192.168.200.11 + floating ip)

bastion · ip route show
10.10.0.0/24 dev ens3 proto kernel scope link src 10.10.0.11        # 直連 k8s-net
192.168.200.0/24 dev ens4 proto kernel scope link src 192.168.200.11# 直連 mgmt-net
default via 192.168.200.1 dev ens4                                  # 預設路由(SNAT 對外 + floating ip 對內)
# 沒有任何 172.16.0.0/16 的路由!

刻意的限制:bastion 完全不裝 FRR(見 templates/bastion-init.sh.tftpl vs templates/frr-init.sh.tftpl 的分流邏輯)。這表示 bastion 可以直接連到任何節點的節點位址 (因為 k8s-net 是同一個 flat subnet,直連不需要路由),但完全連不到任何 Pod IP——bastion 上跑 curl 172.16.x.x 會直接失敗(no route to host)。這不是 bug,是因為 bastion 的定位是 「SSH + kubectl 操作入口」,它需要的是「能連到每個節點」跟「能連到 apiserver(透過 k8s-api.internal 這個節點位址,不是 pod 位址)」, 從來不需要直接戳 pod IP。

Master / LB / Worker(k8s_nodes,以 ms-0001 · 10.10.0.20 為例)

ms-0001 · ip route show
10.10.0.0/24 dev ens3 proto kernel scope link src 10.10.0.20        # 直連 k8s-net
192.168.200.0/24 dev ens4 proto kernel scope link src 192.168.200.20# 直連 mgmt-net
default via 192.168.200.1 dev ens4                                  # 預設路由只在 mgmt-net(image pull 用這條)
172.18.0.0/16 dev ens3 scope link                                  # service-cidr,netplan 加的靜態路由(下面詳述)
172.16.4.0/24 via 10.244.X.1 dev cilium_host proto kernel          # 自己的 PodCIDR,Cilium 建的 connected route
172.16.0.0/24 via 10.10.0.40 dev ens3   # BGP 學到:ap-0001 的 PodCIDR
172.16.1.0/24 via 10.10.0.21 dev ens3   # BGP 學到:ms-0002 的 PodCIDR
# ...其餘節點的 /24,每個 k8s_nodes 成員各一條(除了自己那條是 connected)

這張路由表是整個 native routing 設計的核心證據:要送到任何一個 Pod IP 的封包,不管目的地是哪個節點,查完路由表就直接知道下一步要送到 哪個節點的 ens3,完全不用查詢任何 overlay 的 VTEP mapping、 不用封裝 VXLAN header——因為這條路由本身就是靠 iBGP 動態學來的。 這也是為什麼「172.18.0.0/16 dev ens3 scope link」這條路由需要存在的原因, 下一段詳細解釋。

service-cidr 那條看起來多餘的靜態路由,到底在解決什麼

這是整個 native routing 落地過程中唯一一個純網路(不是 k8s 也不是 Cilium) 層級的 bug,值得在架構層級講清楚(逐行除錯過程見 Role: kubelet 頁)。

Kubernetes 的 ClusterIP(172.18.0.0/16)從來不是一個「真的路由得到」 的位址——任何送往 ClusterIP 的封包,一定會先被 Service 轉譯機制改寫成某個真實 backend(例如某台 master 的 10.10.0.20:6443),才會真正離開這台 主機。這個 bug 是在叢集還沒移除 kube-proxy 時發現的(當時的轉譯 機制是 kube-proxy 裝的 iptables DNAT 規則,現在已經是 Cilium 的 eBPF kube-proxy replacement),但根因是 更底層的問題:Linux 決定「這個連線要用哪個網卡/哪個來源 IP 送出去」的 時間點,是在轉譯生效之前——kernel 針對原始目的地 (172.18.x.x)做一次路由查詢來決定來源位址,這時候不管是 iptables DNAT 還是 eBPF 的 socket-level 轉譯都還沒套用。這條路由的修法對兩種機制都成立, 移除 kube-proxy 之後不需要回頭改。

沒有這條路由
172.18.x.x 沒有任何專屬路由
→
路由查詢 fallback 到
mgmt-net 的預設路由
→
來源位址選成
192.168.200.x
→
DNAT 把目的地改成
真正的 master fabric_ip
→
封包帶著錯的來源位址
離開,對方原路回覆
回不到正確的連線狀態

tcpdump 實測抓到的現象:SYN 封包的來源位址是 192.168.200.30(mgmt_ip),不是預期的 10.10.0.30 (fabric_ip)——即使目的地已經正確 DNAT 成某個 master 的 fabric_ip。

修法是在每個 k8s 節點上,用 netplan 加一條 172.18.0.0/16 dev ens3 scope link 的靜態路由——這條路由 不會真的被拿去轉送任何封包(封包一定會先被 DNAT),它唯一的作用 是讓「決定來源位址」那次路由查詢,對 172.18.0.0/16 這個目的地 能查到一個落在 k8s-net 上的結果,連帶讓 kernel 選中 10.10.0.x 當來源位址。細節與 ansible 實作見 Role: kubelet。

為什麼選 native routing,不是 overlay(VXLAN/Geneve)

Cilium(以及幾乎所有主流 CNI)預設或常見的做法是用 VXLAN/Geneve 把 pod 封包包一層再送出去——這樣不管底層網路長什麼樣子、節點是不是同一個 L2/L3 網段都無所謂,CNI 自己處理「怎麼把封包從一個節點送到另一個節點」。 這個 lab刻意不用這條路,原因分三層:

🎯

已經有一個能用的 BGP fabric,不用等於浪費

整個 Phase 1(見 歷史頁面)存在的目的 就是證明「這個 OpenStack tenant 上可以自己組出一個真的能動的 iBGP fabric」。如果裝 CNI 的時候選 overlay,這個 fabric 對「pod 怎麼互相 連到對方」這件事完全沒有貢獻,整個 Phase 1 的投資就只剩下歷史意義。 native routing 讓 Phase 1 建的東西變成 Phase 3 真正依賴的基礎設施。

📉

k8s-net 本身已經是 OpenStack 的 overlay(MTU 1442)

k8s-net 底層其實是 OpenStack Neutron 自己的 VXLAN/Geneve overlay (這也是為什麼所有介面 MTU 被 cloud-init 設成 1442,不是標準的 1500 ——已經扣掉 OpenStack 自己那層 overlay 的封裝開銷)。如果 Cilium 再疊一層 VXLAN,就是「overlay 疊 overlay」,每個 pod 封包要被封裝兩次, 有效 MTU 會再往下掉一截,每個節點的 CPU 也要多做一輪封裝/解封裝。 native routing 只有 OpenStack 那一層(躲不掉),不會再疊第二層。

🧩

不想在同一批節點上跑兩個獨立的 BGP 實作

Cilium 自己也有 BGP Control Plane 可以做類似的事(用 GoBGP)。 但那樣等於每個節點上同時有 FRR(既有 fabric)跟 Cilium 內建的 BGP speaker(pod CIDR)各自維護一份跟 tor 的 BGP session,兩套獨立的 狀態機、兩套設定、兩套除錯路徑。這個 lab 選擇只維護一個 BGP 實作(FRR),把 Cilium 動態決定的 PodCIDR 動態餵回同一個 FRR instance——用 bgpControlPlane.enabled: false 明確關掉 Cilium 自己的 BGP,細節見 Role: cilium。

Cilium / FRR / Service 轉譯三者怎麼分工

native routing 能動,靠的是這幾個獨立系統各司其職、彼此透過 kernel 路由表 溝通,沒有任何一個系統直接呼叫另一個系統的 API。下表是移除 kube-proxy 之前的分工——Service 轉譯那一列現在已經是 Cilium 的 eBPF 實作,不是 kube-proxy,完整原因見下方。

系統負責什麼怎麼跟其他系統溝通
Cilium(agent + operator) eBPF 資料平面:pod 網卡設定(veth)、cilium_host 介面、本節點 PodCIDR 的 connected route、NetworkPolicy 執行 operator 自己配發、寫進 CiliumNode 的 .spec.ipam.podCIDRs(ipam.mode=cluster-pool, 不依賴 kube-controller-manager);在 kernel 路由表留下一筆 connected route,被動地等 FRR 去讀取、宣告 ——Cilium 完全不知道 FRR 的存在
FRR(每個節點的 iBGP peer) 把 Cilium 留下的 connected route 廣播給整個 fabric(透過 tor 反射),並且把從其他節點學到的 PodCIDR 路由裝進本地 kernel 路由表 用 vtysh 由 ansible 動態注入 network 陳述式(見 Role: cilium 的 bgp_announce);把學到的路由寫回 kernel(zebra 負責),讓一般的核心轉送邏輯就能正確送達
kube-proxy(iptables 模式)——已移除,見下方 Service ClusterIP → 真實 backend 的 DNAT 規則,跟 Pod-to-Pod 路由完全無關 讀 Kubernetes API 的 Service/Endpoints 物件;產生的 iptables 規則跟 Cilium/FRR 完全獨立運作,只有在「目的地是 ClusterIP」的 封包才會經過它

這個分工的好處:三個系統各自都可以獨立除錯、獨立重啟, 任何一個出問題都有清楚的邊界。Pod-to-Pod 連不通,先看 FRR 有沒有學到對方 的 PodCIDR(vtysh -c "show ip bgp");Service 連不通, 先看 iptables 的 KUBE-SVC-* 規則;Pod 起不來卡在 ContainerCreating,先看 /etc/cni/net.d 有沒有 Cilium 寫的 conf。三條除錯路徑互不干擾。

kube-proxy 後來被換掉了:兩階段的決定

Cilium 導入之初,kubeProxyReplacement 是明確設成 false——保留 kube-proxy,那一階段的目標範圍刻意畫得 很窄:只解決「CNI + 跟既有 BGP fabric 整合的 native routing」,kube-proxy 替換被視為一個獨立的、需要另外評估的決定,留待之後有需要再單獨討論。

後來使用者明確要求「移除 kube proxy, 改用 cilium ebpf」,這個決定才真的 執行:kubeProxyReplacement: true,kubeadm init 加上 --skip-phases=addon/kube-proxy 從一開始就不部署它。 拿掉 kube-proxy 之後,Cilium 在 bootstrap 期需要一個不依賴 kube-proxy 就能連到的 apiserver 入口(k8sServiceHost /k8sServicePort)——這正是當初評估時提到的那個「涉及拿掉 apiserver 的 in-cluster service access 這種特殊處理」的複雜度,實際 執行時也確實在這裡撞到一個 TLS SAN 不匹配的 bug,完整過程見 Role: cilium。
