基礎設施FRR / iBGP Fabric 設計

這是整個 lab 的地基:每一台節點(除了 bastion)開機時, cloud-init 就把 FRR 裝好、設定好、啟動好。這頁講的是這份設定每一行 為什麼這樣寫——完整模板在 templates/frr-init.sh.tftpl。

拓樸模型:單一 ASN,tor 當 Route Reflector

選 iBGP(不是 eBGP)、單一 ASN(65000,由 var.bgp_asn 統一分配給所有節點)是刻意簡化——這個規模的 fabric 不需要 eBGP 的 AS Path 機制,用 iBGP + Route Reflector 的 hub-and-spoke 模型就夠:tor 是唯一的 RR,其他所有節點都是它的 RR client,彼此之間不建立 BGP session(iBGP 全互聯 的 O(n²) session 數在只有一個 tor 的情況下完全沒必要)。

tor · /etc/frr/frr.conf(精簡)
router bgp 65000
 bgp router-id 10.10.0.10
 neighbor 10.10.0.20 remote-as 65000
 neighbor 10.10.0.20 next-hop-self all
 neighbor 10.10.0.20 route-reflector-client
 # ...對每個節點各重複一組(ms-0001~3, l4-0001~2, ap-0001~2)
 !
 address-family ipv4 unicast
  neighbor 10.10.0.20 activate
  # ...對每個節點各一行 activate
  maximum-paths ibgp 8
 exit-address-family
ms-0001(peer 角色)· /etc/frr/frr.conf
router bgp 65000
 bgp router-id 10.10.0.20
 neighbor 10.10.0.10 remote-as 65000
 !
 address-family ipv4 unicast
  neighbor 10.10.0.10 activate
 exit-address-family

兩邊的設定不對稱是刻意的——只有 tor 一邊需要 next-hop-self/route-reflector-client, 這兩個指令的語意本來就是「我是 RR,以下是我的 client」,只有站在 RR 的角度設定才有意義。peer 角色的節點完全不知道自己是 RR client,它只知道「我跟 tor 建 iBGP session」。

next-hop-self all:為什麼要 all,不能只寫 next-hop-self

這是整個 fabric 能動的關鍵一行,也是最容易漏掉的一行。iBGP 有個 標準行為:一般的 iBGP peer 之間轉發路由時不會改寫 next-hop (只有 eBGP 邊界才會),但 Route Reflector 反射路由給其他 client 時, 預設也是保留原始 next-hop——如果 tor 只是單純 next-hop-self(不帶 all),它只會替自己 發起的路由改寫 next-hop,對反射給其他 client 的路由 不會生效(這是 RFC 4456 的標準行為)。

結果就是:ms-0001 宣告了自己的 PodCIDR,tor 反射給 ap-0001 時,如果沒有 all,ap-0001 收到的路由 next-hop 會是ms-0001的原始位址——這剛好是對的 (因為 k8s-net 是 flat subnet,ap-0001 確實可以直連 ms-0001)。但如果 fabric 不是 flat subnet (例如之後要接多個不同的 L2 網段),沒有 all 就會讓 ap-0001 收到一個它根本連不到的 next-hop。這個 lab 加 all 是為了讓「tor 是唯一 L3 決策點」這個設計前提在 架構上是保證成立的,不是「剛好因為現在是 flat subnet 所以矇對了」。FRR 內部把 next-hop-self all 存成 force(show running-config 會顯示成 next-hop-self force),語意等價。

ECMP:maximum-paths ibgp 8

FRR 預設就算收到多條「等成本」的 iBGP 路徑(同一個 prefix、 LocPrf/weight 都一樣),也只會選一條當最佳路徑裝進 kernel——這是 Phase 1 用兩台 l4lb 節點宣告同一個 Service VIP 時發現的:沒有這行,tor 永遠只把流量 導向其中一台 l4lb,另一台完全沒有流量,ECMP 名存實亡。加上 maximum-paths ibgp 8 之後,FRR 才會把所有等成本路徑 都裝進 kernel 的路由表,變成 kernel 層級真正的多路徑(可以用 ip nexthop show 或 ip route show 看到一個 prefix 對應多個 nexthop)。數字 8 給得比目前節點數寬裕,之後加更多 節點不用回頭改這裡。

這行只加在 tor 的設定裡(%{ if role == "tor" }) ——ECMP 的決策點在 tor(它是唯一收到多條路徑、需要決定要不要都裝進 kernel 的節點),其他節點各自只會收到 tor 反射過來的、已經決定好的 多路徑集合。

四組 sysctl 調校,每一組解決一個實測到的問題

1. net.ipv4.ip_forward=1

最基本的:一台機器要當路由器(轉發不是自己的封包),kernel 預設是關的, 要手動開。所有跑 FRR 的節點都要開,不分 tor/peer。

2. net.ipv4.conf.*.rp_filter=0

rp_filter(reverse path filtering)預設(cloud image 通常是 2,loose mode)會檢查「這個封包的來源位址,是否至少有一條 路由讓我把回應送回去」,不符合就丟棄。在一個路由完全由動態 BGP 決定、且存在非對稱路徑可能性的 fabric 上,這個檢查太容易誤殺合法流量 ——關掉(設成 0,不檢查)。

非追溯性陷阱(這個模板裡出現兩次,務必記住這個模式): net.ipv4.conf.all.X 跟 net.ipv4.conf.default.X 分別代表「套用到所有已存在介面」跟「套用到之後新建立的介面」的預設值 ——但 cloud-init 執行的當下,ens3/ens4 早就已經存在(開機時 kernel 就建立好了),它們各自的值是各自介面 自己的 per-interface 設定,不會因為改了 all/default 而回溯更新。這個模板對 rp_filter 跟 send_redirects/accept_redirects 都額外用 for f in /proc/sys/net/ipv4/conf/*/rp_filter; do echo 0 > "$f"; done 這種迴圈,逐一介面覆蓋——只寫 all/default 看起來設定生效了(sysctl -a 查得到),但實際行為完全沒變, 這是實測踩到的坑,不是預防性寫法。

3. send_redirects / accept_redirects = 0

在共用 L2 網段上,如果 kernel 發現「我把封包從某個介面轉發出去, 而且發現目的地跟真正的 next-hop 剛好在同一個網段」,會主動送一個 ICMP Redirect,建議對方之後直接抄捷徑,不要繞路由器。這違反這個 fabric 的設計前提——「tor 是唯一的 L3 決策點,所有跨節點流量都要讓它決定 怎麼走」,如果對端抄了 ICMP Redirect 的建議繞過 tor,tor 上的 ECMP/hash policy 這些集中式決策就會被繞過。所以來源(tor)不送、 所有節點也不接受,兩邊都關,不依賴 secure_redirects 這種「只信任預設閘道送來的 redirect」的折衷保護。

4. arp_ignore=1 / arp_announce=2

這組是 Phase 1 DSR demo 專用的 ——DSR 架構裡 Service VIP 會同時出現在 l4lb 的宣告介面跟每台 realserver 的 lo 上,如果不管 ARP 行為,多台機器可能同時 回應同一個 VIP 的 ARP 請求(ARP Flux),造成流量不可預期地分散。 arp_ignore=1 讓機器只回應「請求的目的位址剛好是收到請求 那張介面自己的位址」的 ARP;arp_announce=2 讓機器發送 ARP 時一定用「最適合目的網段」的來源位址,不要洩漏 VIP 這種借來的位址。 現在的拓樸沒有 DSR 場景了,但這組設定對一般的 BGP fabric 節點無害, 沒有特別移除。

這份模板裡還留著的 dormant 邏輯

frr-init.sh.tftpl 是跟 Phase 1 共用的同一份模板,裡面還留著 role == "node"(假 Pod + LVS-DR realserver 設定)跟 role == "l4lb" (ipvsadm DSR 規則)兩段邏輯,還有 dummy0 介面 + network 宣告的機制。現在的 terraform.tfvars 沒有任何一台機器用 node/l4lb 角色,這兩段 完全不會被執行到——留著是因為之後如果要重現/延伸 DSR demo, 不用重寫這段 template 邏輯,而且它證明了一件事:用 dummy0 + network 陳述式宣告一個 prefix 這個機制,後來在 Role: cilium 的 bgp_announce 裡被重新用了一次(拿掉 dummy0,改成直接讀 Cilium 已經建好的 cilium_host connected route)—— Phase 1 驗證出來的「FRR network 陳述式需要一筆對應的 connected route 才會生效」這個知識,直接被 Phase 3 繼承。
