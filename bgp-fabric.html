基礎設施 FRR / iBGP Fabric

這頁是 FRR 與 iBGP fabric 的設定參考。除了 tor 與 bastion，每台節點開機時由 cloud-init 安裝並啟動 FRR，完整模板是 templates/frr-init.sh.tftpl。bastion 也套用同一份模板，角色是 peer。這頁說明模板裡每一段設定的作用，以及各自解決過的問題。

拓樸：單一 ASN，tor 當 route reflector

所有節點屬於同一個 ASN（65000，由 var.bgp_asn 統一分配），使用 iBGP。tor 是唯一的 route reflector（路由反射器，讓 iBGP 節點不必兩兩建立連線），其他節點都是它的 client，彼此之間不建立 session。

選 iBGP 與單一 ASN 是為了簡化。這個規模不需要 eBGP 的 AS Path 機制，hub-and-spoke 的 route reflector 模型就夠了，也避開了 iBGP 全互聯的 O(n²) session 數。

tor · /etc/frr/frr.conf（精簡）
router bgp 65000
 bgp router-id 10.10.0.10
 neighbor 10.10.0.20 remote-as 65000
 neighbor 10.10.0.20 next-hop-self all
 neighbor 10.10.0.20 route-reflector-client
 # ...對每個 peer 各重複一組：bastion、ms-0001~3、l4-0001~2、ap-0001~3
 !
 address-family ipv4 unicast
  neighbor 10.10.0.20 activate
  # ...對每個 peer 各一行 activate
  maximum-paths ibgp 8
 exit-address-family
ms-0001（peer 角色）· /etc/frr/frr.conf
router bgp 65000
 bgp router-id 10.10.0.20
 neighbor 10.10.0.10 remote-as 65000
 !
 address-family ipv4 unicast
  neighbor 10.10.0.10 activate
 exit-address-family

兩邊設定不對稱。next-hop-self 與 route-reflector-client 的語意是「我是 route reflector，以下是我的 client」，只有站在 tor 的角度才有意義。peer 角色的節點不知道自己是 client，只知道要與 tor 建一個 iBGP session。

節點開機後，Ansible 還會在 router bgp 區塊補上本節點的 PodCIDR，見 PodCIDR 如何進入 BGP。

route reflector 與 next-hop-self

tor 對每個 client 設定兩個指令，缺一個 fabric 都無法正確運作。

決策：tor 對所有 client 設 route-reflector-client 與 next-hop-self all。

理由：標準 iBGP 的 split-horizon 規則是「從 iBGP peer 學到的路由，不會再轉給其他 iBGP peer」。沒有 route-reflector-client，所有 session 都 Established，但 leaf 節點收不到彼此的路由（Bug #1）。

反射路由時，RFC 4456 規定預設保留原始 next-hop。單純的 next-hop-self 只改 tor 自己發起的路由，對反射出去的路由不生效，必須加 all。沒有它，ap-0001 收到的 ms-0001 PodCIDR 其 next-hop 是 ms-0001 本身。因為 k8s-net 是 flat L2，ap-0001 會直接 ARP ms-0001 並繞過 tor（Bug #2）。

考慮過的替代方案：不加 all，接受節點之間直連 — flat subnet 下封包確實能到，但 tor 就不再是唯一的 L3 決策點，ECMP 與 hash policy 這類集中式決策會被繞過。用實體拓樸（每個節點與 tor 各自獨立網段）強制 — 需要 tor 有與節點數相同的網卡，超過 flavor 的網卡上限。

代價：同一個網段的兩個節點之間的 Pod 流量也要先繞到 tor 再繞回來，這是 router-on-a-stick 的行為。tor 的轉發能力與可用性決定整個資料平面。

結果是：節點的路由表裡，所有 BGP 學到的 PodCIDR，next-hop 都是 tor（10.10.0.10）。tor 自己的 RIB 則保留原始發起節點的位址，因為 next-hop-self 只改 tor 發給 client 的宣告。完整的路由表見網路架構總覽。

FRR 內部把 next-hop-self all 存成 force，show running-config 會顯示 next-hop-self force，語意相同。

這個設計還依賴 ICMP redirect 被關閉。在共用 L2 上，kernel 發現「封包從某介面進來又從同一介面轉出，且對方與真正 next-hop 同網段」時，會送 ICMP Redirect，誘導對端抄捷徑繞過 tor。所以 tor 不送、所有節點也不接受，見下方 sysctl 一節。

ECMP 設定

tor 有兩項與 ECMP 有關的設定，都只加在 tor，對應模板裡的 %{ if role == "tor" } 分支：

  • maximum-paths ibgp 8：FRR 預設即使收到多條等成本的 iBGP 路徑，也只選一條裝進 kernel。等成本指同一個 prefix 且 LocPrf 與 weight 相同。加上這行之後，所有等成本路徑都會裝進 kernel，用 ip route show 或 ip nexthop show 可以看到一個 prefix 對應多個 nexthop。數字 8 比現有節點數寬裕，加節點不需要回頭改。
  • net.ipv4.fib_multipath_hash_policy=1：Linux 預設值 0 的 ECMP 雜湊只取來源 IP 與目的 IP。同一組來源與目的之間不管開幾條連線，雜湊結果都一樣，流量永遠走同一個 next-hop。改成 1（L3 加 L4）後，不同來源埠的連線才會分散到不同路徑（Bug #7）。

ECMP 的決策點在 tor，因為它是唯一收到多條路徑、要決定要不要都裝進 kernel 的節點。其他節點只會收到 tor 已經決定好的結果。目前每個 PodCIDR 只由一個節點宣告，所以現在沒有任何 prefix 實際擁有多條路徑，這兩項設定處於待命狀態。它們是在兩台 l4lb 宣告同一個 Service VIP 時驗證出來的，過程見 DSR／L4LB 歷史。

sysctl 調校

下面四組由 cloud-init 寫入 /etc/sysctl.conf，所有跑 FRR 的節點都套用（含 bastion）。tor 專屬的 fib_multipath_hash_policy 已在上一節說明。

1. ip_forward

net.ipv4.ip_forward=1。機器要轉發不是自己的封包，kernel 預設是關的，必須手動開。

2. rp_filter

net.ipv4.conf.*.rp_filter=0。cloud image 預設是 2（loose mode），會檢查封包的來源位址是否至少有一條路由可以送回去，不符就丟棄。路由完全由動態 BGP 決定、又可能出現非對稱路徑的 fabric 上，這個檢查容易誤殺合法流量，所以關掉。

非追溯性陷阱，模板裡出現兩次：net.ipv4.conf.all.X 與 net.ipv4.conf.default.X 分別是「套用到已存在介面」與「新建介面的預設值」的設定入口。但 cloud-init 執行時，ens3 與 ens4 早已存在，它們各自的 per-interface 值不會因為改了 all 或 default 而回溯更新。

模板因此對 rp_filter、send_redirects、accept_redirects 都額外用 for f in /proc/sys/net/ipv4/conf/*/rp_filter; do echo 0 > "$f"; done 這樣的迴圈逐介面覆蓋。只寫 all 與 default 時，sysctl -a 看起來設定生效，實際行為完全沒變。見 Bug #5。

3. ICMP redirect

send_redirects 與 accept_redirects 都設 0。ICMP Redirect 會建議對端抄捷徑，違反「tor 是唯一 L3 決策點，所有跨節點流量都由它決定怎麼走」的前提（Bug #4）。來源（tor）不送、所有節點不接受，兩邊都關，不依賴 secure_redirects 那種「只信任預設閘道送來的 redirect」的折衷保護。

4. ARP 行為

net.ipv4.conf.all.arp_ignore=1 與 arp_announce=2。arp_ignore=1 讓機器只回應「請求的目的位址剛好是收到請求那張網卡自己的位址」的 ARP。arp_announce=2 讓機器發送 ARP 時用最適合目的網段的來源位址。

這組設定原本是為了 DSR 設計的。Service VIP 會同時出現在 l4lb 與每台 realserver 的 lo 上，不處理 ARP 行為的話，多台機器會同時回應同一個 VIP 的 ARP 請求，也就是 ARP Flux。現在的拓樸沒有 DSR，這組設定對一般 fabric 節點沒有實際影響，保留沒有移除。

PodCIDR 如何進入 BGP

各節點的 PodCIDR 在 Cilium 運行時才決定，沒辦法像 Terraform 的 announce_prefix 那樣在開機當下寫死。所以 Cilium 的 BGP 功能保持關閉，改由 Ansible 的 bgp_announce 任務，用 vtysh 把本節點的 PodCIDR 加進 FRR。它會執行兩步：

  1. 讀取 CiliumNode 的 .spec.ipam.podCIDRs[0]，並在 FRR 加一條 ip route <cidr> Null0 200 靜態路由。
  2. 在 router bgp 區塊加 network <cidr>。

為什麼需要 Null0 路由？FRR 的 network 陳述式要求這個 prefix 在 zebra 自己的 RIB 裡有一筆有效路由，否則停在 invalid, not advertised。Cilium 建的那條 proto kernel 且帶 via gateway 的路由，zebra 沒有吸收進自己的 RIB，加上 redistribute kernel 也沒用（Bug #19）。

這條 Null0 路由的 distance 是 200：255 在 FRR 代表「永遠不會被選上」，BGP 會視為 invalid，實測無效。200 遠高於 Cilium 那條路由在 kernel 裡的優先權，ip route get 驗證過封包仍走 cilium_host，Null0 只是給 BGP 當存在憑證。完整推導見 Role: cilium。

這個機制源自 Phase 1：當時用 dummy0 加 network 陳述式宣告 Service VIP，驗證出「network 陳述式需要一筆對應的 connected route 才會生效」。

驗證方式

在 tor 上
$ sudo vtysh -c "show ip bgp summary"
$ sudo vtysh -c "show ip bgp"
$ ip route show

預期結果：每個 peer 的 session 都是 Established；show ip bgp 為每個 k8s 節點各列一條 *>i 的 PodCIDR；ip route 看得到對應的 proto bgp 路由。smoke-test 會自動比對這個條目數。

在任一節點上
$ sudo vtysh -c "show running-config"
$ ip route show proto bgp

預期結果：running-config 內有 network 本節點 PodCIDR 與對應的 ip route ... Null0 200；proto bgp 的路由其他節點的 PodCIDR 全部以 10.10.0.10 為 next-hop。

已知限制

模板中休眠的 DSR 邏輯

frr-init.sh.tftpl 與 Phase 1 的 DSR 驗證共用同一份模板，裡面仍有下列段落。目前的 terraform.tfvars 沒有任何 VM 使用 node 或 l4lb 角色，所以這些段落不會被執行。

  • role == "node"：把 Service VIP 綁在 lo 上扮演假 Pod，並啟動一個 Python http.server 的 vip-demo.service。
  • role == "l4lb"：安裝 ipvsadm、載入 ip_vs，並用 ipvsadm-restore.service 在重開機後重新套用 DSR 規則。
  • announce_cidr 與 dummy0：node／l4lb 角色用來宣告 prefix 的 connected route。

保留它們是因為之後若要重現 DSR demo，不必重寫這些邏輯。但它們讓模板的條件分支變複雜，也是修改模板時容易出錯的地方。

修改模板的注意事項

只改 tor 專屬設定時，terraform plan 曾顯示另外 3 台不相干的 VM 也要重建。原因是 %{ if role == "tor" } 沒加 ~ trim 修飾詞，非 tor 分支的渲染結果多了一行空白，字串 diff 就判定要重建 VM。修法是加 ~，並用 terraform console 對非 tor 分支的輸出做逐字元 diff（Bug #8）。

其他限制

  • 只有一個 route reflector，沒有備援。
  • 節點只與 tor 建立 session，BGP 沒有加 BFD，tor 故障的偵測依賴 BGP 預設的 keepalive 與 hold timer。
  • bgp_asn 在 Terraform 與 Ansible 各有一份，需要手動同步，見 Terraform / OpenStack。
