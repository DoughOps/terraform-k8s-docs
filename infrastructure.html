基礎設施Terraform / OpenStack 層

這一層負責的是「IaaS」——虛擬機器、網路、路由器、security group、 floating IP。這一層完全不知道 Kubernetes 存在;它的責任只是把 9 台 VM 跟 它們之間的網路可達性準備好,交給 Ansible 層去把 CRI-O/kubeadm/Cilium 裝上去。

VM 資源清單

全部定義在 terraform.tfvars 的 vms map 裡, 每個角色的 flavor 大小是刻意選的——master/lb 用小 flavor 是因為它們 本身不太吃資源(etcd/apiserver/scheduler/kube-proxy/cilium-agent 都不重), worker 用大一點的 flavor 是因為之後真正的工作負載會排程到那裡。

名稱k8s-net IPflavorbgp_role角色
tor10.10.0.10d1.mediumtorRoute reflector + apiserver haproxy
bastion10.10.0.11d1.mediumbastion唯一操作入口,唯一有 floating ip,不裝 FRR
ms-0001~310.10.0.20~22d1.mediumpeerControl-plane(etcd + apiserver + scheduler + controller-manager)
l4-0001~210.10.0.30~31d1.mediumpeer原規劃當 L4LB,現在也是一般 worker
ap-0001~210.10.0.40~41d2.largepeer純 worker,flavor 較大準備跑實際工作負載

bgp_role 目前只有三種有效值在用: tor、bastion、peer。peer 是一個刻意通用的角色——它只建立跟 tor 的 iBGP session、不宣告任何 prefix (announce_prefix = "")。變數定義裡還留著 node/l4lb 兩個舊角色(見 variables.tf),那是 Phase 1 DSR 驗證用的角色,目前的 terraform.tfvars 沒有任何一台 機器用它們,但程式邏輯還留著沒刪——之後如果要重現/延伸 DSR demo, 不用重寫這段 template 邏輯。

所有機器統一 boot_mode = "image"(直接從 Ubuntu-24.04 image 開機,不額外掛 boot volume)、統一 keypair_name = "k8s"。 image 名稱大小寫是刻意對齊 Glance 裡實際的名稱(Ubuntu-24.04, 首字大寫)——這個專案早期踩過一次大小寫不符直接讓 terraform apply 失敗的坑。

兩個網路,兩份不同的 cloud-init

每台 VM 的 user_data 由 Terraform 的 templatefile() 在 main.tf(locals.user_data)組出來,依 bgp_role 分成兩條路:

設定

tor、bastion 以外所有節點(現在全部是 peer)
templates/bastion-init.sh.tftpl bastion

這個分流本身就是「bastion 不是資料平面成員」這個設計決定在 Terraform 層的體現——bastion 有 k8s-net 的 IP(10.10.0.11),但完全 不參與 iBGP,所以它連得到其他節點的節點位址(flat subnet 直連),但連不到任何 Pod IP(需要 BGP 學到的路由, bastion 沒有),詳見 網路架構總覽。

網路資源:為什麼要拆成兩張網路

這是整個基礎設施最核心的一個決定,完整的網路架構角度分析在 網路架構總覽,這裡列 Terraform 實際怎麼設定:

資源設定為什麼
k8s_subnet_v4 10.10.0.0/24
no_gateway = true		 不掛任何 Neutron Router,連 DHCP 都不會發預設路由——逼所有 k8s-net 內部的可達性都要靠 iBGP 學到的具體路由,不能有任何一張 介面「剛好贏得」default route 的僥倖情況
mgmt_subnet 192.168.200.0/24
掛 mgmt_router		 mgmt_router 接 external_network, 是整個架構唯一的 SNAT 出口——ansible 對外 (apt/helm/image pull)、DNS(8.8.8.8/8.8.4.4) 全部走這裡
fabric port(每台 VM 一個) port_security_enabled = false Neutron OVS 的 conntrack-based 防火牆跟 BGP 動態學到的路由、 (歷史上)DSR 非對稱路由天生衝突,見下方完整說明
mgmt port(每台 VM 一個) 維持 Neutron 預設 security 一般端點,不轉發任何流量,沒有理由關掉基本防護
bastion_fip 只掛在 bastion 的 mgmt port 全架構唯一的 floating ip,壓縮對外攻擊面到只有一台機器

為什麼 fabric port 的 port_security_enabled 是 false,是最終結論不是 TODO

這個決定在專案裡被重新驗證過一次(mgmt-net 分離之後,一度嘗試改回 port_security_enabled = true + allowed_address_pairs, 結果失敗,又改回 false)——值得在這裡把完整推論寫清楚, 因為表面上看「關掉安全機制」總是可疑的,需要證明不是偷懶。

  1. Neutron 的 security group 是 conntrack-based 的狀態防火牆 ——它不只檢查單一封包是否符合規則,還會追蹤整條 TCP 連線的狀態 (NEW → ESTABLISHED),只有已經被標記成 ESTABLISHED 的連線,後續封包 才會被放行。
  2. DSR(Direct Server Return,見 L4LB 歷史頁面)的設計本質就是非對稱路由——去程流量經過負載平衡器, 回程流量從 realserver 直接送回 client,完全不經過負載平衡器。
  3. 兩者放在一起:負載平衡器的 Neutron port 只會看到「去程」 (SYN),它的 conntrack 狀態機永遠等不到回程的 SYN-ACK, 連線永遠卡在 NEW,標記不了 ESTABLISHED。
  4. client 後續送出的 ACK / 實際資料封包,因為對應的連線 狀態不是 ESTABLISHED,被 conntrack 當成「不合法的狀態轉換」直接丟棄 ——這是 DSR/非對稱路由架構跟任何 conntrack-based 防火牆的結構性衝突, 不是規則寫錯,加再多 allowed_address_pairs(只解決 anti-spoofing/來源位址檢查,完全不碰 conntrack 狀態機)都解決不了。

用三點同時 tcpdump(tor / l4lb / realserver)實測驗證過這個結論: l4lb 的 port 上只看得到 SYN,永遠看不到 SYN-ACK。這也解釋了為什麼 即使 DSR 階段已經是歷史,這個 port_security_enabled = false 的決定仍然保留到現在—— 整個 k8s-net 網段的性質(需要承載動態、非對稱、由軟體層決定的路由) 沒有變,即使目前的工作負載(kubeadm/Cilium)本身不再直接依賴 DSR。

Security Group 規則:寫了但目前不生效的部分

k8s-ibgp-lab-sg(刻意取獨立名稱,避開這個 OpenStack 專案裡一個已存在、非 Terraform 管理的同名殘留 security group 造成 API 名稱解析歧義)裡有 4 條規則:SSH(22)、ICMP、iBGP(179)、 Service port。因為 fabric port 已經整段關掉 port security, 後兩條(179、service port)目前不會被實際套用 ——留著純粹是文件用途,記錄「如果哪天恢復 port security,這是 當時預期需要開的 port」。

BGP ASN 從哪裡設定

variables.tf 的 var.bgp_asn(預設 65000)會透過 templatefile() 傳進 cloud-init,渲染進每台機器的 FRR 設定。這個值只存在 Terraform 這一層——Ansible 端沒辦法直接讀 Terraform 變數,只能在 ansible/inventory/group_vars/all/main.yml 手動維護一份一樣的 bgp_asn: 65000,兩邊改的時候要記得一起改,細節見 Role: cilium(bgp_announce 需要這個值來組 vtysh 指令)。
