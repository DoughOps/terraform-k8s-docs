基礎設施 Terraform / OpenStack

這一層是 IaaS：虛擬機器、網路、路由器、security group、Floating IP 與 Cinder 資料碟，全部由 openstack/ 目錄的 Terraform 管理。它完全不知道 Kubernetes 存在，只負責把 10 台 VM 和它們之間的網路準備好，交給 Ansible 層安裝 CRI-O、kubeadm 與 Cilium。

VM 資源清單

所有 VM 定義在 terraform.tfvars 的 vms map。新增或移除節點只要改這個 map，再執行 terraform apply，Ansible 的 inventory 會從 terraform output 自動重新產生。

bgp_role 只有三種值在使用：tor、bastion、peer。peer 是刻意通用的角色，只與 tor 建立 iBGP session，不宣告任何 prefix（announce_prefix = ""）。master、lb、worker 的差異只存在於 Ansible 層，inventory 依主機名稱前綴（ms-、l4-、ap-）分組，不看 bgp_role。

開機方式與共用設定

  • 所有 VM 的 boot_mode 都是 boot_mode = "image"，映像是 Ubuntu-24.04。Glance 裡的名稱首字大寫，大小寫不符會讓 terraform apply 失敗。keypair_name = "k8s" 也一律相同。
  • 多數 VM 直接從 image 開機。有資料碟的 VM（目前只有 bastion）改成用明確的 block_device 宣告開機碟，從 image 建一顆 100 GB 的 Cinder volume 開機，image_name 留空。這個雲的 Nova 不接受 image_name 屬性與額外 block device 混用，會回 400，見 Bug #31、#32。
  • 開機碟是 Cinder volume 後，guest 的磁碟走 SCSI bus，裝置名稱是 /dev/sdb、/dev/sdc，不是 vdb、vdc，見 Bug #33。
  • keypair 資源 openstack_compute_keypair_v2.k8s 只註冊公鑰，來源是 ansible/files/ssh/id_ed25519.pub。私鑰完全不經過 Terraform，也不會出現在 state 裡，管理方式見 Ansible 框架設計。

兩份 cloud-init

每台 VM 的 user_data 由 main.tf 的 locals.user_data 用 templatefile() 組出來。bastion 同時套用兩份模板，其餘節點只套用 FRR 那份。

bastion 因此也跑 FRR，並以 peer 角色加入 iBGP：它學得到所有 PodCIDR，但不宣告任何 prefix。bastion 到 Pod IP 的路徑與其他節點相同，經由 tor。

root 登入需要額外處理。Ubuntu cloud image 預設 disable_root=true，cloud-init 會把同一把公鑰寫進 /root/.ssh/authorized_keys，但前面加了一個 forced command，一登入就印出提示並斷線。sshd 取第一個命中的那行，所以只在後面追加乾淨的一行沒有用。frr-init 先把含有這把公鑰的既有行全部刪掉，再追加乾淨版本。

bastion 的 Docker 設定

/etc/docker/daemon.json 必須在安裝 docker-ce 之前寫好，因為 docker0 在套件安裝完成、dockerd 第一次啟動時就建立，之後補寫的 MTU 設定不會重建它。內容有三項：

  • "mtu": 1442：只影響 default bridge。網路的實體 MTU 是 1442，Docker 預設的 1500 會讓大封包被靜默丟棄，見 Bug #10。
  • "default-network-opts"（Docker 23.0 以上）：讓之後每個新建的 network 也套用 MTU 1442，包含 GitHub Actions runner 為每個 job 建立的 github_network_*，見 Bug #38。
  • "default-address-pools"：新建 network 從 10.99.0.0/16 切 /24。Docker 預設會依序配發 172.17、172.18⋯⋯，其中 172.18.0.0/16 與 service-cidr 重疊，見 Bug #45。

Security Group

k8s-ibgp-lab-sg 掛在每台 VM 的 mgmt port 上，實際生效的規則是 SSH（22/tcp，來源 0.0.0.0/0）和 ICMP。名稱刻意與專案裡一個非 Terraform 管理的殘留 k8s-sg 區隔，同名會讓 Nova 在建立 VM 時解析 security group 名稱產生歧義。

fabric port 關閉 port security

k8s-net 上每台 VM 的 fabric port 都設 port_security_enabled = false。這個決定被重新驗證過一次：mgmt-net 分離之後，曾改回 true 搭配 allowed_address_pairs，結果失敗，又改回 false。

決策：所有 fabric port 完全關閉 port security，mgmt port 保留。

理由：Neutron 的 OVS security group 是 conntrack-based 的狀態防火牆，與 BGP 動態路由和非對稱路由天生衝突（推論見下方）。tor 與每個節點都要轉發「不是自己」的來源與目的位址，Neutron 預設的 anti-spoofing 也會擋掉這類流量，這是 Bug #3。

考慮過的替代方案：port_security_enabled = true 加 allowed_address_pairs — 只放寬來源位址檢查，不影響 conntrack 狀態機，實測仍然失敗（Bug #6）。

代價：fabric port 上沒有 Neutron 層的任何過濾，k8s-net 的存取控制完全落在節點自己的設定。這個網段只承載 Kubernetes 資料平面，不對外，風險限縮在 mgmt-net 與 Floating IP 之外。

推論與實測

  1. Neutron 的 security group 是 conntrack-based 的狀態防火牆：它追蹤整條 TCP 連線的狀態，從 NEW 到 ESTABLISHED。只有已標記為 ESTABLISHED 的連線，後續封包才會放行。
  2. DSR 的本質是非對稱路由：去程經過負載平衡器，回程由 realserver 直接送回 client，完全不經過負載平衡器（背景見 DSR／L4LB 歷史）。
  3. 兩者合在一起：負載平衡器的 Neutron port 只看得到去程的 SYN，conntrack 永遠等不到回程的 SYN-ACK，連線卡在 NEW，無法標記為 ESTABLISHED。
  4. 後續封包被丟棄：client 之後送出的 ACK 與資料封包，因為連線狀態不是 ESTABLISHED，被 conntrack 當成不合法的狀態轉換丟掉。allowed_address_pairs 只處理來源位址檢查，碰不到 conntrack 狀態機，加再多都沒用。

用三個點同時 tcpdump（tor、l4lb、realserver）驗證過：l4lb 的 port 上只看得到 SYN，看不到 SYN-ACK。DSR 階段雖然已是歷史，k8s-net 仍需要承載由軟體層動態決定、可能非對稱的路由，所以這個決定沿用至今。

資料碟與 prevent_destroy

bastion 額外掛 2 顆 100 GB 的 NVMe Cinder volume，獨立於 instance 的生命週期，用來存放不能隨 VM 消失的資料：

volume裝置掛載點用途
bastion-nfs-data/dev/sdb/srv/nfs/k8sNFS 匯出目錄，給叢集內的 csi-driver-nfs 與監控資料使用
bastion-user-data/dev/sdc/data/userdata一般使用者資料；其中 userap 子目錄以 bind mount 蓋回 /userap（Vault、Keycloak 等的資料都在此）
  • 用 cloud-init 格式化與掛載：資料碟必須在 instance 建立當下就 attach，做法是 main.tf 的 block_device 加 boot_index = -1，因為 user_data 只在第一次開機執行一次。事後才 attach 的 openstack_compute_volume_attach_v2 會與 cloud-init 競爭，磁碟可能還沒出現腳本就跑完了。
  • 只在沒有檔案系統時才 mkfs.ext4：同一顆 volume 重新接到重建後的 bastion 時，不會洗掉舊資料。/userap 也只在 volume 內還沒有對應子目錄時才搬移一次。
  • 不處理 /home 與 /root：那兩個是 cloud-init 寫入 SSH authorized_keys 的路徑。bastion 重建又換了 keypair 時，bind mount 舊資料上去會把自己鎖在外面，風險大於好處。
  • 裝置順序：data_volumes list 的順序就是 attach 順序，bastion-init.sh.tftpl 寫死 sdb 為 NFS、sdc 為使用者資料，調整順序要同步改該檔案。

決策：兩顆資料碟同時設定 delete_on_termination = false 與 lifecycle.prevent_destroy = true。

理由：前者只擋住「instance 被刪除或替換」；terraform destroy 或從 tfvars 移除 data_volumes 條目，仍會直接刪除 volume 資源。後者補上這一層。

考慮過的替代方案：只用 delete_on_termination = false — 擋不住 volume 資源本身被 destroy。把資料放在 Terraform 之外手動管理 — 失去 volume 與 instance 綁定的宣告式描述。

代價：只要 plan 含有刪除這兩個資源，整個 plan／apply／destroy 都會直接報錯中止，這是 Terraform 的既定行為，不只擋這一個資源。要拆掉其他資源又保留 volume，必須先把它們從 state 移除。

make teardown 與 make build 已把下面的流程自動化，ID 暫存在 openstack/.data-volume-ids.json。手動版本如下，完整情境見全部拆除：

openstack/ 目錄 · 拆除前
$ terraform output data_volume_ids
$ terraform state rm \
    'openstack_blockstorage_volume_v3.data_volumes["bastion__nfs-data"]' \
    'openstack_blockstorage_volume_v3.data_volumes["bastion__user-data"]'
$ terraform destroy

預期結果：state rm 只改 state，不呼叫 OpenStack API，volume 不受影響；destroy 不再被 prevent_destroy 擋下。

openstack/ 目錄 · 重建時接回同一顆 volume
$ terraform import 'openstack_blockstorage_volume_v3.data_volumes["bastion__nfs-data"]' <記下的 id>
$ terraform import 'openstack_blockstorage_volume_v3.data_volumes["bastion__user-data"]' <記下的 id>
$ terraform apply

預期結果：新的 bastion 掛上舊 volume，既有檔案系統與資料原封不動。只是 instance 被替換、整個 module 沒被 destroy 時，不需要 import。

Terraform state backend

openstack/ 與 cloudflare/ 兩份 Terraform state 都存在同一個 S3 相容 bucket，不在本機。

項目值
bucketterraform-state-k8s
endpointhttps://s3.cloudnative.tw:6780（Ceph RGW，同時支援 Swift 與 S3 協定）
state keyopenstack/terraform.tfstate、cloudflare/terraform.tfstate
regionRegionOne（虛設值，搭配 skip_region_validation）
憑證.env 內的 AWS_ACCESS_KEY_ID、AWS_SECRET_ACCESS_KEY，由 Keystone 的 OS-EC2 API 簽發

決策：使用 Terraform 的 s3 backend，指向 Ceph RGW 的 S3 endpoint。

理由：GitLab CD pipeline 的 job container 每次都從全新 clone 開始，碰不到本機才有的 state，無法安全執行 terraform destroy／apply。state 放在共用 bucket，本機與 CI 才會看到同一份資源清單。

考慮過的替代方案：swift backend — 已被 Terraform 標記 deprecated，目前版本已移除。本機 state 檔 — 與 CI 不共用。

代價：每次 terraform init／plan／apply／destroy／output／state 都必須先有那組 EC2 風格憑證；endpoint 不可用時所有 Terraform 操作都會停擺。backend 區塊沒有設定 state locking，同時對同一份 state 操作要自行避免。

make ssh、scripts/ansible.sh、scripts/build.sh、scripts/teardown.sh、scripts/sync-cloudflare-secrets.sh 與重新產生 hosts.ini 的 pre-commit hook，都會自動從 .env 讀取並匯出這兩個值。只有在這些封裝之外直接執行 terraform 時，才需要手動 export。憑證的簽發步驟屬於一次性前置，見從零開始建置。

BGP ASN 的設定位置

var.bgp_asn（預設 65000）透過 templatefile() 傳進 cloud-init，渲染進每台機器的 FRR 設定。Ansible 讀不到 Terraform 變數，所以 ansible/inventory/group_vars/all/main.yml 另有一份手動維護的 bgp_asn: 65000，給 bgp_announce 組 vtysh 指令用，見 Role: cilium。兩邊必須一起改。

已知限制

休眠的 Terraform 邏輯

下列程式碼目前不會被執行或不產生效果，保留的原因是 DSR 驗證環境之後可能重現，見 DSR／L4LB 歷史。

  • variables.tf 的 bgp_role 型別註解仍列出 node 與 l4lb。沒有任何 VM 使用這兩個角色，frr-init.sh.tftpl 對應的分支（假 Pod、ipvsadm）不會執行，見 FRR / iBGP Fabric。
  • announce_prefix、service_vip（172.31.255.1）、service_port（8080）與 local.backend_ips 只服務上述分支。
  • Security group 的 179/tcp 與 service port 兩條規則掛在 mgmt port 上。BGP 與 service 流量走 fabric port，所以這兩條規則不會命中任何流量。fabric port 沒有 security group。
  • boot_mode = "volume" 的分支沒有 VM 使用，涉及 vms_with_volume 與 boot_volumes。
  • data.openstack_images_image_v2.vm_image 把映像名稱寫死為 Ubuntu-24.04，只用於有資料碟的 VM，其他 VM 才讀各自的 vm_image_name。

其他限制

  • 資料碟的 prevent_destroy 讓 terraform destroy 不能直接使用，必須經過 make teardown 或上面的手動流程。
  • bgp_asn 在 Terraform 與 Ansible 各維護一份，沒有機制檢查兩邊一致。

state 遷移的驗證

openstack/ 與 cloudflare/ 各自用 backend "s3" {} 指向同一個 bucket，以 key 前綴區分兩份 state。遷移前後逐一比對 state 內容，兩邊都是 byte-for-byte 相同，確認搬遷過程沒有資料遺失。

搬完之後，make ssh、scripts/ansible.sh、scripts/build.sh、scripts/teardown.sh、scripts/sync-cloudflare-secrets.sh 與重新產生 inventory 的 pre-commit hook 都會呼叫 terraform，一開始都沒有匯出 S3 憑證。後來逐一補上，沿用 OS_PASSWORD、CLOUDFLARE_API_TOKEN 同一套「從 .env 讀值再 export」的做法。

遷移後 terraform plan 顯示 bastion 要整台重建。直接比對遷移前後的 state，證實這與遷移無關：openstack/templates/bastion-init.sh.tftpl 在 bastion 上次 apply 之後，被後續的 Cilium 與 Docker 修復 commit 改過，之後沒有再 apply。這個差異目前沒有處理，見已知限制。
