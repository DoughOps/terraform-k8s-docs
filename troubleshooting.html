Phase 1 · iBGP + DSR L4LB 驗證階段

完整脈絡見 DSR / L4LB(歷史階段)。

#症狀根因修法
1iBGP session 都 Established,但 leaf 節點互相收不到對方的路由標準 iBGP split-horizon,RR 沒設 route-reflector-clienttor 對每個 client neighbor 加 route-reflector-client
2路由學到了但 next-hop 不對,節點抄 L2 近路next-hop-self 沒加 all,RFC 4456 反射路由預設保留原始 next-hopnext-hop-self all(FRR 存成 force),詳見 FRR / iBGP Fabric
3BGP/next-hop 都對,但節點間 ping 100% 掉封包Nova 隱式建立的 port 預設開 Neutron port security(anti-spoofing),擋掉「不是自己」的轉發流量改用明確 openstack_networking_port_v2 + port_security_enabled = false
4ping 通了,但 TOR 主動送 ICMP Redirect 誘導節點抄近路Linux 轉發封包時,進出介面相同且同網段就自動送 redirect,這是一般路由器最佳化行為,但違反此架構前提來源關 send_redirects,所有節點關 accept_redirects,不依賴 secure_redirects 的僥倖保護
5rp_filter 設了 all/default=0,但介面自己的值還是 2conf.all/default.X 只是「新介面」的預設值,對已存在的 ens3 不追溯生效——跟 #4 同一個模式逐一遍歷 /proc/sys/net/ipv4/conf/*/rp_filter
6Pod-to-pod ping 正常,VIP curl 全部逾時(port security 改成 allowed_address_pairs 之後)Neutron OVS 是 conntrack-based 狀態防火牆,l4lb 的 port 只看得到 DSR 的去程,永遠等不到 SYN-ACK 完成握手,後續封包被當 invalid state 丟棄fabric port 恢復整段 port_security_enabled = false,這是最終結論不是 TODO
7兩台 l4lb 加了 ECMP 路由,但流量 100% 固定走同一台fib_multipath_hash_policy=0,雜湊只看來源/目的 IP,單一 client 測試的雜湊輸入從頭到尾不變tor 專屬設 fib_multipath_hash_policy=1(納入 L4 埠號)

#症狀根因修法
31bastion 加額外 Cinder 資料碟後 terraform apply 直接 400,Boot sequence for the instance and image/block device mapping combination is not valid這朵雲的 Nova 不接受頂層 image_name 屬性(隱含 ImageRef)跟任何 block_device_mapping_v2 條目同時出現,即使那些條目全部是非開機用的資料碟(boot_index=-1)有額外資料碟的 VM 改用明確 block_device 宣告開機碟、image_name 留空,見 main.tf 該段註解
32修完 #31 後,provider 自己又報 Neither a boot device, image ID, or image name were able to be determinedterraform-provider-openstack 的 getImageIDFromConfig() 一偵測到 source_type="image" + destination_type="local" 的開機 block_device,就會堅持要解析出 image_id/image_name 塞回 ImageRef——直接跟 #31 的修法互斥,又踩回同一個 400開機 block_device 改用 destination_type="volume"(從 image 建一顆新 Cinder volume 來開機),provider 判斷不需要 image_id,ImageRef 留空,乾淨地只靠 block_device 開機
33volume-boot 修好之後,cloud-init 在 /dev/vdb 前面死等 30 秒後失敗,兩顆資料碟完全沒被格式化開機碟本身也改成從 image 建立的 Cinder volume(#32 的修法),連帶讓整台 instance 的磁碟走 SCSI bus,guest 裡的裝置命名全部變成 sdX,不再是 ephemeral image boot 慣用的 vdXcloud-init 腳本改用 /dev/sdb//dev/sdc,見 templates/bastion-init.sh.tftpl 開頭註解
34bastion 重建後跑 playbooks/bastion.yml 連環報錯:internal key Permission denied (publickey) → 修完換 kubectl: No such file or directory → 修完換 k8s-api.internal DNS 解析失敗internal SSH key 的信任、kubectl 本身、admin kubeconfig、k8s-api.internal 這條 /etc/hosts 記錄,全部只存在 bastion 自己的 ephemeral 開機碟上——這些東西過去只在「全新環境第一次架設」時裝過一次,從沒設計成「bastion 單獨重建、叢集其他節點都還活著」這個情境也要能重跑先跑一次 BOOTSTRAP=1 ... internal-ssh-key.yml 重新佈署信任;把 kubeadm.yml 最後裝 kubectl+抓 kubeconfig 那段、跟 apiserver-lb.yml 的 DNS 那個 play,各自抽成獨立的 playbooks/bastion/kubeconfig.yml、playbooks/bastion/apiserver-dns.yml,納入 playbooks/bastion.yml 這個一次性入口,見 框架設計
35部署 csi-driver-nfs 後,驗證用的三個測試 pod(kubectl run 建的裸 busybox)全部卡在 kubectl wait --for=condition=Ready,120 秒後 timeout——連完全沒掛 PVC 的「blocked」測試 pod 也一樣卡住demo namespace 開了 istio-injection=enabled(給 demo-app.yml 的展示用),所以每個在這個 namespace 建立的 pod 都會被自動注入一個 istio-proxy sidecar;這幾個裸 busybox 測試 pod 沒有走 Istio 的 pilot-agent 注入配套流程,注入進去的 istio-proxy 的 startup probe(打 :15021/healthz/ready)永遠連不上——kubectl wait --for=condition=Ready 是等「pod 裡所有 container 都 Ready」,不是只看主要那個 container,所以三個測試 pod(包括完全沒有掛 volume、跟 NFS 毫無關係的 blocked pod)全部被這個不相干的 sidecar 卡住三個 kubectl run --overrides 都加一段 "metadata":{"annotations":{"sidecar.istio.io/inject":"false"}},明確跳過這個 namespace 的自動注入,見 playbooks/k8s/nfs-csi.yml 開頭的說明註解
36(嚴重,實際造成約 10 小時的叢集 egress 中斷)部署 CiliumClusterwideNetworkPolicy 之後,叢集內幾乎所有 pod 的 DNS 解析全滅、cloudflared 進入 crash-loop(lookup cfd-features.argotunnel.com: i/o timeout)——bastion 上跑 ansible/kubectl 完全正常,沒有任何徵兆,問題撐了快 10 小時才在最終 code review 時被抓到Cilium 的 egressDeny-only rule,只要沒有明講 enableDefaultDeny: {egress: false},就會把「被這條 policy 選到的每個 endpoint」直接打成 egress 整個 default-deny——語意上跟寫一條 allow-list rule 幾乎一樣,不是文件字面上看起來的「單純疊加一條擋規則」。這條 policy 的 endpointSelector 用 app NotIn [csi-nfs-node],幾乎選到全叢集每個 pod(沒有 app label 的 pod 也會被 NotIn 選到),又是叢集裡唯一一條 Cilium policy,完全沒有其他 allow rule 可以 fallback。hostNetwork pod(bastion 的 ansible/kubectl 存取)不受影響,才會完全看不出異狀——這個「hostNetwork pod 不受 per-pod policy 影響」正是 Bug #34 已經記錄過的同一個機制,這次反而變成掩蓋問題的原因policy 補上 enableDefaultDeny: {egress: false};驗證步驟加一個正面對照組——用同一個 pod 連 policy 完全沒提過的另一個 port,必須連得到,才能證明剛剛的「連不到」是精準擋下,不是整個 pod 斷網(原本的測試只有負面斷言,擋不住這類問題,細節見 docs/superpowers/specs/2026-07-27-nfs-csi-driver-design.md 的 Correction 段落跟 playbooks/nfs-csi.yml 的正面對照組任務)
37不相信文件、直接照程式碼重新推演「從 0 建置」的真實順序時發現:在真正全新的環境(叢集從未 kubeadm init 過)單獨執行 playbooks/bastion.yml 會在第 4 步當場失敗,ansible.builtin.fetch 抓不到 masters[0] 上的 /etc/kubernetes/admin.conf,後面的 apiserver-dns.yml/tools.yml/cloudflare-tunnel.yml/github-runner.yml 全部不會執行到playbooks/bastion/kubeconfig.yml(Bug #34 的修法產物)只驗證過「bastion 單獨重建、叢集其他節點都還活著」這個情境,從沒測過「叢集本身也還沒建立」這個更早的情境——`ansible.builtin.fetch` 預設在來源檔案不存在時直接 fail 整個 play,不會靜默跳過。附帶發現:bastion/cloudflare-tunnel.yml 被放在 bastion.yml 的 import 鏈裡也是想當然爾的安排——它部署的 Deployment/Secret 活在叢集自己的 etcd、跑在一般 k8s 節點的 pod 上,根本不是 bastion 本機狀態,bastion 重建完全不影響它,放在 bastion.yml 裡只是多餘的重複匯入,還會被同一個「叢集不存在」問題拖累失敗bastion/kubeconfig.yml 抓檔案前先 stat 檢查 admin.conf 存不存在,不存在就跳過 fetch/copy(kubectl 本身照裝);roles/cloudflare_tunnel 比照辦理,檢查 bastion 上有沒有 kubeconfig,沒有就跳過 kubectl apply;bastion/cloudflare-tunnel.yml 從 bastion.yml 的 import 鏈移除,改成只在 playbooks/k8s.yml(cert-manager.yml 之後)匯入一次,那才是叢集第一次真的活著的時間點。完整稽核過程見 bootstrap-order-audit.md

看得出來的模式

🔁

「conf.all/default 不追溯」出現兩次(#4、#5)

同一個 kernel 網路設定的陷阱,在不同時間點被不同的 sysctl 參數各撞了一次——第一次修完之後應該要意識到這是一個通用模式, 但實際上是各自獨立發現的。

🧩

ansible 字串處理陷阱出現三次(#13、#17、#22)

模板頭沒帶註解字元、YAML block 純量縮排、command 模組 shlex 解析——都是「以為模板/字串照抄就會照預期渲染」結果不是 的案例,值得養成「渲染完先看實際輸出」的習慣。

🔬

所有根因都靠實測工具找到,不是讀文件猜到

tcpdump -e 三點同時抓包(#6)、terraform console + diff(#8)、ip route get (#18)、vtysh show ip route(#19)——每一個 「懷疑」都有對應的實測驗證步驟,不是改完就假設好了。

🔐

「憑證 SAN 綁的是特定字串/IP,中間節點不能頂替」出現三次(#16、#23、#24)

certificate-key 加密 key 的一次性語意(#16)、 upload-certs 單獨呼叫時猜錯 advertise address(#23)、Cilium 直連 tor 的 IP 而不是 control-plane-endpoint 的 hostname(#24)——三次 都是同一類「以為某個中間位址可以拿來頂替真正的權威來源」的 假設,分別在不同時間點、不同元件上各自撞了一次才發現。

👻

手動修的 fix 沒寫進 code,bastion 一重建就會再犯一次(#10、#34)

Docker MTU(#10)第一次是手動改 /etc/docker/daemon.json 修好的,從沒補進 cloud-init;kubectl/kubeconfig/k8s-api.internal DNS 記錄(#34)也是同樣的性質——bastion 過去被當成「裝一次就不會再 重建」的節點,直到真的因為要加持久化資料碟而重建一次,才發現這些 「只存在於某台機器記憶裡」的手動修復全部得重來一遍。現在 #10 的 修法已經補回 bastion-init.sh.tftpl,#34 也拆成獨立 playbook 收進 playbooks/bastion.yml——但這提醒了一個 通用原則:任何「手動 SSH 上去改一行設定」的修法,沒有回寫進 Terraform/Ansible,就等於沒修過,只是還沒遇到下一次重建而已。

🌱

只在「重建」情境下驗證過的 playbook,沒人測過「從 0」情境(#34、#37)

#34 把 kubeconfig/DNS 修好,前提是叢集本來就活著(bastion 單獨重建); #37 才發現同一份 playbook 在「叢集從未建立過」這個更早的情境下會直接 硬失敗——兩個情境共用同一段程式碼,卻只有其中一個真的被跑過驗證。 修法是讓程式碼自己偵測「叢集存不存在」並各自安全跳過,不要求操作者 記得兩種情境該用哪個順序。

🕳️

負面斷言沒有正面對照組,擋不住「整個壞掉」偽裝成「精準擋下」(#36)

驗證 network policy 時只測了「應該被擋的連線真的失敗」,沒有 同時測「不該被擋的連線真的成功」——結果 egressDeny 少了 enableDefaultDeny: {egress: false},把幾乎全 叢集的 pod egress 打成 default-deny,而不是精準擋下一個 port。 兩種情況下,「應該被擋的連線」都會失敗,測試都顯示通過—— 唯一能分辨的方法是額外測一個「不該被擋的連線」有沒有跟著死掉。 這次還疊加了 #34 已經記錄過的同一個盲點:hostNetwork pod (bastion 自己的 ansible/kubectl 存取)不受影響,完全看不出 叢集其他地方已經斷線,問題撐了快 10 小時才在 code review 時 被抓到,不是靠監控或使用者回報。通用原則:任何「擋住 X」的 驗證,都要配一個「X 以外的東西還能通」的正面對照組,不然沒辦法 分辨「精準擋下」跟「整個壞掉,剛好包含 X」。
