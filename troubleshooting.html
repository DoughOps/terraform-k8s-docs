這頁登錄整個專案遇到的 74 個 bug，用來回答「這個錯誤訊息我好像在哪見過」。每筆都有症狀、根因、修法、怎麼確認修好和相關 bug，Role 頁有完整故事的會連過去。

怎麼用這頁

在瀏覽器按 Ctrl+F（macOS 是 Cmd+F），直接搜尋你看到的錯誤訊息，例如 Connection reset by peer。每筆的「症狀」都保留了原始錯誤訊息。

  1. 用錯誤訊息搜尋。找不到就搜元件名稱，例如 haproxy、Cilium、Keycloak。
  2. 也可以先看下方目錄表，一行一個 bug，用編號跳到內文。
  3. 找到後依序讀「根因」「修法」「怎麼確認修好」。修完用最後一欄的指令或現象確認，不要只看錯誤訊息消失。
  4. 看「相關」欄。同類型的 bug 常有共同的根因，頁尾的模式分析整理了這些共同點。

Phase 1

Phase 1 · 驗證 iBGP、ECMP 與 DSR L4LB：本階段 8 筆。完整脈絡見 DSR / L4LB 歷史與 FRR / iBGP Fabric。

#1 · iBGP 全部 Established，leaf 卻收不到彼此的路由

  • 症狀：iBGP session 全部是 Established，但 leaf 節點互相收不到對方的路由。
  • 根因：標準 iBGP 的 split-horizon 規則不會把從 iBGP peer 學到的路由再轉給其他 peer，而 route reflector 沒有設 route-reflector-client。
  • 修法：tor 對每個 client neighbor 加 route-reflector-client。
  • 怎麼確認修好：在 leaf 節點執行 show ip bgp，看得到其他節點宣告的 prefix，節點之間的流量可以轉發。
  • 相關：同一個設計的第二半是 #2。設計理由見 FRR / iBGP Fabric。

#2 · 路由學到了，next-hop 卻讓節點抄 L2 近路

  • 症狀：路由學到了，但 next-hop 不是 tor，節點直接 ARP 對方並繞過 tor。
  • 根因：next-hop-self 沒有加 all。RFC 4456 規定反射路由預設保留原始 next-hop，單純的 next-hop-self 只改 tor 自己發起的路由。
  • 修法：改成 next-hop-self all。FRR 會把它存成 force，show running-config 顯示 next-hop-self force，語意相同。
  • 怎麼確認修好：在任一節點執行 ip route show proto bgp，其他節點的 PodCIDR 全部以 tor（10.10.0.10）為 next-hop。
  • 相關：#1、#4。設計理由見 FRR / iBGP Fabric。

#3 · BGP 與 next-hop 都對，節點間 ping 卻 100% 掉封包

  • 症狀：BGP 路由與 next-hop 都正確，但節點之間 ping 100% 掉封包。
  • 根因：Nova 隱式建立的 port 預設開啟 Neutron port security（anti-spoofing），擋掉來源或目的不是自己的轉發流量。
  • 修法：改用明確宣告的 openstack_networking_port_v2，並設 port_security_enabled = false。
  • 怎麼確認修好：節點之間 ping 不再掉封包，流量可以經 tor 轉發。
  • 相關：#6 證明只用 allowed_address_pairs 放寬並不夠。設計決策見 Terraform / OpenStack。

#4 · TOR 送 ICMP Redirect，誘導節點抄近路

  • 症狀：ping 已經通了，但 tor 主動送 ICMP Redirect，誘導節點改走 L2 捷徑。
  • 根因：Linux 轉發封包時，只要進出介面相同且在同一網段，就會自動送 redirect。這是一般路由器的最佳化行為，但違反「tor 是唯一 L3 決策點」的前提。
  • 修法：來源（tor）關閉 send_redirects，所有節點關閉 accept_redirects。兩邊都關，不依賴 secure_redirects 提供的保護。
  • 怎麼確認修好：tor 的 send_redirects 與節點的 accept_redirects 都是 0，節點路由表裡沒有出現繞過 tor 的條目。
  • 相關：#5 是同一個陷阱的另一個 sysctl。sysctl 全貌見 FRR / iBGP Fabric。

#5 · rp_filter 設了 all/default=0，介面自己的值還是 2

  • 症狀：rp_filter 的 all 與 default 都設成 0，但介面自己的值仍是 2。
  • 根因：conf.all/default.X 只影響新建的介面，對開機時已存在的 ens3 不會追溯生效。這和 #4 是同一個模式。
  • 修法：用迴圈逐一覆蓋 /proc/sys/net/ipv4/conf/*/rp_filter。
  • 怎麼確認修好：cat /proc/sys/net/ipv4/conf/ens3/rp_filter 回傳 0。只看 sysctl -a 的 all 欄位會誤以為設定已生效。
  • 相關：#4。模板寫法見 FRR / iBGP Fabric。

#6 · port security 改成 allowed_address_pairs 後，VIP curl 全部逾時

  • 症狀：pod-to-pod ping 正常，但改用 allowed_address_pairs 放寬 port security 之後，對 VIP 的 curl 全部逾時。
  • 根因：Neutron 的 OVS security group 是 conntrack-based 的狀態防火牆。DSR 的回程不經過 l4lb 的 port，l4lb 的 conntrack 永遠等不到 SYN-ACK，後續封包被當成 invalid state 丟棄。
  • 修法：fabric port 恢復成整段 port_security_enabled = false。allowed_address_pairs 只放寬來源位址檢查，改變不了 conntrack 狀態機。
  • 怎麼確認修好：對 VIP 的 curl 恢復正常，ipvsadm --stats 的 OutPkts 為 0，證明回程確實繞過 l4lb。
  • 相關：#3。完整脈絡見 DSR / L4LB 歷史，決策記錄見 Terraform / OpenStack。

#7 · 兩台 l4lb 都加了 ECMP 路由，流量卻 100% 走同一台

  • 症狀：tor 上兩台 l4lb 都有 ECMP 路由，但流量 100% 固定走同一台。
  • 根因：fib_multipath_hash_policy=0 的雜湊只看來源與目的 IP。單一 client 測試時雜湊輸入從頭到尾不變，永遠選到同一個 next-hop。
  • 修法：只在 tor 設 fib_multipath_hash_policy=1，把 L4 埠號納入雜湊。tor 是唯一做雜湊決策的節點。
  • 怎麼確認修好：同一個 client 開多條 TCP 連線，兩台 l4lb 都收到流量，分流數據記錄在 DSR / L4LB 歷史頁。
  • 相關：設定位置見 FRR / iBGP Fabric，驗證過程見 DSR / L4LB 歷史。

#8 · 只改 tor 的設定，terraform plan 卻要重建另外 3 台 VM

  • 症狀：只修改 tor 專屬設定，terraform plan 卻顯示另外 3 台不相干的 VM 也要重建。
  • 根因：模板的 %{ if role == "tor" } 沒加 ~ trim 修飾詞，非 tor 分支的渲染結果多出一行空白，字串 diff 判定 user_data 變了而重建 VM。
  • 修法：在指示詞加上 ~。
  • 怎麼確認修好：用 terraform console 渲染非 tor 分支，再用 diff 比對修改前後，輸出逐字元相同，terraform plan 只剩 tor 的變更。
  • 相關：修改模板時的注意事項見 FRR / iBGP Fabric。

#9 · bastion 的 /etc/hosts 寫入失敗：Device or resource busy

  • 症狀：寫 bastion 的 /etc/hosts 失敗，錯誤是 [Errno 16] Device or resource busy。
  • 根因：ansible_connection: local 的前提錯了。實際執行位置是 ansible-runner 容器自己的檔案系統，不是 bastion 本機。Docker 把容器內的 /etc/hosts bind-mount 成特殊檔案，擋掉 atomic rename。
  • 修法：移除 ansible_connection: local，bastion 和其他節點一樣走正常 SSH。
  • 怎麼確認修好：重跑 playbook，bastion 的 /etc/hosts 寫入成功，不再出現 Errno 16。
  • 相關：Ansible 框架設計。

#10 · bastion 上 docker build 卡在 apt-get update

  • 症狀：bastion 上的 docker build 跑到某個 apt-get update 就卡住，重試無限迴圈。
  • 根因：k8s-net 與 mgmt-net 的 MTU 都是 1442（OpenStack overlay 的額外標頭），Docker 預設 bridge 的 MTU 是 1500，大封包被靜默黑洞掉。
  • 修法：/etc/docker/daemon.json 加 {"mtu": 1442} 並重啟 docker。Acquire::ForceIPv4 是排查時誤判的旁支，沒有解決問題，保留無害。頂層 mtu 只對 dockerd 自己建的 default bridge 生效，自訂 network 不會繼承，同一類黑洞後來在 #38 又出現一次。
  • 怎麼確認修好：bastion 上的 docker build 跑得完，apt-get update 不再卡住。
  • 相關：#38、#45 是 Docker network 預設值的同類問題。設定位置見 Terraform / OpenStack。

#11 · stdout_callback = yaml 報錯，輸出格式壞掉

  • 症狀：stdout_callback = yaml 報錯，ansible-playbook 的輸出格式壞掉。
  • 根因：community.general.yaml callback 在該 collection 12.0.0 被移除。
  • 修法：改用內建的 default callback，搭配 result_format = yaml。
  • 怎麼確認修好：ansible-playbook 恢復正常的 YAML 格式輸出，沒有 callback 錯誤。
  • 相關：設定位置見 Ansible 框架設計。

#12 · ansible 警告 group and host with same name

  • 症狀：ansible 印出「group and host with same name」警告。
  • 根因：YAML 版本的 inventory 為 tor 與 bastion 各開了一個和自己同名的 group。
  • 修法：inventory 改成 INI 格式。沒有 group 標頭的 host 行自動歸為 ungrouped，不需要這個繞路。
  • 怎麼確認修好：重新產生 inventory 後執行 ansible all -m ping，沒有再出現該警告。
  • 相關：inventory 設計見 Ansible 框架設計。

#13 · haproxy 設定驗證失敗：unknown keyword 'Ansible'

  • 症狀：haproxy 設定驗證失敗，錯誤是 unknown keyword 'Ansible' out of section。
  • 根因：{{ ansible_managed }} 模板頭沒有帶 # 註解字元，渲染出來的第一行不是合法的 haproxy 語法。
  • 修法：改成純文字的 # 註解。
  • 怎麼確認修好：validate: "haproxy -c -f %s" 通過，haproxy 正常重啟。
  • 相關：與 #17、#22 同屬模板與字串處理陷阱。細節見 Role: apiserver-lb。

#14 · haproxy stats 頁面打不開

  • 症狀：haproxy 的 stats 頁面打不開。
  • 根因：listen stats 沿用全域 defaults 的 mode tcp，但 stats 頁面本質是 HTTP 服務。
  • 修法：在 listen stats 區塊內明確設回 mode http。
  • 怎麼確認修好：對 stats 端點發 HTTP 請求，能取得頁面和 CSV。
  • 相關：#21 是 smoke-test 讀這份 CSV 時的欄位問題。細節見 Role: apiserver-lb。

#15 · kubeadm init preflight 因 conntrack 缺失而 fatal

  • 症狀：kubeadm init 的 preflight 直接 fatal，錯誤是 [ERROR FileExisting-conntrack]。
  • 根因：節點沒有安裝 conntrack 套件。
  • 修法：kubelet role 一次裝齊 conntrack、socat、ebtables、ethtool，避免每個 preflight 錯誤各修一次。
  • 怎麼確認修好：kubeadm init 的 preflight 階段通過。
  • 相關：細節見 Role: kubelet。

#16 · 第二台 master join 失敗：cipher: message authentication failed

  • 症狀：第二台 master join 失敗，錯誤是 cipher: message authentication failed。
  • 根因：兩台 master 同時各自呼叫 --upload-certs，互相覆蓋對方的 certificate-key。
  • 修法：只在 kubeadm_init 呼叫一次，結果透過 hostvars 共用給所有 join 的節點。
  • 怎麼確認修好：兩台 master 同時 join 都成功。
  • 相關：#23、#24 同屬憑證綁定特定字串的問題。細節見 Role: kubeadm。

#17 · 3 台 master 的 kube-controller-manager 同時消失

  • 症狀：3 台 master 的 kube-controller-manager 同時消失。
  • 根因：blockinfile 用 YAML block 純量（block: |）寫多行內容，縮排被 YAML 吃成 0，插進 manifest 後語法錯誤。
  • 修法：改用單行雙引號字串，手動帶 \n。

#18 · Cilium init container 連 ClusterIP 逾時，SYN 來源位址錯誤

#19 · FRR 的 network 陳述式一直是 invalid, not advertised

#20 · 改 CIDR 重建叢集後，pod 卡在 ContainerCreating：no CNI configuration file

#28 · 任何 *.dough-ops.com 子網域回 503，叢集內測試卻成功

  • 症狀：真實請求連任何 *.dough-ops.com 子網域（例如 hubble）都回 503 的 Cloudflare 錯誤頁，但在叢集內部直接測試永遠成功。
  • 根因：Cloudflare Tunnel 的 originRequest.originServerName 設成 zone apex（dough-ops.com），而 Istio Gateway 443 listener 的 SNI 比對規則是 *.dough-ops.com，至少要有一段子網域。apex 名稱對不上任何 filter chain，TLS handshake 在 HTTP 層之前就被 Envoy 斷線，cloudflared 回報 connection reset。
  • 修法：把 originServerName 改成任何帶子網域的名字。它不需要對應真實服務，這裡用 gateway.dough-ops.com。
  • 怎麼確認修好：用臨時 curl pod 讓 SNI 與 Host header 故意不一致，重現出和 cloudflared 相同的失敗。修好後 test、hubble、dashboard、grafana、prometheus、alertmanager 六個子網域全部重新驗證，cloudflared 的錯誤日誌不再出現。
  • 相關：細節見 Role: cert_manager 與 內部工具。影響範圍是所有掛在同一條 wildcard ingress 規則下的服務。

#29 · ssh.dough-ops.com 登入正常，瀏覽器卻沒有出現終端機

#56 · 換掉 Tunnel token 後，cloudflared Pod 仍用舊 token

#57 · 換掉 Tunnel token 後，bastion 上的 cloudflared 沒套用新 token

  • 怎麼確認修好：換 token 後重跑 playbook，/etc/cloudflared/token 內容更新且 service 重啟，Tunnel 恢復連線。

#58 · 自訂 ClusterRole 用 wildcard，整個 Access org 都能讀 Secrets

  • 症狀：部署前檢查發現，自訂 ClusterRole 的唯讀規則寫成 apiGroups: ["*"]、resources: ["*"]。
  • 根因：原意是用一個 wildcard 角色完全取代 view，因為 view 涵蓋不到 nodes 這類 cluster-scope 資源。但 RBAC 沒有排除語法，wildcard 連 secrets 一起放行。任何通過 Cloudflare Access 的人都能 kubectl get secret -o yaml。範圍是整個 GitHub org，不限 oidc_admin_emails 名單。可讀到的內容包括 Grafana admin 密碼、TLS 私鑰與 Cloudflare tunnel token。內建 view 刻意排除 secrets 就是為了避免這件事。
  • 修法：改成兩個 ClusterRoleBinding 疊加。繼續綁內建 view，沿用官方已審查、排除 secrets 的範圍。自訂角色只明確列舉要補上的 cluster-scope 資源與三個寫入 verb，完全不用 wildcard。
  • 怎麼確認修好：部署後用 kubectl auth can-i ... --as=system:authenticated 逐項驗證。get pods、delete pods、get nodes、patch configmaps 為 yes，get secrets、delete configmaps、update deployments 為 no。

#31 · bastion 加 Cinder 資料碟後 terraform apply 回 400

#32 · 修完 #31 後 provider 報 Neither a boot device, image ID, or image name

#35 · 部署 csi-driver-nfs 後，驗證用的測試 pod 全卡在 Ready

  • 症狀：部署 csi-driver-nfs 後，驗證用的三個 busybox 測試 pod 在 kubectl wait --for=condition=Ready 等 120 秒後逾時，連沒掛任何 PVC 的 blocked pod 也一樣。

  • 修法：三個 kubectl run --overrides 都加上 "metadata":{"annotations":{"sidecar.istio.io/inject":"false"}}，跳過這個 namespace 的自動注入。說明寫在 playbooks/k8s/nfs-csi.yml 開頭。
  • 怎麼確認修好：三個測試 pod 在逾時內變成 Ready，nfs-csi.yml 的驗證段落通過。
  • 相關：#36 是同一次部署的另一個問題。注入行為見 Role: istio，NFS CSI 見 內部工具。

#36 · CiliumClusterwideNetworkPolicy 讓全叢集 DNS 失效約 10 小時

  • 根因：Cilium 的 egressDeny-only rule，只要沒有明講 enableDefaultDeny: {egress: false}，被選到的每個 endpoint 都會被打成 egress 整個 default-deny。語意近似一條 allow-list，不是單純疊加一條擋規則。這條 policy 的 endpointSelector 是 app NotIn [csi-nfs-node]，幾乎選到全叢集的 pod，連沒有 app label 的也算，而且它是叢集裡唯一一條 Cilium policy，沒有其他 allow rule 可以 fallback。這些語意是 code review 時讀 Cilium v1.19 的 pkg/policy/api/rule_validation.go 與 pkg/policy/repository.go 才確認的。hostNetwork pod 不受 per-pod policy 影響，bastion 上的存取因此完全正常，看不出異狀。#34 已記錄過同一個機制，這次它反而掩蓋了問題。
  • 修法：policy 補上 enableDefaultDeny: {egress: false}。驗證步驟加一個正面對照組：用同一個 pod 連 policy 沒提過的另一個 port，必須連得到，才能證明「連不到」是精準擋下，不是整個 pod 斷網。這個任務寫在 playbooks/k8s/nfs-csi.yml。原本的測試只有負面斷言，擋不住這類問題。
  • 怎麼確認修好：被擋的 NFS port 連不到，同一個 pod 連另一個 port 連得到（正向對照組用 bastion 的 22 port）。叢集內 DNS 恢復，cloudflared 不再 crash-loop。
  • 排查證據：cilium-dbg endpoint list 的 POLICY (egress) ENFORCEMENT 欄顯示大多數 endpoint 是 Enabled，pod 內查 DNS 逾時，cloudflared 重啟了 165 次。

#53 · 加 HashiCorp apt repo 後出現 NO_PUBKEY

#54 · play 跑完 failed=0，Vault 卻是 sealed

  • 症狀：整個 play 成功，failed=0，但 vault status 顯示 sealed: true，unseal 明明成功過。

#55 · VSO 登入 Vault 回 403：namespace not authorized

#60 · openssl 讀不到掛載進 container 的 GitHub App private key

#49 · role 重跑後 Keycloak 的 Postgres 起不來

  • 症狀：Postgres 容器重啟後報 FATAL: data directory "/var/lib/postgresql/data" has invalid permissions 與 could not open file "global/pg_filenode.map": Permission denied。
  • 根因：第一版用同一個 ansible.builtin.file task 建 secrets 目錄與 Postgres 資料目錄，owner: root。容器內 Postgres 以 uid 999 執行，首次啟動時自己 chown 所以正常。但 role 每次重跑，宣告式的 file task 都把 owner 蓋回 root，下次容器重啟就失敗。

#50 · Dex 連 Keycloak 被 Cloudflare Access 擋住，拿到 HTML 登入頁

#38 · GitHub runner 的 git fetch 反覆 Connection reset by peer

  • 症狀：GitHub Actions self-hosted runner（github-runner container）第一次跑 run-playbook.yml，actions/checkout 的 git fetch 反覆出現 fatal: ... Recv failure: Connection reset by peer，內建重試 3 次全部失敗。直接在 bastion 主機上 git clone 同一個 repo 完全正常，一開始被誤判成 GitHub 端的暫時性網路問題。
  • 根因：#10 的 MTU 修法只對 dockerd 自己建的 default bridge（docker0）生效。runner 執行 container: job 時，會自己 docker network create 一個新的 github_network_<hash>。dockerd log 的 net=github_network_... 可證實這點。這個網路沒有繼承 daemon.json 的 "mtu": 1442，落回 Docker 預設的 1500，與底層網卡的 1442 不符。git fetch 拉 pack data 這類大封包在半路被黑洞。既有的 keycloak-net 也有同樣的問題，只是流量都是小封包沒被注意到。主機上的 git clone 繞過所有 Docker network，所以沒事。
  • 修法：daemon.json 加上 Docker 23.0 起支援的 "default-network-opts": {"bridge": {"com.docker.network.driver.mtu": "1442"}}，讓之後所有 bridge driver 新建的 network 都繼承同一個 MTU，不必逐一補 -o 參數。同步補進 openstack/templates/bastion-init.sh.tftpl，避免 bastion 重建後又失效。
  • 怎麼確認修好：run-playbook 的 job 中 git fetch 順利完成。新建的 Docker network 以 docker network inspect 檢視，MTU 選項為 1442。
  • 相關：#10、#45 是 Docker network 預設值的同類問題。設定位置見 Terraform / OpenStack，runner 設計見 Role: github-runner。

#39 · gitlab-rails runner 報 LoadError，檔案明明存在

#45 · ArgoCD 驗證時，新建 pod 連 apiserver 全部 Connection timed out

  • 症狀：驗證 ArgoCD 對接自架 GitLab 時，叢集內幾乎所有 pod 連 apiserver 一律 Connection timed out，不論目標是 ClusterIP 172.18.0.1:443 或三台 master 的 6443。已經跑很久、沒重啟過的 pod（coredns、cilium-operator 等）完全正常。
  • 根因：bastion 的 keycloak-net 這個 Docker 自訂 network，Docker 會依序往上配發 /16 給新 network，順序是 172.17、172.18、172.19⋯⋯。它剛好落進 172.18.0.0/16，與叢集的 Service CIDR 完全重疊。bastion 同時有 ip_forward=1 又參與 BGP fabric，目的地在 172.18.0.0/16 的封包只要經過 bastion，就被導去本機的 keycloak-net bridge。這個重疊是真實存在的問題，但修好之後逾時依舊，真正的原因是 #47。
  • 修法：停用並移除 keycloak-net 與相關 container，資料留在 /userap。/etc/docker/daemon.json 加 "default-address-pools": [{"base": "10.99.0.0/16", "size": 24}]，讓之後所有新建的 Docker network 都落在與 k8s-net、pod CIDR、Service CIDR、mgmt-net 都不重疊的範圍。重跑 keycloak.yml 以 IaC 重建。同步補進 openstack/templates/bastion-init.sh.tftpl。
  • 怎麼確認修好：bastion 上 docker network ls 不再有落在 172.18.0.0/16 的 bridge，新建的 network 從 10.99.0.0/16 配發。但 pod 到 apiserver 的逾時沒有因此消失，見 #46、#47。
  • 相關：#46、#47。#10、#38 是 Docker network 預設值的同類問題。網段規則見 網路架構總覽。

#46 · cilium-dbg 顯示 Host: Legacy、Masquerading: IPTables

  • 症狀：追查上面的逾時時發現，cilium-dbg status --verbose 顯示 Routing: Host: Legacy、Masquerading: IPTables。叢集已經移除 kube-proxy，全交給 Cilium eBPF，不應該還停在 legacy iptables masquerade。

  • 修法：cilium-values.yaml.j2 明確加 bpf: {masquerade: true}，重跑 k8s/cilium.yml 並重啟 daemonset。
  • 怎麼確認修好：cilium-dbg status --verbose 顯示 Host: BPF 與 Masquerading: BPF，不再出現 Legacy、IPTables。這是真實的設定缺口，但和 #45 一樣不是 apiserver 連線逾時的根因，修完逾時原封不動。

#47 · pod 連節點真實 IP 的新連線 100% 逾時（underlay 丟棄 pod-CIDR 來源）

  • 症狀：排除 #45、#46 之後，pod 連節點真實 IP 的新連線依然 100% 逾時。唯一會踩到的情境是 kubernetes service 直接指向三台 master 的 6443。一路查到 OpenStack Neutron OVS 與 hypervisor underlay，租戶身份查無可查。
  • 根因：pod-CIDR（172.16.0.0/16）來源的封包，在 OpenStack fabric 裡被靜默丟棄，但只限目的地不是 tor 的情況。pod 到 tor 本身、以及節點自己真實 IP 來源的封包（不論目的地是誰）都 100% 暢通。cilium-dbg monitor 證實 Cilium 每次都把 SYN 送上 ens3，結果是 action: allow，沒有 drop event。Neutron port 的 MAC 與 IP 也逐一查過沒有衝突，問題不在 Cilium 的 policy 與 datapath。同一個 project 下新增了 3 台不由這個 repo 管理的 VM，名稱是 hw-k8s-1/2/3，預設 port_security_enabled: true 並掛 security group。時間點吻合，但查不到 OVN Southbound DB 與 hypervisor 的 OVS flow table，只能證明相關，無法證明因果。
  • 修法：繞過底層問題，並沒有修好它。Cilium 有專門對付這個情境的旗標 enable-remote-node-masquerade。文件寫明 BPF masquerade 預設跳過對 remote-node 與 kube-apiserver identity 的 SNAT，且不受 ipv4NativeRoutingCIDR 控制。在 cilium-values.yaml.j2 用 extraConfig 打開，把 pod 連節點真實 IP 的流量來源強制 SNAT 成節點自己的 IP，在 fabric 眼裡就和一直暢通的節點對節點流量相同。改 extraConfig 只會更新 ConfigMap，helm upgrade 的 kubectl rollout status 會回報成功但沒有重啟任何 pod，BPF 程式不會重新載入，必須手動 kubectl -n cilium rollout restart daemonset/cilium。
  • 怎麼確認修好：改完並重啟 daemonset 後，tcpdump 看到 SYN 的來源位址變成節點 IP，三向交握成功，需要建立新連線的 pod 可以連上 apiserver，例如 argocd-application-controller。
  • 相關：#45、#46。這是全專案唯一違背「pod 內部一律帶真實 IP，NAT 只在 tor 發生一次」的設定，取捨見 Role: cilium，細節見 Role: cilium。

#47 是 workaround，根因沒有解開

#45 與 #46 都是真實存在、已修好的 bug。但修完之後，argocd-application-controller 這類需要對 apiserver 建立全新連線的 pod 仍然逾時，這才發現它們只是順路撞到的另外兩個坑。

分層測試收斂出唯一會壞的路徑。測試涵蓋 pod 與 pod 同節點和跨節點、pod 到一般 Service ClusterIP、pod 到 apiserver ClusterIP 或直接後端 IP。壞掉的是 pod 發起、目的地是節點真實 IP，也就是 k8s-net 上的 host IP，不是 pod IP。kubernetes 這個 service 沒有 selector，Endpoints 直接指向三台 master 的 6443，剛好命中這條路徑。

定位用 cilium-dbg monitor 加三點同步 tcpdump，三點是來源 pod 所在節點、收到連線的 master 和 tor。SYN 從 pod 以 orig-ip 0.0.0.0 直接從節點的 ens3 送出，native routing 下這是設計上正確的行為。master 準時收到，立刻回 SYN-ACK，並依標準 TCP 行為重傳 4 次。master 的路由 via TOR dev ens3 和 ARP 都正確，ARP 與 tor 自己回報的 MAC 完全吻合，不是快取過期。

但 tor 那端同步抓包，對這個目的地完全零封包。tcpdump 的抓包點在 kernel 網路層最前端，比 routing、iptables、rp_filter 都早。0 封包代表這個 SYN-ACK 在 master 的虛擬網卡到 tor 的虛擬網卡之間就消失了，不是任何一台 VM 內部的規則擋掉的。

已排除的可能如下：

  • Cilium 的 masquerade 與 routing 設定（#46），行為符合設計。
  • bastion 的 Docker CIDR 衝突（#45）。
  • Cilium daemonset 本身狀態，以及 ARP 快取過期。
  • Terraform 宣告的 Neutron port security。openstack/main.tf 的 openstack_networking_port_v2.fabric 對所有節點都是 port_security_enabled = false，master 沒有被漏掉。
  • Neutron port 的 MAC 與 IP 衝突，已逐一查過 k8s-net 上所有 port。
  • 跨租戶網路洩漏。k8s-net 沒有標成 shared，新增的 3 台 VM 屬於同一個 project。

這也解釋了為什麼舊的 pod 都沒事。coredns、cilium-operator 這類已經跑了好幾天的 pod，對 apiserver 的長連線在問題出現前就建好了，連線沒斷就不需要重新握手。

真正的根因在 OpenStack Neutron OVS 與 hypervisor underlay 這一層。VM 內部已經無法再往下查，包含這個 repo 管得到的所有 Ansible 與 Terraform 設定。需要的資訊如下，都要 hypervisor 或 OpenStack 管理層權限，而這個共享雲（openstack.cloudnative.tw）只給一般 project 身份：

  • master 與 tor 是否在同一台 compute host。
  • br-int 的 OVS flow table，指令是 ovs-ofctl dump-flows。
  • OVN Southbound DB 裡每個 logical port 的 chassis binding。
  • compute host 上有沒有 Neutron security group 以外的防火牆機制，例如 ebtables 或 nftables。

enable-remote-node-masquerade 解決的是「pod 連不上 apiserver」這個症狀，沒有解決「pod-CIDR 來源的封包在 fabric 裡被吃掉」這個根因。雲的維運方若查出原因並修好 fabric，這段 extraConfig 可以拿掉，讓 pod 對 apiserver 的連線恢復帶真實 pod IP。目前的代價是 apiserver 的 audit log 與連線來源只看得到節點 IP，看不出是哪個 pod 發起的。

#67 · ArgoCD 的 oidc.config 內換行變成字面的 \n

  • 症狀：用 Jinja 字串串接組 ArgoCD 的 oidc.config，這是 ConfigMap 裡一個值本身是多行 YAML 的 key。結果字串裡的換行是字面上的兩個字元 \ 加 n，套進 ArgoCD 會把它解析成壞掉的 YAML。
  • 根因：第一版用 'name: ...\n' ~ 'issuer: ...' ~ ... 這類字串串接，整個 set_fact 包在 >- 折疊純量裡。折疊純量不會把 \n 轉成真正的換行字元。部署前在本機用 ansible-playbook 單獨測這一段才抓到，沒有直接套到叢集。
  • 修法：改用 YAML 的 | 區塊純量，裡面直接放真正的換行，搭配 vars: 與一般 YAML dict，再用 combine(..., recursive=True) 組完整的 helm values。
  • 怎麼確認修好：本機重新測試，結果是 dict 型別，換行是真正的換行字元，之後才套用到叢集。
  • 相關：與 #13、#17、#22 同屬字串處理陷阱。ArgoCD 的設定見 Role: argocd。

#68 · ArgoCD 登入被 Cloudflare 拒絕：Invalid redirect URL

  • 症狀：登入被 Cloudflare 拒絕，訊息是 Invalid redirect URL: the protocol and host (including port) must match and the path must be within allowed URLs if provided。

#69 · ArgoCD 登入後每 5 分鐘被登出

  • 症狀：ArgoCD 登入後不到半小時就被強制登出。同一套 Cloudflare Access SSO 的 Grafana 與 Vault 沒有這個問題。
  • 根因：Access for SaaS 核發的 id_token 固定 5 分鐘，而且不發 refresh_token。ArgoCD Web UI 在 id_token 到期時不會自動重新導向，所以每 5 分鐘要手動登入一次。這是已知行為，見 argoproj/argo-cd 的 issue #10126、#24807、#27041。第一版修法把 access_token_lifetime 拉到上限 24h，套用後症狀不變，直接看 argocd-server log 才確認 exp - iat 仍是 300 秒，這個欄位對 Access for SaaS 沒有作用。
  • 修法：改走 ArgoCD 內建 Dex，由 Dex 自己簽發 id_token，效期由 argocd_dex_id_token_expiry 控制（8760h）。代價是 token 外流後一年內有效，且權限是 admin，詳見 Role: argocd 的已知限制。
  • 怎麼確認修好：登入一次，在 argocd-server log 讀 Dex 簽發的 claims：exp - iat 等於 31536000 秒，iss 變成 https://argocd.dough-ops.com/api/dex。Settings → Accounts 等管理頁面可正常進入。
  • 相關：#70、#71 是接上 Dex 後連續遇到的問題。登入設計見 Role: argocd，排查過程見 演進歷史。

#70 · Dex 登入失敗：missing "name" claim

  • 症狀：第一次接上 Dex 登入就失敗，argocd-dex-server log 印 failed to authenticate err="missing \"name\" claim"。
  • 根因：Dex 的 oidc connector 預設要求 name claim，檢查寫在 connector/oidc/oidc.go 的 createIdentity()，沒有 skip 開關。Cloudflare 核發的 id_token 中，這個帳號的 name 是 null，因為 GitHub 帳號沒有設公開顯示名稱。
  • 修法：connector 設 userNameKey: email。email claim 一定有值，因為 Access policy 本來就用 email 過濾 org 成員。
  • 怎麼確認修好：重新登入，log 不再印這個錯誤，接著會遇到 #71。
  • 相關：#69、#71。細節見 Role: argocd。

#71 · Dex 登入失敗：missing "email_verified" claim

  • 症狀：修完 name 之後，log 換成 failed to authenticate err="missing \"email_verified\" claim"。
  • 根因：Dex 預設還要求 email_verified claim 存在且為 true。Cloudflare 的 id_token 只有 email，沒有這個 claim，無從映射。
  • 修法：connector 設 insecureSkipEmailVerified: true，略過整個檢查。oauth2-proxy 那邊為同樣原因加了對應的 flag。
  • 怎麼確認修好：重新登入成功，並完成 #69 的 exp - iat 驗證。
  • 相關：#52 是 oauth2-proxy 側的同類問題。細節見 Role: argocd。

看得出來的模式

把 bug 放在一起看，會出現重複的類型。下面是目前看得出來的共同點，括號內是相關編號。

🔁

all/default 不追溯

相關：#4、#5。同一個 kernel 網路設定的陷阱，在不同時間點被不同的 sysctl 參數各撞了一次。第一次修完之後應該要意識到這是通用模式，實際上卻是各自獨立發現的。

🧩

Ansible 字串處理陷阱

相關：#13、#17、#22、#67。模板頭沒帶註解字元、YAML block 純量縮排、command 模組的 shlex 解析、折疊純量裡的 \n，都是「以為字串照抄就會照預期渲染」的案例。#67 靠部署前在本機單獨測那一段才抓到，值得養成「渲染完先看實際輸出」的習慣。

🔬

根因靠實測找到

相關：#6、#8、#18、#19、#69。例子有 tcpdump -e 三點同時抓包、terraform console 加 diff、ip route get、vtysh show ip route，以及在 argocd-server log 讀 id_token 的 exp - iat。每個懷疑都有對應的驗證步驟，不是改完就假設好了。#69 的第一版修法調高 access_token_lifetime 沒有效果，直接看 token 才確認是平台硬限制。

🔐

憑證 SAN 不能頂替

相關：#16、#23、#24。三次都是「以為某個中間位址可以頂替真正的權威來源」的假設。certificate-key 有一次性語意（#16）。upload-certs 單獨呼叫時猜錯 advertise address（#23）。Cilium 直連 tor 的 IP，而不是 control-plane-endpoint 的 hostname（#24）。

👻

手動修的 fix 沒回寫

相關：#10、#34、#38、#45。Docker MTU（#10）第一次是手動改 /etc/docker/daemon.json，沒有補進 cloud-init。kubectl、kubeconfig 與 k8s-api.internal 記錄（#34）也是同樣的性質。bastion 一直被當成「裝一次就不會重建」的節點，直到為了加持久化資料碟而重建，這些只存在於某台機器上的手動修復才全部得重來。

#10 的修法後來補回 bastion-init.sh.tftpl，#34 拆成獨立 playbook 收進 playbooks/bastion.yml。通用原則是：任何「SSH 上去改一行設定」的修法，沒有回寫進 Terraform 或 Ansible，就等於沒修過，只是還沒遇到下一次重建。

#38 是同一個教訓的第三次，涵蓋範圍不同。#10 只讓 default bridge 的 MTU 正確，之後 Docker 新建的每個自訂 network 都不會繼承，包括 github_network_* 和 keycloak-net。#45 是第四次，Docker 依序配發位址而撞上 Service CIDR。兩次的修法都收進 daemon.json 的 default-network-opts 與 default-address-pools，並同步寫進 cloud-init。

🌱

沒人測過「從 0」

相關：#34、#37。#34 把 kubeconfig 與 DNS 修好，前提是叢集本來就活著。#37 才發現同一份 playbook 在「叢集從未建立」這個更早的情境會直接硬失敗。兩個情境共用同一段程式碼，卻只有其中一個真的被跑過。修法是讓程式碼自己偵測叢集存不存在並各自安全跳過，不要求操作者記得兩種情境該用哪個順序。

🕳️

負面斷言缺正面對照

相關：#36。驗證 network policy 時只測了「應該被擋的連線真的失敗」，沒有同時測「不該被擋的連線真的成功」。egressDeny 少了 enableDefaultDeny: {egress: false}，把幾乎全叢集的 pod egress 打成 default-deny。兩種情況下被擋的連線都會失敗，測試都顯示通過。

這次還疊加了 #34 記錄過的盲點。hostNetwork pod 不受影響，所以 bastion 自己的 ansible 與 kubectl 存取正常，看不出叢集其他地方已經斷線。問題撐了約 10 小時，是 code review 抓到的，不是監控或回報。通用原則：任何「擋住 X」的驗證，都要配一個「X 以外的東西還能通」的正面對照組。

♻️

重跑才暴露的行為

相關：#49、#54、#56、#57、#59、#61。第一次執行都正常，第二次或換一台全新節點才出事。

宣告式的 file task 每次重跑都把 owner 蓋回 root（#49）。handler 拖到 play 結尾才重啟（#54）。環境變數只在 Pod 啟動時讀一次（#56）。非冪等指令用「檔案存在」當守衛（#57）。docker inspect 沒限定種類而永遠命中 image（#59）。對不存在的套件解除 hold（#61）。寫 role 時要同時驗證第一次、重跑、全新節點三種路徑。

🧷

預設值替你做事

相關：#7、#14、#27、#40、#41、#46、#59。預設行為做了你沒要求的事，每一項的修法都是把行為明確寫出來。

ECMP 雜湊預設只看 IP（#7）。haproxy 沿用全域 mode tcp（#14）。CRI-O 預設 enforcing（#27）。GitLab 看到 https 就開 Let's Encrypt（#40）。GitLab 設定只在 seed 時生效（#41）。kubeProxyReplacement 不連帶打開 BPF masquerade（#46）。docker inspect 預設搜尋所有物件種類（#59）。

🚧

外部限制只能繞過

相關：#42、#47、#51、#69。GitHub fine-grained PAT 無法 pull container image（#42）。OpenStack underlay 丟棄 pod-CIDR 封包（#47）。Dex 沒有 SSO cookie（#51）。Cloudflare Access for SaaS 的 id_token 固定 5 分鐘（#69）。

這四項都無法靠改自己的設定解決，做法分別是換成 public image、masquerade、接受每次同意畫面、多放一個 Dex。每個繞過都有代價，要寫在對應 role 頁的已知限制裡。

🪪

權限範圍事後才審

相關：#58、#72。wildcard ClusterRole 放行 Secrets（#58）是部署前檢查發現的。GitLab 預設權限為 Developer 推不了 protected main（#72），修法是提升到 Owner，擴大了範圍。權限類的修法都要寫明影響到誰，再回頭檢查這個範圍是否過大。
